# 작업·지시·승인 프로토콜

## 작업 상태
- READY는 등록된 작업으로, 실행기에서 의존성과 점유를 확인한 뒤 전송한다. 전송 중 SENDING, 영수증 확인이 필요한 경우 SEND_UNCERTAIN, 영수증 확인 후 QUEUED를 기록한다.
- 작업자가 수락하고 시작하면 RUNNING, 결과 제출은 REVIEW, 지정 검수가 통과하면 VERIFIED, 최종 대상 검증은 INTEGRATED, Master 최종 판정은 DONE이다.
- 의존·환경·사람 조치가 필요하면 BLOCKED에 이유와 재개 조건을 남긴다. 실패는 FAILED, 취소는 CANCELLED다. 재작업은 새 배정 버전과 시도로 추적한다.
- BACKLOG, REWORK, INTEGRATING은 설명용 표현으로 쓸 수 있다. 문서·분석 작업의 INTEGRATED는 검토된 최종 산출물 수용을 의미한다. PAUSED_BY_ADMIN과 WAITING_HUMAN은 서비스 상태다.
구현·검수 역할은 상태 변경을 제안하며 공식 상태는 Controller가 적용합니다.

## 배정 버전
plan_revision: 전체 계획 버전.
assignment_revision: 해당 작업 배정의 실질적인 조건 버전.
attempt_id: 해당 실행의 고유 ID.
base_commit: 작업 시작 기준.
result_commit: 실제 결과 대상.
전체 계획 변경이 해당 작업에 영향이 없으면 호환성 판정을 기록하고 계속합니다.
영향받는 배정이 바뀌면 이전 결과를 자동 채택하지 않습니다.
기존 실패 작업을 재시도할 때 새 attempt_id를 발급합니다.

## 관리자 지시
지시 의미는 추가·수정·우선순위·중지·재개·취소·승인·거절·직접 조치 완료·조회로 구분한다. 실행기는 record, pause, resume을 받는다. 나머지 의미는 Master가 해당 배정이나 요청 상태에 반영한다.
자연어도 받을 수 있으며 Master가 의미와 범위를 기록합니다. 정확한 형식을 사용하지 않았다는 이유로 관리자의 명확한 지시를 무시하지 않습니다.
수신 확인과 실제 적용 확인을 구분합니다.
명시적 중지 요청은 관리자 요청 묶음 시점까지 미루지 않습니다.
이력은 정정·대체 링크로 이어서 남깁니다.

## 관리자 요청
종류: DECISION, AUTHORIZATION, MANUAL_ACTION.
요청 준비와 전달은 Master가 담당한다. Controller에는 OPEN, REPORTED, DEFERRED와 종료 상태 VERIFIED·REJECTED를 기록한다. 답변 수신 REPORTED와 증거 확인 VERIFIED를 구분한다.
결정이나 허가가 확인된 뒤 실제 행동과 결과는 해당 작업의 별도 사건으로 남긴다.
승인받지 못한 실행은 요청 상태만 바꾸어 우회하지 않습니다.
변경 범위가 이전 승인 안에 있으면 재승인 없이 진행하고, 밖이면 새 revision을 생성합니다.

## 요청 묶음 시점
준비된 요청을 다음 중 필요한 가장 이른 시점에 모읍니다.
- 정한 마일스톤 또는 관리자 검토 시점
- 주요 후속 작업을 차단하는 결정이 생겨 구체적 결과가 준비된 시점
- 독립적으로 진행할 유용한 작업을 모두 소진한 시점
미완성 요청을 무조건 먼저 보내지 않고, 핵심 작업이 막혔는데 정해진 시간까지 숨기지도 않습니다.
같은 미응답 요청을 계속 재출력해 대화를 방해하지 않습니다. 상태표에는 계속 보이게 둡니다.

## 권한 구분
자율: 이미 요청한 범위의 로컬 구현·디자인·필요 테스트·오류 수정.
사전위임: 대상·환경·한도·조건을 포함하는 기존 승인으로 실행 가능한 일.
추가판단: 새 사업정책·범위 확대·기존 위임을 벗어나는 비용·운영 변경.
직접작업: 실제 계정 로그인·MFA·조직 권한 승인 등 사용자가 수행해야 하는 일.
일반적인 "알아서 개발"만으로 외부 메시지 발송이나 무제한 과금을 허가받았다고 해석하지 않습니다.
