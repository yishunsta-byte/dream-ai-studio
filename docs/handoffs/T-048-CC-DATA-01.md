## 1. 계약 (`dream-code-migration/v1`)

| 항목 | 정한 것 |
|---|---|
| 묶는 범위 | 코드 단계 하나 = **명시한 저장소 파일 목록**이에요. 첫 파일은 실행 모듈이에요. 모듈은 `entry`(자기 경로)와 `run(sqlite)`를 내보내요. 나머지는 그 모듈이 가져다 쓰는 로컬 파일이에요. 단계 SQL(표 만들기)은 `sql`로 같이 묶어요. |
| 해시 | 다음 줄들을 `\n`으로 이은 sha256이에요. `dream-code-migration/v1` / `sql\0<단계 SQL sha256>` / 파일마다 `file\0<저장소 기준 posix 경로>\0<내용 sha256>`(경로 순). 내용은 CRLF→LF로 맞춰요. 형식 이름이 들어 있어서 나중에 v2로 바꿔도 v1 기록과 섞이지 않아요. |
| 실제 실행 코드와 일치 | `codeMigration()`은 목록을 만들 때 디스크 원문으로 해시를 계산해요. 이 값이 **정적으로 import한 모듈 옆에 적은 해시**와 같아야 해요. 적은 해시와 `run`은 같은 빌드에 들어가요. 그래서 빌드 뒤 원문만 바뀌었거나 선언이 낡았으면 DB를 열기 전에 거부해요(`MigrationSourceError`). `entry`는 목록의 첫 파일과 같아야 해요. 같은 파일 두 번, 절대·상위 경로, `.ts`가 아닌 파일, 심볼릭 링크, 빈 목록은 거부해요. |
| 숨은 의존 금지 | 목록 파일은 목록 안 파일, `node:crypto`, type-only import만 쓸 수 있어요. 다음은 모두 거부해요. 목록 밖 로컬 파일·패키지, side-effect import, `require`, 동적 `import()`, `import.meta`, `Date`, `performance`, `Math.random`, crypto 난수, `process`, 전역 객체, `eval`/`Function`. SQL의 `'now'`·`CURRENT_*`·`random()`·`randomblob()`도 목록 파일과 단계 SQL 모두에서 거부해요. |
| 실행 | `migrateDatabase`는 `codeMigration`이 만든 객체(WeakSet 확인, freeze됨)일 때만 `run`을 실행해요. 아닌 객체에 `run`이나 `kind:"code"`가 있으면 **어떤 단계도 적용하기 전에** 거부해요. 변환은 그 단계 SQL 바로 뒤, 같은 트랜잭션에서 실행돼요. 기록 행은 그다음에 써요. `verify`는 모든 단계 뒤의 검사로만 남겨 뒀어요. 실패하면 SQL 단계까지 전부 되돌려요. |
| SQL 단계 | 바뀐 것이 없어요. `kind`·`run`·`sources`는 선택 칸이고, 제품 0001~0004 해시는 파일 원문 sha256 그대로예요(s4 manifest 기록과 같은지 시험으로 확인했어요). manifest와 DB 기록에는 계속 `version·name·sha256`만 들어가요. 그래서 백업 형식과 앞부분 일치 판정은 그대로 코드 단계까지 덮어요. |

`Function.toString()`은 쓰지 않았어요. 해시는 원문 파일에서만 계산하고, 실행할 함수는 같은 빌드의 정적 import로만 받아요.

## 3. 시험 (13개, 모두 임시 폴더, s4 원본 해시는 매 시험 뒤 대조)

- **SQL 호환:** 0001~0004 해시 = 파일 원문 sha256 = s4 manifest 기록이에요. 제품 목록에는 `run`과 `kind`가 없어요.
- **해시 결합:** 형식, SQL, 경로, 파일 내용이 바뀌면 해시가 달라져요. CRLF로 바꾸거나 파일 순서만 바꾸면 해시가 같아요.
- **원문 불일치 거부:** 원문을 다른 폴더에 복사해서 바꿨어요.
  - 도우미 한 글자, 실행 모듈 문구를 바꾸면 거부해요.
  - 파일이 없으면 거부해요.
  - 모양이 다르면 거부해요(7가지).
- **숨은 의존·비결정 거부:** 21가지를 거부하고, 허용 예시는 통과해요. 도우미에 `Date.now()`를 넣거나 SQL에 `datetime('now')`를 넣으면 **해시를 맞춰도** 거부해요.
- **위조 실행 거부:** `{...test5Code()}` 복사본, `run`만 붙인 SQL 단계, `kind:"code"`만 붙인 단계는 모두 거부하고 DB가 그대로예요.
- **결정성·보존:** s4 사본 두 개를 다른 시각에 올렸어요.
  - 기록의 `applied_at`만 빼면 두 결과가 같아요.
  - 새 표만 생기고 옛 표와 행은 그대로예요.
  - 기록 끝은 `{5, 0005_test_only_code.ts, e20c30e4…}`이에요.
- **전부 되돌림:** 변환 중 `TypeError`(layers 없는 스냅샷)가 나거나 데이터 검사에 실패하면, 단계 SQL로 만든 표까지 없어지고 DB가 그대로예요.
- **지금 DB 올리기:** `migrateLiveDatabase`는 바꾸기 전 사본(= 올리기 전 DB)을 남기고, 결과는 직접 migrate와 같아요(기록 시각·활동 기록 제외). 실패하면 DB는 그대로이고 사본은 남아요.
- **기록 불일치:** 시험 5단계가 기록된 DB에 원문이 바뀐 5단계 목록을 쓰면 적용하지 않고 거부해요. 같은 원문이면 이미 최신(0개)이에요.
- **백업 staging 복원:** s4를 코드 5단계 목록 앱에서 복원했어요.
  - `upgrade 4→5`로 판정되고, staging에서 올린 직후 DB가 직접 migrate 결과와 같아요(A4와 같은 기준).
  - 복원 DB 기록 끝에 코드 해시가 있어요. 원본 ZIP 해시도 그대로예요.
- **코드 단계로 만든 백업:** 같은 원문 앱이면 `same 5→5`예요. 원문이 바뀐 앱이면 `BACKUP_SCHEMA_MISMATCH`, 코드 단계가 없는 앱이면 `BACKUP_TOO_NEW`이고, 목적지가 없고 ZIP 해시도 그대로예요.
- **되돌려 보기(7가지):** 다음 검사를 하나씩 빼면 시험이 각각 실패했어요. 인증 확인(1), `run` 실행(6), 선언 해시 비교(1), 원문 검사 호출(1), 단계 SQL 검사(1), LF 정규화(1), 형식 이름(9). 원래대로 되돌린 뒤 모두 통과했어요.
- **전체:** lint 통과, typecheck 통과, test 31파일 320개 통과(+1 건너뜀, s4 생성 모드), build 경고 0개예요. 빈 임시 폴더에서 `npm.cmd run db:migrate`를 두 번 실행했더니 처음은 4개 적용, 다음은 0개였어요(SQL 경로 그대로).

## 4. 정해야 할 것 (추천 1안)

1. **원문 위치:** `codeMigration`은 기본으로 `process.cwd()`(앱 소스 폴더)에서 목록 파일을 읽어요. 지금 앱과 CLI는 소스 폴더에서 실행해요(README 복원 절차와 같아요).
   - **추천:** 제품 등록에서는 `root`를 넘기지 않고, `root`는 시험에서 원문을 바꿔 보는 용도로만 써요.
   - 패키징 배포를 하게 되면 그때 원문 동봉 방식을 따로 정해요.
2. **제품 0005 등록 위치:** `productMigrations()` 끝에 `codeMigration({...})`을 붙이는 방식을 추천해요(타임라인 0005 배정 때).
   - 그때 등록 파일이 import하는 모듈이 목록 첫 파일과 같은지 확인하는 저장소 시험을 하나 더해요. 지금 계약은 "디스크 원문 = 선언"을 증명하지만, 검토하지 않은 등록 코드가 다른 모듈을 import하는 것까지는 막지 못해요.
3. `MigrationSourceError`가 시작 점검과 `db:migrate` 화면에서 어떤 문구와 코드로 보일지는 제품 코드 단계가 생길 때 정하면 돼요. 지금 제품 목록에는 코드 단계가 없어서 이 오류가 날 일이 없어요.
