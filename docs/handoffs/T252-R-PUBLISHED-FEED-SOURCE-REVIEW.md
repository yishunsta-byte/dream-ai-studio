# T252-R 공개 콘텐츠 공급원 설계 독립 검수

**판정 수정 필요** · 설계 `ea1013716420dc55298cbdc6643e900c694742fe`

전용 승인 기록, 비공개 배포 사본, 서버 공개 DTO, 정상 빈 목록과 장애를 구분하는 방향은 적합하다. 아래 계약을 확정한 뒤 합성 이미지 1건으로 구현을 검증할 수 있다. 특히 공개 파일 경로와 이미지 최적화는 같은 변경에서 닫아야 철회 이후 새 요청에 대한 약속을 검증할 수 있다.

## 필수 수정

### 1. 익명 미디어 요청을 전용 핸들러에만 연결

`lib/auth/config.ts`의 T241 익명 집합은 `/`와 예시 이미지 6개의 정확한 경로다. 새 주소는 T249의 URL 변환을 통과할 수 있지만 현재 `proxy.ts`에서는 익명 우회 대상이 아니다. 인증 설정이 빠지면 503, 설정이 있고 익명이면 로그인 리다이렉트가 먼저 발생할 수 있다. `isPublicPath`에만 추가해도 proxy의 인증 확인과 세션 갱신을 피할 수 없다.

기존 정확 경로 집합을 유지하고, 이미지 1차의 고정 슬롯·형식과 제한된 slug·세대를 파싱하는 별도 조건을 proxy의 인증 전 분기에 둔다. GET·HEAD만 승인 조회 핸들러에 연결한다. 핸들러도 같은 정규형을 검증하고, 실제 활성 레코드와 슬롯을 확인한 다음 해당 배포 사본만 읽는다. T249가 거절하는 예약 경로 조각도 slug 등록 시 배제한다. 인코딩·정규화·후행 슬래시·메서드·인접 보호 경로와 Next의 자동 HEAD/OPTIONS 처리를 HTTP에서 대조한다. 승인 전·철회·이전 세대는 404, 승인 조회/Storage 장애는 닫힌 오류 응답으로 합의한다. `/media/public/` 전체를 익명 접두사로 등록하지 않는다.

### 2. 최적화 주소와 각 캐시 계층의 철회 계약 고정

`components/public-showcase/neon-showcase.tsx`의 대표·카드·목록·상세 이미지는 모두 `next/image`를 사용한다. 설치된 Next의 기본 이미지 최적화 최소 TTL은 14,400초이고, proxy matcher는 `/_next/image`를 제외한다. 원본 미디어의 `no-store`만으로는 최적화 결과가 요청마다 활성 세대를 확인한다는 보장이 없다. 모든 승인 이미지 표현을 직접 주소로 제공하고, `images.localPatterns` 등으로 최적화 엔드포인트가 새 승인 미디어를 직접 변환할 수도 없게 한다. 허용 패턴을 좁힐 때 기존 앱의 로컬 이미지 경로도 대조한다. [Next.js Image](https://nextjs.org/docs/app/api-reference/components/image#localpatterns)

`app/layout.tsx`의 `force-dynamic`에 더해 홈 HTML·RSC, 로더, 미디어 GET·HEAD의 무캐시 동작을 명시한다. 미디어 성공·404·장애 모두 `no-store`로 처리하고, 프록시/CDN 우선 헤더와 stale 응답, 새 탐색 시 RSC 재사용을 검증한다. 사전 로드가 가능한 홈 링크와 새로고침·재탐색을 검사한다. 이미 내려간 화면과 바이트, 허가된 진행 중 전송은 회수 약속에서 제외한다. [Next.js 캐시](https://nextjs.org/docs/app/guides/caching-without-cache-components) · [Vercel 캐시 헤더 우선순위](https://vercel.com/docs/caching/cache-control-headers#behavior)

### 3. DB 조회와 Storage 다운로드 각각 최소 권한을 증명

목록 자격에는 활성 공개 DTO 투영만, 파일 조회 자격에는 지정 slug·세대·슬롯의 활성 배포 객체 확인만 허용한다. 각각의 허용 관계·열·연산과 실행 역할을 설계에 적는다. 테이블 전체 조회, 수정, 작업실·원본 자료 접근을 차단한다. PostgreSQL 뷰를 쓰면 뷰 소유자와 실제 RLS 적용 주체를 기록한다. `security_invoker`는 호출자의 기저 관계 권한을 요구하므로, 이 옵션만으로 비공개 기저 열이나 행을 차단했다고 판단할 수 없다. 비공개 `dream`과 `anon`·`authenticated`·`authenticator` 미노출 계약을 지킨다. [PostgreSQL 17 CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html)

현행 `lib/storage/supabase/config.ts`와 `reader.ts`는 서버용 `service-role` 자격을 사용한다. 이 키는 Storage RLS를 우회하므로 비공개 버킷과 파일 경로 검사만으로 자격 자체를 배포용 읽기에 제한할 수 없다. 첫 운영 연결에는 배포 버킷으로 제한된 읽기 전용 서비스 주체와 실효 정책, 또는 같은 경계를 강제하는 별도 읽기 서비스가 필요하다. 원본 접근과 쓰기·목록·삭제를 거부하는 증거가 있어야 한다. 그 전에는 합성 Storage로만 진행한다. 다운로드는 DB에서 확인한 불변 키로 고정하고, 확정한 이미지 크기·형식·해시와 전송 한도 및 오류 처리를 명시한다. 브라우저에 저장 주소·서명 URL·자격을 반환하지 않는다. [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control#bypassing-access-controls)

발행 쓰기는 `resolveServerAuth()`의 검증된 UUID와 별도 발행 허용, 권리자 동의 및 원본 범위를 함께 확인한다. `dream_api`의 actor는 소유자 범위이고 `dream_worker`는 교차 소유자 역할이다. 발행 담당자와 원본 소유자가 다를 때 소유자 승인 증표와 좁은 대상 검증 경로를 정하거나, 1차에서 소유자와 발행 담당자가 같은 경우로 제한한다. 요청 소유자 ID로 actor를 바꾸거나 홈에 기존 worker·owner 자격을 부여하지 않는다. 인증 해제·비인가·교차 출처에서 쓰기를 닫는다.

### 4. 활성 세대 경쟁과 철회 시점 명문화

활성 슬롯 유일 제약은 두 활성 행을 막지만 최초 준비 중 철회, 철회 뒤 이전 복사 작업 완료, 중복 요청의 결과까지 결정하지는 않는다. 활성 행 유무와 관계없이 잠글 수 있는 slug 단위 기록과 단조 증가 세대 또는 버전을 두고, 준비 작업은 예상 버전을 가진다. 승인과 철회는 같은 잠금 경계에서 버전·후보 리비전·권리·사본 준비 상태를 대조한다. 교체한다면 기존 세대 비활성화와 새 세대 활성화를 한 DB 트랜잭션으로 처리한다. 철회는 pending 후보에도 효력을 갖게 하고 이전 주소·객체 키를 재사용하지 않는다. 동일 요청의 재실행, 커밋 응답 유실 후 조회, 충돌·실패 시 사본 정리의 결과를 정의한다. 권리 만료가 첫 버전 범위에 포함되면 목록과 파일이 동일 기준 시각으로 처리하게 하고, 지원 범위와 한계를 승인 계약에 기록한다.

목록과 파일의 권위 있는 활성 판정은 요청마다 기본 DB에서 새로 수행한다. 철회 커밋 이후 시작된 읽기에는 이전 트랜잭션 스냅샷·읽기 복제본·캐시를 사용하지 않는다. 승인 전과 철회 후의 캐시 없는 404, 승인 후 200, 동시 승인·철회, 이전 시도 뒤늦은 완료를 후속 합성 검증에서 다룬다. [PostgreSQL 17 트랜잭션 격리](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)

### 5. 정상 빈 목록과 운영 계약 실패를 호출부에서 분리

T251의 `buildShowcaseFeed`는 변환 결과가 비면 예시를 반환하고 `excluded`를 버린다. 운영 로더는 이 fallback 전에 조회 성공·시간 초과·설정 누락·권한 실패·DB 계약 실패를 구분해야 한다. 성공 행을 T249로 변환하는 단계에서 제외뿐 아니라 중복·의도치 않은 잘림도 확인한다. 명시적 예시 전용 모드와 정상 0건만 예시를 보여 준다. 승인 데이터 오류와 공급원 불가는 로그인 링크가 있는 안내를 표시하고, 기존 승인 카드나 예시를 대신 내보내지 않는다. 운영 장애 UI의 HTTP 상태 계약을 정하고 HTML·RSC에서 각각 확인한다.

이미지 사본이 빠졌으나 활성 DB 행이 남아 있는 경우 파일 경로 장애와 승인 부재의 외부 응답 및 서버 진단을 구분한다. 실시간 파일 검증을 홈에서 수행하지 않는다면 홈의 정상 판정은 승인 메타데이터 조회에 한정된다고 명시한다. 서버 진단은 분류 코드·개수만 남긴다. 하드 리밋 적용 전에 검증하는 대상 범위를 정하고, SQL과 T249가 같은 밀리초 정밀도와 ASCII 정렬 기준을 사용하게 한다. SQL의 하위 밀리초 정밀도 또는 다른 collation이 24번째 선택을 바꾸지 않는지 경계 데이터를 검증한다.

### 6. PG17 배포 전제와 합성 검증 분리

기존 B8 읽기 전용 기록의 관리형 대상은 PostgreSQL **17.12**였고 관찰 당시 `dream`과 관리 이력이 없었다. 현재 운영 상태를 새로 조회하지 않았다. 프로젝트 계획상 관리형 PG17 호환성과 권한·TLS 검증은 남아 있고, `migration-catalog-v3.ts`의 현재 관찰 스키마는 PG18을 명시적으로 요구한다. B6의 버전 하한이나 합성 PG18.7 통과로 PG17 이관이 검증됐다고 볼 수 없다. 1차 SQL 설계는 PG17 공통 기능으로 제한하고 합성 PG17에서 승인 기록·활성 제약·역할·동시성·롤백을 먼저 검증한다. 실제 적용 전에는 지원되는 이관·카탈로그 경로, 관리형 schema·role provision, 전용 런타임 TLS/풀러, Storage 정책을 별도 확인해야 한다. PG18 판별을 완화해 우회하거나 운영 신규 테이블을 수동 적용하는 단계는 첫 범위에 넣지 않는다.

## 권장 구현 순서

1. **계약 확정과 합성 PG17.** 공개 ID·세대·고정 이미지 슬롯, 승인/철회 상태 전이, 자격별 권한, DB와 Storage 장애 결과를 먼저 고정한다. 역할·동시성·권리·소유자 경계를 시험한다.
2. **파일 전달과 철회.** 별도 비공개 합성 버킷/대역에서 이미지 한 건의 복제·검증, 좁은 proxy 예외, GET·HEAD 재승인 확인, 직접 이미지와 최적화 차단을 함께 검증한다. 기존 예시·보호 경로도 회귀 검사한다.
3. **홈 공급원 연결.** 명시적 예시 전용 모드로 시작하고 격리 Next에서 정상 한 건, 정상 0건, 마지막 철회, 계약 위반, 장애, HTTP/RSC/캐시를 검증한다. 기존 T249/T251 테스트와 정렬 경계 검사를 유지한다.
4. **운영 전환 기준 별도 확인.** 관리형 PG17 경로와 Storage 자격을 확인한 뒤 승인된 이미지 1건을 대상으로 연결할 수 있다. 영상·음악의 Range, 내보내기, 서명 URL, 범용 관리자 발행 화면은 첫 이미지 검증에서 제외한다.
