## 2. 지금 코드에서 바꿔야 하는 것 (규모)

| 영역 | 현재 | 이전 후 | 규모 |
|---|---|---|---|
| DB | SQLite(`better-sqlite3`) 17개 표, 마이그레이션 0001~0010, 직접 사용 14파일, 묶음 처리(트랜잭션) 22곳 | Supabase Postgres. 동기 호출 → 비동기로 바뀌어 저장 계층 전체를 다시 써야 해요 | 큼 |
| 파일 | 로컬 폴더(`storage/`), 파일 시스템 사용 33파일(업로드·썸네일·렌더 결과·백업 zip) | Supabase Storage(비공개 버킷, 서명된 주소) | 큼 |
| 작업 처리 | `jobs` 표 + PC의 상시 작업 처리기 | 표는 Postgres로, 처리기는 **PC(또는 별도 서버)에 그대로** 두고 Supabase에 접속 | 중 |
| 영상 만들기 | PC의 FFmpeg·Remotion 브라우저(.tools 약 750MB) | 그대로 PC 처리기에서. Vercel에서는 하지 않아요(PLAN P7-4) | 작음 |
| 로그인 | 없음(127.0.0.1 전용) | Supabase Auth + 모든 화면·API 보호 + 표마다 행 단위 보호(RLS) | 중 |
| 백업·복원 | 로컬 zip·사본 | Postgres 백업 + Storage 사본 기준으로 다시 설계 | 중 |
| 화면 | 15개 화면, API 19개 | 대부분 그대로. 로그인 화면·접속 보호·파일 주소만 바뀜 | 작음 |

## 3. 단계 (각 단계 끝에 검수·은영님 확인)

| 단계 | 내용 | 끝났다는 기준 | 외부 반영 |
|---|---|---|---|
| V0 연결 준비 | GitHub 비공개 저장소 생성·첫 올리기, Vercel·Supabase 프로젝트 생성, 비밀값은 각 서비스 환경변수에만 | 비공개 저장소에 코드, 비밀값 0건 검사 통과 | 저장소만(비공개) |
| V1 로그인 먼저 | Supabase Auth, 로그인 화면, 모든 화면·API 접속 보호. 이 단계까지 Vercel 주소는 **보호 켠 미리보기만** | 로그인 안 한 접속은 전부 막힘(시험으로 확인) | 보호된 미리보기 |
| V2 DB 이전 | Postgres 스키마(0001~0010 대응), 저장 계층 비동기 전환, 시험을 Postgres 시험 DB로 | 기존 시험 전체 통과, 가짜 fixture 이전 리허설 | 시험 DB |
| V3 파일 이전 | Storage 버킷·업로드·미리보기·다운로드 | 업로드→보기→내려받기, 원본 덮어쓰기 금지 유지 | 시험 버킷 |
| V4 작업 처리기 연결 | PC 처리기가 Supabase의 작업을 가져가 렌더 후 Storage에 결과 저장 | 웹에서 요청→PC 렌더→휴대폰에서 재생 | 운영 |
| V5 실데이터·공개 | 3013의 실제 데이터 이전(현재 프로젝트 0개라 단순), 운영 주소 열기 | 1280·390 화면, 실제 휴대폰 확인 | 운영 |

예상 기간: V0~V1 1~2일, V2~V3 1주 안팎, V4~V5 2~3일. 검수 시간은 따로예요.

## 4. 은영님이 정하거나 해 주셔야 할 것
1. GitHub: `gh auth login` 로그인, **비공개** 저장소 이름 결정.
2. Vercel·Supabase 계정 로그인(무료 요금제로 시작 가능, 파일 용량이 늘면 유료 검토).
3. 로그인 대상: 은영님 혼자인지, 다른 사람도 쓰는지(역할 구분 필요 여부).
4. 영상 만들기 PC: 이 PC가 켜져 있을 때만 렌더가 진행돼요. 괜찮은지, 별도 서버가 필요한지.
5. 도메인: 기본 `*.vercel.app` 주소로 시작할지.
6. Remotion 라이선스: 사용자가 4명 이상이 되면 유료(PLAN 기록). 혼자면 지금 기준 유지.

- API 키·Supabase 비밀키는 서비스 환경변수에만 두고 저장소에 올리지 않아요. 서비스 키는 서버와 PC 처리기에서만 써요.

- 고정 마이그레이션 0001~0010과 fixture는 바꾸지 않고, Postgres용은 새 파일로 만들어요.
