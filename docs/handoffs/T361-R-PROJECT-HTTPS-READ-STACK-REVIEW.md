# T361-R 프로젝트 HTTPS 조회 전체 스택 독립 검수

2026-11-19 KST · Codex(Tester) · 고정 커밋 `58ce64f` · Master 배정 `msg_79705800c278`

**격리 검수 통과.** 고정 3경로는 전체 스택 실행기 두 개와 인계다. 앱 아카이브 `633c10b`, 기존 T358 설치·복귀 SQL과 실행기 blob을 대조했다. 중첩 사본에서 저장소를 찾도록 검수용 실행기에만 Git 작업 경로를 명시했다.

- Next 개발 서버에서 로컬 게이트웨이까지 HTTPS를 사용했다. 기본 신뢰의 자체 서명 인증서 접속은 거절됐고, 명시 CA 신뢰와 루프백 IP 인증서 일치 조건에서는 통과했다. 합성 Auth가 응답했고 같은 JWT를 실 PostgREST와 소유 PG17.12가 처리했다.
- A/B 목록과 상세는 각자 소유한 활성 프로젝트에 한정됐다. 익명 401, 타인·보관 상세 404, 성공·실패 API `no-store`를 확인했다. 실제 PostgREST 프로필과 0·1·2건 `Content-Range`를 대조했고 앱 DTO는 단계 순서 정규화 뒤 기존 PostgreSQL 읽기와 깊은 동등성을 보였다. 개인 목록·상세·관리 화면을 확인했다.
- A의 DB 승인을 회수한 뒤 같은 쿠키의 Auth는 성공했지만 목록·상세에 데이터가 없었고 B의 결과는 유지됐다. 재승인하자 A 조회가 복구됐다. 기존 프로젝트·단계·작업 쓰기가 조회에 반영됐고 T358 복귀에서 기반 행·이력·ACL·정책·트리거를 보존했다.
- 스키마 제거 직후에도 HTTPS가 선택된 설정에서는 실제 PostgREST 실패가 앱 503 `no-store`로 매핑됐다. 비활성 설정으로 다시 열었을 때 목록·상세는 503 `no-store`, 개인 관리는 조회 불가였고 Data API 호출은 0건이었다. 이 경우에도 기존 Auth 상류 호출은 있었다.
- 관련 회귀 1,280건 통과·300건 조건부 건너뜀, 소스 타입 검사, 실행기 ESLint와 diff 공백 검사가 통과했다. Next·HTTPS·PostgREST·PG 리스너와 인증서·실행 파일·임시 DB를 정리했다. 소유 프로세스 및 내부 사본 0건을 확인하고 검수용 사본도 제거했다.

시험 경로는 게이트웨이까지 로컬 TLS, 게이트웨이에서 PostgREST까지 루프백 HTTP, PG까지 로컬 SCRAM이다. 실제 Supabase Auth 발급·HTTPS, 관리형 역할·Data API 설정, 운영 세션 갱신 또는 배포는 범위 밖이다. 외부 운영 주소 접속·빌드·배포·새 세션 생성은 없었다.
