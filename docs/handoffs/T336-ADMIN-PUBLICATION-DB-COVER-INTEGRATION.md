# T336 게시 DB와 비공개 표지 통합 검증

2026-11-19 KST · Codes(Backend) · 기준 `18340be` · Master 배정 `msg_957d80fae44e` · PG17 실행기 재사용 승인 `msg_70b22fe95969`

서버 전용 `createPublicationServerConfig()`는 한 설정에 포함된 운영자 UUID를 정규화해 T332 DB 어댑터와 T334 표지 리더에 전달한다. DB 대상과 권리 조회 함수는 T332에, Storage 프로젝트·자격·크기·시간 제한은 T334에 전달한다. Storage 설정에서 별도의 운영자를 지정할 수 없으며 버킷은 T334의 `publication-covers-private`으로 고정된다. 반환값은 기존 T327 런타임에 전달하는 옵션이다. 제품의 기본 구성에는 이 팩터리를 연결하지 않았다. [서버 조립](../../lib/public-showcase/publication-server-config.ts)

형식이 잘못된 Storage 설정은 DB 초기화에 도달하기 전에 비활성 결과를 반환한다. DB 로그인·역할 또는 운영자 바인딩이 틀리면 T332 조립이 닫히고 Storage 호출은 발생하지 않는다. Storage의 비공개 버킷 검사와 객체 접근은 대상 표지를 읽는 시점에 수행한다. 읽기 실패는 해당 게시 완료 트랜잭션을 롤백하고, 공개 표지는 바이트 없이 실패로 응답한다. 그동안 승인 목록은 DB의 현재 상태를 따른다. DB 역할 검증 자체가 실패하면 공유 그룹의 세 공급원이 닫힌다.

## 자체 검증

`node --conditions=react-server --import tsx tests/public-showcase/t328-publication-db-preflight.pg17.ts`로 소유 PG17·TLS와 실제 Supabase SDK를 사용하는 루프백 Storage 서버를 함께 실행했다. 기존 T328/T330/T332 조건을 유지하면서 아래 통합 시나리오를 추가했다. [T336 전용 시나리오](../../tests/public-showcase/t336-publication-db-cover-integration.pg17.ts)

- 프로젝트 URL 형식, 승인 운영자, DB 역할 불일치에서 비활성 및 Storage 호출 0건을 확인했다. 정상 흐름은 오직 승인 프로젝트의 고정 버킷 메타데이터와 정규 객체에 인증된 GET을 보냈다. 중첩된 운영자·버킷 값이나 구성 생성 뒤 자격 객체를 바꾸어도 실제 요청 대상과 승인 운영자가 달라지지 않았다.
- 실제 관리자 HTTP로 게시를 준비했다. 공개 버킷 응답과 Storage 503에서는 공개 목록과 표지에 작품이 나타나지 않았고, 게시 완료 요청의 원장·감사·DB 게시 기록이 생성되지 않았다. 같은 요청으로 재시도하자 게시가 완료됐으며 공개 목록과 실제 WebP GET·HEAD가 활성 세대를 보여 줬다.
- 같은 크기의 변조 바이트는 503으로 거절됐다. 지연된 객체 스트림은 시간 제한에 따라 닫혔고 다음 표지 읽기는 성공했다. 표지 다운로드 중 철회하면 응답 직전 권한 확인에서 404가 반환됐고 이후 공개 목록에서 작품이 사라졌다.
- 표지 DB 역할 철회 뒤에는 표지·관리자·목록이 상태 코드 또는 실패 상태로 닫혔고 Storage 호출 수는 늘지 않았다. 관리자 JSON과 공개 목록·표지 응답에서 내부 키·버킷·자격·제공자 오류가 노출되지 않았다. Storage 시험 리스너와 DB 검증 세션, 임시 클러스터를 정리했다.
- 관리자·공개·기존 Storage 회귀 299건이 통과했다. 변경 TypeScript ESLint와 `.next` 생성 검증 파일을 제외한 소스 527개 진입 파일 타입 검사도 통과했다.

## 인계

실제 프로젝트의 운영자 자격 매핑·버킷·객체와 승인된 운영 연결은 후속 범위다. 이번 검증은 소유 임시 PG17과 합성 Storage에 한정했다.
