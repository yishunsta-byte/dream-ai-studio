## 1. 지금 무슨 일이 일어나나 (코드 읽기)

1. 데이터 구조 올리기는 앱 시작 때 자동으로 하지 않고 `npm.cmd run db:migrate`(CLI)로만 한다.
2. 실패하면 CLI 창에만 문장이 나온다(예: "데이터 구조를 바꾸지 못했어요. 바꾸기 전 데이터는 그대로이고, 따로 복사본도 남겨 두었어요." + 복사본 파일 이름).
3. 그 뒤 앱을 열면 시작 점검 "데이터베이스·마이그레이션" 줄은 `verifyMigrations` 예외 문장만 보여 준다 — 예: "데이터베이스 버전이나 마이그레이션 기록이 맞지 않아요. 적용 상태를 확인해 주세요." **데이터가 안전한지, 복사본이 어디 있는지, 다음에 무엇을 할지 알 수 없다.**

은영님은 CLI 창보다 앱 화면을 본다. P2-1의 0005가 첫 실제 사용이라 그 전에 화면 안내가 있어야 한다.

## 2. 적용 범위 결정 (권장 A)

| 안 | 내용 | 권장 |
|---|---|---|
| **A. 최소 구현** | CLI가 마지막 결과를 작은 기록 파일로 남기고, 시작 점검이 DB 검사 실패일 때만 그 기록을 읽어 알맞은 문장·복사본 이름·다음 행동을 보여 준다 | **권장.** 코드 작음, DB를 건드리지 않음 |
| B. 범위 축소 | "이관 실패 안내는 CLI 출력으로 충족, 시작 화면은 일반 문장"으로 T-017 3.5.3을 공식 축소 | 0005 첫 실행 때 은영님이 원인을 모를 위험. 권하지 않음 |

## 3. A안 명세

### 3.1 결과 기록 파일

- 위치: `data/migration-last.json` (DB 파일 옆. DB 안에 쓰지 않음 — 실패 때 DB는 되돌려지므로).
- 내용: `{ "schema": 1, "result": "failed" | "succeeded", "code": "<LiveMigrationCode>" | null, "at": "<ISO>", "from": <적용돼 있던 개수>, "to": <코드의 개수>, "snapshot": "backups/pre-migrate/<파일 이름>" | null }`
- 쓰기: 임시 새 파일 → 이름 바꾸기. **기록을 못 써도 DB에는 아무 영향 없어야 한다**(CLI에 "실패 기록을 남기지 못했어요. 위 안내를 그대로 따라 주세요." 한 줄 추가).
- 성공하면 `result: "succeeded"`로 바꿔 쓴다(상태 파일이라 덮어써도 됨 — 원본 데이터 아님). 자동 삭제 없음.
- 절대 경로·키·개인 정보를 쓰지 않는다. 복사본은 `backups/pre-migrate/` 아래 상대 경로만.

### 3.2 시작 점검이 기록을 쓰는 조건

- DB 검사가 **통과**하면 기록을 보지 않는다(성공·옛 실패 기록 모두 무시).
- DB 검사가 **실패**하고, 기록이 `result: "failed"`이며, `to`가 지금 코드의 마이그레이션 수와 같고, `from`이 지금 DB에 적힌 수와 같을 때만 기록을 쓴다. 하나라도 다르면 **옛 기록**으로 보고 무시 → 3.4 기본 문장.
- 기록 파일을 읽지 못하거나 형식이 틀리면 무시(시작 점검이 실패로 멈추지 않음).

### 3.3 문장 (한 곳에서 관리)

CLI와 시작 점검이 **같은 문장표**를 쓴다(예: `lib/db/migration-copy.ts`). 시작 점검 줄 모양: 굵은 첫 문장 → (있으면) "바꾸기 전 복사본: backups/pre-migrate/{파일}" → 다음 행동 → 작은 코드 줄 `코드 {code}`.

| code | 첫 문장 (CLI 현재 문장 유지) | 다음 행동 (시작 점검에 추가) |
|---|---|---|
| `MIGRATION_FAILED` | 데이터 구조를 바꾸지 못했어요. 바꾸기 전 데이터는 그대로이고, 따로 복사본도 남겨 두었어요. | 앱과 작업기를 끈 뒤 `npm.cmd run db:migrate`를 한 번 더 실행해 주세요. 계속 실패하면 이 화면과 복사본 이름을 알려 주세요. |
| `DATABASE_BUSY` | 앱이나 작업기가 데이터를 쓰는 중이라 바꾸지 않았어요. 지금 데이터는 그대로예요. | 앱과 작업기를 모두 끈 뒤 `npm.cmd run db:migrate`를 실행해 주세요. |
| `SNAPSHOT_FAILED` | 바꾸기 전 복사본을 만들지 못해 시작하지 않았어요. 지금 데이터는 그대로예요. | 저장 공간과 `backups` 폴더 쓰기 권한을 확인한 뒤 다시 실행해 주세요. |
| `SNAPSHOT_EXISTS` | 바꾸기 전 복사본을 남길 파일 이름이 이미 있어 시작하지 않았어요. 지금 데이터는 그대로예요. | 잠시 뒤 다시 실행해 주세요. 있던 복사본은 지우지 않아요. |
| `SCHEMA_MISMATCH` (기록이 다름) | 데이터 구조 기록이 이 앱과 맞지 않아 바꾸지 않았어요. 지금 데이터는 그대로예요. | 더 새 버전의 앱에서 쓰던 데이터인지 확인해 주세요. |
| `SCHEMA_MISMATCH` (F039-2: 기록 없는/빈 기록인데 내용이 있는 DB) | 이 데이터베이스가 어느 버전에서 만들어졌는지 확인할 수 없어 바꾸지 않았어요. 지금 데이터는 그대로예요. | 설정한 데이터 폴더가 맞는지 확인해 주세요. 새로 시작하려면 빈 데이터 폴더를 지정해 주세요. |

F039-2 경우는 code를 늘리지 않고 기록 파일에 `"reason": "unrecorded"`를 더해 문장만 고르는 방식을 권장(코드 집합 유지). 지금 CLI 문장 "더 새 버전의 앱에서 쓰던 데이터인지"는 이 경우에 맞지 않는다.

### 3.4 기록이 없거나 옛 기록일 때 (기본 문장 정리)

| DB 상태 | 문장 |
|---|---|
| DB 없음 | 데이터베이스 준비가 필요해요. 앱과 작업기를 끈 뒤 `npm.cmd run db:migrate`를 실행해 주세요. (현재와 같은 뜻) |
| 적힌 기록이 코드의 앞부분(올리기 필요) | **데이터 구조를 새 버전에 맞게 바꿔야 해요. 지금 데이터는 그대로예요.** 앱과 작업기를 끈 뒤 `npm.cmd run db:migrate`를 실행해 주세요. 바꾸기 전에 복사본을 자동으로 남겨요. |
| 그 밖의 불일치 | 현재 문장 유지 |

"올리기 필요"는 지금 일반 불일치 문장으로 보이는 가장 흔한 경우(새 버전 받은 뒤 아직 migrate 안 함)라 따로 안내한다.

## 4. 수용 기준 (T-042용 제안)

1. 실패 주입(각 code) → CLI 문장 그대로 + 기록 파일 생성 → 앱 시작 점검에 같은 첫 문장·복사본 상대 경로·다음 행동·코드 줄. 1280·390 넘침 0.
2. 기록 파일 쓰기 실패 주입 → DB 해시 불변, CLI 추가 한 줄, 시작 점검은 3.4 기본 문장.
3. 옛 기록(`to`·`from` 불일치)과 깨진 기록 → 무시, 시작 점검 멈추지 않음.
4. 성공 migrate 뒤 → 시작 점검 통과, 실패 문장 안 보임.
5. F039-2 DB → `reason: "unrecorded"` 문장, DB·스냅샷 폴더 변화 없음.
6. 기록·화면에 절대 경로 0, 키 모양 글자 0.
