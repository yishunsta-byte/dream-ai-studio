## 서버 동작

- 같은 프로젝트·소유자·리비전을 사용한다. 관리형 프로젝트를 생성해 브리프를 승인한 뒤 `GET /api/projects/:id/plan`에서 저장 기준을 읽는다. `POST`에서 `revision`과 `version`을 대조한다. 초안 또는 쇼츠 초안 가져오기는 내용·부가 자료·감사를 원자적으로 기록한다. 저장 응답을 잃으면 GET으로 최신 저장본을 확인할 수 있다. 이전 버전으로 다시 제출하면 409다.
- 명시 승인에는 `action: "approve-plan"`, `acknowledged: true`, 현재 `revision`, `version`, `planId`가 필요하다. 별도 승인 계정이 현재 기획·자료·상태를 검증하고, 승인 정본·장면 스냅샷·장면·단계·감사를 한 트랜잭션에 저장한다. 같은 기획·버전·리비전의 승인 재요청은 기존 승인 결과를 돌려준다.
- 기획 저장과 승인은 동일 프로젝트 행 잠금을 사용한다. 승인 응답의 `produceOpen`은 DB에 저장된 다음 단계 상태다. 이 후보의 `hostedProductionAvailable`은 false다.
- 변경 범위는 기획 라우트, 관리형 서비스 및 SQL, 기존 로컬 기획 접속에 필요한 최소 어댑터, 쇼츠 저장 계약의 검증 스키마, 검수 파일이다. 모델·파일 업로드·제작 GET·Front 및 실제 운영 설정은 이번 작업에서 다루지 않았다.

## 커밋별 자체 검수

- 초안 후보는 실제 Next 운영 빌드, 합성 HTTPS Auth, 격리 PostgreSQL 17.12에서 공통 프로젝트 생성·브리프·조회와 기획 저장을 연결했다. 두 소유자의 404/401 경계, 17초·180초 45장면, 4 MiB 경계, 자막·효과음·장면 프롬프트·BGM, 201/409 경합, 응답 유실 뒤 재조회, 감사 오류 롤백을 확인했다. 초안 단계의 관리형 승인은 409였다.
- 승인 후보는 같은 시험에 더해 실제 역할별 DB 세션에서 모두 TLS 1.3을 확인했다. 작성·승인 역할, 브라우저 역할을 분리했다. 작성 자격증명을 승인으로 설정하면 503이고 쓰기 0건이다. 승인 응답 유실 뒤 동일 승인 요청에 대한 장면·감사 중복은 0건이다. 17초·180초 승인에서 실제 3개·45개 장면이 정본의 UUID와 순서에 일치했다. 늦은 제작 단계 오류는 모두 롤백됐다. 승인 먼저와 저장 먼저의 경합은 각각 200·409, 201·409였다. 강제 generic 계획에서 승인 연결을 반복 사용해도 성공했다.
- 각 후보에서 기존 루프백 Next 경로와 고정 구버전 SQL로 초안·부가 자료·명시 승인·낡은 버전 409를 확인했다. 각 관리형 빌드에는 기존 공통 프로젝트 생성·재시도·롤백·소유권 HTTP 사례도 포함했다.
- 집중 Vitest는 초안 41개, 승인 48개 통과다. 변경 파일 ESLint, TypeScript 포함 Webpack 운영 빌드, 파일 추적 검사가 통과했다. T198에는 목록·상세, 브리프, 기획 경로 분류를 합쳤다. 두 후보에서 103개 통과, 고정 기준과 같은 Style DNA 관련 19개 실패다. 실패 이름을 대조했다.
- 최초 시험의 영어 장면 요약 표본을 스키마가 거부했고, 구버전 SQL의 자료 영수증 선행 관계가 누락된 로컬 시험도 중단됐다. 합성 표본과 격리 초기화만 수정하고 각각 재실행했다.
