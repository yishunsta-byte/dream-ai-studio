**판정 — 수정 후 재검수.** 정상 흐름, 권리 체크와 철회 확인, 같은 UUID의 재전송, 공급자 형식을 확인했습니다. 목록 새로고침이 작업 완료보다 늦게 도착하면 화면이 이전 버전으로 돌아갑니다. [Front 인계](T289-ADMIN-PUBLICATION-QUEUE.md)

## F289-1 — 늦은 목록 응답이 성공한 작업을 덮어씀

헤드리스 Chromium에서 검수 대기 v0의 목록 `load()`가 v0을 읽은 뒤 응답을 보류했습니다. 불러오는 동안 권리 확인과 `v0 게시 준비`가 가능했습니다. 준비를 실행하자 공급자는 v1/준비 세대 1을 커밋했고 화면도 `게시 준비됨`으로 갱신됐습니다. 보류한 목록 응답을 풀자 화면이 v0/검수 대기로 복귀했습니다. 공급자 상태는 계속 v1/준비 세대 1이었습니다.

`reload()`는 시작 시 `busyCount`만 검사합니다. `send()`가 그 뒤 시작할 수 있고, 목록 응답과 행 초기화는 작업 성공 여부와 무관하게 반영됩니다. 요청 세대나 버전으로 오래된 목록을 버리거나 조회 중 변경을 막아야 합니다. 같은 경합에서 성공 상태와 미확정 재전송 상태가 사라지지 않는 회귀가 필요합니다. [큐의 reload·send](../../components/admin/publication-queue.tsx#L52)

## 독립 확인

- 390px와 1280px에서 합성 안내, 타 소유자 미노출·직접 동작 거절, 권리 미확인 항목 차단을 확인했습니다. 키보드 Space로 권리 확인, Tab으로 준비 버튼 이동, Space로 준비를 실행했습니다. 다시 권리를 확인한 후 게시할 수 있었고, 철회 취소는 요청을 보내지 않았습니다. 명시 철회로 v3 검수 대기 상태가 됐습니다.
- 공급자가 게시를 기록한 뒤 응답을 버리자 같은 요청 재시도가 표시됐습니다. 재시도와 최초 게시 요청의 전체 DTO 및 UUID가 동일했고 공급자 게시 버전은 v2로 한 번만 증가했습니다. 충돌에서는 작업이 먼저 차단된 뒤 다시 불러온 새 버전을 표시했습니다.
- 기본 닫힘은 조작 요소 없이 미연결을 표시했습니다. 목록 실패와 빈 목록도 구분했습니다. 두 너비에서 가로 넘침은 없었습니다. 준비 버튼은 두 너비 모두 44px였고 상단 `목록 다시 불러오기`는 390px에서 44px, 1280px에서 32px였습니다. 인계의 모든 버튼 44px 관측과 차이가 있습니다.
- T289의 고정 큐·관리자 개요·로그인 **40/40** 통과, 큐 ESLint 경고 0. 고정 T290 코드의 `PublicationProvider` 대조와 별도 서버 검수에서 목록·요청·응답 모양을 확인했습니다. 후속 변경이 있는 공유 통합본에서도 큐와 게시 서비스의 집중 **28/28**이 통과했습니다.
