# T319 송신 허가 영속 원장과 제어기 재시작 검증

2026-11-19 KST · Codes(Backend) · 기준 `6ed3a46` 및 T318-R · 배정 `msg_d0d5de0bded9`

소유한 PostgreSQL 17.12 루프백 클러스터에 T319 전용 원장을 설치했다. 서로 다른 Node 프로세스의 제어기 두 개가 같은 원장에 연결했다. 두 별도 합성 송신 프로세스의 실제 PID와 부팅 ID를 시험에 등록했다. 송신 허가와 종료 증거 등록 역할을 분리했다. ## 원장 계약과 관측

| 항목 | 실제 결과 |
| --- | --- |
| 동시 소비와 권한 | 두 제어 프로세스가 같은 허가를 사용했다. 첫 트랜잭션을 보류하는 동안 별도 읽기는 `prepared`였고 두 번째 백엔드가 실제 PostgreSQL 잠금을 기다렸다. 먼저 커밋한 쪽만 `starting`으로 전이했고 두 번째는 이미 소비됐다고 응답했다. 시작 이벤트는 한 건이었다. 다른 주체의 소비, 직접 원장 접근, 역할 전환 및 제어 역할의 종료 증거 등록은 거절됐다. |
| 제어기 강제 종료 후 재시작 | 원래 제어기에서 `sending`을 커밋한 뒤 시험 호출자에게 응답을 전달하지 않았다. 별도 DB 연결에서 커밋을 확인하고 원래 제어기 프로세스를 종료했다. 새 PID로 시작한 제어기는 `starting`, `sending`, `finished`의 기존 상태·이력을 그대로 읽었고 재소비는 거절됐다. |
| 종료 미확인과 전환 보류 | 전환을 준비하면 사용 전 허가는 취소되고 새 허가는 차단됐다. 시작·송신 중인 허가는 종료 증거 없이 남았다. 잘못된 PID와 시작 상태의 완료 표기를 거절했다. 시험 관리자가 미종결 허가의 기한을 과거로 옮겨도 전환은 기다렸다. |
| PostgreSQL 정지와 재시작 | 소유 postmaster를 `pg_ctl -m fast stop`으로 정지하고 PID 파일과 리스너가 없음을 확인했다. 살아 있는 제어기의 신규 발급·활성화·상태 읽기는 모두 `ledger_unavailable`이었다. 같은 데이터 디렉터리의 서버를 다시 올려 동일 클러스터 식별자와 달라진 postmaster 시작 시각을 대조했다. 상태·이력, 대기 중인 전환과 신규 허가 차단이 유지됐고 오프라인 요청의 행은 생기지 않았다. |
| 실제 기존 송신자 종료와 복구 | 기존 합성 송신 프로세스를 실제 종료했다. 제어기는 종료 증거가 원장에 기록되기 전까지 계속 기다렸다. 별도 감독 역할이 부팅 ID·PID를 대조하여 격리를 기록한 뒤 두 미종결 허가가 `isolated`로 종결되고 다음 세대를 열었다. 이전 세대의 시작 보고·발급·종료 보고 및 새 송신자가 구 허가를 소비하는 요청을 거절했다. 새 세대는 새 허가로 정상 완료했다. |
| 종료 정리 | 제어기 DB 세션 0건, 소유 Node 제어·합성 송신 프로세스 전부 종료, PostgreSQL postmaster·PID 파일·루프백 리스너 부재와 임시 클러스터 삭제를 확인했다. |

## 이번 검증의 한계

- 실제 PostgreSQL의 원장과 로컬 프로세스의 강제 종료·재생성을 검증했다. DB 재시작은 같은 소유 클러스터의 정상 정지·시작이다. 전원 손실, 복제·승격, WAL 복구, 독립 원장의 분할 상태는 시험하지 않았다.
- 정상 전송의 첫 바이트·종료 보고는 합성 사건이다. 기존 송신자의 격리 증거는 시험 감독자가 관측한 실제 자식 프로세스 종료이며, 원장 함수 자체는 호스트를 조사하지 않는다. 허가 소비와 실제 TLS 첫 바이트의 원자성이나 프록시 큐 종료는 이 시험의 보장 범위 밖이다. 실제 두 TLS 송신 경로의 루프백 관측은 T318에 있다.
- 제품 경로, 운영 인증·권한과 복수 호스트의 증거 수집·전환·네트워크 분할, 운영 DB 및 배포는 연결하지 않았다.

**Master 전달문** · T319 실제 루프백 PG17 원장에서 동시 소비 1회, 제어기 강제 종료와 같은 DB 재시작 뒤 상태 유지, 원장·종료 증거 부재 시 차단, 기존 송신자 프로세스 종료 확인 후 전환 및 구 요청 거절을 확인했다. 독립 재현을 요청한다.
