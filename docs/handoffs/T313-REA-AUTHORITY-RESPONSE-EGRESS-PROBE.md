# T313 REA 권한 전환과 응답 전송 루프백 검증

2026-11-19 KST · Codes(Backend) · 설계 기준 `ae3431e` · 배정 `msg_1c79e8f49726`

소유한 Node HTTP 서버를 `127.0.0.1`의 임시 포트에서 실행했다. 브라우저에 해당하는 별도 HTTP 클라이언트가 실제 소켓을 통해 받은 본문 바이트를 비교했다. 시험 서버가 합성 HTML, RSC 유사 본문, POST 분석 JSON을 준비하고 같은 전송 경계에서 허가 소비, 첫 바이트 큐 삽입, 나머지 전송과 종료를 관리했다. [T309 응답 설계](T309-REA-AUTHORITY-EVIDENCE-ISSUANCE-DESIGN.md) · [루프백 실행기](../../tests/reference-analysis/t313-authority-response-egress.loopback.mjs)

| 시험 | 실제 관측 |
| --- | --- |
| 정상 전송과 동일 허가 반복 | 세 유형 모두 HTTP 200, 예상 Content-Type, `private, no-store`, 합성 본문 전체가 일치했다. 전송 전·중·후의 동일 허가 반복은 HTTP 409, 본문 0바이트였고 허가 소비는 유형별 한 번이었다. |
| 첫 바이트 전 철회 또는 만료 | 각 유형의 전송을 보류하고 철회 또는 만료를 적용했다. 여섯 경우 모두 HTTP 403/410, 클라이언트가 받은 본문 0바이트, 허가 소비 0이었다. 기존 작업을 재개해도 첫 바이트가 들어가지 않았다. |
| 이미 전송 중인 응답의 전환 | HTML 접두부를 받은 뒤 전환을 요청했다. 완료 전에는 기존 세대와 닫힌 신규 허가 상태를 유지했다. 본문 완료와 실제 소켓 종료를 확인한 뒤 다음 세대를 열었다. RSC 전송 취소는 클라이언트가 이미 받았던 접두부만 남겼고, 나머지 바이트는 보내지 않았다. 실제 연결 종료 확인 뒤 다음 세대를 열었다. |
| 종료 상태 불명 | POST의 첫 부분을 받은 클라이언트가 소켓을 끊었을 때, 전환 상태 관리 쪽의 종료 관측을 의도적으로 유실시켰다. 이전 상태가 불명인 동안 새 세대가 보류됐고 재시도 본문은 0바이트였다. 시험 전송 경계의 실제 소켓 종료 기록을 다시 확인한 뒤에만 새 세대를 열었다. |
| 보류 중 전환과 새 세대 | 첫 바이트 전 전환에서 이전 요청과 늦게 다시 들어온 호출은 HTTP 409 및 본문 0바이트였다. 이전 소켓 종료 후 새 세대의 새 허가로 POST 본문을 정상 수신했다. |

대기·철회와 만료 시각은 픽스처에서 제어했다. 실제 TCP 연결, HTTP 바이트, Node의 서버 응답 종료·소켓 닫힘과 클라이언트 취소는 관측했다. 정상·경합·장애 흐름을 포함한 실행 10회 및 ESLint가 통과했다. 마지막에 포트 리스너가 닫혔고 서버 소켓과 클라이언트 요청 모두 0건이었다.

```powershell
node tests/reference-analysis/t313-authority-response-egress.loopback.mjs
node node_modules/eslint/bin/eslint.js tests/reference-analysis/t313-authority-response-egress.loopback.mjs --max-warnings 0
```

송신과 전환 판정은 단일 시험 프로세스에서 직렬화했다. RSC는 합성 프레이밍이며 Next의 실제 직렬화, 프리페치, 스트리밍 또는 호스팅 프록시 정책을 검증하지 않았다. 종료 기록 재확인도 공유 전송 계층의 프로세스 장애·교대나 하위 프록시 큐 폐기를 입증하지 않는다. 실제 호스트의 단일 전송 경계, 우회 차단, 이전 소유자와 하위 큐의 종료 증명은 후속 검증이 필요하다. 제품 라우트·운영 DB·외부 플랫폼·배포 변경은 없었다.

**Master 전달문** · T313 실제 소유 루프백 HTTP에서 세 응답 유형의 허가 단일 소비, 전송 전 철회·만료 시 0바이트, 전송 중 완료·취소 대기와 종료 불명 시 전환 보류를 확인했다. 루프백·세션 정리를 확인했고 독립 재현을 요청한다.
