# T341 게시 DB 위임 설치 검증

2026-11-19 KST · Codex(Backend) · Master 배정 `msg_b64739ec7786` · 설계 `5d5a519`

소유한 로컬 PostgreSQL 17 직접 TLS에서, 관리자가 역할을 준비한 뒤 `NOCREATEROLE`·`NOINHERIT` 설치자가 게시 객체를 설치하고 독립 검증자가 임시 권한 회수를 확인하는 경로를 검증했다. 게시 v1이 이미 있는 대상과 일부 게시 스키마만 존재하는 대상은 이 후보에서 중단한다.

## 설치와 독립 검증

| 단계 | 실제 실행 주체와 확인 항목 |
| --- | --- |
| 준비 | fixture의 관리자가 `postgres` 제어 세션에서 클러스터 공통 잠금을 획득한다. 대상 DB의 쓰기 잠금 안에서 역할을 만들고 설치자에게 여덟 개 NOLOGIN 소유 역할의 임시 `SET`, 설치자와 두 스키마 소유자에게 대상 DB `CREATE`를 부여한다. PG17이 비슈퍼유저 `CREATEROLE` 발급자에게 자동 부여한 관리자 간선까지 승인된 OID와 옵션에 포함한다. |
| 설치 | 별도 설치 로그인이 대상 DB에서 고정 SQL을 실행한다. 초기 객체 소유자인 설치자가 먼저 ACL을 확정한다. 새 객체 소유자에게 임시 스키마 `CREATE`를 부여한 뒤 함수와 테이블의 소유권을 넘긴다. 임시 스키마 ACL을 회수한 다음 업무 스키마는 `t341_schema_owner`에, 이력 스키마와 테이블은 `t341_history_owner`에 귀속된다. 실행 함수의 전용 소유자, 강제 RLS 및 고정 검색 경로는 카탈로그에서 대조한다. |
| 최초 이력 | 설치 트랜잭션에서 별도 이력 소유자로 `SET LOCAL ROLE`한 뒤 버전 2, 소스·계획·카탈로그 해시를 한 행에 기록한다. 계획 해시에는 DB와 클러스터 식별자, 승인자·설치자·검증자 OID, 역할 속성과 모든 관련 간선의 부여자 및 옵션이 들어간다. |
| 회수 | 관리자가 같은 제어 잠금 아래 설치자를 `NOLOGIN`으로 만들고, 임시 멤버십과 대상 DB `CREATE`를 회수한다. 설치자 로그인으로 열렸던 모든 세션을 종료한다. 이미 소유 역할로 전환된 세션도 로그인 사용자의 OID로 감지한다. |
| 독립 확인 | 별도 TLS 검증 계정이 `REPEATABLE READ READ ONLY`에서 사전 고정된 카탈로그와 현재 구조·ACL을 대조한다. 이력의 허용 열과 역할 속성, 직접 간선, 실효 `SET`·`USAGE`, DB ACL, 기존 설치 세션 수를 확인한다. 카탈로그가 같고 임시 권한과 설치 세션이 모두 제거된 경우 `sealed`를 반환한다. |

- SQL SHA-256 `66a966e09207709288226544e2e6a7f20a95f8a4ba1d59246a533e9609f03375`
- 카탈로그 SHA-256 `91b44500cc02b7625b6ed26bab80b8957f65b069149feb8170696130e7956605`. 로컬 후보에서 확보한 고정값을 새 클러스터에서 재현했다. ACL은 저장 순서와 기본값 표기 차이를 정규화하며, 부여자·권한·위임 가능 여부까지 대조한다.

## 검증과 운영 범위

- 두 대상 DB에서 동일한 제어 잠금을 요구하며, 획득한 잠금의 작업 권한은 승인된 대상 DB에 묶인다. 부분 스키마, 승인 OID·부여자 불일치, 우회 상속, DDL 중단, 커밋 응답 유실, 부분 회수, 살아 있는 기존 설치 세션, 이력·ACL 변경을 검증했다. DDL 롤백 뒤에는 `prepared`, 커밋 뒤 회수 완료 전에는 `pending-seal`, 회수가 불완전한 중간 상태는 `BLOCKED`로 처리한다. 응답 유실 직후와 최종 회수 직후에는 새 검증 세션에서 다시 읽는다.
- 검증 계정의 일반 SQL 세션에서도 이력 수정, 게시 데이터 직접 조회, DDL, 소유 역할 전환 및 공개 실행 함수 호출이 거절됐다. 최초 이력 한 행과 시각을 재검증했다.
- 제어 접속 단절 이후에는 기존 작업 권한으로 확인을 재개할 수 없다. 새 제어 세션에서 잠금을 다시 잡아 같은 승인 계획과 최초 이력을 확인했다.
- 독립 확인이 끝난 fixture에서 게시 준비, 게시, 공개 피드와 WebP 서빙, 철회 후 피드 제거와 404를 확인했다. 이력과 Auth를 포함한 foundation 1~3 및 SQL4 물리 객체의 스냅샷을 보존했다. T339와 같이 SQL4는 DDL 공존을 검증하는 fixture다.
- 로컬 실행 명령은 `node --conditions=react-server --import tsx tests/public-showcase/t328-publication-db-preflight.pg17.ts --delegated-publication-installer`다. 러너가 만든 루프백 TLS 클러스터와 세션은 테스트 종료 시 정리한다.
- 기존 PG17/TLS 스위트와 게시·관리자·공개 홈·비공개 스토리지 Vitest 299건을 통과했다. 변경 TypeScript 파일의 ESLint와 생성된 `.next` 검증기 제외 소스 TypeScript 검사도 통과했다.
- 관리형 검증에는 제공자의 직접 TLS와 클러스터 식별자 조회, 승인된 역할 발급·회수, 기존 세션 종료 및 복원 후 OID 재승인 증거가 필요하다. 이 변경의 호출 경로는 명시적인 로컬 실행 모드이며 제품 런타임의 게시 설정과 기존 T338 게시 v1, foundation 0001~0005, 공통 마이그레이션 CLI의 기준은 그대로 유지된다.
