## 1. 적용 범위와 근거

클라우드에서 **지금 읽어 온 내 프로젝트 목록의 범위와 기록된 상태**, 아직 연결하지 않은 관리 기능을 구분해 보여 준다. 기존 클라우드 셸·인증 경계·토큰을 유지한다. T180 로컬 개인관리의 정보 정직성·상태·반응형 원칙을 가져오되, 로컬 시작 점검·백업/복원 폼이나 PC 경로를 클라우드로 옮기지 않는다. T208 홈 3안 선택·적용과 별개이며 새 브랜드나 셸 시안을 정하지 않는다.

직접 읽은 근거:

- `docs/handoffs/T-180-ADMIN-UI-PLAN.md`, `T-180-A1-SETTINGS-DATA-IMPLEMENTATION.md`, `T-180-A2-SETTINGS-OVERVIEW.md`: 조회 시각·최근 응답·성공/파일 존재 구분, 오류와 빈 목록 분리, 단일 snapshot, 폼 상태 보존·키보드 기준. 과거 자체 시험 수치는 이번에 다시 실행한 증거로 계수하지 않는다.
- `app/(cloud)/layout.tsx`, `cloud.module.css`: 클라우드 헤더·계정 메뉴·공통 `.content`; `SessionBoundary` 아래 본문 전체가 `ProtectedContent` 안에 있음. StudioLayout/SQLite 시작 점검을 경유하지 않음.
- `lib/cloud/project-read-page.ts`, `lib/services/postgres/project-read-request.ts`, `project-reads.ts`, `lib/repo/postgres/projects.ts`, `lib/domain/stages.ts`: 실제 읽기·권한·목록·표시 상태 계약.
- `components/cloud/project-list-readonly.tsx`, `components/auth/session-boundary.tsx`, `use-session-watch.ts`, `account-menu.tsx`: 로컬/실패/로그인·계정 변경·포커스 동작.
- `docs/DESIGN.md`, `docs/design/tokens.css`, `app/globals.css`, `components/ui/primitives.tsx`, `ui.module.css`, `lib/ui/status.ts`: 기존 토큰·컴포넌트·레이아웃·상태 명칭.

확인 범위는 위 소스와 문서의 **읽기 검토**다. 실제 클라우드/사용자 데이터/DB/worker/Storage/backup/운영 SHA를 조회하지 않았다. 브라우저 캡처·접근성 도구·실제 폰·스크린리더·제품 시험·빌드·배포는 실행하지 않았다. 아래 검수표는 **앞으로 실행할 완료 조건**이며 통과 기록이 아니다.

## 2. 데이터 의미 — 필수

T229는 같은 성공 응답의 배열에서 건수와 분포를 함께 파생한다. 새 통계 endpoint·클라이언트별 집계 store·polling은 필요하지 않다.

| 화면 항목 | 사용할 근거 | 표시와 금지 |
|---|---|---|
| 표시 목록 건수 | `readCloudProjects()`가 `kind:ok`로 반환한 `data.length` | **“표시 목록 N개”**, 설명 “이번에 불러온 프로젝트 목록 기준이에요.” 전체 계정/PC/보관 프로젝트 총수라고 하지 않음 |
| 상태 분포 | 같은 배열의 `project.status`를 각 프로젝트당 한 번 집계 | 확인 필요·만드는 중·승인 대기·완료·대기. 합계=N. 단계 7개나 작업 이력 행을 별도 프로젝트처럼 더하지 않음 |
| 조회 시각 | 이 목록을 성공적으로 읽고 변환한 뒤 얻은 서버 시각을 직렬화해 전달하는 제안 | **“목록 조회 시각 … (한국시간)”**. 현재 DTO에 시각 필드는 없으므로 T229 페이지에서 한 번 추가할 표시값. heartbeat·DB 백업·마지막 프로젝트 수정 시각 아님 |
| 프로젝트 수정 시각 | 각 `CloudProjectCard.updatedAt` | 상세/목록에 필요할 때 “마지막 수정”. `max(updatedAt)`를 목록 조회 시각으로 사용하지 않음 |
| worker | 현재 읽기 DTO에 없음 | **“작업 처리기 · 미연결”**, “이 화면에서는 최근 응답과 실행 상태를 확인할 수 없어요.” 켜짐/꺼짐/정상/응답 없음/작업0개로 바꾸지 않음 |
| Storage | 현재 읽기 DTO에 없음 | **“파일 저장소 · 미연결”**, “사용량과 파일 보관 상태는 아직 확인할 수 없어요.” 0B·0%·여유 용량·파일 안전·접속 정상 없음 |
| backup | 현재 읽기 DTO에 없음 | **“백업 · 미연결”**, “백업 이력과 복구 가능 여부는 아직 확인할 수 없어요.” 백업 없음/실패/마지막 성공 시각을 만들지 않음 |

현재 repository는 서버가 확인한 owner의 `archived_at IS NULL` 행만 반환하고 `updated_at DESC`로 정렬한다. 소스에 현재 LIMIT는 없지만 **독립적인 전체 총수 계약이 없고 보관 행·로컬 작업도 포함하지 않는다.** 따라서 “표시 목록”이라는 한정은 생략하지 않는다. 후속 UI가 목록을 일부만 제시하더라도 임의 절단을 전체 집계라고 부르지 않는다.

상태는 이미 제공된 resolver의 결과 그대로 사용한다. 우선순위는 `warning`(실패 작업 이력/단계 존재) → `running`(running 작업 기록) → `approval` → `done`(export 승인 기록) → `queued`다. **과거 실패가 남은 프로젝트를 현재 미해결 장애 건수로 확대하지 않는다.** `running`은 실시간 worker 응답, `done`은 파일 존재·재생·최종 품질 검증이 아니다. 분포 아래에 **“기록된 프로젝트 상태 기준이며, 처리기의 현재 실행 여부를 뜻하지 않아요.”**를 둔다. 공통 StatusPill의 “만드는 중”도 이 범위 설명과 함께 쓰며 상태 계산을 UI에서 다시 정의하지 않는다.

목록 길이가 0인 **성공 응답**에서만 0을 표시할 수 있다. 읽기 실패·로컬 경계·인증 거부·확인 중에 가짜 0이나 0개씩의 정상 분포를 채우지 않는다. 성공 시각은 자료와 함께 갱신한다. 오류 발생 시 현재 시각을 성공 조회 시각으로 찍지 않는다. 날짜 형식이 유효하지 않으면 “조회 시각 확인 불가”로 처리하고 `Invalid Date`를 노출하지 않는다.

## 3. 정보 구조와 반응형 — 필수 / 배치 추천

**필수 순서:** 클라우드 공통 헤더/계정 → 읽기 전용 진입 링크 → 제목·설명 → 목록 건수·조회 시각 → 상태 분포 → 미연결 관리 영역. 두 화면 폭에서 같은 DOM·읽기 순서를 쓴다. 프로젝트 개인 정보는 모두 기존 ProtectedContent 안에 둔다. 내 프로젝트(`/cloud/projects`)와 개인 관리(`/cloud/manage`)의 이동 링크에는 현재 위치를 텍스트/`aria-current=page`로 표시하며, 쓰기 화면이나 `/settings`의 로컬 운영 폼으로 우회하는 링크를 만들지 않는다. 기존 계정 메뉴의 로그인/로그아웃 계약은 그대로다.

제목: **“개인 관리”**. 설명: **“클라우드에 표시된 내 프로젝트와 연결 범위를 확인해요. 지금은 보기만 할 수 있어요.”** 정상·빈 목록·자료 오류·local의 안정된 본문에는 h1 하나를 둔다. 세션 경계의 일시 안내를 위해 별도 h1이나 복제 본문을 만들어 공통 경계를 바꾸지 않는다.

권장 PC 1280 구성:

```text
기존 클라우드 헤더 · 계정
내 프로젝트 | 개인 관리(현재)
개인 관리                                      [다시 불러오기]
클라우드에 표시된 내 프로젝트와 연결 범위를 확인해요. …

표시 목록 N개                     목록 조회 시각 YYYY. MM. DD. HH:mm (한국시간)
이번에 불러온 프로젝트 목록 기준이에요.             내 프로젝트 보기 →

기록된 상태 분포
확인 필요 n | 만드는 중 n | 승인 대기 n | 완료 n | 대기 n
기록된 프로젝트 상태 기준이며, 처리기의 현재 실행 여부를 뜻하지 않아요.

작업 처리기 · 미연결    파일 저장소 · 미연결    백업 · 미연결
확인할 수 없는 범위      확인할 수 없는 범위      확인할 수 없는 범위
```

- 본문은 기존 `.content` 최대폭 `--content-max`와 여백을 사용한다. 미연결 3카드는 기존 `.grid`의 3열→1열 규칙을 재사용할 수 있다. 건수/시각의 한 카드 구성 또는 2열 요약은 선택 가능하다. 분포는 가독성 있는 `dl`/리스트로 충분하며 차트 라이브러리를 추가하지 않는다.
- **390px 필수:** 제목·동작 줄바꿈, 건수→시각→분포→worker→Storage→backup 한 열, 본문 좌우 `--sp-4`, 카드 내부 `--sp-4`/`--sp-5` 기준. 고정 너비·nowrap 숫자 행·가로 캐러셀·작은 표를 만들지 않는다. 날짜와 긴 한국어 설명은 카드 안에서 자연스럽게 줄바꿈한다.
- 분포 5항목을 PC에서 한 줄에 놓는 것은 추천이며 필수가 아니다. 공간이 부족하면 줄바꿈/1열로 전환한다. 색 막대·원형 그래프는 필요 없다. 0인 항목을 표시해도 되지만 빈 목록에서는 큰 0 숫자/경고 카드 5개보다 짧은 빈 안내를 우선한다.
- 기존 `PageHeader`, `Card`, `Callout`, `StatusPill`/`Badge`, Link 및 역할 토큰만 사용한다. `--fg-default`/`--fg-muted`, `--bg-app`/`--bg-surface`, `--line`, 상태 토큰을 쓴다. 미연결은 중립 배지와 문장으로 표현하며 failure/success 배지를 붙이지 않는다. 새 색상·그라디언트·미디어 히어로·T208 자산을 넣지 않는다.

## 4. 상태 행렬 — 필수

| 상태 | 보여 줄 것 | 복구·제약 |
|---|---|---|
| normal / ok, N>0 | 실제 N·같은 배열 분포·성공 조회 시각·미연결 3영역·목록 링크 | 읽기 전용 안내 유지. 건강 점수·운영 성공 배지 없음 |
| empty / ok, N=0 | “이번에 불러온 목록에 프로젝트가 없어요.”, 표시 목록 0개, 실제 조회 시각 | “계정에 프로젝트가 전혀 없음/삭제됨”으로 단정하지 않음. 0은 성공 응답에만 사용. 실제 생성 버튼 대신 내 프로젝트 보기 |
| 최초 데이터 읽기 중 | “목록을 불러오고 있어요.” 등 짧은 status와 안정된 자리 | 아직 N/분포/성공 시각 없음. 실제 route loading을 만들지 않는다면 새 loading 파일을 명세 때문에 의무 추가하지 않음 |
| data error / unavailable | “관리 정보를 불러오지 못했어요.”, “잠시 뒤 다시 불러와 주세요.”, 다시 불러오기 | 0/정상·기존 개인 자료를 새 자료처럼 표시하지 않음. raw exception/stack/환경 값/host/PC 경로 없음. 계정 경계는 그대로 |
| local | 기존 CloudReadLocal의 “이 PC에서는 기존 작업실을 써요”와 작업실로 가기 | 클라우드 조회/로컬 시작 점검/SQLite 읽기로 우회하지 않음. 개인 통계 없음 |
| 서버 인증 401 | 기존 정책으로 로그인 이동, 개인 본문 없음 | 기존 안전한 next 처리 유지. 로그인/재시도 경로를 별도 인증 로직으로 재구현하지 않음 |
| 서버 인증 403 / 인증 확인 불가 | 기존 forbidden/unavailable 로그인 안내 정책 | data error로 삼켜 빈 프로젝트·운영 장애로 표현하지 않음. 허용 목록/설정값 노출 없음 |
| 세션 signal 확인 중 / checking | 공통 SessionBoundary 안내, 개인 본문 hidden+inert | 계정 이메일과 개인 숫자·분포·조회 시각·링크 모두 같이 차단. DOM을 임의 재생성해 T224 보존 계약을 깨지 않음 |
| 의심 상태에서 offline / unavailable | 공통 “로그인 상태를 확인하지 못했어요” 안내와 다시 확인 | 자료 읽기 오류의 다시 불러오기와 다른 행동. 의심 계정의 마지막 자료를 카드로 노출하지 않음 |
| 같은 계정 재확인 | 기존 경계가 같은 본문을 복원 | 공통 포커스 복원 계약 유지. 이를 새 프로젝트 조회 성공으로 간주하거나 시각을 바꾸지 않음 |
| 계정 변경·로그인 없음·허용 밖 확정 / cleared | 기존 본문 제거와 전체 문서 reload/login 이동 정책; stale이면 새로 고침 | 이전 계정의 건수·시각·분포·링크를 부활시키지 않음. 지연된 이전 응답도 새 계정 데이터처럼 적용하지 않음 |

**세션 우선순위:** 인증/세션 경계가 자료 상태보다 우선한다. `current`일 때의 조용한 focus/visibility 재검증은 현 `useSessionWatch`의 `keep` 정책을 따른다. 모든 네트워크 오류마다 본문을 가리도록 별도 정책을 추가하지 않는다. 숨김이 필요한 signal/의심 상태에서는 기존 hidden+inert와 cleared 제거를 확실히 유지한다. 세션 경계는 화면 노출 정책이며 서버 권한 검증을 대체하지 않는다. 이미 내려온 메모리 자료의 완전 삭제를 보장한다고 말하지 않는다.

현재 `readCloudProjects()`는 로그인 후 next를 `/cloud/projects`로 지정한다. T229에서 이 기존 함수를 재사용하면 인증 후 목록으로 돌아가는 기존 정책이 유지된다. `/cloud/manage`로 복귀를 정교화하려면 허용된 adapter 범위에서만 조정하고 서버 인증 정책 자체를 변경하지 않는다. 이는 관리 화면 요약을 구현하지 못할 충돌이나 선행 차단 사유가 아니다.

## 5. 다시 읽기·키보드·접근성 — 필수

- **다시 불러오기**는 새로운 실제 서버 읽기를 일으켜야 한다. 같은 URL의 캐시된 화면만 다시 보여 주고 성공 시각을 새로 찍는 행동은 안 된다. 가장 작은 구현은 같은 `/cloud/manage`로의 일반 페이지 이동 링크다. router refresh를 선택하면 실제 결과 수신 경계를 확인하며, 클릭 즉시 성공 Toast/완료 문구를 띄우지 않는다.
- SSR 페이지는 새 문서의 기본 포커스 순서를 따른다. 클라이언트 재조회가 있는 경우에만 pending 중 중복 요청을 막고 진행 문구/`aria-busy`를 제공한다. 불필요한 polling·타이머·페이지 전용 세션 감시는 추가하지 않는다.
- 현 소스는 개인관리의 클라이언트 snapshot을 요구하지 않는다. 같은 계정의 이전 자료를 유지하는 재조회 UI를 선택한 경우에만 “마지막으로 읽은 자료”와 원래 성공 조회 시각+오류를 묶고, 계정 signal/epoch 변경·cleared 때 노출/재사용하지 않는다. 새 store를 만드는 것은 필수가 아니다.
- 링크는 이동, 버튼은 실행으로 구분한다. 상태 항목·카드·미연결 배지에는 버튼/tabIndex를 주지 않는다. 제공하지 않는 재시작/복원/연결/결제 버튼을 비활성 상태로 줄지어 놓지 않는다. 제공하는 동작이 막힐 때만 공통 `disabledReason`의 보이는 이유·`aria-describedby` 계약을 사용한다.
- 새 본문 조작 영역은 44px 이상, 별도 주 행동을 둘 경우 48px. 카드 전체를 불필요하게 링크로 만들지 않는다. 긴 링크 텍스트도 줄바꿈하고 focus ring이 카드 overflow에 잘리지 않아야 한다. 기존 공통 헤더/세션 안내도 검수 범위에 포함하되 문제를 발견하면 범위 밖 공통 컴포넌트를 임의 수정하지 않고 위치·측정값을 Master에 보고한다.
- 소스상 공통 Button `sm`은 PC에서 32px이며 휴대폰에서는 44px로 올라간다. AccountMenu/ProtectedContent의 기존 작은 버튼이 이 규칙을 사용한다. **현재 클라우드 전체 조작 영역이 양폭 44px라고 읽기 검토만으로 인증하지 않는다.** T229의 새 이동/다시 읽기 영역은 범위 내에서 확보하고 공통 영역 실측 차이는 별도 조정할 사안이다.
- 제목 계층 h1→h2, 분포의 이름/값은 `dt/dd` 또는 이름이 연결된 목록. 단순 분포를 progressbar로 읽지 않는다. 색·아이콘만으로 상태를 표시하지 않는다. spinning 상태 pill도 기록된 상태임을 문장으로 한정하고 `prefers-reduced-motion`을 존중한다.
- 날짜는 ISO `dateTime`의 `time` 요소와 한국시간 표시를 권장한다. 중요한 문장은 본문 최소 `--text-md`; 보조 정보는 기존 `--text-sm`/`--fg-muted`. `--fg-subtle`을 작은 도움말/실패 설명에 쓰지 않는다. 본문 대비 4.5:1 기준을 유지한다.
- 오류는 제목·이유·다음 행동을 인접 배치한다. 초기 SSR 안내에 불필요한 assertive alert를 중복하지 않는다. 클라이언트 새 오류는 한 번 알리고, 조회 성공마다 Toast/초점 강제 이동을 반복하지 않는다. 세션 경계의 status/포커스 이동·복귀와 중복 handler를 만들지 않는다.
- Tab/Shift+Tab의 순서는 계정 조작→이동 링크→다시 불러오기→목록 링크 등 시각/DOM 순서와 일치한다. Enter로 이동·재조회 가능해야 한다. 확인 중에는 hidden 본문이 탭·접근성 트리·클릭 대상에 남지 않아야 하고, 확정 후에는 본문이 DOM에 남지 않아야 한다.

## 6. 구현 분담·충돌 판단

T229 Front가 자신의 배정 경로에서 구현한다. 이 명세는 제품 파일 점유를 취득하지 않는다. 기존 읽기 결과를 집계하고 성공 조회 시각을 추가하는 정도로 구현 가능하며 **Front를 전면 대기시킬 사양 충돌은 발견하지 않았다.** 새 endpoint·DB·Auth·Storage·worker·backup 계약을 설계할 필요가 없다. 실제 구현 배정 범위 밖 변경이 필요하면 정확한 경로·이유만 Master와 조정한다.

T180의 local startup probe·백업 폼·restore ticket·polling을 가져오거나 공통 SessionBoundary를 다시 쓰는 것은 이번 범위가 아니다. 서비스 연결/쓰기/재시작/백업 생성/복원/데이터 이동/과금·예산·환경변수 확인/host 진단은 제공하지 않는다. 공용 TEAM/PLAN/REVIEW와 원본 시안도 수정하지 않는다.

필수 기준은 2·4·5절의 데이터 의미·보호 경계·조작/반응형이다. 3절의 PC 카드 수·배치, 차트 생략, 날짜 형식의 세부 모양은 기존 토큰 안에서 Front가 판단할 수 있는 추천이다. 이 추천의 차이만으로 구현을 반환하지 않는다.
