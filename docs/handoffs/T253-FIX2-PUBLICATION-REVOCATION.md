## F2 · 같은 세대의 완료와 철회

철회 입력은 관찰한 버전과 양의 대상 세대를 모두 요구한다. 대상 세대가 관찰 버전보다 크거나 관찰 버전이 잠금 후의 현재 버전보다 크면 거절한다. 잠금을 얻은 뒤에는 그 세대가 현재 준비 포인터 또는 활성 포인터와 일치할 때 해당 포인터만 제거한다. 따라서 준비 상태를 관찰한 철회 요청은 같은 세대의 완료가 먼저 커밋돼도 그 활성 세대를 닫는다. 이미 다른 세대로 교체됐다면 충돌을 기록하고 새 세대를 유지한다.

같은 slug에서 활성과 준비가 공존할 수 있다. 준비 세대 철회는 이전 활성 세대를 유지하고, 활성 세대 철회는 다른 준비 세대를 유지한다. 완료는 예약 버전과 대상 세대가 같고 잠금 뒤에도 해당 준비 포인터 및 manifest가 일치해야 한다. 이 규칙으로 다른 세대의 철회가 슬롯 버전을 올려도 아직 유효한 준비는 완료할 수 있다. 새 준비의 CAS는 현재 슬롯 버전에 붙고, 원장은 철회에도 대상 세대를 포함한다. 같은 ID의 동일 입력은 저장된 결과를 재생하고, 동일 ID의 다른 대상은 지문 불일치로 거절한다.

러너는 두 물리 연결이 각자 같은 준비 버전·세대를 조회한 뒤 발행 역할을 복원한다. 양쪽 실행 순서에서 두 번째 연결이 `pg_blocking_pids`로 첫 연결을 실제 기다리는지 확인하고, 대기 증거에 slug·관찰 버전/세대·두 PID를 기록한다. 철회 선행이면 지연 완료 충돌, 완료 선행이면 같은 관찰값의 철회 성공을 요구한다. 두 경로 모두 최종 목록과 파일 조회를 확인한다. 별도 대조군은 경쟁 없는 준비 철회, 두 방향에서 다른 세대 보존, 교체된 파일 보호, 철회·완료 영수증 재생, 준비 후 원본 리비전·SHA·완료 상태 변경이다.

## F3 · RLS와 분리 권한

활성·준비·철회 행의 공존을 관리자 조회로 먼저 확인한다. 이어 각 함수 소유자의 허용 열 직접 SELECT를 활성 조건 없이 실행해 RLS 자체가 활성 행만 반환하는지 검사한다. 각 목록/파일 호출 역할의 반대 함수·발행 함수·기저 조회·쓰기 거부, 발행 역할의 두 공개 함수 거부와 익명 계열 역할의 거부를 검증한다. 카탈로그에서는 네 테이블의 RLS 및 FORCE RLS, 각 SECURITY DEFINER 소유자, 여섯 역할의 NOLOGIN·NOBYPASSRLS 등 속성과 membership 부재를 확인한다. 이 시험은 폐기 DB의 `SET ROLE`을 사용한다. 관리형 로그인 프로비저닝은 후속 검증 범위다.
