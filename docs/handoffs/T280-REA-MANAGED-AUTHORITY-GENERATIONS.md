# T280 REA 관리형 등록 권한 세대 설계

2026-11-19 KST · Codes(Backend) · 기준 `09dab66edd8ff515838b1b897effed80b8c2090e` · 배정 `msg_c917a26e4d94` · F1 보완 `msg_2980e9b04df6`

**추천안은 삭제되지 않는 프로젝트–자료 권한 행과 소유자별 권한 세대입니다.** 기존 링크가 사라졌다 돌아와도 같은 권한으로 인식되지 않게 합니다. 복원은 별도 신뢰 영역에서 매번 새 게시 세대를 발급해야 합니다. 해당 증거가 없는 환경에서는 T279의 현재 등록 상태 조회까지만 허용하고, 분석·확인 발급·적용 권한을 닫습니다. [서버 연계 설계](T274-REA-SERVER-APPLY-INTEGRATION.md) · [T279 독립 검수](T279-R-REA-REGISTERED-AUTHORITY-REVIEW.md)

## 기존 제어 주체와 공백

| 영역 | SQL1–5 및 호출부에서 확인한 현재 경계 |
| --- | --- |
| 링크 삭제·재연결 | SQL1의 `project_assets` 키는 소유자·프로젝트·자료·용도입니다. 같은 소유자를 요구하는 FK는 연결의 현재 정합성을 보장합니다. 삭제 후 키를 그대로 재삽입할 수 있고 SQL2의 공용 가드는 링크 세대를 남기지 않습니다. SQL3에서 `dream_api`는 소유 행의 CRUD, `dream_worker`는 교차 소유 SELECT/INSERT/UPDATE 권한을 가집니다. 저장소에서 확인된 관리형 제품 서비스는 미연결 프로젝트 생성에서 링크를 INSERT합니다. 관리형 링크 변경/철회를 통합하는 서비스는 확인되지 않았습니다. |
| 프로젝트·자료 보관과 소유자 | SQL1의 각 행에 `archived_at`이 있고 SQL2는 `owner_id` 변경을 거절합니다. 자산의 파일·해시·형식 등 식별 정보는 불변이며 보관 값은 변경 가능합니다. Auth 사용자 참조의 `ON DELETE RESTRICT`는 소유 관계 보존 규칙입니다. 로그인 세션 취소나 보관 후 복원을 기록하는 세대는 아닙니다. 실제 노출된 보관 서비스는 legacy SQLite 경로입니다. 관리형 직접 변경은 SQL3 권한으로 가능하므로 새 REA 경계가 관리형 호출부 하나만 감시해서는 부족합니다. |
| Auth와 권한 철회 | 공통 `resolveServerAuth`는 현재 요청의 `getUser`와 허용 이메일을 확인하며, DB는 제한 API 역할과 검증된 UUID를 사용합니다. Auth 제공자의 계정·세션 변경과 런타임 허용 목록 변경은 프로젝트 DB 밖에서 일어납니다. SQL1–5에는 이를 프로젝트 권한 세대로 동기화하는 경로가 없습니다. |
| 스토리지 | SQL4의 `asset_receipt_state`와 `storage_objects.active_generation`은 객체의 검증·철회·재검증을 기록합니다. `dream_api`에는 관련 테이블의 소유자 SELECT가 부여됩니다. SQL5의 제한 `dream_upload_reserver` 및 두 진입 함수는 업로드 예약 범위이며, 프로젝트 링크·권한·복원 관리 권한은 주지 않습니다. 이 기록은 스토리지 바이트의 근거이며 프로젝트 권한 세대와 별도로 대조합니다. |
| 관리형 복원 | 확인된 백업·복원 제품 경로는 SQLite와 관리 로컬 파일용입니다. SQL1–5와 관리형 서비스에서 Postgres+Storage의 복원 게시, 복원 세대 발급 또는 클러스터 변경을 검증하는 제어 주체는 확인하지 못했습니다. 관리형 게시자는 제품 계정에 부여된 권한으로 추정할 수 없습니다. |

## 최소 데이터 계약과 대안

| 안 | 권한 단절을 판별하는 방법 | 비용과 전제 |
| --- | --- | --- |
| **명시적 세대, 추천** | `(owner_id, project_id, asset_id)`에 지속되는 권한 행 하나를 두고, 활성 상태·링크 세대·범위 권한 세대를 유지합니다. 소유자별 상태 행에는 현재 계정/제품 승인과 소유자 권한 세대를 둡니다. | 현재 상태를 고정 비용으로 확인하고 취소 후 재활성화가 명확합니다. 잠금 순서와 모든 변경 경로의 원자적 세대 갱신이 필요합니다. 첫 단계에는 한 소유자의 관련 변경을 직렬화하는 비용을 수용합니다. |
| **동등한 이력** | 생성·삭제·철회·보관·복구를 같은 트랜잭션의 추가 전용 이벤트로 기록하고, 해당 스트림의 현재 순번과 링크 상태를 잠금 아래 도출합니다. | 감사에는 유리합니다. 안정적인 잠금 기준 행, 고유 순번·현재 상태 계산, 재생·압축 이후에도 연속성을 보장하는 별도 계약이 필요합니다. 기존 활동 로그에는 모든 변경을 담는 강제 규칙이 없어 그대로 재사용할 수 없습니다. |

- 권한 행은 서버가 허용한 링크 용도를 기준으로 조회하며, 링크 집합의 관련 변경마다 링크 세대를 증가시킵니다. 삭제 뒤에도 비활성 행과 마지막 세대를 보존합니다. 같은 키로 재연결하거나 같은 트랜잭션에서 삭제·재연결해도 세대를 증가시킵니다. 활성 플래그만 바꾸거나 행을 새로 만들어 카운터를 초기화하는 경로는 허용하지 않습니다. 첫 구현은 복합 FK와 함께 보관·비활성 전이만 지원합니다. 부모를 물리 삭제할 때도 키 재사용과 세대 초기화를 막는 별도 소멸 이력을 설계한 뒤 연결합니다.
- 프로젝트 또는 자산의 보관·해제, 권한 부여·철회는 해당 범위 권한 세대를 증가시킵니다. 보관 해제가 자동으로 종전 권한을 복원하지 않도록 새 활성 승인과 새 분석을 요구합니다. 소유자 권한 철회·재승인은 소유자 세대를 진행시키고, 다른 소유에게 이전하는 작업이 허용될 경우 별도 소유 ID와 검증된 새 등록을 사용합니다. 해당 경로를 제공하기 전에는 소유자 변경을 거절합니다. SQL4의 스토리지 철회는 바로 실행을 닫고, 재검증 시에도 이전 분석의 스토리지 증명과 활성 검증은 일치하지 않아야 합니다.
- T275에 전달할 권한 세대는 소유자·범위 세대의 버전 있는 합성값으로 구성합니다. 서버는 키와 카운터를 고정 순서로 인코딩합니다. 링크·권한 세대, 원본 리비전과 등록 SHA-256/사본 해시, 스토리지 객체 아이덴티티·검증 세대, 분석 ID·리비전, 외부 복원 세대를 각각 저장 및 대조합니다. 저장소 검증 재발급으로 링크·Auth 권한을 연장하지 않습니다. 현재 값이 없거나 출처가 검증되지 않으면 새 분석 게시와 대기 확인 실행을 거절합니다.
- 기존 링크에 대해서는 승인된 제한 역할로 동일 소유·활성 프로젝트/자료·지원 용도와 검증 기록을 대조한 뒤 최초 기준 세대를 부여합니다. 초기 등록은 통제된 변경 경로가 활성화되고 쓰기 잠금으로 경합을 차단한 뒤 수행합니다. 이력 없는 과거 확인을 새 행으로 이관하지 않습니다. 불일치 행은 미등록 상태로 두고 운영자가 별도로 해결합니다. 현재 등록 상태의 읽기와 일반 프로젝트 읽기는 기존 계약을 유지합니다.

## 최초 승인과 권한 상태 전이

최초 도입의 허용 용도는 서버 정책 버전에 고정한 `rea-reference` 하나로 제안합니다. 기존 메뉴 입력 용도는 그 자체로 분석 승인에 해당하지 않습니다. 승인된 운영자가 변경 심사를 거쳐 허용 목록을 새 버전으로 게시하고, 영향을 받는 범위 세대를 같은 쓰기 경계에서 진행시켜야 합니다. 기존 T279 조회는 등록 상태 관측을 계속할 수 있습니다. 최초 REA 승인은 검증된 소유자의 요청과 별도로 권한을 부여받은 운영자의 승인 기록을 요구합니다. 투입할 운영자 역할과 신뢰 주체는 아직 배정되지 않았습니다.

권한 행은 `미등록`, `대기/비활성`, `활성`으로 판단합니다. 세대는 범위 안에서 재사용하지 않는 양의 단조 카운터입니다. 초기 기준값과 이후 값은 제한 함수에서만 발급하며, 최대값에 닿으면 범위를 닫습니다. 링크 INSERT나 보관 해제만으로 활성화하지 않습니다.

| 입력 또는 전이 | 같은 트랜잭션의 규칙과 결과 |
| --- | --- |
| 미등록 링크·첫 승인 | 링크와 동일 소유·활성 프로젝트/자료를 확인합니다. 소유자 기준 행이 없으면 고유 소유자 키에 `INSERT … ON CONFLICT DO NOTHING` 후 별도 문장으로 기준 행을 잠그고 재조회합니다. 두 번째 연결은 승자가 만든 상태를 이어서 검사합니다. 운영자 승인과 허용 용도·스토리지 검증이 모두 유효한 첫 요청만 활성화합니다. 신규 링크 생성이 함께 필요하면 같은 직렬화 경계에서 수행하며, 일반 링크 INSERT의 결과는 대기입니다. |
| 여러 용도 중 일부 삭제·용도 변경 | 허용 여부나 허용 링크 집합이 바뀌면 링크 세대를 진행시키고 대기로 돌립니다. 다른 허용 링크가 남아도 먼저 승인했던 선택의 연속성을 가정하지 않습니다. 허용 목록 밖에서만 바뀌고 허용 집합에 영향이 없는 변경은 REA 세대를 유지합니다. 허용 안→안, 안→밖, 밖→안 변경은 모두 새 승인·분석이 필요합니다. |
| 프로젝트·자료·용도 이동 | `project_assets` 키의 직접 UPDATE를 차단합니다. 지정된 이동 함수가 이전·새 범위를 정렬해 잠그고 삭제 및 삽입의 두 전이를 같은 트랜잭션에 기록합니다. 양쪽의 영향받은 세대를 진행시키고 활성 인증을 재사용하지 않습니다. |
| 링크 탈거·재연결 | 마지막 허용 링크를 빼면 비활성으로 전환하고 행과 세대를 보존합니다. 같은 ID·바이트로 붙이거나 한 트랜잭션에서 삭제·재삽입해도 링크 세대가 감소하거나 초기화되지 않습니다. 재연결 후 대기와 새 승인·분석을 거칩니다. |
| 프로젝트/자료 보관 및 해제 | 보관 또는 해제에서 범위 권한 세대를 진행시킵니다. 프로젝트 보관은 그 프로젝트, 자산 보관은 같은 소유 아래 연결된 모든 프로젝트를 같은 잠금 경계에서 변경합니다. 해제는 대기 상태이며 명시 재승인이 필요합니다. 첫 단계는 물리 삭제를 닫고 비활성 행을 보유합니다. |
| 권한 철회·재승인 | 범위 철회는 해당 권한 세대, 계정·세션 철회는 아래의 소유자 세대를 진행시킵니다. 승인 시 새 세대로 대기를 해제합니다. 이전 분석·확인·종결 영수증이 사용자 경로에서 되살아나지 않습니다. |

**초기 등록 순서.** 새 실행을 닫고 구 관리형 쓰기와 워커를 멈춘 뒤 기존 접속·작업을 정리합니다. 이관에서 세대의 기본 부재를 거절로 정하고, 현재 동일 소유·활성 링크에 비활성 기준 행만 작성합니다. 승인 이력과 근거가 없는 경우는 미등록/대기 상태입니다. 잠금·역할·트리거를 통한 새 변경 경로를 활성화한 뒤 최초 명시 승인을 받습니다. 이력 없는 분석이나 확인은 소급 귀속시키지 않습니다. 혼용 또는 이관 중 실패에는 쓰기 입장을 다시 열지 않습니다. | 현재 주체와 위험 | 이관 이후 쓰기 허용 범위 | 잠금 및 다시 읽는 조건 |
| --- | --- | --- |
| SQL3 `dream_api` 및 `dream_worker` | `project_assets`의 직접 INSERT/UPDATE/DELETE를 회수합니다. `projects`의 `archived_at`, `current_timeline_rev_id`, 소유/키, `assets`의 `archived_at`, 소유/키/파일 식별 필드의 직접 UPDATE를 닫고 두 부모의 DELETE를 닫습니다. 테이블 수준 UPDATE를 제거한 뒤 기존 비권한 업무에 필요한 열만 재부여합니다. 프로젝트 생성·링크·보관·타임라인 저장/복원은 제한 진입점으로 이관합니다. 부모 INSERT가 남는 경우에도 최초 등록과 권한을 우회할 수 없어야 합니다. 타임라인 행 INSERT와 포인터 변경은 정식 업무 진입점에서만 수행하고 기존 이력 UPDATE/DELETE 금지는 유지합니다. 워커에 교차 소유 REA 직접 권한을 부여하지 않습니다. | 현재 관리형 생성의 자산 `FOR SHARE` 선행 잠금을 이관합니다. 새 경로는 **소유자 기준 행 `FOR UPDATE` → 프로젝트 → 자산 → 링크/권한 → 스토리지 → 분석 → 확인 → 타임라인/워크플로** 순서입니다. 관련 행 잠금은 변경에 필요한 범위로 제한하며 같은 종류의 다중 행은 키 순서입니다. 대량 쓰기는 소유자부터 정렬하고 기존 트랜잭션을 구 순서에서 시작한 채 새 함수로 이어가지 않습니다. |
| SQL4 스토리지 상태 전이 | 현재 SQL4의 `dream_api`는 소유자 SELECT이며 실제 전이 쓰기 주체의 배치는 확인되지 않았습니다. 전이 실행이 승인되면 등록/재검증/철회 경로가 소유자 잠금에 참여하도록 먼저 이관합니다. REA 조회나 검증을 위해 일반 API에 스토리지 UPDATE를 추가하지 않습니다. 지정한 NOLOGIN 역할의 잠금 함수가 소유자·객체·검증 상태만 대상으로 합니다. 행 잠금에 필요한 열 권한을 좁게 부여하고 직접 UPDATE 실행 권한은 호출자에게 주지 않습니다. | 등록 자료 및 참조 증명을 바꿀 수 있는 전이는 공통 순서를 사용합니다. REA 최종 쓰기는 같은 연결에서 객체와 현재 검증 상태를 그 순서로 잠근 뒤 재조회합니다. 영수증이 만료됐거나 철회됐으면 쓰지 않습니다. 문제를 모르는 관리자 수정·수동 객체 교체가 허용되는 환경은 닫습니다. |
| SQL5 `dream_upload_reserver` 두 진입 함수 | 현재 예약/재전송 범위만 유지합니다. REA 관련 테이블·타임라인의 잠금 함수나 변경 함수는 부여하지 않습니다. 상위 서비스는 SQL5를 호출한 트랜잭션에서 REA나 SQL4의 새 소유자 제어 함수를 이어 호출하지 않습니다. | 기존 정책 `FOR SHARE` → 예약 재조회 객체 `FOR UPDATE` 순서를 유지합니다. 순환을 막기 위해 REA/SQL4 제어 구간은 SQL5 정책 행에 대한 잠금을 요청하지 않고 SQL5는 객체 잠금 이후 소유자·프로젝트·REA 행을 요청하지 않습니다. 새 FK/트리거까지 포함해 역방향이 없음을 두 연결에서 입증하기 전에는 연계를 닫습니다. |
| 제한 REA 및 운영 제어 함수 | `dream_api`가 승인된 SELECT 및 명시 함수 실행만 하도록 설계합니다. 제어 함수 소유는 최소 권한의 NOLOGIN 역할, 고정 `search_path`, `row_security=on` 및 명시적 소유 검증을 사용합니다. 기본 PUBLIC 실행, 브라우저 역할, 일반 워커·예약 역할의 직접 변경과 제공자 광역 역할 사용을 차단합니다. 실제 관리형 적용 롤은 후속 승인이 필요합니다. | 진입 전 신뢰 게시 상태를 확인합니다. 쓰기함수는 `READ COMMITTED`로 잠금 후 새 문장에서 현재 세대·스토리지·권한·링크·CAS를 재조회합니다. `clock_timestamp()`를 잠금과 재조회 뒤에 읽어 실행 만료를 판정하고, 종결 시각도 따로 읽습니다. T279의 `READ ONLY REPEATABLE READ` 결과는 쓰기 승인에 쓰지 않습니다. |

잠금 대기 초과와 직렬화 실패는 롤백 후 구분 가능한 오류를 반환합니다. 소비 여부가 불명확한 응답은 동일 권위 저장소에서 영수증을 재조회합니다. 확정 CAS 충돌은 새 미리보기·확인으로 돌아갑니다. 트랜잭션 중간 실패를 재시도 가능한 커밋으로 간주하지 않습니다. 장시간 복사·분석은 쓰기 잠금 밖에서 수행하고, 분석 게시와 적용 직전 각각 현재 권한, 연결, 실제 사본 해시, 스토리지 객체 ID/검증 세대와 대상 타임라인을 대조합니다. 확인은 타임라인 CAS 및 결과 기록과 함께 소비합니다. 스토리지 증명은 실행 입력으로 따로 검증하며 기존 T275 엄격 스키마를 바꿔야 한다면 별도 계약 승인을 받습니다.

## 계정·세션 철회와 종결 영수증

| 변경 주체 | 차단 시점과 재개 |
| --- | --- |
| 계정 차단 또는 허용 목록 제거 | 승인된 운영자가 외부 Auth나 런타임 목록을 바꾸기 전에 DB 소유자 기준 행을 잠가 비활성으로 전환하고 소유자 권한 세대를 증가시켜 커밋합니다. DB 차단이 먼저 커밋되면 진행 중 요청은 최종 재검증에서 거절됩니다. 적용이 먼저 끝난 경우에는 이력을 보존하며 사용자 접근은 차단 이후 닫힙니다. 외부 변경이나 복구에 실패해도 DB는 닫힌 상태로 유지합니다. |
| 개별 세션 철회 | 첫 단계는 해당 소유자의 REA 권한을 통째로 차단하고 세대를 진행시키는 보수적 경계입니다. 그 뒤 제공자가 해당 세션을 철회합니다. 현 `getUser`의 UUID만으로는 기존 세션을 구별할 수 없습니다. 재승인은 철회 세션이 재입장할 수 없다는 서버 확인 뒤 새 소유자 세대로만 개방합니다. 검증된 세션 식별과 철회 확인을 못 얻으면 해당 소유자의 REA를 닫은 상태로 둡니다. 장래 세션 단위 운영은 검증된 세션 ID 및 세션 세대 결합이 선행합니다. |
| 운영자 경로 밖에서 발생한 철회 | 제공자/관리자 변경이 DB 차단과 직렬화되지 않는 환경에서는 분석 게시·확인 발급·소비·사용자 영수증을 활성화하지 않습니다. 비동기 이벤트나 유효 토큰 만료를 쓰기 권한의 증거로 사용하지 않습니다. |

**Master 기본안.** 완료 영수증은 사용자 `read_receipt`와 이미 완료된 `confirm` 재전송 양쪽에서 같은 정책을 씁니다. 현재 조회권·보존 기간에 더해 종결 시 묶은 링크·범위 권한·소유자 권한·복원 세대가 현재 값과 정확히 일치해야 합니다. 재연결·재승인으로 새 세대를 받아도 이전 영수증은 사용자에게 계속 닫힙니다. 영수증에는 위 세대를 서버 내부 판정용으로 보존하고, 사용자 응답에는 결과 유형·타임라인 ID·리비전·시각만 제공합니다. 타임라인이 후속 수정됐다는 이유로 현재 세대의 유효 영수증을 막지는 않습니다. 해시·스토리지 활성 증명·현재 분석·실행 만료·CAS는 대기 실행에만 사용합니다. 과거 종결 행의 내부 보존과 제한된 감사는 기존 정책을 따릅니다. 현재 T275에 종결 세대 검사가 없으므로 기존 코드를 그대로 관리형에 연결할 수 없습니다. ## 복원 게시 상태

게시 제어면은 DB 백업·PITR·클론으로 복사되지 않는 곳에서 승인된 DB·스토리지 대상의 검증 가능한 식별자와 재사용하지 않는 게시 세대를 관리합니다. 런타임은 서명 검증과 최신 상태 확인을 함께 수행합니다. 이름·DSN·DB 내부 카운터·예전 유효 서명만으로 동일 대상 또는 최신 게시를 판단하지 않습니다.

| 게시 상태 | 집행자와 완료 조건 | 요청 동작 |
| --- | --- | --- |
| **차단** | 승인된 복원 운영자가 제어면의 현재 상태/세대를 기대값으로 비교해 입장을 차단합니다. 배포/DB 운영자는 구 런타임 경로 및 제한 접속을 해제하고 구 풀·진행 트랜잭션·예약 작업이 종료됐음을 확인합니다. 워커도 이전 세대로 일을 받을 수 없어야 합니다. | 분석·준비·적용과 영수증 조회·재전송 차단. 외부 증거 미확인도 같은 상태로 취급. |
| **준비** | 복원 운영자가 격리 대상과 스토리지 일관성을 검증하고 새 세대를 발급합니다. 복원본 DB에서 대기 확인·진행 분석을 무효화하며 새 게시 세대와 대상 식별을 기록합니다. 영수증은 내부 보존 범위에서만 남깁니다. DB와 제어면은 별도 커밋을 사용합니다. | 두 시스템 값이 일치하더라도 준비 중에는 닫힘. 기록 중단이나 응답 유실 후 권위 있는 두 상태를 다시 대조합니다. |
| **승인** | 지정된 게시자가 기존 차단/준비 상태와 예정 세대를 기대 조건으로 비교하여 승인 상태를 한 번만 갱신합니다. 확인된 DB/스토리지 쌍과 새 제한 런타임만 연결합니다. 이전 주소가 남아도 새 입장을 얻을 수 없어야 합니다. | 새 런타임이 현재 제어면·대상·DB 세대와 맞을 때만 요청을 처리합니다. 영수증 읽기와 완료 재전송도 실행과 동일한 게시 검사를 통과해야 합니다. |

활성 작업의 최종 쓰기 직전 게시 일치를 재검증하고, 전환에서는 접속 차단과 배출이 끝날 때까지 준비/승인하지 않습니다. 두 곳의 불일치, 오래된 서명이나 풀, 스토리지 매핑 실패, 동시 게시의 패자, 구 요청 배출 증명 실패는 모두 닫힌 상태입니다. 원래 DB로 되돌릴 경우에도 새 세대를 발급합니다. 무통지 PITR이나 복제, 구 경로의 권한 우회가 통제되지 않으면 그 대상에서는 기능을 활성화하지 않습니다. ## 후속 PG17 시험표

별도 승인 후 루프백 전용 PG17에서 합성 소유자 A/B, 애플리케이션 제한 로그인, 시험 준비용 이관 역할을 구분합니다. 관리형 검증은 보호된 시험 매핑과 TLS를 별도로 확인한 뒤 진행합니다.

| 시험 | A/B 합격 근거 |
| --- | --- |
| SQL1–5 / 후보 이관 / 역할·RLS | A의 허용된 함수만 같은 소유 행을 바꿉니다. B·PUBLIC·브라우저·worker·예약 역할의 직접 링크 변경, 보관 열·타임라인 포인터 UPDATE 및 이력 INSERT는 거절됩니다. 강제 RLS, 함수 공개 실행, 멤버십과 풀 재사용의 액터 초기화를 실제 카탈로그·세션에서 대조합니다. |
| 이관·동시 최초 승인 | 세대 없는 링크와 초기 비활성 행은 실행 불가. A의 두 연결이 같은 소유자 기준 행을 처음 만들 때 한 개 행과 유효한 승인만 남습니다. 구 업무 연결과 새 변경 경로가 동시에 쓰지 못합니다. B는 A의 초기 승인이나 범위에 접근할 수 없습니다. |
| 링크 이동·용도·재연결 | 키 직접 UPDATE 차단, 함수 이동 시 이전/새 범위 동반 진행. 다른 허용 링크가 남은 삭제, 허용 안↔밖 용도 변경, 같은 트랜잭션 재삽입 후에도 이전 분석·확인·영수증은 사용자 경로에서 무효입니다. B의 상태는 유지됩니다. |
| 프로젝트/자료 보관·해제 및 계정/세션 철회 | 모든 관련 범위와 소유자 세대를 기록합니다. 같은 자산을 연결한 A의 복수 프로젝트와 B의 무관한 프로젝트를 비교합니다. DB 차단 우선이면 진행 요청 저장/영수증 0건이고, 적용 우선이면 타임라인/영수증 각각 한 행만 남습니다. 재승인 뒤에도 A의 이전 권한 세대 영수증을 조회·확인 재전송 양쪽에서 거절합니다. 외부 철회 실패 및 철회 세션의 재입장은 계속 차단합니다. |
| SQL4 전이 및 SQL5 예약 경합 | 같은 객체의 SQL4 철회/재검증과 A의 최종 쓰기를 두 연결에서 경합시킵니다. 만료 직후·스토리지 증명 교체에서 이전 확인 적용 0건. SQL5 정책→예약 객체 잠금 경로와 REA의 공통 잠금 경로가 교착 없이 분리되고, 권한 없는 B의 객체 기록은 읽거나 잠그지 못합니다. |
| 타임라인 CAS와 실패·유실 복구 | 중간 실패에서 분석·확인·타임라인·활동 로그·영수증이 모두 롤백됩니다. 확인된 잠금/직렬화 실패와 CAS 충돌, 커밋 응답 유실을 구분합니다. 현재 세대 내 동일 확인은 새 타임라인 변경 뒤에도 기존 영수증만 반환합니다. |
| 복원과 게시 격리 | A/B로 같은 DSN 복원·복제본과 잘못된 스토리지, 유효하지만 오래된 서명, 구 풀·예약 작업을 대조합니다. 차단/준비 사이 장애, 준비/승인 사이 장애 및 동시 게시에서 승인 승자는 하나이고 불일치·구 요청은 읽기/쓰기 모두 0건입니다. 원 DB로 복귀한 경우에도 새 외부 세대에서만 실행합니다. |

## 외부 연결과 승인 대기

| 결정 | 현재 근거와 결정 책임 |
| --- | --- |
| 실제 Auth 계정·세션 및 허용 목록 철회 | 기존 Auth는 서버 UUID를 제공하지만 DB와 직렬화하는 계정/세션 운영 경로는 확인되지 않았습니다. Master·Auth/운영 담당이 철회 집행자와 세션 확인 수단, 재승인 흐름을 확정해야 합니다. |
| 제한 쓰기 역할과 구 경로 전환 | SQL1–5의 현재 ACL과 역할은 읽어 확인했습니다. 소유자 세대 도입의 정확한 열 권한 변경, 대량 쓰기 호환, SQL4 전이 주체와 잠금 함수 부여는 DB 담당·Master의 검토 및 승인이 필요합니다. |
| 관리형 복원 게시와 비용 | DB 밖 제어면, 대상 확인 방식, 구 워커·접속 회수와 현재성 확인 수단을 아직 선정하지 않았습니다. 운영자와 Master가 승인된 격리 환경 및 담당을 확정하고 외부 자원·비용·운영 변경은 사용자 승인 범위에서 결정합니다. |
| 보호 PG17/관리형 시험 연결 | 로컬 합성 PG17 시험 이후 보호된 별도 관리형 대상, 배포·계정·권한 및 TLS 매핑을 별도로 검증합니다. 현재의 운영 실측이나 설정 변경을 의미하지 않습니다. |

T280 및 F1은 고정 저장소의 정적 대조와 설계 문서입니다. PG17 시험은 예정이며 환경·운영, 코드나 SQL을 변경하지 않았습니다. T279-R의 실제 로컬 PG17은 기존 현재 등록 조회의 근거이며 이 새 권한·복원 계약의 시험 결과는 아닙니다.

Master 전달문 · T280 완료. 지속 링크/범위 세대와 소유자 권한 세대를 권고하고, DB 복사 밖의 복원 게시 세대·제한 역할·같은 트랜잭션 잠금 및 두 액터 PG17 시험을 명시했습니다. 해당 근거가 없는 관리형 경로의 실제 분석·적용은 닫습니다.
