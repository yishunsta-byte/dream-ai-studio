**판정 — 수정 후 재검수.** 완료 영수증 조회와 재전송의 네 세대 검사, 동일 세대 응답 유실 복구, 보존 경계와 공개 DTO는 통과했습니다. 세대를 입증하지 못한 구 대기 확인은 현 코드에서 만료·오래된 분석·CAS 충돌 분기를 만나면 확인 행을 변경합니다. [T282 인계](T282-REA-RECEIPT-AUTHORITY-GENERATIONS.md)

## 필수 수정 F282-1 — 세대 증명 전에 대기 확인 종결

격리 SQLite에 구 `permissionGeneration`을 가진 v1 대기 행을 넣고, 구 방식으로 일치하는 실행 권한을 공급하되 `receiptGenerations`를 생략했습니다. 실행 조건이 모두 정상일 때는 `unavailable`과 전체 무변경을 확인했습니다. 같은 조건에서 다음 한 가지를 바꾸면 `apply(..., true)`가 확인 행을 종결했습니다.

| 변경 | 관측 |
| --- | --- |
| 실행 만료 시각 도달 | `expired`를 반환했습니다. |
| 분석 ID 교체 | `stale`을 반환했습니다. |
| 대기 기준의 콘텐츠 리비전과 현재 CAS 불일치 | `conflict`를 반환했습니다. |

각 경우 `rea_synthetic_apply`의 해당 행만 바뀌었고 `state_json`, `plan_json`은 `NULL`이 됐습니다. 타임라인·워크플로·활동 로그는 유지됐고 영수증도 생기지 않았습니다. 새 합성 권한 형식의 대기 행에 잘못된 소유자 권한 세대를 공급한 경우에도 만료 분기에서 같은 쓰기를 재현했습니다.

`apply`는 `expired`·`stale`·`conflict`를 `retire`로 먼저 처리하고 나서 세대 증명을 대조합니다. 완료 영수증의 공통 분기를 유지하면서 대기 행의 세대 증명을 모든 종결 쓰기 전에 검사해야 합니다. 증명이 없거나 맞지 않으면 `unavailable`과 전체 DB 무변경을 유지하고, 현재 세대가 입증된 만료·충돌·오래된 분석의 종결은 기존대로 보존하는 회귀가 필요합니다. ## 독립 통과 항목

| 범위 | 검증 결과 |
| --- | --- |
| 동일 세대 유실 복구 | 한 Node 프로세스가 저장 응답을 버리고 종료했습니다. 별도 프로세스가 실행 만료 뒤 원래 v2 영수증을 조회했고, 재전송도 같은 영수증을 반환했습니다. 적용은 한 번만 저장됐습니다. 후속 타임라인 수정 뒤에도 같은 세대의 이전 영수증이 유지됐습니다. |
| 네 세대, 조회권 및 이전 종결 | 링크·범위·소유자·복원 세대를 각각 바꾸고, 세대 누락·잘못된 값·현재 조회권 미확인·거절·새 세대로 재승인·v1 종결을 독립 대조했습니다. `readReceipt`와 완료 `apply(..., true)`가 모두 `unavailable`을 반환했고, 각 요청 전후 전체 논리 스냅샷이 같았습니다. |
| 보존 경계와 DTO | 완료 시각과 보존 기한 직전에는 열렸고 완료 직전·보존 기한부터 닫혔습니다. 영수증 응답은 결과 유형·타임라인 ID·타임라인/콘텐츠 리비전·완료 시각만 포함했습니다. 세대는 v2 내부 행에만 저장됐습니다. `no_change`도 같은 계약을 따르며 추가 타임라인·활동 기록을 만들지 않았습니다. |
