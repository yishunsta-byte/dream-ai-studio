## 단계 3에서 교차 확인할 요청

| 요청 유형 | 합격 기준과 수집 근거 |
| --- | --- |
| 보호 페이지 및 서버 렌더 | `/cloud/reference-analysis`의 초기 HTML, 인라인 Flight, RSC, 라우터·세그먼트 프리페치에 자료 목록, 소유자/프로젝트/자료 식별자와 보호 본문이 없고 송신 허가 소비는 0이다. 익명·비허용·무효·만료 세션도 같은 기준으로 기록한다. |
| 승인된 별도 송신 | A/B 각자 승인된 자기 등록 자료에서만 승인된 앱 오리진과 올바른 세션 교환으로 본문 한 번을 받는다. 반대 계정, 이전 키·세션·소유 번호, 잘못된 Origin·CORS·CSRF 및 교차 계정 프리페치는 보호 본문·허가 소비 0이다. |
| 기존 앱 POST 및 우회 | 기존 `POST /api/studio/reference-analysis`, 별도 오리진 직접 주소, 이전 허가 재사용과 경계 밖 캐시 요청에서 단계 3 보호 응답과 허가 소비는 0이다. 계정 전환·로그아웃·뒤로 가기와 bfcache/공유 캐시에서도 이전 사용자 자료를 다시 꺼낼 수 없어야 한다. |
| 증거와 중단 | 같은 합성 요청 ID로 실제 Preview 빌드, 오리진 및 클라이언트의 상태·바이트 수, DB/송신 원장의 허가·의도·종결 건수를 맞춘다. 운영 대상에 매핑되거나 하위 홉의 차단·큐 상태를 확인할 수 없으면 실행 상태를 보류한다. 인계는 식별자·해시·계측량에 한정한다. |

이번 대조는 추적 문서와 Git·Orca의 배정 기록만 사용했다. 새 연결·계정·비용·배포·작업 폴더·제품 및 운영 변경은 없었다.

**Master 인계** · T321 단계 3 검수 입력과 담당을 정리했다. 단계 1의 격리 근거, 보호 셸과 로컬 MP4 검증은 재사용한다. 실제 두 호스트 종료·격리와 별도 보호 Preview/오리진 및 합성 환경 식별은 승인·확인 대기다. 다음 후보는 이미 완료된 PCM 검증 이후 운영 발급·승인·복원 역할의 최신 공백을 기존 음악 공급원 인계 한 문서에 대조하는 작업이다.
