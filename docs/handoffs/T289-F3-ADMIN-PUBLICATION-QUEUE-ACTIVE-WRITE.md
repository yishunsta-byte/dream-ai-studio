**A. 쓰기 잠금을 목록 줄과 분리**
- 진행 중 쓰기 잠금을 줄 상태(`Row.busy`)에서 뺐어요.
- 대신 동기 판정용 `inflight` 맵(slug → 공급자 세대)과 그리기용 `writes` 상태가 잠금을 가져요.
- 상단 잠금(`anyBusy`)은 `writes`로 계산하고, `reload()`는 맵을 동기로 한 번 더 확인해요.
- `initial`만 바뀌어 줄이 목록에서 빠져도 응답이 올 때까지 잠금이 유지돼요.
- 실제 공급자 교체(`gate.restart`가 `true`를 돌려줌) 때만 맵과 상태를 비워요.

**B. 늦은 결과는 최신 권위 목록과 대조**
- 쓰기 응답이 오면, 같은 커밋에서 기록한 최신 화면(`viewRef`)과 `retryDecision`으로 대조해요.

| 판정 | 조건 | 처리 |
|---|---|---|
| keep | 같은 줄·같은 버전이거나, 최신 화면이 실패·미연결이라 권위가 없음 | 기존 처리(재시도 표시 등) |
| notice | 같은 줄이 다른 버전(v5) | 재시도·결과 반영 없이 안내만: “이전 요청의 결과를 확인하지 못했어요. 그사이 새 목록을 받았으니 지금 목록 기준으로 판단해 주세요.” |
| drop | 줄이 삭제됨 | 아무것도 되살리지 않아요 |

**C. 중복 전송 방지**
- `send`는 같은 줄이 맵에 있으면 바로 끝내요. 그래서 같은 이벤트 안의 두 번째 클릭도 전송되지 않아요.
- 같은 요청 재시도 버튼은 진행 중일 때 `disabled={loading || !!busy}`로 꺼져요.

F2의 실패 → 같은 버전 복구, `view`·`provider` 세대, 공급자 교체, 조회·쓰기 상호 잠금, 상단 44px는 그대로예요.

**브라우저 확인** (ego 공간, 격리 서버 127.0.0.1:43292). 사본 전용 확인 화면에서 실제 `PublicationQueue`에 메모리 공급자를 넣고, 쓰기 보류·커밋 전 실패, `initial`만 교체, 조회 실패, 공급자 교체를 조작했어요. 조회·쓰기 호출 수도 셌어요. 1280과 390에서 같은 결과가 나왔어요.

- **A. 줄 삭제 중 잠금 유지:** v0 준비 쓰기를 보류한 채 `initial`을 빈 목록으로 바꿨어요.
  - 상단 새로고침은 꺼져 있었고(44px), 눌리지 않았어요. 응답 전 조회 호출은 0회(0 → 0), 쓰기는 1회 그대로였어요.
  - 쓰기를 풀자 잠금이 풀렸고, 빈 목록이 유지됐어요. 늦은 응답 안내는 없었어요.
- **B. v5 교체 뒤 늦은 실패:** 커밋 전 실패할 v0 준비를 보류한 채 `initial`만 v5로 바꿨어요.
  - v5 줄은 `게시 준비 요청 중`으로 잠겨 있었어요.
  - 실패를 풀자 v5가 유지됐고, 버튼 0개에 “이전 요청의 결과를 확인하지 못했어요…” 안내만 나왔어요. 쓰기는 1회뿐이었어요.
- **B. 삭제 뒤 늦은 실패:** 빈 목록으로 바꾼 뒤 실패를 풀어도 빈 목록이 유지됐어요. 아무것도 되살아나지 않았어요.
- **B. 대조(같은 v0 줄로 교체):** 늦은 실패 뒤 `같은 게시 준비 요청 다시 시도`가 나왔어요.
- **C. 중복 클릭:** 재시도 쓰기를 보류한 채 재시도 버튼을 같은 이벤트에서 두 번 눌렀어요.
  - 추가 전송은 1건이고 원래 요청과 UUID가 같았어요(1280 `98b175` ×2, 390 `ddd26c` ×2).
  - 진행 중에는 재시도·줄 새로고침이 꺼졌고, 풀자 v1 `게시 준비됨`이 됐어요.
- **기존 동작:**
  - 커밋 전 게시 실패 → 목록 실패 → v1 복구 → 같은 UUID 재시도로 v2가 됐어요(UUID 같음 ×2).
  - 철회 쓰기 중 공급자를 교체하면 교체 화면 v0이 유지되고 상단 버튼이 켜졌어요. 이전 쓰기 응답을 풀어도 변화가 없었어요.
