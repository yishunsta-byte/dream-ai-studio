| 항목 | 현재 |

| 공개 DTO | `published-works.ts`는 `artifact.media`(`{kind, src}`)를 받을 수 있어요. 허용 확장자는 `MEDIA_EXT`(video `mp4·webm`, audio `mp3·m4a·ogg·wav`), 허용 접두는 `/media/public/`이에요. 하지만 공급원이 media를 주지 않아서 항상 `null`이에요 |

## 1. 원칙

1. 표지 계약(T-254)을 그대로 이어요:
   - 정규 주소 하나
   - 요청마다 활성 세대와 권리 재확인
   - 철회·권리 만료·과거 세대는 다음 요청부터 404
   - 운영 공급원이 비활성이면 404
   - 응답에 저장 키·서명 주소·자격 정보를 싣지 않음
2. **철회가 바로 먹혀야 해요.** 한 번의 응답이 보내는 양에 상한을 둬서, 재생 중인 사람도 다음 구간 요청에서 끊기게 해요.
3. 공개 HTML·DTO에는 재생 주소(`src`)와 종류만 실어요. 해시·크기·저장 위치는 서버 안에만 둬요.
4. 플레이어는 상태 코드를 화면에 보여 주지 않아요. 실패는 모두 같은 문구와 '다시 불러오기'로 처리해요.

## 2. 재생 DTO

### 2-1. 게시 manifest 추가 필드(Backend, `apply_command` 허용 키 확장)

| 키 | 형식 | 규칙(제안) |
|---|---|---|
| `mediaKind` | `"video" \| "audio"` | 없으면 재생 없음(지금과 같음). 아래 키는 함께 있거나 함께 없어야 해요 |
| `mediaMime` | 문자열 | video: `video/mp4`(H.264+AAC) 또는 `video/webm`(VP9/AV1+Opus). audio: `audio/mpeg` 또는 `audio/mp4` |
| `mediaExt` | 문자열 | mime과 1:1: `mp4`·`webm`·`mp3`·`m4a` |
| `mediaSha` | 64자 소문자 hex | 게시 시점에 원본 전체로 계산해요 |
| `mediaBytes` | 정수 | 1 이상. 상한은 결정 사항 D1(video 500 MiB, audio 50 MiB 제안) |

- 객체 키는 표지와 같은 불변 규칙이에요: `<slug>/<generation>/<mediaSha>.<mediaExt>`. 키가 해시에 묶여 있어 덮어쓰기가 불가능해요.
- 게시 단계(Backend)에서 확인할 것:
  - 컨테이너와 코덱이 위 허용 목록에 맞는지
  - 길이·해시가 맞는지
  - 영상이면 `moov`가 앞쪽에 있는지(faststart) — 없으면 Range 재생이 느려요
  - 확인에 실패하면 게시를 거절해요.

### 2-2. 공개 목록 행(`list_approved`)

- 행에 `media`를 추가해요: `{ "kind": "video", "ext": "mp4" }` 또는 `null`.
- `media`는 frozen manifest의 값과 같아야 해요. 표지처럼 `active_display`·manifest 일치 조건에 묶어요.
- 해시·크기·키는 목록에 싣지 않아요. 파일 경로에서만 서버 내부로 조회해요.

### 2-3. 공개 화면 DTO(Front, `published-works.ts`)

```ts
media: { kind: "video" | "audio"; src: `/media/public/${slug}/${generation}/play.${ext}` } | null
```

- `src`는 목록 행의 slug·generation·ext로 Front가 만들어요. 외부 주소는 받지 않아요.
- `MEDIA_EXT`를 `video: mp4|webm`, `audio: mp3|m4a`로 좁혀요(`ogg·wav` 제거). 목록과 다른 조합은 `invalid_media`로 그 행만 거절해요.
- 예시 작품(`sample: true`)은 계속 `media: null`이에요.

## 3. 파일 경로: GET / HEAD / Range

### 3-1. 주소와 메서드

| 항목 | 계약 |
|---|---|
| 정규 주소 | `/media/public/<slug>/<generation>/play.<ext>`. 쿼리가 있으면 404. slug·generation 형식은 `cover-path`와 같아요 |
| 메서드 | GET·HEAD만 받아요. 그 밖은 405 + `Allow: GET, HEAD`이고, proxy가 인증 전에 처리해요(표지와 같음) |
| 공급원 비활성(지금 운영) | 정규 주소도 404 |
| 공급원 활성, 정확히 일치하는 활성 세대 + 유효 권리 + ext 일치 | 200 또는 206 |
| 미등록·준비 중·철회·권리 만료·과거 세대·ext 불일치 | 404 |
| 설정 누락·조회 실패·저장소 실패·첫 바이트 시간 초과·메타데이터 불일치 | 503 |

### 3-2. Range(단일 구간만)

| 요청 | 응답 |
|---|---|
> **T370-B 반영(Backend 검토 `msg_e686c7482382`, Master 수용 `msg_79dcc295cfed`)**
> 처음 제안한 '무범위 GET도 상한 C까지만 보내기(206 대체)'는 철회했어요.
> 근거: RFC 9110 14.2. 200은 전체 표현이어야 하고, 정상 종료처럼 중간에 끊으면 안 돼요.

| 요청 | 응답 |
|---|---|
| `Range` 없음 | **200 전체 스트림**이에요. `Content-Length`는 전체 크기예요. 전송 중에 철회되면 4절처럼 스트림을 오류로 중단해요(정상 종료처럼 끝내지 않아요) |
| `bytes=a-b`, `bytes=a-`, `bytes=-n` (유효·충족 가능) | **206**이에요. `Content-Range: bytes a-b'/size`와 `Content-Length`에 **실제 보내는 구간과 길이**를 적어요 |
| 충족 불가(시작이 크기 이상 등)·형식 오류 | **416**이에요. `Content-Range: bytes */size`는 **권리·활성 세대 확인을 통과한 뒤에만** 실어요. 확인 실패면 404라서 크기가 드러나지 않아요 |
| 여러 구간(`,` 포함) | 416(위와 같은 순서). 브라우저 플레이어는 보내지 않아요 |
| `If-Range` 있음 | 검증자(ETag·Last-Modified)를 내보내지 않으므로 항상 불일치로 봐요. Range를 무시하고 **200 전체 스트림**이에요 |
| HEAD | **Range를 무시**해요. 200 + 전체 `Content-Length`·`Accept-Ranges: bytes`예요. 본문은 없어요 |

### 3-3. 응답 헤더

```
Content-Type: <mediaMime>
Content-Length: <보내는 바이트 수>
Accept-Ranges: bytes
Content-Range: bytes a-b/size      (206일 때)
Cache-Control: no-store
X-Content-Type-Options: nosniff
Cross-Origin-Resource-Policy: same-origin
```

- ETag·Last-Modified·`Content-Disposition`은 내보내지 않아요.
- 오류 응답(404·405·416·503)은 표지와 같이 `text/plain; charset=utf-8`이에요(HEAD는 본문 없음).
- **오류 응답을 포함해 모든 응답이 `Cache-Control: no-store`예요**(D5 확정).

### 3-4. 서버 처리 순서(구간 요청마다)

1. 주소 파싱 → 메서드 확인 → 공급원 확인.
2. `t295.find_media(slug, generation)`(신규, `find_cover`와 같은 조건)으로 `{object_key, mime, ext, size_bytes, sha}` 한 행을 읽어요. 없으면 404.
3. 행 검사: 키가 `<slug>/<generation>/<sha>.<ext>`이고, mime·ext가 허용 쌍이고, 크기가 상한 이하인지 봐요. 어긋나면 503.
4. 구간을 계산해요(3-2). 416은 2~3을 통과한 뒤에만 내요.
5. 비공개 저장소에서 그 구간만 읽어요(서버 자격, 응답에는 노출하지 않음).
   - 저장소가 돌려준 206의 `Content-Range` 시작·끝·전체 크기와 길이가 요청 계획·`size_bytes`와 정확히 맞는지 확인해요.
   - 고정한 객체 버전과 같은지도 확인해요(D4). 어긋나면 첫 바이트 전이면 503, 전송 중이면 스트림을 오류로 중단해요.
   - 받은 바이트 수가 계획과 다르면 스트림을 오류로 중단해요.
6. 스트림을 보내기 직전에 `confirmMedia`(표지 `confirmCover`와 같은 역할)로 한 번 더 확인해요. false면 404예요.
7. **내부 청크마다 권리·활성 세대를 다시 확인해요.** 철회·만료가 확인되면 다음 청크를 보내지 않고 스트림을 오류로 중단해요.
8. 첫 바이트 마감 D3를 넘기면 503이에요. 클라이언트가 끊으면 저장소 읽기도 바로 중단해요.

**무결성 범위(D4 확정)**
- 표지는 요청마다 전체 해시를 검증하지만, 재생 파일은 구간마다 전체 해시를 확인할 수 없어요.
- 대신 아래 넷으로 막아요:
  - 게시 시점에 전체 해시를 검증해요(2-1).
  - 비공개 저장소는 **불변 버전 고정** 또는 **쓰기 후 덮어쓰기 금지**를 강제해요. 같은 크기로 바꿔치기하는 쓰기는 거절해요.
  - 키가 해시에 묶여 있어요.
  - 상위 저장소 206 응답의 범위·길이·버전을 검증해요(5단계).

## 4. 권리·철회

| 상황 | 결과 |
|---|---|
| 철회·권리 만료 | 새 요청은 첫 바이트 전에 404예요. 전송 중인 응답은 다음 청크 확인에서 오류로 중단돼요. 플레이어는 오류 상태로 넘어가요 |
| 이미 받은 바이트 | **회수할 수 없어요.** 브라우저 버퍼·병렬 다운로드로 이미 받은 분량은 재생될 수 있어요. 철회 뒤 남는 재생 시간의 상한은 보장하지 않아요(T370-B) |
| 새 세대 게시 | 이전 세대 주소는 404예요. 목록을 다시 읽으면 새 `src`(새 generation)를 받아요 |
| 공개 홈 | 기존 철회 가드(T-255-F1~F3)가 그대로예요. bfcache 복원 때 다시 읽어서 철회된 카드가 사라져요 |
| 상세가 열린 채 철회됨 | 다시 불러오기를 해도 404 → 오류 유지예요. 창을 닫고 다시 열면 목록 갱신 전까지 같은 카드가 남지만 재생은 막혀요(파일 경로가 최종 권한) |


## 5. 캐시

- 공개 홈 HTML(`force-dynamic`), 표지, 재생 파일 모두 `Cache-Control: no-store`예요.
  - CDN·브라우저 캐시가 철회를 늦추지 않게 하기 위해서예요.
- 비용·대역폭(D5 확정): 오류 응답을 포함해 `no-store`를 유지해요. 같은 사람이 다시 볼 때도 서버를 거쳐요. 전송·호출 비용은 운영 실측 항목이에요(9절).
- Next 이미지 최적화는 재생 파일에 쓰지 않아요. proxy가 재생 주소를 인증보다 먼저, 최적화를 거치지 않고 route로 보내요(T-254와 같음).

## 6. CSP(지금은 헤더 없음, 나중에 도입할 때)

```
media-src 'self';
img-src 'self';
```

- 재생·poster 모두 같은 출처(`/media/public/...`)라서 `blob:`이나 외부 저장소 도메인은 필요 없어요.
- 서명 주소로 저장소에 직접 보내는 방식은 이 계약에서 쓰지 않아요(D6 참고).
- 철회 가드 인라인 스크립트가 CSP로 막히면, 번들 설치 경로와 HTML `hidden` 기본값으로 안전해요(T-255-F3). 도입할 때는 nonce 방식을 권장해요.

## 7. 플레이어 실패 계약(Front, 이미 구현 — T250·T360·T360-F1)

| 상황 | 화면 |
|---|---|
| 상세 열기 | `preload="none"`이라 재생 파일 요청이 없어요. 영상 poster는 표지 상태를 따라요(알려진 실패면 poster 없음 + 대체 바탕, 조작 줄 56px 비움) |
| 재생 시작·버퍼링 | "재생 파일을 불러오고 있어요."(`role=status`) |
| 404·416·503·네트워크·디코딩 실패(`error` 이벤트) | "재생 파일을 불러오지 못했어요. 다시 시도해 주세요." + "재생 파일 다시 불러오기" 버튼. 상태 코드는 보이지 않아요 |
| 다시 불러오기 | 플레이어에 초점을 두고 `preload=auto` 뒤 `load()`예요. 철회된 작품이면 다시 실패해요 |
| 표지 실패 | 재생 오류로 보지 않아요. 재생이 실제로 시작되면(`playing`) 대체 바탕을 내려요 |
| 창 닫기·Esc | 재생을 멈추고 카드로 초점을 돌려요 |
| 키보드 | 상세 안 Tab 순서는 브라우저 기본 조작을 따라요(재생 작품은 Tab 가두기 예외) |

Front 쪽 남은 작업은 구현 배정 때 해요:
- DTO `src` 조립과 `MEDIA_EXT` 축소(2-3)
- 오디오 상세의 표지·플레이어 배치 재확인
- 철회 뒤 재생 실패 시험

## 8. 시험 계획

**Backend(구현 배정 시)**
- Range 파서 단위 시험: 유효·끝 생략·접미·0 길이·초과·다중·잘못된 형식·`If-Range`
- 상태표(3-1) 전체
- 무범위 GET 200 전체·HEAD 무본문·`If-Range` 200·권리 확인 전 416 미노출
- 상위 저장소 206 범위·길이·버전 불일치 → 503 또는 전송 중단
- 청크마다 권리 재확인 → 전송 중 철회 시 오류 중단, 동시 요청
- 전송량 측정(PG17 + 비공개 로컬 HTTP + 실제 Next로 가능, T370-B)
- 첫 바이트 마감
- 클라이언트 중단 → 저장소 읽기 중단
- 철회 직후 다음 구간 404
- 세대 교체
- PG17 `find_media` 권한·RLS

**Front**
- DTO 조립·거절 시험
- 합성 재생 라우트(격리 사본 전용)로 브라우저 확인. 1280/390/320 폭에서:
  - 재생·탐색(Range 206)
  - 중간 철회 → 오류 + 다시 불러오기 실패
  - 표지 실패와 재생 분리
  - 키보드
- 합성 mp4는 faststart로 만들어요.

**Tester 독립 검수**
- 위 두 결과를 격리 사본에서 다시 확인해요.
- 실작품 리허설 때 모바일 Safari·Android Chrome에서 Range 재생과 철회를 확인해요(T365 6절 흐름).
