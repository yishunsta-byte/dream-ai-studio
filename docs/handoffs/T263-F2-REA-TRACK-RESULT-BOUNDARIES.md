## 계약 변경과 연결 영향

| 항목 | 적용 결과 |
| --- | --- |
| 컨테이너와 트랙 | [로컬 검사](../../lib/reference-analysis/local-file.ts)는 ffprobe의 format·stream 시작 시각과 길이를 각각 읽는다. `timeline.containerDurationMs`와 `timeline.tracks`를 분리하며, 영상과 음원에서 각각 유일하게 식별되고 컨테이너 원점에 정렬된 구간만 기록한다. 동일 유형 복수 트랙, 누락된 시작·길이, 컨테이너 경계 모순은 해당 트랙의 시간 정렬을 미확인으로 둔다. |
| 탐색과 공유 | [결과 스키마](../../lib/reference-analysis/result.ts)는 영상 자료의 시간 근거를 영상 트랙에, 음악 자료의 시간 근거를 음원 트랙에 묶는다. 시작점은 트랙 안에 있어야 하고 구간 끝은 트랙 끝과 같을 수 있다. 시간 위치가 미정렬이면 소유자 화면에 참고 값으로만 남고 `seekable=false`다. 공유 요약에는 그 시간 위치가 들어가지 않는다. MP4의 음원 길이로 영상 근거를 허용하지 않는다. 혼합 파일에서 별도 음원 근거를 직접 탐색하도록 노출하는 일은 후속 트랙 식별 계약이 필요하다. |
| 취소·실패 | `cancelled`, `timed_out`, `inspection_failed`, `local_tool_failed`, `local_tool_unavailable` 상태는 같은 원인의 `file_metadata` 미확인 항목 하나만 허용한다. 이전 작업의 관찰·추정·파일 값, 추가 항목, 다른 원인은 거절한다. 상태와 결과에 같은 검증기가 사용되며, [표시·공유 출력](../../lib/reference-analysis/projection.ts)도 기존 소유자 판정 뒤 다시 검증한다. 소유자가 이 항목을 명시적으로 공유하면 분류와 정해진 원인만 나간다. |
| 실제 크기 | 로컬 실행기는 관리 파일에서 사본으로 스트리밍하며 관측한 byte 수를 성공 메타데이터의 `observedBytes`에 기록한다. 표시·공유의 `sizeBytes`는 이 값에서만 온다. 신고 크기에 일치하는 `values.sizeBytes`를 넣어도 내보내지 않는다. 불일치 값과 완료가 아닌 결과의 `observedBytes`는 스키마에서 거절한다. |

JSON v1은 유지한다. 이전 정상 결과는 `timeline`·`observedBytes` 없이도 파싱한다. 기존 `values.durationMs`는 표시용 참고 값으로 남지만 트랙 탐색 권한을 주지 않는다. 이전 검사기가 허용하던 종료 상태+관찰 조합은 보완판에서 거절한다. 엄격한 이전 스키마는 새 선택 필드를 모르므로 새 생산자·판독기를 같은 배정에서 갱신해야 한다. 화면에서는 `seekable`을 사용하고 집계 길이로 탐색을 복원하지 않는다. T266 UI·라우트 경로는 이 커밋에 포함하지 않았다.

## 고정 회귀 결과

- 로컬 FFmpeg로 만든 동일 파일에서 별도 ffprobe 관측이 **영상 500ms / 음원 1500ms / 컨테이너 1500ms**를 반환했다. REA 검사 결과에는 두 정렬 구간이 각각 `0–500ms`, `0–1500ms`로 기록됐다. 같은 결과에 490–500ms 영상 구간은 추가할 수 있고 900–1000ms 영상 구간은 거절됐다.
- 단위 시험은 지연 시작 트랙, 트랙 끝에서 시작하는 점, 정렬되지 않은 영상과 정렬된 음원만 있는 결과, 기존 집계 길이의 탐색 제한을 대조했다. 각 취소·실패 상태의 허용 결과와 잘못된 finding 조합, 신고 크기가 관측 크기로 승격되지 않는 표시·공유 결과도 시험했다.
- Backend의 `contract.test.ts`, `boundaries.test.ts`, `local-file.test.ts`만 명시해 기본 실행 **36 통과·9 건너뜀**, `DREAM_REA_NATIVE_TEST=1` 실행 **45/45 통과**. 세 시험 파일 및 REA 라이브러리 범위의 TypeScript와 ESLint 경고 0 검사 통과. TypeScript 설정은 `tmp/t263-f2-rea-typecheck.json`에 있다. 처음의 넓은 경로 TypeScript 검사는 진행 중인 Front 작업의 CSS 모듈까지 포함했으므로 Backend 범위로 좁혀 검증했다.

실제 저장 연결에는 서버에서 생성한 관측 결과의 소유자·파일·작업 ID·세대 바인딩이 필요하다. 취소 요청과 종료 결과를 확인한 뒤 이전 세대의 늦은 결과를 원자적으로 거부해야 한다. 이 모듈의 스키마는 결과 형상을 검증하며, 운영 저장소에서의 작업 세대나 입력 증거의 출처를 그 자체로 증명하지 않는다. 외부·운영 환경과 배포는 범위 밖이다.
