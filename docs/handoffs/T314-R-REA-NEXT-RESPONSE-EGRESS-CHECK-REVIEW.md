# T314-R Next 분석 응답 전송 결과 독립 검수

기준 보고 `103e4af` · 비교 실행기 `131fde6` · Master 인계 `msg_51097a3c8fca` · Codex(Tester)

**판정은 로컬 관측에 근거한 전송 경계 판단 수용, 문구 보완 및 Main PC 재현 필요.** 고정 커밋에는 보고서만 포함됐다. 격리 Next 시험 소스·클라이언트 스크립트·원시 기록은 기준 커밋과 검토 작업공간에 없었다. Tester는 Next를 빌드하지 않았다. 기존 T313의 소유 Node HTTP 실행기는 고정 Git 소스에서 빌드 없이 재실행해 통과했다.

| 검토 항목 | 근거와 판정 |
| --- | --- |
| Response 반환 전 · 첫 `pull` | 반환 전 차단은 대기 중 헤더가 없었고, 판정 후에는 403/410 응답 헤더와 빈 본문을 받았다. 첫 `pull` 대기 중 철회한 세 유형에서는 상태·헤더·본문 없이 `ECONNRESET`과 허가 소비 0을 기록했다. 보호 본문 0바이트라는 결과는 그 조건에서 성립한다. 정리의 ‘헤더 0’은 **대기 구간**이라고 명시해야 한다. Response 반환 후 첫 `pull`의 만료와, 호스트가 헤더를 먼저 확정하는 경우의 결과는 아직 관측하지 않았다. [T314 결과 ②·③](T314-REA-NEXT-RESPONSE-EGRESS-CHECK.md) |
| 전송 중 철회와 늦게 관측한 바이트 | HTML과 POST에서 읽기 재개 뒤 약 0.6MB가 더 도착했다. 앱이 철회를 감지한 뒤 새로 enqueue한 바이트가 없었다는 관측과 양립한다. 측정은 서버 enqueue와 Node 클라이언트 데이터 콜백을 비교하므로, 철회 시 그 바이트가 서버·커널·수신 측 버퍼 중 어디에 있었는지 또는 철회 뒤 네트워크를 통과했는지까지 가르지는 못한다. 0.6MB는 이 실험의 관측량이다. [T314 결과 ④](T314-REA-NEXT-RESPONSE-EGRESS-CHECK.md) |
| `after()`와 스트림 종료 | 512KB 실험에서 클라이언트가 65,529바이트만 전달받아 읽기를 멈춘 동안 앱의 두 신호가 끝났고, 재개 뒤 나머지 458,759바이트를 받았다. 이 반례는 앱 신호가 클라이언트 수신 완료나 하위 큐 폐기의 증명이 될 수 없음을 보여 준다. 4MB 케이스의 지연은 관측 조건에서 역압력이 작동했다는 보조 근거다. 취소 신호 역시 앱이 취소를 관측했다는 근거로 해석한다. T313은 `ServerResponse`와 실제 소켓 종료를 직접 관측한다. 그래도 애플리케이션이나 브라우저의 수신 확인까지 증명하는 계약은 아니다. [T314 결과 ⑤·⑥](T314-REA-NEXT-RESPONSE-EGRESS-CHECK.md) · [T313 소켓 종료·전환](../../tests/reference-analysis/t313-authority-response-egress.loopback.mjs#L156) |
| App Router HTML·RSC·Suspense | 페이지 렌더 중 거절은 보호 표식 없는 404였다. 수동 RSC 요청은 리다이렉트 이후 보호 표식과 허가 소비를 관측했으며, 시험한 기본 프리페치는 라우트 트리와 허가 미소비였다. 렌더 완료 뒤 철회해도 보호 본문 전체가 도착했다는 관측은 렌더 검사만으로 전송을 닫을 수 없음을 뒷받침한다. 3MB 입력과 6,006,726 수신 바이트의 관계는 원시 본문·크기 기준으로 확인해야 한다. Suspense의 200·공개 셸은 보호 분기보다 먼저 전송됐고 보고된 보호 표식은 0이었다. 상태 코드·공개 셸과 보호 본문을 별도로 판정한다. 전체 프리페치와 브라우저 캐시는 후속 범위다. [T314 결과 ⑦·⑧](T314-REA-NEXT-RESPONSE-EGRESS-CHECK.md) |

제품 라우트의 분석 응답은 여전히 DTO를 `Response.json`으로 반환한다. T314 결과로 입증된 범위는 격리 시험 라우트의 관측이다. 보호 본문을 별도 핸들러로 분리하면 페이지에 실리는 범위를 줄일 수 있다. T309의 세대 전환을 만족하려면 실제 송신 경계가 허가 소비·첫 삽입·종료를 소유하고 하위 큐 및 우회 경로를 통제함을 별도로 입증해야 한다. ## Main PC 독립 재현 준비물과 측정

1. `131fde6` 격리 사본의 시험 파일 5개(게이트, 제어 API, 합성 본문 API, 일반 페이지, Suspense 페이지), 별도 Node 클라이언트 전체, 실행 순서와 원시 출력, 시험 추가분의 해시가 필요하다. 보고된 Node 26.13.0, Next 16.4.6, 고정 잠금 파일, 인증이 꺼진 환경과 루프백 `next start`로 기존 조건을 먼저 재현한다.
2. 요청 ID·허가 ID별로 제어 요청 확정, Response 반환, 첫 pull, 허가 소비 및 enqueue 누적량, 서버 close·after·abort·cancel, 별도 클라이언트의 상태줄·헤더·첫 바이트·본문 길이 및 종료 원인을 기록한다. 첫 pull 철회와 만료를 양쪽에서 시험한다. 대기 구간과 최종 응답은 별도로 분류하고, 측정값은 한 프로세스의 단조 시각 또는 명시적 사건 동기화로 대조한다.
3. 512KB·4MB와 느린 수신 실험에서 클라이언트의 읽기 정지·재개, 철회 직전·직후 enqueue 및 표시된 수신량, 전송 계층 종료를 대조한다. 패킷 또는 실제 전송 큐의 관측이 없으면 지연 바이트의 버퍼 위치를 단정하지 않는다. 페이지 시험은 실제 리다이렉트와 RSC 헤더, 본문 길이·해시 및 보호 표식 수, 기본/전체 프리페치의 허가 소비, Suspense 공개 셸 뒤 보호 조각을 별도 기록한다. 브라우저 라우터 캐시와 bfcache는 HTTP 시험에 이어 별도로 실행한다.

고정 변경의 `git diff --check`와 T313 소유 루프백 소켓·리스너 정리를 확인했다. Next 실행 재현, 실제 호스팅, 운영 변경과 배포는 이번 독립 검토에서 수행하지 않았다.
