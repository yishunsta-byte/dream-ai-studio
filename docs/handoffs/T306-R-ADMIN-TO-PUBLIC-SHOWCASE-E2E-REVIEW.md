**판정 · 정상 종단 흐름 통과, 만료 전 권리 증빙 불일치 보완 필요.** 관리자 쓰기, 공개 읽기, 원장과 감사가 동일한 PG17을 사용했습니다. 만료 후 권리 판정이 어긋나면 롤백했으나, 만료 전 양쪽이 성공하면 서로 다른 만료 증빙을 커밋할 수 있었습니다.

## F306-1 · 권리가 아직 유효하면 다른 만료 증빙으로 게시될 수 있음

소유 루프백 PG17의 B 작품에 T295 시한부 권리와 만료 없는 앱 증빙을 설정했습니다. 두 증빙은 동일 작품과 권리 참조를 가리켰습니다. T295 만료 전에 준비·게시하자 API와 SQL이 각각 같은 `prepared`·`published`를 반환해 트랜잭션이 커밋됐습니다. 앱 상태의 `rightsUntilMs`는 `null`, 공개 활성 권리는 `timed`와 실제 종료 시각이었습니다. 새 공개 홈·표지는 만료 뒤 정상적으로 차단됐지만 앱에는 무기한 활성 기록이 남았습니다. 같은 종류의 불일치에서 만료 뒤 게시를 요청하는 대조군은 v1과 네 원장·감사 수를 유지했습니다.

[`t306-publication-e2e-store.ts`](../../tests/admin/t306-publication-e2e-store.ts)의 저장 단계는 서비스와 SQL 상태 DTO를 비교합니다. 실험에서 두 성공 DTO는 일치했지만 증빙의 모드와 만료 값은 달랐습니다. 운영 어댑터의 권리 증빙 정합성 검사에는 만료 전의 `perpetual`/`timed` 불일치도 포함해야 합니다. 이 결과는 T306 시험용 쓰기 어댑터에서 관측됐습니다.

| 실제 관리자 흐름 | 소유 격리 Next와 PG17.12에서 390px 화면의 키보드로 준비 v1→게시 v2→철회 v3을 실행했습니다. 기존 UUID와 게시 본문을 재전송해 같은 결과가 돌아왔고, 철회 뒤 이전 성공을 재생해도 원장·감사·공개 상태가 바뀌지 않았습니다. 준비·게시·철회 각각 앱 원장, 감사, T295 요청, T253 요청은 1건씩이었습니다. |
