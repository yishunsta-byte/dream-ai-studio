# 등록 자료 분석 · 같은 문서 세션 공백과 최소 연결 조건

2026-11-20 · Codex(Front) · Master 배정 `msg_06260ea590be`

## 이 문서의 성격

- 근거는 같은 문서 세션 경계 시험(`REA-CLOUD-WAV-SAME-DOCUMENT-SESSION.md`)에서 관찰한 사실이다.
- 새 제품 동작은 만들지 않았다. 제품을 고칠지, 누가 맡을지는 Master가 정한다.
- 서버 권한은 이미 요청마다 판정된다. 아래 공백은 모두 **화면 표시** 쪽이고, 서버 원본 읽기는 어느 경우에도 생기지 않았다.

## 관찰한 공백

### G1 · 분석 POST 401을 일반 실패로 표시

- **관찰:** S1에서 POST가 401을 받았다.
  - 화면은 ‘이 자료의 분석 결과를 가져오지 못했어요. 다시 시도해 주세요.’를 띄웠다.
  - 자료 선택과 권리 체크가 남았다.
  - 계정 표시도 그대로였다.
  - 로그인 안내와 로그인 이동은 `focus`나 화면 보이기 같은 복귀 계기가 생긴 뒤에야 일어났다.
- **원인:** `studio-registered-analysis-provider.ts`는 `!response.ok`를 모두 `analysis_unavailable`로 바꾼다. 그리고 `revocationAware`는 `source_unavailable`과 `invalid_selection`에만 반응한다.
- **이미 지워지는 것:** 이전 결과와 초안. ‘다시 분석’ 과정에서 지워진다.

### G2 · 의심 중 늦은 응답이 가려진 DOM에 들어감

- **관찰:** S2의 의심 상태에서 이전 계정 A의 늦은 응답이 도착했다.
  - 응답이 가려진 본문(`hidden`, `inert`)의 DOM에 그려졌다(`RMS 25%`).
  - 보이는 화면, 초점, 클릭으로는 닿지 않았다.
  - `changed`가 확정되자 본문이 지워졌고 문서도 다시 받았다.
- **설계상 한계:** `ProtectedContent`는 “이미 브라우저 메모리에 내려온 데이터를 지운다고 보장하지 않는다”고 밝히고 있다. 보호 목록 화면은 경계의 `epoch`를 보지 않는다.
- **참고:** `admin-render-queue`는 `epoch`를 쓰는 선례다.

### G3 · 신호 없는 쿠키 교체를 경계가 바로 알지 못함

- **관찰:** S3에서 다른 탭 신호 없이 같은 문서의 쿠키가 바뀌었다.
  - 경계의 계정 표시는 A로 남았다.
  - 화면 데이터는 기존 철회 경계(`source_unavailable` → 목록 재조회) 덕분에 B 목록으로 바뀌었다. 이전 결과와 초안도 지워졌다.
- **실제 앱에서 생길 가능성:** 실제 앱의 계정 전환은 로그인·로그아웃 화면을 거치고, 그 화면이 신호를 보낸다. 같은 사용자의 토큰 갱신은 계정이 바뀌지 않는다. 그래서 이 경우는 주로 시험이 만든 경로다.

## 최소 연결 조건 (제안)

제품 변경은 하지 않았고, 아래는 제안이다.

1. **분석 POST 401·403 구분 (G1)**
   - 공급자가 401을 `authentication_required`처럼 따로 구분해 돌려준다. 결과 DTO에 이유를 하나 늘려야 한다.
   - 보호 목록 화면은 이 값을 받으면 목록 GET 401과 같은 ‘다시 로그인’ 상태로 바꾼다. 선택, 체크, 결과를 지운다.
   - 경계가 있으면 `useSessionBoundary()?.retry()`로 바로 다시 확인하게 한다.
   - 403도 같은 방식으로 ‘접근 불가’ 상태로 보낸다.
2. **경계 세대 반영 (G2)**
   - 보호 목록 화면이 `useSessionBoundary()`의 `view`와 `epoch`를 읽는다.
   - `view !== "current"`인 동안 도착한 분석·목록 응답은 그리지 않고 버린다.
   - 요청을 보낸 뒤 `epoch`가 바뀌었다면, 그 요청의 응답도 버린다.
   - 경계 밖(`null`)에서는 지금처럼 동작한다.
3. **경계 재확인 계기 (G3, 선택)**
   - 보호 목록·분석 응답에서 401, `source_unavailable`, `invalid_selection`을 받으면 경계 `retry()`를 부른다.
   - 그러면 신호가 없어도 계정 변경을 바로 확인한다.
   - 서버 판정은 바꾸지 않는다.
4. **검증 기준**
   - 이번 시험 S1~S3를 그대로 다시 돌린다.
   - S1: POST 401 직후 ‘다시 로그인’ 안내가 뜨고, 선택과 체크가 0이어야 한다.
   - S2: 늦은 A 응답 뒤 가려진 DOM의 `RMS 25%`가 0이어야 한다.
   - S3: 쿠키 교체 직후 경계가 다시 확인해 B로 다시 받아야 한다.
   - 이 기준은 실제 Next 셸(보류된 3488 경로)에서도 다시 확인한다.
