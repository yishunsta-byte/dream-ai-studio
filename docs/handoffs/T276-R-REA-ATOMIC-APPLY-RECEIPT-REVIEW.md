# T276-R 확인 소비와 적용 영수증 원자성 독립 검수

**조건부 통과.** 같은 SQLite 연결의 확인 소비·타임라인 CAS·활동 로그·영수증 원자성과 프로세스 간 재조회는 확인했다. 실제 연결 전에는 영수증 완료·보존 시각이 쓰기 지연으로 소진되지 않도록 계약을 보완한다. [구현 보고](T276-REA-ATOMIC-APPLY-RECEIPT.md)

## P2 · 쓰기 전 시각을 완료 시각과 보존 기준으로 사용

현재 코드는 권한과 실행 만료를 평가할 때 한 번 읽은 `now`를 영수증의 `completedAtMs`와 `retainUntilMs`에 재사용한다. 격리 SQLite의 활동 로그 트리거에서 합성 시계를 150ms에서 320ms로 진행시키고, 보존 기간을 150ms로 두었다. 적용은 성공했으나 영수증은 완료 시각 150ms·보존 끝 300ms로 저장됐다. 커밋 직후 현재 시각 320ms에 새로 조회하면 곧바로 `unavailable`이었다. 응답 유실 후 영수증으로 판별할 수 있어야 하는 구간이 사라진다. [적용 저장소](../../lib/reference-analysis/synthetic-apply-store.ts)

실행 권한 판정에 사용한 시각과 영수증을 종결할 때의 시각을 구분한다. 타임라인 쓰기 후 같은 트랜잭션에서 신뢰 시각을 다시 읽고, 보존 기한의 산술·유효성을 검사한 뒤 영수증을 종결한다. 이 값이 커밋 이전의 종결 시각임을 명시하고, 제품 보존 기간에는 종결 기록부터 커밋까지의 지연도 고려한다. 쓰기 지연과 응답 유실을 함께 재현해 커밋 직후 원래 영수증을 읽을 수 있는지 확인한다.

## 독립 확인

- 합성 S4 SQLite와 테스트 테이블을 별도로 구성했다. 서로 다른 두 Node 프로세스에서 같은 확인의 적용을 병렬 실행한 결과 `applied` 한 건과 원래 `receipt` 한 건이었다. 세 번째 프로세스가 실행 만료 뒤 같은 영수증을 조회했다. 기준을 공유한 다른 확인은 `conflict`였고 타임라인 리비전과 `timeline.save` 활동 로그는 각각 한 번만 증가했다.
- 다른 연결의 쓰기 잠금이 유지된 동안 `{ status: "busy", retryable: true }`와 전체 DB 무변경을 확인했다. 영수증 종결 쓰기에 실패를 주입했을 때 이미 진행된 소비, 타임라인, 워크플로 및 활동 로그까지 롤백됐다. 실패를 제거한 뒤 같은 확인으로 적용할 수 있었다. 조건부 소비·종결과 타임라인 쓰기는 같은 연결의 트랜잭션 안에 있었다.
- 철회된 실행 권한은 대기 확인을 거절했고 현재 조회권이 없는 완료 영수증도 반환되지 않았다. SQLite 복제본에서 새 복원 세대를 공급하자 예전 대기 확인과 완료 영수증 모두 거절됐으며 복제본 행은 그대로였다. 별도 시험에서 `no_change` 종결 영수증, 취소 및 미확정 소비 거절, 보존 경계를 재검증했다. [격리 시험](../../tests/reference-analysis/atomic-apply.test.ts)
- 종결 확인에는 최소 영수증과 내부 범위·보존 기한이 남았고 대기 계획·사본 해시·분석과 장면 매핑은 제거됐다. 제품에 새 스키마·마이그레이션이나 서버 라우트는 추가되지 않았다. 합성 픽스처만 권한·테이블을 제공한다. 실제 인증과 파일 해시, 소유 자료·매핑의 증거, 복원 게시에서 새 세대 발급, 물리적 정리는 후속 통합 범위다. [픽스처](../../tests/reference-analysis/atomic-apply-fixture.ts)
