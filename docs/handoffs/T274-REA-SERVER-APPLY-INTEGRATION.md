# T274 REA 서버 적용 연계 설계

2026-11-19 KST · Codes(Backend) · 기준 `0c0e5d88ef53118428d5489d4c49a7682aecb750` · Orca 배정 `msg_104d5bafdb0a`

첫 연계 범위는 **현재 프로젝트에 등록된 파일에서 확인한 영상 컷으로, 이미 소재가 선택된 두 장면의 순서를 바꾸는 작업**이다. 현행 저장 계약의 0프레임 컷을 사용한다. 사용자 확인을 다른 프로세스에서 처리하려면, 서버가 발급한 확인 레코드를 기존 타임라인 쓰기와 같은 DB 트랜잭션에서 소비하고 그 결과를 남겨야 한다. 실제 사용자 연결의 선행조건은 검증된 프로젝트·자료 소유권과 서버가 저장한 분석 상태다. ## 저장소에서 확인한 경계

| 경로 | 현재 재사용 가능한 것 | 연계에 필요한 것 |
| --- | --- | --- |
| 로컬 프로젝트와 자료 | SQLite의 `projects`, `assets`, `project_assets`로 활성 프로젝트·자료 연결을 대조할 수 있다. 자료 업로드는 관리 파일의 크기·SHA-256·형식을 기록하고 `resolveStoredFile`은 실제 경로를 저장소 내부로 제한한다. | SQLite 스키마에는 사용자별 소유자 열이 없다. 인증 게이트 및 ID 조회는 행 소유권을 입증하지 않는다. 현재 로그인 비활성 모드의 `kind: "local"`에도 검증된 사용자 ID가 없다. 개인용 모드는 별도 승인된 OS/작업공간 권한과 격리로 경계를 입증하는 경우에 한한다. 여러 사용자가 같은 SQLite를 쓰는 모드는 프로젝트·자료의 서버 관리 소유권, 기존 자료의 귀속 이관 및 관련 쓰기·읽기에 일관된 검증이 선행해야 한다. |
| 로컬 REA와 타임라인 | 검사기는 소유 확인을 마친 관리 경로로부터 사본을 만들고 영상·오디오·이미지의 관찰을 반환한다. 적용 서비스는 별도의 소유 범위 조회를 받고, 기존 `timelineService.save`는 내용 리비전과 현재 타임라인 ID의 CAS, 편집 선행 승인, 장면 선택, 타임라인 검증과 원자적 리비전·포인터·워크플로 쓰기를 제공한다. | Studio 화면은 합성 표본을 사용한다. 실제 자료에 대한 REA 분석 저장·조회 및 철회 상태, 확인과 적용 결과의 지속 저장이 필요하다. `project-preview.ts`의 후보와 `project-apply.ts`의 확인 객체는 각각 프로세스 내부 WeakMap에 있다. `resolveOwnedScope`는 제품 연결이 없는 의존성이다. |
| 클라우드 프로젝트와 자료 | Postgres의 프로젝트·자료·연결·타임라인 행에는 소유자 문맥이 있고 RLS와 같은 소유자의 FK·불변성 검사가 있다. 프로젝트 GET은 검증된 세션에서 액터를 만들고 읽기 전용 트랜잭션에서 소유 범위로 조회한다. 비공개 객체 검증기는 크기·해시·형식을 검증한다. | Postgres 프로젝트 생성 서비스는 별도 미연결 코드이며 REA 쓰기 경로가 아니다. 제품 타임라인/자료 API는 legacy 데이터 게이트를 사용해 Vercel·Postgres 선택에서 닫힌다. Postgres 타임라인 쓰기 서비스와 권한 범위, 분석용 비공개 객체 인계, 분석·확인 테이블의 소유 FK/RLS, 런타임·보호 시험 승인이 별도 필요하다. 현재 객체 검증기는 검증 요약을 반환하고 임시 파일을 정리하므로 분석기에 지속 경로를 제공하지 않는다. |

## 최소 저장 및 조회 계약

아래 이름은 제안이며 이 작업에서 스키마를 추가하지 않는다.

- **분석 레코드.** 소유자·프로젝트·자료 ID 및 연결, 서버가 계산한 소스 리비전, 서버 발급 분석 리비전, 형식 버전, 완료 시각과 상태, 필요한 구조화 관찰·추정만 저장한다. 등록 파일의 바이트 해시는 기존 자산 값에서 얻고 분석에 실제 사용한 사본을 대조한다. 활성 상태와 소스 리비전은 파일 식별자와 바이트뿐 아니라 연결·권한의 세대까지 포함한다. 가장 작은 구현은 소유 구조를 확보한 뒤 아카이브·연결 해제·교체·권한 철회와 분석 무효화를 같은 트랜잭션에서 처리하고, 복원·재연결 시 새 분석을 요구하는 방식이다. 해당 변경 경로를 통제할 수 없다면 자료·연결의 별도 세대 상태가 필요하다. 등록 링크, 붙여 넣은 본문, 미등록 파일은 이 적용 경로의 범위 밖이다.
- **확인 레코드와 적용 영수증.** 별도 큐 없이 한 레코드에 무작위 확인 ID, 동일 소유자·프로젝트·자료·분석 리비전, 계약 버전, 선택 근거 ID와 서버가 검증한 이동 장면·대상, 확인 화면의 타임라인 ID·내용 리비전, 만료와 상태를 둔다. 필요하면 확인 화면과 정규화된 계획의 일치를 구조적 비교나 버전이 포함된 요약값으로 검사한다. 적용 완료 시 결과 타임라인 ID·리비전과 처리 시각만 붙인다. 확인 ID는 조회 키로만 쓰며 모든 요청에서 인증과 소유 범위를 다시 확인한다. 서로 다른 분석이 같은 `video-cut-1`을 가질 수 있어 ID는 분석 레코드에 종속된다.
- **데이터 최소화.** 저장할 후보 증거는 검증된 시간·영역·수치와 근거 종류로 제한한다. 자유 형식 분석 원문, 파일명, URL, 사본 경로, 픽셀·PCM, 원본 바이트와 토큰 비밀은 확인·영수증·로그에 넣지 않는다. 단순 장면 적용은 기존 타임라인 JSON만 저장한다. 프롬프트나 근거의 프로젝트 보관, 이미지·음악 자산 생성·선택은 저장 모델과 동의 범위가 필요한 별도 기능이다.

전송 가능한 확인 ID를 기존 WeakMap 토큰 대신 사용한다. 수평 확장 시에도 같은 DB를 권한·확인·타임라인의 기준으로 삼는다. 기존 메모리 객체 형식·분석 스키마를 그대로 직렬화하는 방식은 채택하지 않는다. 첫 구현은 하나의 저장 백엔드에서 동작시키며 다른 백엔드로 읽기나 쓰기를 자동 전환하지 않는다.

## 요청, 쓰기, 재처리

1. **분석/준비.** 검증된 세션 또는 승인된 로컬 소유권 경계와 기존 시작 점검을 먼저 확인한다. 분석기는 서버가 선택한 자료 ID의 실물 사본을 처리한다. 장시간 분석은 타임라인 쓰기 트랜잭션 밖에서 실행하며, 완료를 기록할 때 소유권·활성 연결·소스 리비전과 취소 상태를 재검사한다. 준비는 완료된 현재 분석의 후보 한 건과 사용자가 매핑한 두 장면을 대조하고 짧게 만료되는 확인 레코드를 만든다. 이 단계는 타임라인을 바꾸지 않는다. 원본 탐색은 `sourceSeek.ptsMs`, 편집 미리보기는 `draft.editGridApproximation`을 이용한다. 프로젝트의 실제 배치는 선택된 장면 ID로 계산한다.
2. **명시적 적용.** 별도 변경 요청에서 확인 ID와 확인 의사만 받는다. 쿠키 인증의 변경 요청에는 기존 제품의 인증·출처 검증을 적용하고, 응답은 `no-store`로 제한한다. 클라이언트가 보낸 소유자, 분석 결과·버전, 미리보기 DTO 또는 타임라인 JSON은 쓰기 근거로 삼지 않는다. DB 쓰기 트랜잭션에서 프로젝트와 연결·자료·분석·확인 상태를 다시 읽는다. SQLite는 같은 연결의 쓰기 잠금 안에서 대조하고, Postgres는 버전 비교와 함께 관련 행을 일정한 순서로 잠근다. 취소·철회·교체·삭제도 같은 잠금·버전 규칙에 참여한다. 행이 없는 경우도 권한 또는 버전 검증 실패로 처리한다. 트랜잭션의 잠금 획득 후 신뢰 가능한 서버 기준 시각을 읽어 만료·분석 유효성을 비교한다.
3. **원자적 저장.** 대조된 기존 장면 순서만 재계산한다. 편집 규칙·장면 선택·기준 리비전·포인터가 달라지면 새 확인을 받아야 한다. 같은 트랜잭션에서 타임라인 리비전·포인터·워크플로와 완료 영수증을 기록한다. 변경이 없는 계획은 `no_change`로 종료한다. 이미 완료한 동일 확인의 재전송은 현재 접근권 확인 후 영수증만 반환한다. 별도 확인을 동일 기준으로 실행해 경쟁에서 밀리면 `conflict`다. Postgres의 제한된 역할에서 동일한 동작을 입증하기 전에는 로컬의 CAS 의미를 클라우드에 적용했다고 간주하지 않는다.
4. **취소·삭제.** 적용 전 취소, 분석 재실행, 자료 연결 해제, 권한 철회, 프로젝트·자료 보관은 대기 확인을 무효화한다. 진행 중 분석은 중단시키고, 취소 이후 도착한 완료 이벤트는 상태·리비전 조건으로 거절한다. 적용과 취소가 경합하면 트랜잭션을 먼저 완료한 쪽의 결과를 반환한다. 완료된 장면 변경의 되돌리기는 기존 타임라인 복원 경로에서 새 명시적 요청으로 수행한다. REA 삭제는 분석의 비공개 필드를 지우고 대기 확인을 취소한다. 이미 적용한 타임라인과 기존 불변 기록은 기존 정책을 따르며, 영수증은 권한 및 승인된 짧은 보존 기간 안에서만 조회한다. 만료·삭제된 확인은 다시 발급하며 이전 ID를 되살리지 않는다. 외부에서 관리 파일을 바꿀 수 있는 환경에서 DB의 행 검증만으로 실물 철회를 보장할 수 없다. 파일 변경·삭제 권한을 기존 서버 관리 경계에 묶는 것이 선행조건이다.

| 제안 응답 | 처리 |
| --- | --- |
| 미인증·금지·범위 외 | 기존 인증의 401/403/503을 따르고, 소유 범위 조회의 실패는 다른 사용자의 존재를 드러내지 않는 404로 처리한다. 거절 시 분석·확인·타임라인 데이터는 반환하지 않는다. |
| `stale` / 만료 / 취소 | 적용 없이 종료한다. 새 분석 또는 현재 상태를 바탕으로 새 확인을 만든다. |
| `conflict` / `no_change` | 변경이 없음을 반환한다. 충돌은 최신 상태를 조회해 사용자에게 다시 보여 준다. |
| `busy` | 현재 SQLite 서비스처럼 최상위 쓰기 시작 전의 확인된 잠금 대기 초과만 제한된 재시도 상태로 반환한다. 재시도는 같은 확인과 최신 검증을 통과해야 한다. |
| 커밋 응답 유실·기타 오류 | 드라이버 원문을 응답에서 빼고, 권한을 재확인한 뒤 같은 DB의 영수증을 조회한다. 완료 영수증은 이미 적용된 결과이며, 조회 불가 또는 이력 만료는 현재 타임라인을 읽어 조정한다. 실패 단계가 확정되지 않은 요청의 자동 재적용은 금지한다. |

## 통합 시험과 착수 순서

- **격리 로컬 합성.** 별도 프로세스 A에서 실제 분석·확인 생성, B에서 확인 소비 후 재시작이나 응답 유실을 모의한다. 두 프로세스가 같은 확인을 보내도 타임라인 행·내용 리비전·활동 로그가 각각 한 번 증가하고 영수증이 일치해야 한다. 다른 확인 두 개의 충돌, 시작 잠금과 커밋 단계 실패, 쓰기 직전 실패에서 확인·타임라인 동반 롤백을 검사한다.
- **권한·수명.** 같은 파일의 다른 프로젝트, 다른 소유자, 이전 소스·분석·타임라인 버전, 고립된 연결, 잘못된 근거 ID, 만료 직전·경계·직후, 아카이브 후 복원, 연결 해제 후 재연결, 취소/삭제와 적용 경합을 검사한다. 오래된 화면의 전송 및 지연 완료가 쓰기를 일으키지 않아야 한다. DB·응답·로그·사본에서 금지된 필드를 대조하고, 만료·삭제 및 작업 사본 정리를 확인한다. 120fps 원본의 992ms와 30fps 근사값이 프로젝트 배치를 결정하지 않는지도 확인한다.
- **다음 순서.** 로컬 소유권 모델과 보존 정책을 먼저 확정하고 두 레코드 및 무효화 경로를 격리 구현한다. 클라우드는 승인된 별도 보호 환경에서 검증된 두 계정과 제한 API 역할로 역할·소유 FK/RLS, 객체 버전 확인, 권한 철회, Postgres CAS·커밋 유실을 재현한 뒤 연결을 판단한다. 운영 매핑·승인 상태는 기존 기록을 따르며 외부 환경을 조회하지 않았다.
