# 선택한 프로젝트 WAV의 타임라인 저장 계약 제안

Master 배정 `msg_f1cb3447d127`, 기준 커밋 `9253d1a`. 설계 인계 한 건. 현재 선택·미리듣기는 편집 화면 상태이며, 명시적 저장을 성공시켰을 때만 새 사용자 리비전에 배경 음악 클립을 추가한다.

## 현행 경계

| 근거 | 이미 있는 동작 | PG 연결에서 필요한 것 |
|---|---|---|
| 편집 음원 선택기와 프로젝트 음원 GET | 같은 소유자의 productionAudio 첨부, 보관 상태, 검증 WAV를 확인한 뒤 미리듣기 | 저장 시에도 같은 조건을 잠금 아래 재확인 |
| 기존 timeline API·timelineService | SQLite의 save는 편집 선행 승인, 프로젝트 contentRevision 및 현재 timelineId를 검사한다. 정규화한 JSON이 같으면 새 버전을 만들지 않는다. 새 저장은 changeContent로 단계 무효화·포인터·활동 기록을 함께 처리한다. | 직접 PG 저장 어댑터에서 같은 편집 게이트와 변경 효과를 한 트랜잭션에 구현. 기존 SQLite 저장 메서드를 PG 요청으로 호출하지 않는다. |
| timeline_revisions와 DB 제약 | 소유자·프로젝트·revision 고유성, 이전 행 보존, 정규 JSON 바이트의 SHA-256 및 v2 오디오 형식 검사 | 기존 테이블·현재 포인터 재사용. 프로젝트 입력 JSON이나 PNG 생성 기록 수정 불필요 |
| 타임라인 스키마와 audio-ops | 30fps, 음악 클립과 소스 범위, 출력 길이, 겹침, 자산별 권리 행 검증 | DB 파일 경로 대신 소유 WAV 등록의 해시·길이·메타데이터 사용 |

## 최소 쓰기 계약

로컬 선택형 `POST /api/projects/{id}/timeline/audio-clips`를 제안한다. 요청 본문은 `assetId`, `expectedContentRevision`, `expectedTimelineId`이고 논리 저장마다 UUIDv7 `Idempotency-Key`를 보낸다. 첫 범위는 **편집이 허용되고 현재 출력 길이가 양수인 저장 타임라인**에 음악 한 클립 추가다. 현재 리비전이 없는 신규 PNG 프로젝트는 편집 가능한 기준 타임라인이 마련된 뒤 재개한다. 메뉴에서 음원을 선택하는 것만으로 빈 장면이나 임의 길이를 생성하지 않는다.

1. 인증 소유자의 프로젝트를 잠그고 접근 가능 여부를 확인한다. 요청 키와 정규 요청 지문(프로젝트·원본 리비전·음원 ID·작업 종류)을 같은 프로젝트의 저장 활동 기록에서 찾는다. 같은 키·같은 입력은 최초 결과를 재반환하고 같은 키·다른 입력은 409다. 이전 성공을 반환할 때 현재 포인터를 되돌리거나 음원 바이트를 제공하지 않는다. 기존 SQLite의 CAS 다음 동일 JSON 검사만으로는 응답 유실 뒤 최초 결과를 복구할 수 없어 이 기록이 필요하다.
2. 신규 요청은 편집 선행 승인과 두 기대값을 대조한다. 하나라도 다르면 409로 재조회한다. 현재 리비전의 프로젝트·저장 해시, 서버가 알고 있는 장면과 현재 선택 결과의 일치도 검증한다. 첨부와 WAV를 같은 소유자로 한정해 보관 처리와 경합하는 행을 잠그고, 등록 해시·종류·키·길이와 자산을 대조한다. 타인·미첨부·보관·무효 WAV는 추가할 수 없다.
3. 전체 현재 스냅샷을 기준으로 기존 audio-ops 규칙을 사용한다. v1의 빈 audio는 v2로 변환하고 소리가 있는 v1은 기존 규칙대로 거절한다. `audio[]`에는 새 클립 id, assetId, role=music, startFrame, sourceInFrame=0, durationFrames, gainDb=0, fadeInFrames=0, fadeOutFrames=0, duckUnderVoice=false를 쓴다. 첫 음악은 0프레임, 다음 음악은 마지막 음악 끝에서 시작한다. 길이는 원본 프레임 수와 남은 출력 프레임 수 중 작은 값이다. 1프레임 미만이면 저장하지 않는다. `audioMixProfile=p2-5-local-v1`, 기존 audioJoins와 audioRights를 보존하고 새 자산에만 빈 권리 구조 한 행을 추가한다. 업로드 메모만으로 사용 허가나 라이선스 정보를 채우지 않는다.
4. timelineSchema와 기존 편집 검증을 적용한다. `canonicalJson`과 같은 문자열을 해시하고 새 timeline_revisions 행에 owner_id, project_id, 새 id, 직전 프로젝트 타임라인 번호+1, 새 content_revision, timeline_json, timeline_sha256, source=user를 기록한다. 복원·이관 참조는 NULL이다. 프로젝트 current_timeline_rev_id와 content_revision 갱신, 기존 edit 변경의 검수·내보내기 승인 무효화, 저장 활동 기록을 함께 커밋한다. 활동 기록에는 요청 키·지문·클립 ID와 결과 타임라인 ID·번호·내용 버전을 남긴다. 성공 응답도 이 결과를 반환한다.
5. 과거 리비전과 보관된 소스를 가리키는 이전 클립은 보존한다. 기존 SQLite와 같이 현재 기준 버전에서 내용이 동일한 기존 클립은 유지할 수 있다. 보관된 파일을 새로 추가하거나 기존 클립의 범위를 변경하는 것은 거절한다. 새 렌더·다운로드는 각각 해당 시점의 소스 접근 정책을 따른다.

## 완료 시험

| 시나리오 | 기대 결과 |
|---|---|
| 100ms WAV, 30fps, 출력에 공간 있음 | 음악 3프레임, 자산별 권리 행 하나. 새 리비전과 포인터·내용 버전·승인 무효화 일치. 이전 JSON·해시·PNG 첨부 보존 |
| 두 창이 같은 기준 버전에서 다른 저장 | 하나만 성공, 다른 요청 409. 응답 유실·동시 동일 키는 리비전·클립·활동 각각 하나. 이후 다른 편집이 성공한 뒤 이전 키 재시도도 현재 포인터 유지 |
| 첨부·소유·보관 경계 | 익명 401, 타인 프로젝트·파일·미첨부 거절. 보관 선행 시 신규 추가 0건, 저장 선행 시 과거 리비전 보존 |
| 편집 불가·범위 부족 | 편집 선행 미승인, 기준 타임라인 없음, 장면 변경, 출력 0프레임, 소스 1프레임 미만, 남는 출력 없음은 쓰기 0건 |
| 원자성·회귀 | 포인터 또는 활동 기록 실패 주입 후 전체 롤백, 같은 키 복구. 현재 GET과 과거 리비전 재조회 비교. SQLite 저장·복원, 기존 PNG/WAV 첨부 및 9253d1a 미리듣기 회귀 |
