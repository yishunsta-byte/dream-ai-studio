# T358-R 조회 전용 DB 설치 후보 독립 검수

2026-11-19 KST · Codex(Tester) · 고정 커밋 `cb29c98` · Master 배정 `msg_855746d068bf`

**격리 검수 통과.** 고정 변경은 별도 설치·복귀 SQL, 시험 실행기, 인계 4경로다. 소유 PG17.12와 해시가 고정된 PostgREST 16.6으로 설치·조회·복귀를 독립 실행했다.

- 기반 SQL 1~3은 기존 v2 러너와 이력 계약으로 적용했다. 조회 후보 SQL의 실행 주체는 소유 bootstrap 세션에서 `SET ROLE`한 비슈퍼유저 공통 테이블 소유자였다. 예약 스키마의 부분 객체, 예약·기존 공개 정책, 강제 RLS 해제, 열 타입 변경, 역할 속성, 브라우저 역할의 기존 열 권한을 거절했다. 예상 밖 기본 ACL은 중간 DDL을 롤백했다. 다시 설치한 요청도 충돌로 닫혔다. 실패 뒤 후보 객체가 남지 않았고 기존 행·이력·권한·정책·트리거는 보존됐다.
- 카탈로그에서 인증 역할의 허용 열을 대조했다. 프로젝트·단계·작업의 조회에 필요한 열만 부여했고 `owner_id`는 권한 목록에 없었다. 기반·내부 스키마 직접 조회, 기존 API·worker 역할 전환 및 DML을 거절했다. 실제 PostgREST에서도 POST·PATCH·DELETE 뒤 기존 데이터가 같았다.
- 합성 JWT의 승인 A/B는 자기 활성 프로젝트만 봤다. 타인·보관·미승인·미존재 상세는 빈 결과였고 익명 조회는 401, 비공개 프로필은 406이었다. A 승인 회수 뒤 같은 토큰의 목록·상세가 비었고 B는 영향을 받지 않았다. 재승인 뒤 A 조회가 복구됐다. 페이지 범위와 허용 DTO 필드도 확인했다.
- 복귀는 버전 표식이 누락되거나 예상 밖 객체가 있으면 전체를 롤백했다. 정상 복귀 뒤 후보 스키마·정책·열 권한이 제거되고 기존 기반 행, 이력, ACL·RLS·트리거가 보존됐다. 설치 중과 복귀 후 기존 프로젝트·단계·작업의 승인된 쓰기가 계속 동작했고 다른 소유자 쓰기는 차단됐다. 깨끗한 재설치에서 승인 목록은 비어 있었다.
- PostgreSQL·프로젝트·인증 관련 회귀 1,280건 통과·300건 조건부 건너뜀, 소스 타입 검사, 실행기 ESLint와 diff 공백 검사가 통과했다. 두 루프백 리스너와 실행 파일·임시 클러스터를 제거했고 소유 프로세스가 0건임을 확인한 뒤 검수 사본을 정리했다.

검증은 소유 루프백 PostgreSQL·PostgREST와 합성 JWT에 한정한다. 실제 Supabase 설치 역할·Auth·관리형 Data API, 운영 이관, 빌드·배포는 범위 밖이며 새 세션은 생성하지 않았다.
