# T310 REA 발급·폐기 요청 직렬화 PG17 검증

2026-11-19 KST · Codes(Backend) · 설계 기준 `ae3431e` · 배정 `msg_4d5995597c37`

고정 SQL1–4, T281, T307 픽스처를 소유한 PostgreSQL 17.12 루프백 클러스터에 적용했다. 실제 등록 객체와 검증 기록의 식별 정보를 고정한 뒤, T310의 전용 원장과 자료 증거 포인터에서 발급·폐기 요청의 경쟁을 재현했다. [T309 재실행 설계](T309-REA-AUTHORITY-EVIDENCE-ISSUANCE-DESIGN.md) · [T310 시험 SQL](../../tests/reference-analysis/t310-authority-issuance.sql) · [실행기](../../tests/reference-analysis/t310-authority-issuance.pg17.mjs)

## 시험 계약

- 원장 고유 키는 `(storeId, restoreGeneration, requestId)`다. 정규화한 요청 지문을 예약에 기록한다. 같은 키의 예약·처리·재시도는 제어 행과 동일 요청의 트랜잭션 잠금을 획득한 뒤 `READ COMMITTED`의 새 조회로 원장을 읽는다. 예약을 커밋하기 전에는 업무 변경을 거절한다.
- 자료 포인터 변경과 원장 종결을 함께 커밋한다. 같은 키와 지문의 완료 결과는 쓰기 없이 재조회된다. 폐기 후에는 리비전을 유지해 이전 리비전으로 예약한 발급이 증거를 되살리지 못하게 한다.
- 실행기는 지연 제약 트리거에 소유 제어 연결의 advisory lock을 걸어 별도 백엔드를 **실제 COMMIT 내부**에서 정지시킨다. `pg_stat_activity`와 `pg_blocking_pids`로 COMMIT 대기와 같은 요청의 후속 호출 대기를 확인한다. 별도 원장 관측에서 행이 없거나 예약만 보이는 것은 미확정이다. 잠금 기한 초과(`55P03`) 뒤 트랜잭션 실패와 롤백을 확인한다.

## 실제 결과

| 시나리오 | 관측 결과 |
| --- | --- |
| 최초 예약 COMMIT 대기 | 별도 조회에 행 0건. 기한 초과한 후속 호출은 성공 상태를 반환하지 않았다. 대기 중 같은 지문과 다른 지문을 함께 보냈고, 원본 커밋 뒤 같은 지문은 예약을 읽고 다른 지문은 거절됐다. 원장 1행과 자료 리비전 0을 확인했다. |
| 첫 발급 COMMIT 대기 | 별도 조회에는 기존 예약만 보였고 포인터 리비전은 0이었다. 기한 초과는 미확정으로 처리했다. 원본 커밋 뒤 같은 키의 대기 호출과 재조회는 기존 발급 결과를 반환했다. 포인터는 리비전 1과 발급된 자료 세대를 유지했다. |
| 발급 COMMIT 취소 | 실제 대기 중인 백엔드의 COMMIT을 취소해 `57014`와 트랜잭션 종료를 확인했다. 원장 예약과 기존 리비전 1이 유지됐다. 이후 같은 요청 재시도에서 한 번만 발급해 리비전 2가 됐다. |
| 최초 예약 COMMIT 취소 | 취소 전 원장 부재와 잠금 기한 초과를 확인했다. 취소 및 트랜잭션 종료 확인 뒤 같은 키로 예약했다. 기존 자료 상태는 바뀌지 않았다. |
| 폐기와 늦은 발급 | 폐기가 리비전 3으로 확정된 뒤, 리비전 2로 예약한 별도 발급은 거절됐다. 이전 성공 조회도 포인터를 바꾸지 않았다. 이전 작업 번호는 거절됐고 최종 상태는 리비전 3의 폐기였다. |
| 제한 역할 및 환경 종료 | 직접 원장 조회·포인터 수정·내부 잠금 함수 호출·보호 역할 전환을 거절했다. 대여된 발급자 세션과 열린 트랜잭션 0건을 확인했다. 소유 postmaster를 중지하고 PID 파일·루프백 리스너·임시 클러스터를 정리했다. |
