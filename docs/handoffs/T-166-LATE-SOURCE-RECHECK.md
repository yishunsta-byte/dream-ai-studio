## 1. 수정
- `runClaimedExport`의 **성공 경로**를 바꿨어요.
  - 이제 ZIP을 쓰고 확인(새로 쓴 `.part`, 또는 이어받는 기존 파일의 `verifyZip`)하고, 그 ZIP의 해시를 잰 **다음**, 확정 트랜잭션 **전에** 모든 소리 원본을 다시 재요.
  - 다시 잴 때는 size·mtime 캐시 없이 `fileDigest`로 전체 sha256과 크기를 재요.
  - 등록 기록과 다르면 `EXPORT_INVALID`(409, 다시 시도 불가)로 실패해요. 문장은 "소리 파일 '…'이 저장할 때와 달라요"예요. 파일이 없으면 "…을 찾을 수 없어요"예요.
  - 성공 파일로 link하지 않고, `.part`는 기존 finally에서 지워요.
- 이어받는 orphan ZIP도 같은 재검사를 거쳐요. 그래서 현재 원본이 다르면 성공으로 돌아가는 길이 없어요. orphan 파일 자체는 지우지 않고 그대로 둬요.
- 순서
  1. 비동기 재측정
  2. 동기 트랜잭션: 작업 소유권, 취소, `context`(구간·크기·stat) 확인
  3. link(noreplace), 성공 행 갱신
  - 이 순서는 따로 나뉘어 있고, 기존 롤백(link 뒤 DB 실패 시 unlink)은 그대로예요.
- 작성 실패 때의 재측정(T162)은 이제 파일이 없을 때 "찾을 수 없어요" 문장을 써요. 바뀐 경우의 문장은 그대로예요.
- 장면 파일은 기존 동작 그대로예요. 작성 전 해시와 작성 실패 때의 재측정은 하고, 성공 경로의 재측정은 소리만 해요(지시 범위).

## 2. 한계 (솔직하게)
- 재측정이 끝난 뒤 link 사이의 아주 짧은 구간에 원본이 바뀌면 잡지 못해요(ABA).
  - 앱은 원본 파일을 OS 수준에서 잠그거나 따로 떼어 두지 않아요.
  - 원본은 이 PC의 사용자 저장소에 있고, 다른 프로세스가 동시에 바꿀 수 있어요.
  - **완전한 OS 격리는 주장하지 않아요.**
- ZIP 안의 소리는 처음 읽은 등록 바이트이고, `verifyZip`으로 확인돼요. 이번 수정은 "작성 중 원본이 바뀌면 거절한다"는 계약을 지키기 위한 것이에요.
- 요청 단계는 여전히 크기까지만 확인해요(T162 한계). 미리보기에서 문제가 없다고 나와도 해시까지 확인했다는 뜻은 아니에요.

## 3. 시험 (`tests/t166-late-source-change.test.ts`, 6개)
- **환경**
  - 모두 고정 s9 ZIP을 OS 임시 폴더에 풀고 9→10으로 올린 사본에서 해요.
  - 실제 `writeZip`·`verifyZip`은 그대로 부르고, **끝난 직후**에 변경을 넣는 시험용 이음매만 감쌌어요.
  - 이음매 안에서는 단언하지 않아요. 단언을 넣으면 그 실패가 '쓰기 오류'로 바뀌어 엉뚱한 이유로 통과할 수 있어서요.
1. **정상 경로**: manifest 2로 확정되고, 확정 파일 `verifyZip`이 통과해요.
2. **F163-1 원재현**
   - `writeZip` 반환 직후 voice 마지막 1바이트를 바꿨어요. **크기는 같고, 수정 시각은 원래 값으로 되돌렸어요(ms 단위까지 같음).**
   - 결과는 `EXPORT_INVALID`(저장할 때와 달라요)이고 다시 시도할 수 없어요. 행은 failed이고 성공 ZIP과 `.part`가 없어요.
3. **ZIP 확인 뒤 원본 사라짐**: `EXPORT_INVALID`(찾을 수 없어요)이고 성공 파일이 없어요.
4. **orphan 이어받기**
   - 1차 시도: 실제로 쓴 ZIP을 확정 위치에 복사해 둔 뒤 저장 오류를 냈어요 → `STORAGE_FAILED` 대기
   - 2차 재시도: 그 orphan을 `verifyZip`한 직후 원본을 같은 크기·같은 시각으로 바꿨어요 → `EXPORT_INVALID`, 다시 시도 불가
   - orphan 바이트(sha)는 그대로예요.
5. **noreplace**: 확정 직전 같은 이름에 다른 파일을 놓았어요.
   - 그 파일을 덮어쓰지 않고 `STORAGE_FAILED`가 돼요. 재시도해도 성공하지 않고 그 파일은 그대로예요. `.part`는 없어요.
6. **확정 뒤 DB 실패**
   - 시험 사본에만 성공 갱신을 막는 트리거를 넣었어요. 결과는 `STORAGE_FAILED` 대기이고, 확정 파일과 `.part`가 없어요.
   - 트리거를 지우고 재시도하면 manifest 2로 성공해요.
   - **먼저 성공한 묶음 ZIP의 바이트는 그대로예요.**
- **수정이 실제로 막는지 확인**: 재검사 줄만 잠시 뺐더니 2번(F163-1)과 4번(orphan)이 실패했어요. 바로 되돌렸어요. 3번은 기존 확정 단계 검사로도 막혀요.
