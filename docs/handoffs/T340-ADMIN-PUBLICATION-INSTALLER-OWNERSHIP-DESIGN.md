**제안은 내부 역할을 승인된 관리 단계에서 준비하고, 별도 제한 설치자가 그 상태를 검증한 뒤 DDL을 적용하는 안이다.** 먼저 소유 PG17에서 검증한다. **사전 입력 계약.** 관리자가 독립적으로 승인한 계획에 클러스터 식별자·DB OID와 이름·직접 TLS 대상, 패키지 버전과 파일 해시, 역할 OID·이름·속성, 멤버/부여자/부모 역할 OID 및 `ADMIN/INHERIT/SET`를 고정한다. 직접 간선과 유효 전환/상속 경로를 모두 확인한다. 이름이 같아도 예상 OID가 다르면 거절한다. 검사 대상이 현재 카탈로그를 읽어 자체 기대값을 만들 수 없게 한다. 실제 역할을 만들기 전에는 계획 형식을 검증하고, 발급 뒤에는 별개 승인 기록에 실제 OID를 대조한다. 비밀번호·DSN·토큰은 이력과 증거 출력에서 제외한다.

**B의 소유권 이전 순서.** 설치 트랜잭션에서 스키마를 만들고, 해당 스키마에 필요한 함수·테이블 소유자의 임시 `CREATE`를 부여한 뒤 소유권을 이전한다. ACL과 이력을 정리하고 임시 스키마 권한을 제거한 후 마지막으로 영속 NOLOGIN에 스키마를 넘기는 방식을 시험한다. PostgreSQL 17에서 스키마를 넘겨받는 역할에는 대상 DB `CREATE`도 필요하므로, 이 권한과 설치 로그인에 제공한 DB `CREATE`를 관리 단계의 발급·회수 목록에 넣는다. 필요한 `CREATE` 권한이나 회수 수단이 없으면 이 안은 차단된다. [PostgreSQL 17 ALTER SCHEMA](https://www.postgresql.org/docs/17/sql-alterschema.html)

## 부분 상태·동시 실행·이력 계약

1. **설치 시작.** 허용 상태는 A의 깨끗한 대상 또는 B의 승인된 사전 역할만 존재하는 대상이다. B의 준비 상태에는 게시 스키마·이력·작품 데이터가 없다. 예상 역할 일부만 존재하거나 승인되지 않은 ACL·스키마·이력 구조가 있으면 중단한다. 이력 접근 전에 실제 테이블 유형·소유권·열과 ACL을 확인한다. v1 객체를 자동 채택하지 않는다.
2. **동시 실행.** 같은 DB의 관리·설치·권한 회수는 하나의 작업 키로 직렬화한다. 설치 커밋 전 검사와 이력 읽기는 트랜잭션 잠금 획득 뒤 새 스냅숏으로 한다. 역할은 클러스터 단위로 공유되고 PostgreSQL advisory lock은 DB 단위이므로, 같은 클러스터의 다른 DB에서 같은 역할 집합을 관리하는 작업은 외부 승인 절차에서도 하나씩 실행한다. 동일 실행 요청의 두 번째 세션은 같은 승인 대상·계획과 완료 이력을 확인한 경우에만 무변경 성공이다. [PostgreSQL 17 pg_locks](https://www.postgresql.org/docs/17/view-pg-locks.html)
3. **커밋과 회수.** DDL·최종 객체 소유권·카탈로그 대조와 최초 이력 한 행을 같은 트랜잭션에 넣는다. 이력에는 버전·소스 해시·카탈로그 해시·대상과 역할 계획 식별 해시·최초 적용 시각만 고정한다. B에서 설치 DB 트랜잭션이 완료돼도 임시 전환 간선 회수, 설치 세션 종료 및 독립 읽기 검증까지 게시 런타임 활성화를 보류한다. 최종 카탈로그 해시는 영속 권한 상태를 기준으로 정의한다. 임시 간선은 별도 검사에서 정확한 허용 집합과 최종 0건을 확인한다. 외부 관리 단계의 회수 확인을 위해 원래 설치 이력 행을 덮어쓰지 않는다.
4. **실패·재실행.** 커밋 전 실패는 해당 DDL·이력 전체를 롤백한다. B의 이전 관리 단계에서 만들어진 역할은 승인된 준비 상태로 남으며 임시 접근은 지정 관리자가 회수한다. 커밋 응답 유실 시 새 읽기 세션에서 준비 상태·완료/회수 대기·최종 완료·부분 오류를 판정하기 전에는 다시 실행하지 않는다. 회수 후 같은 요청은 검증 계정의 읽기 결과로 종결하고 설치 권한을 다시 부여하지 않는다. 기존 완료의 해시와 시각을 보존한다. 실제 복원으로 OID가 달라진 경우에는 사전 계획을 새로 승인하고 별도 복원 검증을 진행한다.
5. **독립 읽기.** 승인 대상과 실제 로그인·TLS·DB/클러스터를 확인한 뒤 `REPEATABLE READ READ ONLY`에서 예상 카탈로그·이력과 현재 유효 역할·ACL을 비교한다. 결과는 검증 버전·일치 여부·안전한 오류 코드로 기록한다. 임시 권한이 남은 상태나 이력 불일치는 게시 런타임 개방 조건을 충족하지 못한다. 검증 계정은 요청 원장·승인 행과 실제 데이터에 접근할 필요가 없다.

## 관리형 연결에 남은 결정

Master는 먼저 B의 고정 패키지·준비 상태 명세·읽기 검증 경로를 소유 PG17에서 검증할 담당을 배정한다. A는 승인된 관리 실행 경로가 존재할 때 별도로 선택할 수 있다. 관리형에서 별도 직접 TLS 대상, 실제 역할 발급 및 정확한 소유권·임시 권한 회수, 클러스터 식별자 읽기, 독립 검증 로그인, 복원 권한과 경로는 아직 확인되지 않았다. 시험 통과와 실제 관리형 적용 결정은 별도로 기록한다. [스테이징 준비안](T337-ADMIN-PUBLICATION-STAGING-READINESS.md)

> T340에서는 B안을 첫 소유 PG17 검증 후보로 제안하고 역할 OID·권한 준비, 설치·권한 회수, 이력의 독립 읽기와 실패 복구를 구분했습니다. 관리형 지원과 스테이징 개방은 아직 미확정입니다. 기존 게시 v1과 기반 이관에는 변경을 적용하지 않았습니다.
