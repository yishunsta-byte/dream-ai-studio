# T252 공개 승인 목록의 운영 공급원 설계

T251 구현 `dda8096`과 독립 검수 `d097c46` 기준으로 저장소의 코드와 계약을 대조했다. **기존 Postgres에 공개 승인 전용 테이블 하나를 추가하고, 기존 Storage를 별도 비공개 배포용 버킷으로 재사용**하는 경로를 제안한다. 익명 홈은 승인 목록 전용 서버 읽기만 사용한다. 공개 주소의 파일 요청마다 같은 승인 상태를 확인하면 목록과 파일을 한 번의 철회 커밋으로 닫을 수 있다.

## 재사용할 계약

| 코드 | 현재 계약과 설계에 쓰는 부분 |
|---|---|
| `lib/db/postgres/0001_schema.sql`, `0003_rls.sql`, `lib/services/postgres/project-reads.ts` | 프로젝트·렌더·내보내기·자료·설정은 소유자 범위다. 인증된 사용자 UUID와 트랜잭션 단위 actor, 기존 소유권 관계를 승인 후보 검증에 재사용한다. `dream.settings`도 owner/key 구조라 익명 홈의 승인 목록 공급원으로 쓰려면 별도 권한·조회 계약이 필요하다. |
| `lib/services/renders.ts`, `app/api/assets/[id]/route.ts`, `lib/storage/supabase/{config,object-key,media}.ts` | 완료 렌더의 상태·경로·SHA·크기, 미디어 형식 검사와 비공개 파일 경계를 재사용한다. 원본 다운로드는 보호 경로다. SQLite·PC 파일은 현행 로컬 경로에 속하며 운영 홈에는 연결하지 않는다. |

| `lib/public-showcase/{published-works,showcase-feed}.ts`, `app/(public)/page.tsx` | T249는 신뢰된 승인 원자료를 공개 DTO로 변환한다. T251은 지금 빈 명시 목록을 읽고 예시 6개를 제공한다. 운영 연결점은 홈 서버 호출 하나와 공급원 상태 처리다. 기존 공개 카드와 변환 규칙을 재사용한다. |

렌더·내보내기의 `succeeded`는 산출물 완료를 뜻한다. 업로드 상태의 `publication_json`은 저장 객체 등록 절차의 기록이다. 두 곳 모두 쇼케이스 공개 승인·철회 계약을 담고 있지 않다. 배포에 묶인 JSON이나 정적 파일은 시연에 쓸 수 있지만, 긴급 철회 시 배포와 이전 주소의 접근 제어를 함께 해결해야 한다. 전용 승인 기록은 기존 Postgres 인프라를 쓰면서 프로젝트·업로드 테이블과 RLS를 그대로 유지하는 선택이다. 현재 계획상 관리형 DB와 Storage 사용 가능 여부는 별도 확인이 필요한 상태다.

## 저장과 승인

후속 구현에서 예를 들어 `dream.showcase_publications` 한 테이블을 추가한다. 세대별 기록을 보존하고 같은 공개 slug에 활성 세대가 최대 하나라는 제약을 둔다. 최소 필드는 공개 slug와 세대, 승인/철회 시각과 서버가 확인한 행위자 UUID, 권리 확인과 근거 참조, 소유 범위에서 검증한 원본 종류·ID·리비전·해시, 공개 표시 스냅샷, 배포용 복제본의 슬롯·객체 키·버전 또는 해시·MIME·크기·이미지 가로/세로다. 준비 중에는 비활성 상태를 유지하며, 철회된 세대와 파일 주소를 재활성화하지 않는다. 표시 필드·파일·권리 범위가 바뀌면 새 세대에 다시 승인한다.

1. 소유자 또는 권한을 가진 권리자가 공개 대상과 범위를 확인한다. 첫 버전의 승인·철회 실행자는 서버 설정에 별도 등록한 발행 담당 UUID다. 기존 인증이 반환한 `verified.userId`로만 대조하고, 인증 불가·일반 계정·로컬 인증 해제 상태에서는 쓰기를 닫는다. 상태 변경은 관리 화면에서 같은 출처의 인증된 POST 또는 기존 인증 방식에 맞춘 서버 액션으로만 받는다. CSRF 방어와 엄격한 입력 검사 후 작업한다. 승인자·시각·권리 상태는 서버가 확인하고 기록한다. 권리 철회 요청은 권한 있는 담당자가 처리하며, 정보가 부족하면 공개를 보류한다.
2. 최초 범위는 **완성된 이미지 1건**을 권장한다. 서버가 소유 관계와 대상 리비전, 완료 상태, 원본 해시·크기, MIME 및 이미지의 실제 디코딩 결과를 확인한다. 배포용 이미지는 메타데이터를 제거한 별도 파일로 준비한다. 영상으로 확대할 경우 성공하고 늦은 취소가 없었던 검증된 렌더 또는 파일별 검증이 끝난 내보내기만 받는다. 내보내기 성공 행에 연결된 번들 전체를 배포용 미디어로 취급하지 않는다. 오디오는 지원되는 검증 경로를 확보한 뒤 추가한다.
3. 특정 파일·표시문구·권리 범위에 승인 결정을 묶는다. 별도 비공개 배포 버킷에 불변 복제본을 준비하고 생성된 파일의 검증 결과를 기록한 후, 트랜잭션에서 예상 세대·후보 리비전과 활성 상태를 대조해 승인한다. 실패한 사본은 비공개로 남으며 정리 대상으로 기록한다. 같은 요청 재시도, 동시 승인·철회, 철회 후 도착한 이전 작업은 예상 세대와 유일 제약으로 제어한다. 구현은 기존 프로젝트 인증과 데이터 접근을 재사용하되 임의 소유자 선택이나 `dream_worker`의 교차 소유자 권한을 홈에 넘기지 않는다.

## 읽기와 파일 주소

- 승인 쓰기와 분리된 최소 권한으로 공개 목록을 조회한다. 전용 읽기 자격은 활성 승인 행의 공개용 투영만 볼 수 있게 제한한다. 작업실 테이블과 승인자·권리 증빙·원본 식별자는 이 자격에 노출하지 않는다. 브라우저·Supabase anon에는 테이블을 직접 개방하지 않는다. 활성 조건은 승인 완료·권리 확인·철회 없음·복제본 준비 완료다. 승인 최신순과 slug 오름차순으로 제한된 결과(기본 24)를 읽는다. SQL의 slug 정렬과 T249의 비교 순서를 일치시키고, 24번째 동률 경계를 시험한다.
- 서버 전용 `loadPublishedRecords`가 `{id, publication, artifact, display}` plain object를 만든다. 공개 slug를 `id`로, 서버 승인 UTC 시각을 T249 형식으로 넘긴다. 완료된 복제본으로부터 `artifact.state: "complete"`와 선택적 `media`를 채운다. `display`에는 제목·부제·표시용 제작자명·종류·장르·형식·설명 및 이미지 주소와 규격만 넣는다. URL은 검증된 slug/세대/슬롯에서 서버가 만들고 최초 정책은 같은 출처로 제한한다. T249 뒤에 `ShowcaseWork[]`만 클라이언트에 전달한다.
- `/media/public/<slug>/<generation>/<slot>.<ext>`는 정적 자산 폴더 대신 서버 파일 경로로 구현한다. 확정된 슬롯과 현재 활성 세대만 좁게 조회하고, 그 결과의 배포용 객체만 읽는다. 요청에 들어온 문자열을 저장 키나 업스트림 URL로 사용하지 않는다. 서명 URL 리다이렉트 없이 바이트를 제공한다. 기존 프로젝트/자료 API, 원본 버킷, 계정 폴더·키 및 서비스 자격은 공개하지 않는다. 허용 형식의 응답만 보내고 HEAD와 GET에 같은 승인 검사를 적용한다. 영상·음악을 추가할 때는 Range에도 같은 검사를 적용하고 제한된 스트리밍과 206/416 계약을 검증한다.

## 예시 전환과 철회 시점

운영 어댑터는 `ready(records)`, `unavailable(code)`를 구분한다. 예시 전용 설정은 명시적으로 선택한다. 정상 조회 0건은 예시 6개, 1건 이상 정상 승인 작품이면 그 작품만 보여준다. 철회된 행은 정상 조회에서 제외되므로 마지막 작품 철회 후에는 예시가 돌아온다. 조회 실패·타임아웃·권한 또는 설정 실패는 별도의 일시 이용 불가 UI를 표시한다. 활성 행에 변환 불가·중복·계약 불일치가 있으면 첫 버전은 목록 응답을 실패로 분류하고 공개 카드를 내보내기 전에 닫는다. 기존 T251 합성 목록의 항목별 제외 동작은 유지하되 운영 로더의 성공 분기 앞에서 이 이상 상태를 구별한다. 파일 부재는 미디어 경로에서도 별도 장애로 기록한다. 원문 대신 분류 코드와 개수만 서버 진단에 남긴다. 장애 UI는 기존 쇼케이스에 가짜 빈 배열을 전달하는 대신 공개 홈 서버 분기에서 렌더하고, 로그인 링크는 유지한다.

첫 버전은 홈 HTML/RSC, 목록 조회, 미디어 응답의 공유 캐시와 stale fallback을 사용하지 않는 구성을 요구한다. 동적 렌더와 서버 데이터 무캐시를 설정하고 최종 프록시·CDN·브라우저 응답 정책도 확인한다. 공개 이미지가 별도 최적화 캐시를 경유하는 경우 해당 경로는 직접 제공하도록 구성하고, 홈의 클라이언트 사전 로드와 이전 화면 재사용도 검증한다. 철회는 승인 행을 비활성화하는 트랜잭션 커밋으로 기록한다. **커밋 후 시작된 새 목록 읽기와 새 파일 요청**은 권위 저장소에서 철회를 조회해 목록에서 제외하고 이전 세대 주소에 404를 반환한다. 장애 시 이전 사본으로 대체하지 않는다. 이미 로드·저장되었거나 커밋 전에 허가되어 전송 중이던 바이트는 회수 범위 밖이다. 복제본 삭제는 철회 후 재시도 가능한 정리로 분리한다. 과거에 공유 캐시를 허용한 주소를 도입한다면 그때는 경로별 제거와 실제 전파 확인이 별도로 필요하다.

## 구현 순서와 완료 기준

1. 별도 승인된 후속 작업에서 작은 저장 계약과 최소 권한 읽기·쓰기를 합성 Postgres에 붙인다. 소유자 교차 접근, 비인가/CSRF/로컬 모드, DB 자격의 권한 제한, 완료·해시·권리 불일치, 준비 실패, 재시도·동시 승인/철회 및 오래된 세대의 쓰기 실패를 검증한다. 관리형 연결과 저장소 설정은 해당 작업에서 확인한다.
2. 서버 공급원과 홈을 연결한다. 합성 테스트로 빈 목록·마지막 철회·정상 한 건·정렬/한도·장애·잘못된 활성 행을 검증한다. 실제 홈 HTML과 RSC에서 예시와 승인 작품이 섞이지 않고, 장애가 빈 목록으로 표시되지 않으며, 비공개 필드가 전달되지 않아야 한다. 기존 T249/T251 테스트도 유지한다.
3. 격리된 저장소 대역에서 익명 미디어 요청을 검증한다. 준비/철회/이전 세대는 404, 활성 허용 슬롯은 예상 MIME·바이트, 저장 장애는 안전한 오류다. 동일 URL에 승인 전·후·철회 직후 순서로 접근해 다음 새 요청의 결과를 확인한다. 배포 전 검증 환경에서 홈·RSC·직접 파일 URL과 캐시 헤더, 이미지 최적화 우회, 새로고침·재탐색 결과를 점검한다.
4. 첫 콘텐츠 등록 때 필요한 입력은 **명시적 공개 승인**, 소유 관계와 완성 산출물의 종류·ID·리비전·SHA, 권리자의 허락과 공개 범위·만료/철회 조건, 승인 담당자 지정, 공개 slug·제목·부제·제작자 표시명·종류·장르·형식·설명, 승인할 배포용 이미지와 허용 크기다. 영상·음악을 선택하면 별도 재생 파일 및 포스터와 지원 형식 확인도 필요하다. 승인자가 공개 문구와 배포용 사본을 함께 확인한 뒤 정식 등록 범위를 승인한다.

이번 산출물은 소스와 계약을 대조한 설계다. 제품·SQL 구현과 합성 검증은 후속 완료 기준이며 실제 자산·계정·운영 DB 조회, 공개 및 배포는 수행하지 않았다.

## Master 전달문

T252 설계 반환. 기존 소유권·서버 인증·완성 검증을 재사용하고 Postgres 승인 전용 테이블 하나와 별도 비공개 배포용 Storage를 제안했다. 홈은 T249/T251에 서버 승인 기록만 전달하고, 공개 파일 경로는 활성 세대를 요청마다 확인한다. 정상 빈 목록·승인 작품·장애를 구분하고, 철회 커밋 후 새 목록·파일 요청에 반영하는 합성 검증과 첫 이미지 등록 입력을 정의했다.
