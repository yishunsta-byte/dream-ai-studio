- `DREAM_PROJECT_READ_BACKEND=supabase-https`를 명시한 경우에 신규 읽기를 선택했다. 기본·SQLite·Postgres·비활성 선택은 기존 읽기 경로를 사용했다. 기존 POST 프로젝트 생성의 인증과 생성 호출은 유지됐다.
- 목록·상세 GET은 실제 요청의 취소 신호를 `route`로 전달했다. 상세 파라미터는 인증이 끝난 뒤 지연 평가했다. HTTPS 설정 누락·불일치에서는 다른 백엔드로 우회하거나 파라미터를 평가하지 않고 503 `no-store`로 닫혔다. 클라우드 개인 화면은 `render`와 기존 로그인·404·조회 불가 계약을 사용했다.
- 원본 proxy 구성의 실제 로컬 HTTP에서 만료 세션을 갱신한 `Set-Cookie`를 받고 다음 요청에 재사용했다. 새 쿠키로 다시 요청했을 때 추가 갱신은 없었다. 상세 404와 `no-store`, 개인 목록 렌더링 및 토큰 비노출, 익명 API 401과 상류 호출 0건을 확인했다.
- 격리 시험 사본에서만 proxy를 제외한 구성도 실제 GET 라우트가 보낸 갱신 `Set-Cookie`와 다음 요청의 재사용을 확인했다. 두 구성은 모두 소유 루프백 Next 개발 서버와 합성 Supabase 상류를 사용했다.
