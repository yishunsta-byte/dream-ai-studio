# T312-R 발급 원장·현재 스토리지 증거 통합 독립 재현

기준 `20a7bef` · Master 인계 `msg_c1cbbdf65b4c` · Codex(Tester)

**판정은 소유 루프백 PostgreSQL 17.12의 통합 시험 통과.** 임시 고정 사본에서 원본 실행기를 두 번 실행했다. PG 바이너리 및 고정 SQL1–4·T281·T307·T310·T311 검사와 실행기 ESLint, 고정 변경의 `git diff --check`를 통과했다.

| 검증 | 결과 |
| --- | --- |
| 정책 교체와 동일 요청 경합 | 갱신을 실제 `COMMIT` 내부에 정지시키고 별도 연결에서 예약 및 이전 포인터만 보임을 확인했다. 짧은 시도는 `55P03` 후 롤백했고, 같은 키 요청 및 정책 교체가 원래 발급을 기다렸다. 시험 호출자에 원래 응답을 전달하지 않은 뒤 다른 연결에서 원장과 포인터가 리비전 2에 한 번만 확정된 것을 확인했다. 성공 재조회는 쓰기 및 정책 교체 뒤 예전 자료의 가시성을 복구하지 않았다. |
| 재검증 성공·실패와 동일 요청 경합 | 재검증은 객체 잠금으로 발급을 막았고, 같은 키의 다음 호출은 처음 요청을 기다렸다. 재검증 성공 뒤에는 현재 검증 ID와 세대가 바뀌었다. 실패 뒤에는 기존 검증 포인터가 남았으나 객체 세대가 전진하고 상태가 철회됐다. 두 경우 모두 이전 증거로 실행한 두 요청이 원장·포인터를 변경하지 못했다. 실패 상태에서도 명시 폐기가 가능했다. |
| 실제 COMMIT 취소와 원자성 | 발급 COMMIT에서 `57014`와 트랜잭션 종료를 확인했다. 원장과 포인터가 함께 이전 상태로 돌아갔다. 같은 요청의 한 번의 재처리로 두 상태와 조회가 함께 복구됐다. 별도 폐기 COMMIT을 멈췄을 때도 이전 원장·포인터·조회가 유지됐고, 커밋 후 SQL4 증거가 여전히 현재여도 자료 증거는 숨겨졌다. |
| 갱신과 폐기 뒤 지연 발급 | 같은 검증 ID를 사용한 갱신이 거절됐다. 폐기 전 리비전에 예약된 요청과 새 키로 폐기 당시 검증 기록을 사용한 요청도 거절됐다. 폐기 시점보다 높은 스토리지 세대의 새 검증 ID를 발급받은 후에만 자료가 다시 조회됐다. |
| 소유자 경계·제한 역할·정리 | A/B 목록과 단건, 타 소유자의 발급 및 원장 조회, 상대 요청 키 재사용을 확인했다. A 재검증·폐기는 B의 정상 포인터를 변경하지 않았다. 원장 직접 수정, 보호 역할 전환, 이전 시험용 발급 호출, 읽기 역할의 통합 발급 호출은 거절됐다. 두 실행 모두 열린 트랜잭션, 발급·읽기 연결, PID 파일·리스너·임시 클러스터를 정리했다. 별도 호스트 조회에서도 소유 PG 프로세스와 T312 임시 클러스터가 0개였다. |

응답 미전달은 드라이버가 COMMIT을 완료했지만 시험 호출자에게 결과가 전달되지 않은 모델이다. 실제 HTTP·네트워크 전송 유실, 외부 Storage 바이트·버전, GC 및 삭제 경합, 플랫폼 복원, 운영 역할 프로비저닝은 후속 범위다. 특히 이 시험의 실패 상태 폐기는 SQL4 객체와 상태 행이 남아 있는 경우다. GC 후 관련 행이 없어진 상태의 폐기·정리는 별도 입증이 필요하다. 운영 DB와 배포를 사용하지 않았다.
