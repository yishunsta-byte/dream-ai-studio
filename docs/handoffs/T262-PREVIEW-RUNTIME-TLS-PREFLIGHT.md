# T262 보호 Preview 런타임의 비공개 TLS 사전점검 설계

2026-11-18 KST · Codes(Backend) · 설계 검토용

기준 `e631908d1a855ee6f213d8d7b499c4b63ff00003`, 배정 `msg_5027f15d0381`, 수락 `msg_9103b6d2b4ca`. [T261-F1-R 독립 검토](T261-F1-R-MANAGED-PG17-STAGING-CHECKLIST-REVIEW.md)의 실행 수단 공백을 다룬다.

**판정. 기존 보호 Preview의 `/admin`에 시험 배포 전용 Server Action을 한시적으로 연결하는 안이 저장소 기준 최소 변경이다.** 승인된 비공개 서버 호출 수단이 같은 Preview Node 런타임에서 이미 제공된다면 동일 점검 함수를 그 수단에서 부르고 UI 추가를 생략할 수 있다. 현재 기록에는 그런 실행 수단, 배포 식별 정보의 런타임 제공 여부, 배포 전체에서 공유되는 일회성 승인 저장소가 확인되지 않았다. 승인된 별도 Supabase–보호 Preview 매핑과 실행 수단이 확정될 때까지 읽기 opt-in은 닫힌다.

## 호출과 배포 바인딩

1. **Master와 Front가 시험 배포를 특정한다.** 승인 기록은 보호된 Preview 배포 ID·정확한 소스 SHA·Node 런타임·리전·정확한 보호 HTTPS origin·승인된 Supabase 시험 ref와 DB profile을 한 쌍으로 묶는다. 배포 담당이 플랫폼의 배포 원장과 실제 런타임에서 제공되는 신뢰 가능한 서버 측 식별 정보를 대조한다. 현재 코드에는 배포 ID/SHA의 증명 경로가 없다. 이 값이 제공되는지와 결합 방법을 먼저 확인하며, 요청의 host나 자유 입력을 단독 증거로 쓰지 않는다.
2. **Action은 부작용 전에 닫힌 조건을 검사한다.** 승인된 보호 Preview, Node, 배포 ID/SHA·리전·origin 일치, 짧은 점검 시간 범위, 검증된 시험 담당자 세션이 모두 맞아야 한다. 최초 점검은 opt-in이 꺼져 있어야 한다. 아래의 배포 전환 재확인만 최초 통과 영수증과 별도 승인에 묶인 운영자 전용 절차로 허용한다. 일반 관리자 화면 조회·prefetch·렌더는 접속을 일으키지 않는다. 호출은 승인된 Preview origin의 명시적인 POST로 제한하며, 클라이언트에서 대상 주소·SQL·role·실행 옵션을 받지 않는다. 일반 허용 계정에는 호출 UI와 진단 정보가 제공되지 않는다.
3. **서버에서 DB 대상과 신뢰 설정을 비교한다.** 승인에 묶인 Auth ref와 접속 프로필, 제공 DNS/포트, DB, Session 라우팅 login과 실제 SQL role의 정확한 조합을 제한 API `DATABASE_URL`과 대조한다. 앱이 쓰는 TLS 신뢰 모드 및 명시 CA를 쓸 때의 승인 CA 지문은 별도 필드로 묶는다. DSN·암호·토큰·내부 식별자는 반환하지 않고, 공개해도 되는 대상 해시와 일치 여부만 결과에 포함한다. 대상 hash에는 secret이나 migration approval을 재사용하지 않는다. 기본 신뢰 설정으로 실패하면 읽기는 닫힌 상태이며, 명시 CA가 필요할 경우 실제 앱 풀에도 동일하게 적용되는 좁은 변경을 별도 검토한다.
4. **일회성 권한을 풀 접근 전에 소비한다.** 기존에 승인된 비공개 실행 수단이나 원자적 조정 저장소에서 제한된 run ID를 미사용→사용됨으로 단 한 번 변경한다. run ID의 권한은 배포 ID·SHA, 시험 대상, 담당자와 만료에 귀속한다. 동시 요청과 재전송은 DB checkout 전에 거절한다. 실패해도 같은 ID를 되살리지 않고, 이미 사용된 영수증과 실제 상태를 대조해 필요할 때만 새 배정을 받는다. 모듈 변수나 프로세스 단위 mutex는 서버리스 여러 인스턴스의 중복을 막지 못한다. 배포 전체의 단일 소비를 확인할 수단이 없으면 실행 수단 미확인으로 남긴다. DB 자체에 진단 상태를 쓰거나 새 유료 저장소를 전제로 하지 않는다.

## 같은 제한 연결의 TLS 증거

1. T261의 읽기 스위치는 유지한다. Action 내부의 서버 전용 함수가 위 검사를 통과한 후에만 실제 `getProcessProjectReadPool`에서 client 한 개를 빌린다. 별도 migration/worker 자격, 독립 테스트 풀, 사전 TLS 소켓으로 대체하지 않는다. 기존 공유 연결 설정의 `rejectUnauthorized: true`, 호스트 검증과 startup 옵션을 보존한다. [공유 연결 설정](../../lib/db/postgres/connection.ts)
2. **클라이언트 구간.** 설치된 pg 8.23.1 소스는 DNS host를 TLS `servername`으로 지정하고 기본 Node 검증을 사용한다. 같은 checked-out client의 실제 TLS 소켓에서 TLS 연결, `authorized === true`와 예상 DNS 이름에 대한 피어 인증서 검증을 확인한다. 필요하면 Node의 `tls.checkServerIdentity`로 같은 소켓의 피어와 고정 호스트를 대조한다. 런타임 소켓은 pg 내부 형태에 의존하므로 버전에 묶인 좁은 어댑터와 호환 시험이 필요하다. 검사 인터페이스가 없거나 결과가 모호하면 증거 없음으로 중단한다. 소켓·인증서 본문·driver 오류 원문은 출력하지 않는다.
3. **DB 구간.** 동일 client에서 `BEGIN READ ONLY`을 열고 현재 DB·port·PG17·`session_user=current_user`와 제한 로그인 역할의 일치를 boolean으로 확인한다. 같은 트랜잭션에서 `SELECT ssl FROM pg_catalog.pg_stat_ssl WHERE pid = pg_backend_pid()`를 실행한다. 정확히 한 행의 `ssl=true`만 통과이며 false·NULL·0행·복수 행을 구분한다. Session pooler에서 앞 관측은 client→pooler, 이 관측은 pooler→DB에 해당한다. Direct도 동일 client의 두 보고치를 남긴다. 제품 행, Auth 사용자 테이블, role 전환, actor 설정, DDL/DML은 이 진단에 필요 없다.
4. **정리와 실패.** 짧은 실행 제한 안에서 `ROLLBACK`과 반환을 확인한다. SQL 또는 롤백·연결 상태가 불확실하면 대여 client만 폐기한다. 프로세스 공유 풀을 진단 코드가 닫으면 같은 런타임의 이후 사용까지 막히므로, 손상 client 정리와 시험 런타임 회수를 구분한다. TLS·대상·역할·타임아웃·증거 저장 실패 중 하나라도 있으면 읽기 opt-in을 닫아 둔다. 허용된 열거 오류만 반환하고 자동 재시도나 인증서 검사 완화는 하지 않는다.

## 영수증, 제거와 다음 배정

- **영수증.** 승인 run ID, 관측 UTC 시각, Preview 배포 ID/소스 SHA/리전, 시험 대상 해시, 역할·startup 일치 여부, 클라이언트 TLS/호스트 확인 결과, DB TLS 행 수와 결과, 반환·폐기 상태만 지정 접근 범위에 기록한다. 화면에는 완료 여부나 영수증 참조만 남긴다. 원시 DSN, 권한 토큰, 이메일·UUID, 쿠키, 인증서, SQL 결과 원문은 사용자 응답·브라우저 로그·공개 로그에 보내지 않는다.
- **배포가 바뀌는 경우.** 첫 TLS 판정 전 opt-in을 닫아 둔다. opt-in 적용이 새 Preview ID를 만들면 이전 영수증의 범위를 명시하고 새 Preview는 지정 운영자에게만 접근을 남긴 채 같은 바인딩과 TLS를 다시 확인한다. 이 재확인은 운영자 전용 전환 절차로 별도 승인하고, 처음의 opt-in 전 통과 영수증과 새 배포의 run ID를 함께 요구한다. 새 후보의 증거가 확인되기 전에는 A/B 접근을 열지 않는다.
- **제거.** 관측 직후 권한을 소비 상태로 유지하고 만료·접근을 회수해 해당 배포의 Action을 비활성 상태로 둔다. 한시 UI·Action·점검 설정의 물리적 제거는 같은 배포를 사용하는 A/B 검증을 끝낸 뒤 진행한다. 새 배포만 만들어도 이전 Preview 주소가 남을 수 있으므로 이전 배포의 보호 범위와 호출 거절을 따로 확인한다. 제거 후 새 배포를 계속 검증 대상으로 삼을 경우 승인된 비공개 수단으로 그 배포를 재대조한다. 그 수단이 없으면 새 배포의 판정은 미확인으로 남긴다. 결과 영수증만 보존한다.
- **최소 후속 변경 범위.** 실행 수단 확인 후 서버 전용 함수 하나와 필요할 때 보호 `/admin`의 한시 Action 연결, 재사용 가능한 DSN 검증 변경만 제안한다. 별도 공개 라우트, 새 권한 체계, migration 변경 없이 진행할 수 있는지 구현 배정에서 확인한다. 후속 시험은 잘못된 배포/대상·일반 사용자·동시 재전송에서 checkout 0회, 같은 연결의 TLS 및 거부 분기, 롤백/폐기, 결과 비밀 미출력과 제거 후 재호출 거절을 확인한다.

**현재 필요한 사용자 조치는 없다.** Master가 승인된 시험 매핑과 비공개 일회성 실행 수단을 먼저 대조한다. 기존 승인으로 시험 환경이나 비공개 실행 권한을 확보할 수 없을 때만 선택이 필요한 부분을 사용자에게 올린다. 기존 운영 `DEC-SSL-01`은 대기 상태다. 이번 배정은 문서만 작성했고, 외부 연결·설정 변경·배포·제품 변경은 수행하지 않았다.

Master 전달문 — T262 설계 완료. 보호 Preview의 기존 `/admin`에 운영자 전용 한시 Action을 붙이거나 이미 승인된 동일 런타임 비공개 호출을 재사용하는 최소안을 정리했습니다. 배포/대상 검증과 공유 일회성 소비가 먼저이며, 실제 제한 API 풀의 같은 client에서 인증서·호스트와 같은 트랜잭션의 자체 `pg_stat_ssl`을 확인합니다. 매핑과 실행 수단은 미확인이고 읽기 opt-in과 DEC-SSL-01 상태를 유지합니다.
