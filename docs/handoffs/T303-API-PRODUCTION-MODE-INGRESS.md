## 원인 (Next 16.4.6 소스로 확인)

- 모든 경로에 걸리는 `proxy`(matcher가 `/api` 포함)가 있으면, Next 서버는 POST 본문을 복제해 proxy에 넘겨요(`cloneBodyStream`).
- 그 뒤 `finally`에서 `await requestData.body.finalize()`로 원래 요청 본문이 끝날 때(`end`)까지 기다려요(`next/dist/server/next-server.js`, `body-streams.js`).
  - 그래서 proxy 결과(통과·거절)와 상관없이, 본문이 끝나기 전에는 라우트 진입도 proxy 응답 전송도 없어요.
- 복제 상한은 `experimental.proxyClientMaxBodySize`(기본 10MB)예요.
  - 넘으면 경고를 남기고 앞 10MB만 넘겨요. 앱의 1KB 상한보다 커서 앱 경계가 413으로 먼저 막아요.
  - 이 저장소 `next.config.ts`는 이 값을 바꾸지 않아요.
- 본문 수신 기한은 Next에 없고, Node HTTP 서버 기본값이 적용돼요.
  - `requestTimeout` 300000ms, `headersTimeout` 60000ms(이 Node에서 확인).
  - 실측은 연결 점검 주기까지 더해져 325.5초 뒤 408이었어요.
- 앱 기한(분석 3초, 관리자 413 즉시 반환)은 라우트에 진입한 뒤에만 작동해요. 본문 수신 대기 중에는 작동하지 않아요.

## 실패 경계 정리

- 본문을 끝내지 않거나 중간에 끊긴 요청은 앱에 들어오지 않아요. 그래서 인증 판정·저장소·분석 호출이 모두 0회예요(데이터 안전).
- 대가로 연결은 최대 약 5분 열려 있을 수 있어요(이 로컬 호스트 기준). 1KB 상한·3초 기한은 본문이 다 온 뒤에야 적용돼요.
- 본문이 끝난 요청은 두 경로 모두 인증(머리글 쿠키) → 출처·형식 → 크기 순서로 수 ms 안에 판정돼요.

## 개발 모드 관측과의 구분

- T296-R은 개발 모드(dev/webpack)에서 같은 현상을 봤어요: 미완료 업로드에 핸들러 진입 없음, 완료 뒤 응답.
- T297-F1은 production 빌드(`next start`)의 관리자 경로에서 봤어요.
- 이번 T303은 production mode에서 두 경로 모두, 그리고 proxy 거절 경우와 Node 기한(408)까지 실측했어요.
- 직접 핸들러 시험(vitest)의 즉시 413·출처 판정은 그대로 유효해요(T297-F1: 47/47, T296 계열 회귀 통과). 다만 그 시험은 Next 수신 단계를 거치지 않아요.

## 실제 운영 전 확인 항목 (로컬에서 확인 불가)

1. 배포 호스트(Vercel 등)의 요청 본문 최대 크기, 사전 버퍼링 여부, 본문 수신 기한·함수 실행 시간 제한, 클라이언트 연결 종료가 함수까지 전달되는지.
2. 호스트 앞단에서 미완료 업로드를 얼마 동안 붙잡는지. 로컬 Node의 5분과 다를 수 있어요.
3. `proxyClientMaxBodySize`를 앱 상한에 맞춰 낮출지, proxy matcher에서 두 POST의 본문 대기를 피할지. 둘 다 공용 proxy·설정 변경이라 별도 작업과 승인이 필요해요.
4. 실제 Supabase 세션으로 proxy와 라우트가 각각 한 번씩 getUser를 부르는 비용과 실패 시 응답(이번에는 합성 인증).
5. 실제 호스트의 `Host`·`x-forwarded-proto`가 T297-F1 현재 출처 판정과 T296 출처 비교(`request.url` 프로토콜)에 맞게 들어오는지.
