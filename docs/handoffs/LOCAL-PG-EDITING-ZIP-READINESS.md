# 로컬 PG 재편집 ZIP 연결 범위

기준 `f03a881`. [개발 기준 13장](../PLAN.md#13-내보내기-zip)의 재편집 묶음을 대상으로 현재 PG 승인·원본 경계와 SQLite ZIP을 대조했다.

## 그대로 사용할 부분

| 구성 | 확인 결과 |
| --- | --- |
| ZIP 작성과 검증 | `lib/export/zip.ts`의 `writeZip`은 임시 파일에 저장형 ZIP64로 쓴다. `verifyZip`은 다시 열어 선언한 파일만 있는지, 경로·크기·SHA-256·매니페스트가 일치하는지 확인한다. 누락·중복·변조 시 실패한다. 두 함수는 DB에 의존하지 않는다. |
| 매니페스트 | `lib/export/schema.ts`의 v1/v2를 그대로 쓴다. v2는 v2 타임라인과 실제 오디오 원본이 있을 때 사용하며 타임라인 ID, 오디오 역할, 샘플 여부를 기록한다. JSON에는 공개 가능한 상대 경로와 바이트 검증값을 적는다. |
| 파일 구성 | `lib/services/exports.ts`에서 합의된 장면·대본·글자·검수·권리·폰트/OFL·타임라인·오디오 목록 구조를 재사용한다. 해당 모듈의 `bundleLayout`은 SQLite 저장소를 직접 읽으므로, 먼저 DB에서 읽은 값과 순수 구성 로직의 경계를 정한다. 승인 자막은 기존 `timelineSrt`·`timelineVtt`를 같은 저장본에 적용한다. 최종 MP4는 별도 다운로드를 사용한다. |
| PG 기록 | `lib/db/postgres/0001_schema.sql`에 `dream.exports`와 공용 작업 테이블이 있다. `0002_invariants.sql`은 성공한 내보내기 행을 불변으로 두고 매니페스트의 프로젝트·내용 리비전 및 결과 키 `<owner>/<project>/<export>.zip`를 강제한다. 실제 보관 바이트와 이 키를 연결하는 로컬 PG 제품 경로가 필요하다. |

## 구현 선행조건

1. **승인 스냅샷**. 소유자·프로젝트·현재 내용 리비전·타임라인 ID/JSON SHA를 잠그고 현재 승인 기획·제작·검수를 확인한다. 승인 기획의 장면 목록, 타임라인의 선택 버전과 자산, 리비전별 검수 기록을 같은 입력으로 묶는다. PG 자막 다운로드와 렌더처럼 생성 직전과 결과 확정 직전에 현재 기준을 재검사한다.
2. **원본과 권리**. PNG는 `local-render-execute.ts`의 비공개 Storage 등록·현재 검증 영수증과 선택 버전 확인을 따른다. WAV는 `local-project-audio.ts` 및 `local-pg-wav-input.ts`에서 확인하는 프로젝트 연결·형식·크기·해시를 적용한다. 선택 장면 원본은 각 버전 경로에, 같은 WAV 원본은 묶음에 한 번 넣는다. 등록 SHA와 아카이브에서 다시 읽은 SHA, 원본 권리 메모와 타임라인 음원 권리 기록을 대조한다. 장면 등록 당시 권리 스냅샷과 현재 원본 기록 중 무엇을 표시하는지 명세하고, 작업 도중의 원본·현재 검증 취소는 결과 확정 전에 감지한다.
3. **작성과 보관**. 사용자 요청을 현재 기준에 멱등하게 묶고 스트리밍 작성·재검증·결과 등록·완료 활동을 연결한다. 시작과 완료의 체크포인트 사이에 DB 행 잠금을 오래 잡지 않는다. 기존 PG 렌더처럼 작업 실행과 다운로드를 구분하고, 최초 로컬 범위에서 원본과 완성 ZIP의 크기 한도를 정한다. 현재 PNG와 WAV 업로드는 각각 1MiB 단위이므로 실제 원본 합과 폰트·JSON을 함께 계산한다. 기존 `dream.exports.file_path` 키에 맞는 소유자 전용 보관소 및 읽기 권한을 먼저 결정한다. 성공본의 바이트와 매니페스트는 유지하고, 현재 버전 생성과 과거 성공본 재조회는 각각의 정책에 따른다.
4. **실제 풀기와 복원 확인**. 새 소유 프로젝트에 두 PNG·WAV·한글 자막을 저장하고 승인한다. 실제 ZIP을 닫고 다시 열어 매니페스트 및 전체 바이트를 검사한 뒤 새 임시 폴더에서 장면 순서·타임라인 ID/SHA·WAV SHA·폰트 라이선스·자막·권리 문구를 읽는다. 별도 애플리케이션 복원 시험은 보관 행과 ZIP을 함께 복원해 동일 SHA를 대조한다. 기존 SQLite T162의 백업 복원에서 내보내기 행과 ZIP SHA를 보존한 방식이 기준이다.

## 검증 및 착수 범위

`npm.cmd test -- tests/t158-export-manifest.test.ts tests/scene-export-info.test.ts tests/jobs.test.ts tests/p2-3-text-editor.test.ts` 74건, `npm.cmd test -- tests/bundle-zip.test.ts tests/t162-audio-bundle.test.ts tests/t166-late-source-change.test.ts` 18건, 총 **7파일·92건 통과**. 매니페스트 버전, 실제 ZIP 왕복·누락·변조 거절, 음원 원본, ZIP 생성 뒤 원본 변경 차단, SQLite 백업·복원 결과 보존을 포함한다.

첫 구현은 PG 승인 입력을 읽고 기존 형식의 파일 목록과 매니페스트를 만드는 모듈 및 실제 ZIP 검증으로 분리할 수 있다. 제품 다운로드를 열려면 작업 확정, 아카이브 보관, 소유자 조회 및 이전 버전 정책을 이어서 결정한다. 이번 조사에서 사용한 파일과 DB는 기존 회귀의 합성 로컬 자료다.

> 기존 ZIP/매니페스트 검증 92건이 통과했습니다. PG에서는 승인 타임라인과 선택된 PNG·WAV·권리 스냅샷을 고정하는 모듈부터 구현할 수 있습니다. ZIP을 실제로 풀어 파일별 SHA와 타임라인을 검사하고, 보관 행과 ZIP이 함께 복원되는지 확인하는 범위를 인계합니다.
