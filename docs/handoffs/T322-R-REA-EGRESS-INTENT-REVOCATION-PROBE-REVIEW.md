# T322-R 전송 의도와 철회 완료 독립 재현

기준 `6c793aa` · Master 인계 `msg_f5ee41b7055e` · Codex(Tester)

**판정은 소유 루프백 HTTPS·PostgreSQL 17.12의 고정 시나리오 통과. 미종결 의도를 남긴 송신자의 강제 종료 복구는 보완이 필요하다.** 고정 실행기를 수정 없이 두 번 실행했다. [실행기](../../tests/reference-analysis/t322-egress-intent-revocation.pg17.mjs)

| 검증 | 독립 재현 결과 |
| --- | --- |
| 첫 바이트 전과 보고 누락 뒤 의도 | 첫 쓰기 전 의도 커밋을 별도 DB 연결로 확인했다. 첫 쓰기·종료 시각은 비어 있었고 같은 허가의 반복은 409·0바이트였다. 두 번째 채널은 실제 TLS 클라이언트가 보호 접두부를 받았다. 시험에서 최초 송신 보고만 생략하자 원장은 `starting`과 미종결 의도를 유지했다. |
| 철회 접수 뒤 신규 작업 차단 | 같은 ID의 접수는 대기 상태, 다른 주체의 완료는 충돌이었다. 접수 전에 소비했으나 의도가 없던 제3 요청은 재개 시 409·0바이트였고 의도 행은 생기지 않았다. 접수 뒤 신규 허가와 세대 활성화가 거절됐으며 사용자 권한은 아직 변경되지 않았다. |
| 제어기 재시작·실제 종료·기록 지연 | 제어기 PID를 교체한 뒤에도 두 의도가 보존됐다. 첫 채널이 종료돼도 두 번째 때문에 기다렸다. 두 번째 TLS 연결이 닫히고 접두부만 수신한 상태에서 종료 기록을 모의 지연하자 철회 완료와 전환이 계속 보류됐다. 종료 기록 두 건은 접수 이후·완료 이전이었다. 완료 재조회에서 권한 리비전은 한 번만 전진했다. |
| 완료 후 재시도·세대 전환 | 늦은 재개와 양쪽 리스너의 이전 허가 재사용에서는 새 보호 바이트와 시작 기록이 없었다. 기존 송신자의 실제 PID 종료를 감독 역할이 기록하고 다음 세대를 열었다. 다른 주체의 새 허가는 정상 본문 한 번을 보냈고 반복은 409·0바이트였다. |
| 정리 | 두 실행 모두 제한 DB 세션·마지막 송신자의 소켓과 작업·클라이언트 요청이 0이었다. 자식 프로세스, 두 TLS 리스너, PG PID·리스너, 인증서와 임시 클러스터를 정리했다. 별도 호스트 조회에서도 소유 프로세스와 임시 디렉터리가 0개였다. ESLint와 고정 변경의 `git diff --check`가 통과했다. |

## F322-1 · 감독 격리가 미종결 전송 의도를 종결하지 않음

고정 시나리오는 두 송신 채널이 자신의 종료를 원장에 기록하고 철회 완료까지 확인한 뒤 기존 송신자를 종료한다. 반대로 송신자가 의도 행을 미종결 상태로 남긴 채 종료하면, 현재 감독 경로인 T319 격리 함수는 송신자와 **허가** 상태만 `isolated`로 갱신한다. T322 **의도**의 `terminal`과 `closed_at`은 그대로다. T322의 철회 완료는 미종결 의도가 있는 한 계속 `pending`이고, 활성화는 철회 대기 상태에서 거절된다. 이 동작은 변경분과 호출 경로를 대조해 확인했으며 별도 장애를 주입하지 않았다. [T319 격리 처리](../../tests/reference-analysis/t319-egress-durable-control.sql#L127) · [T322 완료 조건](../../tests/reference-analysis/t322-egress-intent-revocation.sql#L65) · [고정 시나리오 순서](../../tests/reference-analysis/t322-egress-intent-revocation.pg17.mjs#L564)

후속 복구 시험은 미종결 의도가 있는 송신자를 먼저 종료한다. 종료와 관련 채널의 전송 차단이 확인되면 동일 세대·송신자의 해당 허가와 의도를 원자적으로 종결하고, 철회 완료와 새 세대 활성화가 가능해지는지 확인한다. 증거가 불명확할 때는 보류를 유지한다.

TLS 수신 바이트, 소켓 종료와 프로세스 종료, PG 커밋은 실제 관측이다. 최초 송신 보고 누락 및 종료 기록 지연은 시험 제어이며 COMMIT 응답의 실제 네트워크 유실은 별도 범위다. 최종 DB 판정과 물리적 큐 삽입의 원자성, 다중 호스트·프록시 큐·운영 인증은 입증하지 않았다. 운영·빌드·배포는 수행하지 않았다.
