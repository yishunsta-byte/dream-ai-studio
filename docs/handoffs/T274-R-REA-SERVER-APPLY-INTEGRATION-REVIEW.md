# T274-R REA 서버 적용 설계 독립 검토

2026-11-19 KST · Codex(Tester) · 기준 `166a3e1` · 배정 `msg_f499351fda27`

**조건부 설계 수용.** 단일 저장소에서 확인 ID 소비·타임라인 CAS·영수증을 원자적으로 처리하는 방향은 타당하다. 로컬 합성 구현은 아래 계약을 반영해 진행할 수 있다. 실제 서버 연결은 소유권과 관리 파일의 증거 확보, 복원 시 확인 무효화, 영수증 재조회 규칙 및 통합 회귀가 선행돼야 한다. 클라우드 적용 경로는 별도 검증 대상이다. [원 설계](T274-REA-SERVER-APPLY-INTEGRATION.md)

## 설계에 반영할 경계

| 우선순위 | 정적 대조 결과 | 구현 조건 |
| --- | --- | --- |
| P1 · 완료 재전송의 판정 순서 | 적용 성공은 타임라인 ID·내용 리비전을 바꾼다. 이후 같은 확인에 대기 상태와 같은 기준 리비전·만료 검사를 하면, 응답을 잃은 성공 요청에 영수증 대신 충돌이나 만료가 반환될 수 있다. 원 설계는 완료 영수증 재생을 제안하지만 대기 확인과 영수증의 만료·판정 순서를 명시하지 않는다. | 같은 권위 저장소에서 인증·현재 영수증 조회권을 먼저 확인하고, 보존 기간 내 완료 상태는 기존 영수증만 돌려준다. 아직 대기 중인 확인에만 실행 만료·활성 분석·기준 리비전·장면 매핑을 검사한다. 이미 완료한 뒤 타임라인이 다시 변경돼도 영수증은 당시 적용 결과를 가리킨다. 응답 만료·권한 철회·자료 삭제가 영수증 조회에 미치는 효과를 명시한다. [기존 적용 CAS](../../lib/reference-analysis/project-apply.ts) |
| P1 · 백업·복원의 재생 경계 | 기존 SQLite 백업은 DB 전체를 스냅샷으로 복사한다. 복원은 작업·렌더 등 일부 상태를 취소하지만 신규 REA 확인을 아직 알지 못한다. 확인 행·프로젝트 ID·과거 리비전이 함께 복원되면, 같은 ID가 복원본에서 대기 상태로 되살아날 수 있다. | 확인을 서버가 관리하는 작업공간 또는 저장소 세대에 귀속시키고, 복원본 게시 전에 모든 대기 확인과 진행 중 REA 분석을 무효화한다. 이미 끝난 영수증을 복사할지, 복원본에 이력으로만 남길지 명시한다. 복원·복제본에 옛 ID를 전송해도 새 타임라인 쓰기가 없어야 한다. [백업](../../lib/services/backups.ts) · [복원 정규화](../../lib/services/restore.ts) |
| P1 · 자료 권한과 실제 분석 바이트 | 현재 로컬 경로는 실경로·크기·형식을 확인하지만 REA 사본에는 관측 크기만 남고, 분석기가 읽은 바이트의 SHA-256은 계산하지 않는다. SQLite의 현재 연결·아카이브 값만 재조회하면 연결 해제 후 재연결이나 복원 뒤 예전 확인을 구분하지 못할 수 있다. | 분석과 같은 관리 사본을 만들 때 실제 해시를 계산해 등록 파일과 대조하고, 완료를 기록할 때 현재 소유·파일 버전·프로젝트 연결 세대·취소 상태를 다시 확인한다. 아카이브·복원·연결 해제와 재연결·교체 등 모든 관련 쓰기 경로는 같은 DB에서 상태나 세대를 단조롭게 변경한다. DB 밖 파일 교체를 통제할 수 없는 데이터 루트는 실제 적용에 사용하지 않는다. [관리 사본](../../lib/reference-analysis/local-file.ts) · [관리 경로](../../lib/storage/paths.ts) · [아카이브](../../lib/services/library.ts) |

## 권한과 원자적 적용

- `resolveServerAuth`의 verified 사용자 ID만 인증 액터가 될 수 있다. `kind: local`에는 검증된 사용자 ID가 없고 SQLite의 프로젝트·자료·연결 행에도 사용자 소유 열이 없다. 로그인 허용과 행 ID·링크 조회는 소유권 증거가 될 수 없다. 단일 사용자 로컬 모델은 승인된 작업공간 경계를 별도 권한 모델로 정의해야 한다. 다중 사용자 SQLite라면 소유자 귀속 이관과 읽기·쓰기·아카이브 전반의 같은 권한 검증이 선행한다. [서버 인증](../../lib/auth/resolve.ts) · [SQLite 스키마](../../lib/db/schema.ts)
- 현행 타임라인 POST는 `requireApiAuth`로 legacy 사용 여부를 확인하지만 검증된 액터를 돌려주거나 변경 요청 origin을 직접 확인하지 않는다. 새 적용 경계는 서버 인증에서 얻은 액터를 전달하고, 쿠키 기반 변경 요청에 기존 `rejectCrossSite` 계열의 명시적 same-origin·JSON 검사를 붙인다. 보호 게이트를 통과하지 못한 요청에서 본문·DB·파일을 읽지 않는 회귀와 성공·오류 전부의 `no-store`를 확인한다. [타임라인 API](../../app/api/projects/%5Bid%5D/timeline/route.ts) · [API 인증](../../lib/auth/api.ts) · [출처 검사](../../lib/auth/config.ts)
- 확인 ID는 무작위 조회 키로 두고, 서버가 정규화한 계획과 소유·작업공간·프로젝트·자료·연결 세대·분석·기준 타임라인·만료에 묶는다. 클라이언트에서는 ID와 명시적 확인 의사만 받는다. 권한과 활성 상태를 읽은 같은 쓰기 트랜잭션에서 대기 상태 조건부 소비가 정확히 한 행을 바꿨는지 확인하고, 기존 타임라인·워크플로 CAS와 종결 영수증을 함께 커밋한다. 확인과 타임라인을 별도 연결에서 확정하는 방식을 피한다. 코드상 `timelineService(handle).save`는 같은 SQLite 연결의 중첩 트랜잭션을 사용한다. 기존 `WeakMap` 확인은 프로세스 간 권한 증거가 될 수 없어 영속 경로로 교체해야 한다. [타임라인 저장](../../lib/services/timeline.ts) · [현재 확인 서비스](../../lib/reference-analysis/project-apply.ts)
- `no_change`도 재전송에 같은 답을 내려면 타임라인 변경 없는 종결 결과로 저장한다. 취소·만료·충돌 후 같은 ID가 새 기준으로 다시 실행되지 않게 상태 전이를 명시한다. 트랜잭션 시작의 확인된 `busy`는 대기 상태를 유지하고, 롤백은 소비와 타임라인·영수증을 함께 되돌린다. 커밋·응답이 불확실하면 새 연결로 동일 쓰기 저장소의 영수증을 조회한다. 영수증이 없거나 읽을 수 없으면 타임라인을 확인하고 사용자 결정을 새로 받는다. 재전송은 성공을 새로 실행하는 경로가 되면 안 된다. [잠금 재검수](T273-F1-R-REA-APPLY-BUSY-BOUNDARY-REVIEW.md)
- 권한 철회·취소·삭제와 적용은 같은 저장소에서 같은 잠금 순서 또는 CAS 세대 규칙을 공유한다. 철회가 먼저 커밋되면 옛 확인과 늦은 분석 완료가 차단돼야 한다. 적용이 먼저 커밋되면 기존 타임라인 복원 계약으로 되돌린다. 영수증에는 결과 타임라인 ID·리비전·시간만 남기고, 삭제 후 보존이 필요한 최소 정보와 조회권을 정한다. 분석·확인 삭제가 미응답 성공을 대기 상태로 바꾸거나 비공개 원문을 영수증에 남기지 않게 한다.

## 통합 착수 순서

1. 로컬 권한 모델·자료 세대·백업 복원 세대와 확인·영수증 수명을 확정한다. 무권한 또는 타 저장소 요청이 DB·파일에 닿지 않는 경계부터 검증한다.
2. 격리 SQLite 두 프로세스에서 준비한 뒤 재시작해 같은 ID를 적용한다. 동일 ID 동시 요청·다른 확인의 CAS 경쟁, 마지막 로그 또는 영수증 쓰기 실패, 커밋 직후 응답 유실, 현재 타임라인 추가 변경 뒤 영수증 재조회, 락 시작·커밋 오류를 각각 분리한다. 타임라인·단계·로그·확인·영수증 행을 함께 비교한다.
3. 다른 소유자·프로젝트·자료 링크, 취소와 삭제의 양쪽 커밋 순서, 아카이브 후 복원·재연결, SQLite 백업 복원 후 옛 ID, 만료 경계와 지연 완료를 검증한다. 금지 필드와 파일·사본 정리도 확인한다. 이후 Studio가 사용자 확인과 결과에만 연결되도록 검증한다.
4. 클라우드는 로컬 결과와 독립이다. Postgres의 소유 FK와 RLS, 액터 트랜잭션은 재사용 후보다. 현재 제품 프로젝트 어댑터는 읽기 전용이고 legacy 타임라인은 클라우드에서 닫힌다. 같은 제한 역할의 타임라인·확인·영수증 쓰기, 철회 경쟁, 일관 잠금과 커밋 유실, 실제 분석 바이트 인계를 승인된 격리 환경에서 검증한 뒤 연결한다. 기존 객체 검증기는 목록 값만 반환하고 사본을 폐기하므로, 소유자 제한 사본을 분석까지 넘기는 별도 계약이 필요하다. [Postgres RLS](../../lib/db/postgres/0003_rls.sql) · [액터 트랜잭션](../../lib/db/postgres/transaction.ts) · [클라우드 읽기](../../lib/services/postgres/project-read-request.ts) · [비공개 객체 검사](../../lib/storage/supabase/reader.ts)

이번 검수는 고정 코드·설계와 이전 로컬 독립 검수 기록의 정적 대조다. 통합 시험 실행이나 실제 저장소 호출은 없었다. 공유 작업공간에는 이 보고서 한 파일을 추가했다.
