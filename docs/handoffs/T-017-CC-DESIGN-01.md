## 1. 요약

- **D-3 · 이전 백업 올려서 복원:** 백업의 마이그레이션 기록이 현재 코드 기록의 **앞부분과 한 줄도 다르지 않을 때만** 받아들인다. 남은 마이그레이션은 staging 사본에서만 적용하고, 원본 백업 파일은 끝까지 바꾸지 않는다. 더 새 버전이거나 기록이 다른 백업은 거부한다. 지금 쓰는 DB를 올릴 때는 그 전에 스냅샷을 남긴다. 호환 회귀 시험은 단계별 고정 백업(가상 데이터)으로 한다.

## 3. D-3 · 이전 백업 올려서 복원 (P2-1 진입 준비 기준)

### 3.1 판정 규칙

`B` = 백업 DB의 `__schema_migrations` (version, name, sha256) 목록, `C` = 현재 코드의 목록.

| 경우 | 조건 | 결과 | 검사 화면 문구 |
|---|---|---|---|
| 같음 | `B == C` | 지금처럼 복원 | 데이터 구조 버전 맞음 |
| 올려서 복원 | `len(B) < len(C)`이고 `B`의 모든 줄이 `C`의 같은 위치 줄과 version·name·sha256 모두 같음 | staging에서 `C[len(B)..]` 적용 후 복원 | 이전 버전(데이터 구조 {len(B)})에서 만든 백업이에요. 복원하면서 지금 구조({len(C)})로 바꿔요. 원래 백업 파일은 바꾸지 않아요. |
| 새 버전 | `len(B) > len(C)`이고 `C`가 `B`의 앞부분 | 거부 `BACKUP_TOO_NEW` | 더 새 버전의 앱에서 만든 백업이에요. 앱을 업데이트한 뒤 복원해 주세요. |
| 기록 다름 | 한 줄이라도 version·name·sha256이 다름, 번호가 비거나 겹침 | 거부 `BACKUP_SCHEMA_MISMATCH` | 백업의 데이터 구조 기록이 이 앱과 맞지 않아요. 이 백업은 복원할 수 없어요. |
| 기록 없음 | `__schema_migrations` 없음 | 거부 `BACKUP_SCHEMA_MISMATCH` | (같은 문구) |

- manifest의 `migrations` 목록과 DB 안 `__schema_migrations`가 서로 같아야 한다(지금 규칙 유지). 다르면 "기록 다름"으로 거부한다.
- 판정은 **검사하기 단계**(inspect)에서 끝낸다. 결과에 `compat: "same" | "upgrade" | "too_new" | "mismatch"`, `fromVersion`, `toVersion`을 담아 화면에 보여 준다. 거부면 "새 폴더에 복원" 버튼을 잠그고 이유를 적는다.

### 3.2 manifest

- `schemaVersion`(manifest 형식 번호)은 지원 목록 `{1}`으로 검사한다. 모르는 값은 `BACKUP_SCHEMA_MISMATCH`.
- `appVersion`은 기록용 문자열(`z.string().max(32)`)로 바꾼다. 판정에는 쓰지 않는다. 화면에는 "만든 앱 0.1.0"으로만 보여 준다.
- 나머지(해시·인벤토리·파일 수 상한)는 지금 규칙 그대로.

### 3.3 순서 (staging 사본에서만)

1. 원본 ZIP 해시를 `backup.<id>.meta.zipSha256`과 대조. 다르면 거부. **원본 ZIP은 쓰기 열기를 하지 않는다.**
2. staging에 풀기 → 파일·DB 해시를 manifest와 대조(지금과 같음).
3. 3.1 판정. `upgrade`면 staging DB에서 남은 마이그레이션을 **한 트랜잭션**으로 적용. 각 줄을 `__schema_migrations`에 기록(지금 `migrateDatabase`와 같은 함수 재사용).
4. 올린 뒤 검사: `verifyMigrations`(이제 `C`와 같아야 함) · `integrity_check` · `foreign_key_check` · 파일 참조 대조 · 글자 스냅샷 스키마 · **새 마이그레이션이 정한 데이터 검사**(예: 0005가 settings 글자 스냅샷을 `timeline_revisions`로 옮겼다면 프로젝트마다 current 스냅샷 1개 → 첫 timeline 1개, 문구·시간 일치).
5. T-006 정규화(복원으로 멈춤 처리)는 **올린 뒤**에 한다. 정규화 코드는 현재 스키마 기준이기 때문이다.
6. `restore-info.json`에 `schemaFrom`, `schemaTo`, `migrationsApplied`(이름·sha256 목록)를 추가해 기록.
7. 확정(rename) 직전에 원본 ZIP 해시를 다시 대조. 다르면 실패 처리.
8. 3~7 중 하나라도 실패하면 staging 전체를 지우고 목적지·원본은 그대로 둔다. 화면: "이전 백업을 지금 구조로 바꾸지 못했어요. 원래 백업 파일과 지금 데이터는 그대로예요." + 코드 `BACKUP_UPGRADE_FAILED`.

### 3.4 데이터를 옮기는 마이그레이션 규칙

- 데이터 이관(예: settings → `timeline_revisions`)도 **번호 있는 마이그레이션 한 줄**로 둔다. SQL 파일이면 지금처럼 해시가 기록된다.
- 코드로 옮겨야 하면(JSON 변환 등) 그 코드를 마이그레이션 번호에 묶고, 코드 원문의 sha256을 `__schema_migrations.sha256`에 넣는다. 그래야 "앞부분 일치"가 코드 단계까지 덮는다.
- 이관은 **같은 입력이면 같은 결과**여야 한다(시각·난수를 새로 만들지 않음. 새 ID가 필요하면 원래 행 ID에서 결정적으로 만든다). 백업 복원과 지금 DB 올리기가 같은 결과를 내야 하기 때문이다.
- 옛 행은 지우지 않는다. P1 settings 스냅샷은 읽기 전용으로 남긴다(PLAN 7.2 T-002 그대로).

### 3.5 지금 쓰는 DB 올리기 (`npm.cmd run db:migrate`)

1. 적용할 마이그레이션이 있으면, 적용 **전에** `VACUUM INTO backups/pre-migrate/<날짜시각>_s{from}-s{to}.db`로 스냅샷을 남긴다. 실패하면 마이그레이션을 시작하지 않는다.
2. 한 트랜잭션으로 적용(지금과 같음) → 4단계 검사와 같은 검사.
3. 실패: 트랜잭션은 되돌려지고 스냅샷은 남는다. 시작 점검 화면에 "데이터 구조를 바꾸지 못했어요. 바꾸기 전 데이터는 그대로이고, 따로 복사본도 남겨 두었어요." 표시.
4. 성공: 활동 기록 `db.migrated`(from, to, 스냅샷 파일 이름). 스냅샷은 자동으로 지우지 않는다. 지우기는 설정 > 보관함의 정리 규칙(원본 아님·참조 없음·ConfirmPanel)을 따른다.

### 3.6 호환 회귀 시험

| 시험 | 내용 | 통과 기준 |
|---|---|---|

## 4. D-1 · 복원 출처 표시

### 4.1 원칙

- 복원본 DB의 기록을 **사실과 다르게 바꾸지 않는다.** 출처 백업은 스냅샷 순간에 "만드는 중"이었으므로 복원본에서 "성공"으로 고치지 않는다(데이터 보고서 D-1의 방법 (가)는 쓰지 않음).
- 화면은 검증된 출처 정보(`restore.info` + `restore-info.json`: 백업 ID, 백업 만든 시각, 복원 시각, 원본 DB 해시)로 그 행이 무엇인지 설명한다.
- "취소했어요"는 사용자가 누른 취소에만 쓴다. 복원 때문에 멈춘 것은 따로 부른다.

### 4.2 설정 > 백업 목록 (복원본에서)

| 행 | 판정 | StatusPill | 글자 | 버튼 |
|---|---|---|---|---|
| 출처 백업 | `row.id == restore.info.backupId` | info 톤(남색 아이콘 i-shield) **"출처 백업"** | 이 복원본을 만든 백업이에요. 원래 PC에서 {백업 날짜시각}에 검증을 마쳤어요. 백업 파일은 원래 PC의 백업 위치에 있어요. | 없음 |
| 복원으로 멈춘 백업 | `error == RESTORE_INTERRUPTED`이고 출처가 아님 | locked 톤 **"복원으로 멈춤"** | 백업 도중의 데이터로 복원해서 이 복원본에서는 끝나지 않았어요. 원래 PC의 백업 목록에서 결과를 확인해 주세요. | 없음 |
| 복원본에서 만든 백업 | 그 밖 | 지금 규칙 | 지금 규칙 | 지금 규칙 |

- 판정 순서: **출처 → `RESTORE_INTERRUPTED` → 사용자 취소 → 그 밖 실패**. 화면에는 `canceled`가 먼저 나오면 안 된다(Master T-016).
- "마지막 성공 백업" 줄: 복원본에서 아직 백업하지 않았으면 **"이 복원본에서 만든 백업은 아직 없어요."** + 보조 글자 "출처: {백업 날짜시각} 백업" + 버튼 "지금 백업". 출처 백업을 마지막 성공으로 세지 않고, "마지막 실패"로도 세지 않는다.
- 작업실의 백업 상태 카드도 같은 규칙.

### 4.3 작업 대기열·장면 화면 (복원본에서)

- `RESTORED_NOT_RESUMED` 작업: StatusPill canceled 모양에 글자 **"복원으로 멈춤"**. 설명 "복원본에서는 이어서 하지 않아요. 필요하면 다시 만들어 주세요." "다시 시도" 버튼 없음. 장면 카드의 해당 버전도 같은 글자(T-013 3.3 자리 표시의 canceled 행 → "복원으로 멈췄어요.").
- 내보내기 `RESTORE_INTERRUPTED`: 실패 행 대신 locked 톤 "복원으로 멈춤" + "복원본에서는 이어서 하지 않아요. 현재 내용으로 새로 만들어 주세요." + 버튼 "현재 내용으로 새로 만들기"(검수 승인 조건 그대로).
- 이 코드들은 T-013의 `lib/ui/errors.ts`에 넣는다: `RESTORED_NOT_RESUMED`, `RESTORE_INTERRUPTED`(첫 문장 "복원으로 멈췄어요.", 재시도 없음, 청구 없음).

### 4.4 복원본 알림 (설정 > 앱 정보, 작업실 위)

- **위 띠 칩:** "샘플 모드" 칩 옆에 **"복원본"** 칩(locked 톤, 아이콘 i-undo). `title`·접근 이름 "{백업 날짜} 백업에서 복원한 데이터예요". 원래 PC 데이터와 복원본을 동시에 열 때 헷갈리지 않게 하려는 것(독립 검수에서 3026·3027을 같이 띄운 경우).
- **설정 > 앱 정보** Callout(info):
  - 제목: **이 데이터는 복원본이에요.**

## 5. 날짜·시각 표기 (`lib/ui/datetime.ts` 한 곳)

모두 **한국 시간(Asia/Seoul)**, 24시간제, 앞자리 0 채움.

| 이름 | 쓰는 곳 | 형식 | 예 |
|---|---|---|---|
| `short` | 목록·행·카드 | 올해면 `M월 D일 HH:mm`, 아니면 `YYYY년 M월 D일 HH:mm` | 11월 14일 09:02 · 2025년 11월 14일 09:02 |
| `long` | 출처·복원·확인 문장 | `YYYY년 M월 D일 HH:mm` | 2026년 11월 14일 09:02 |
| `date` | 날짜만 | 올해면 `M월 D일`, 아니면 `YYYY년 M월 D일` | 11월 14일 |
| `detail` | 기록 상세 펼침·로그 | `YYYY-MM-DD HH:mm:ss (한국 시간)` | 2026-11-14 09:02:41 (한국 시간) |

- "오늘"·"어제"는 작업실 카드에서만 `short` 앞에 붙일 수 있다("오늘 09:00"). 목록 정렬 기준과 다르게 보이지 않도록 다른 곳에는 쓰지 않는다.
- 저장은 지금처럼 UTC ISO. 표시만 이 함수로 한다. 지금 쓰는 `toLocaleString("ko-KR")`·`toLocaleDateString` 호출을 이 함수로 바꾼다.
- 단위 시험: 해가 바뀌는 날(12월 31일 23:59 UTC+9), 자정 직후, 올해와 다른 해.

**D-1 표시 (P1 안 · T-016과 함께 권장)**

3. 복원본 DB의 출처 백업 행은 정규화 값 그대로다(성공으로 바뀌지 않음, 쿼리로 확인).

6. 날짜가 5장 형식이다(목록 `short`, 출처 `long`).
7. 1280·390 가로 넘침 0.

**D-3 호환 (P2-1 준비 · 지금 미구현)**
8. 3.6 표의 시험이 모두 있고 통과한다.
