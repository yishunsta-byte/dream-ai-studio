소유한 루프백 PostgreSQL 17.12의 실제 SQL4 정책, 검증 작업·실행, 객체, 현재 검증 기록을 대상으로 검증했다. SQL1–4, T281, T307, T310 시험 입력의 다이제스트를 고정했다. ## 읽기 및 발급 판정

- 공통 현재 증거는 정책 ID·epoch·digest, 객체 ID·식별 다이제스트, 검증 기록 ID·스토리지 세대를 결합한다. 등록 자산과 객체의 경로·형식·크기·해시가 일치하고 현재 검증 기록이 성공·유효 상태일 때만 이 증거를 만든다. 목록과 프로젝트·자료 단건은 그 값이 자료 증거와 정확히 일치하고 T281 권한·링크와 복원 증거가 활성인지를 검사한다.
- 제한 로그인으로 발급할 때 T310 전환 제어 행 → 현재 정책 → 객체 → 현재 검증 작업 → 자료·검증 상태 → 증거 포인터 순서를 사용한다. 정책과 객체 잠금을 잡은 뒤의 `READ COMMITTED` 조회에서 현재 튜플을 재검사하고, 기대 증거와 포인터 리비전이 맞을 때만 변경한다. 시험 정책 갱신은 정책 행의 배타 잠금을, 시험 재검증은 정책 공유 잠금 다음에 객체 배타 잠금을 사용했다. [시험 SQL](../../tests/reference-analysis/t311-current-storage-evidence.sql) · [B16 잠금 계약](B16-STORAGE-UPLOAD-WORKER-CONTRACT.md)
- 읽기와 발급을 별도 제한 로그인으로 실행했다. RLS 아래 A/B 상호 목록·단건·발급을 격리했다. 읽기 역할의 발급 호출, 발급 로그인에서 증거 직접 수정·보호 역할 전환·정책 변경은 거절됐다. 정책/객체/검증 튜플의 일곱 필드를 각각 바꾼 요청 및 잘못된 포인터 리비전도 거절됐다.

## PostgreSQL 실제 경합 결과

| 변경 | 변경 트랜잭션이 먼저 잠금을 잡은 경우 | 발급 트랜잭션이 먼저 잠금을 잡은 경우 |
| --- | --- | --- |
| 정책 epoch·digest 교체 | 발급이 정책 행에서 대기했다. 정책 커밋 후 이전 증거로 쓰기 0건. 기존 검증 포인터가 그대로여도 두 계정의 이전 증거가 조회에서 제외됐다. | 정책 변경이 발급의 공유 잠금을 기다렸다. 현재 증거로 발급한 뒤 정책이 커밋되면 그 증거는 새 조회에서 제외됐다. |
| 재검증 성공 | 발급이 객체 행에서 대기했다. 새 기록과 활성 스토리지 세대가 커밋된 뒤 이전 증거로 쓰기·조회가 거절됐다. | 재검증이 발급의 객체 공유 잠금을 기다렸다. 재검증 커밋 뒤 이전 증거는 제외됐다. 새 현재 기록으로 별도 발급한 뒤 다시 조회됐다. |
| 재검증 실패 | 이전 성공 기록 포인터가 남았지만 상태가 철회됐고 활성 세대가 전진했다. 이전 증거로 쓰기·조회가 거절됐다. | 실패 전의 현재 증거 발급과 실패 커밋을 직렬화했다. 실패 커밋 뒤 그 증거는 제외됐고, 후속 재검증 성공 및 새 발급 이후에만 조회됐다. |

여섯 경우 모두 `pg_blocking_pids`로 실제 대기 상대를 확인했다. `pg_locks`로 정책 대기 중에는 객체 진입 전이며, 객체 대기 중에는 검증 작업·상태 진입 전임을 확인했다. 양쪽 후속 실행을 각각 `55P03`으로 기한 만료시키고 실패 트랜잭션을 롤백했다. 검증 하나만 변경한 경우 다른 소유자의 정상 증거와 포인터 상태는 유지됐다. 정책 변경 후에는 새 정책의 검증 및 증거 발급을 두 소유자에서 다시 확인했다.
