# T319-R 송신 원장·제어기 재시작 독립 재현

기준 `ae326ed` · Master 인계 `msg_93a17c83c282` · Codex(Tester)

**판정은 소유 루프백 PostgreSQL 17.12 시험 계약 통과.** 고정 실행기를 수정하지 않고 두 번 실행했다. 실행기 ESLint와 고정 변경의 `git diff --check`도 통과했다. [실행기](../../tests/reference-analysis/t319-egress-durable-control.pg17.mjs) · [시험 SQL](../../tests/reference-analysis/t319-egress-durable-control.sql)

| 검증 | 독립 재현 결과 |
| --- | --- |
| 동일 허가 소비와 역할 | 서로 다른 제어기 PID가 같은 허가를 처리했다. 첫 트랜잭션을 보류했을 때 별도 조회는 `prepared`였고, 두 번째 백엔드는 실제 PG 잠금에서 첫 번째를 기다렸다. 커밋 뒤 한 쪽만 `starting`, 다른 쪽은 `already_consumed`였고 시작 사건은 1건이었다. 다른 주체의 소비, 직접 원장 접근·보호 역할 전환, 제어 역할의 종료 증거 쓰기 및 감독 역할의 허가 발급은 거절됐다. |
| 제어기 종료와 재시작 | `sending` 커밋을 별도 DB 연결에서 관측한 뒤, 응답을 호출자에게 전달하지 않도록 한 원래 제어기 프로세스를 강제 종료했다. 새 PID의 제어기는 `starting`·`sending`·`finished` 상태와 기존 사건 기록을 그대로 읽었다. 같은 허가의 재소비는 거절됐다. |
| 종료 증거 부재 | 전환을 준비하면 사용 전 허가는 취소하고 새 발급은 차단했다. 미종결 허가의 기한을 과거로 옮겨도 전환이 보류됐다. 다른 PID로 제출한 종료 증거와 시작 상태를 완료로 바꾸는 요청도 거절됐다. |
| PostgreSQL 정지·재시작 | 소유 PG를 정상 정지하는 동안 신규 발급·활성화·상태 조회는 모두 `ledger_unavailable`이었다. 같은 데이터 디렉터리로 다시 시작해 클러스터 식별자는 같고 postmaster 시작 시각은 달라졌음을 확인했다. 기존 상태와 전환 보류가 유지됐고 오프라인 때 발급한 행은 없었다. |
| 감독 역할을 통한 복구 | 예전 송신자 프로세스 종료를 실제로 관측한 뒤에도 원장에 증거가 없으면 전환이 보류됐다. 별도 감독 역할이 기존 부팅 ID와 관측한 PID를 근거로 격리를 기록하자 미종결 두 허가가 `isolated`로 바뀌고 새 세대가 열렸다. 그 뒤 예전 세대 명령과 새 소유자에서의 예전 허가 소비는 거절됐고, 새 허가는 완료 상태까지 갔다. |
| 정리 | 두 실행에서 제어기 DB 세션, 소유 제어기·송신 프로세스, postmaster PID 파일과 루프백 리스너를 정리했다. 별도 호스트 조회에서도 소유 프로세스와 T319 임시 클러스터가 각각 0개였다. |

실제 관측 대상은 위 SQL 트랜잭션·잠금·재시작, Node 자식 프로세스 종료와 감독 역할의 기록이다. 송신 첫 바이트와 정상 완료 사건은 합성 IPC 보고다. 원장 함수는 제출된 부팅 ID와 PID를 대조하며 호스트를 직접 조사하지 않는다. 실제 TLS 송신과 허가 소비의 원자성, 하위 큐, 전원 손실·WAL 복구·승격, 다중 호스트 분할과 운영 인증은 별도 시험이다. 빌드·운영 DB·배포는 수행하지 않았다.
