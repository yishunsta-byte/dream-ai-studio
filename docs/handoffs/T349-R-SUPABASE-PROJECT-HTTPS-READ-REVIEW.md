# T349-R 기존 Supabase HTTPS 조회 독립 검수

2026-11-19 KST · Codex(Tester) · 고정 커밋 `b6447a4` · Master 배정 `msg_f2bc1a575359`

**격리 검수 통과.** 제공 실행기로 소유 PG17.12의 실제 RLS·ACL과 합성 JWT를 사용하는 모의 HTTP 응답 계약을 재검증했다.

- 검증기는 합성 서명, 발급자, 대상, 만료, UUID, 고정 인증 역할을 검사했다. 승인된 요청의 역할과 JWT 설정은 DB 트랜잭션에 한정됐다. 같은 풀을 다시 조회했을 때 현재 역할은 게이트웨이 로그인으로 돌아왔고 JWT 설정은 비어 있었다.
- 실제 RLS에서 승인 사용자 A/B는 각자 활성 프로젝트만 읽었다. 승인 목록에서 제외된 사용자의 읽기는 0건이었고 익명 역할은 API 뷰 읽기를 거절당했다. 타인·보관 프로젝트는 반환되지 않았다. 제한 역할의 기반 프로젝트, Auth 및 내부 승인 데이터 직접 조회와 기존 API·worker 역할 전환이 거절됐다. 일반 읽기·쓰기 트랜잭션의 DML도 거절됐고, 카탈로그 검사에서 해당 쓰기 권한이 없었다.
- 모의 목록과 자기 상세는 기존 PostgreSQL 읽기 서비스의 DTO와 일치했다. 단계 배열은 정렬을 정규화해 비교했다. 타인·보관·미존재 상세는 같은 404였고 비승인은 403, 익명·유효하지 않은 JWT는 401, POST는 405, 비공개 프로필은 404, DB 조회 권한 회수는 503이었다. 응답의 `no-store`와 고정 오류 JSON을 확인했다. 인증·프로필·메서드 거절에서 DB를 읽지 않았다.
- 대상 커밋의 변경은 격리 실행기, 시험용 SQL과 인계 세 파일이었다. 제품 조회 서비스·라우트·기반 마이그레이션·기타 서비스 경로에 이 커밋의 변경이 없었다. 관련 회귀 288건 통과·30건 건너뜀, 소스 타입 검사, 실행기 ESLint 및 diff 공백 검사가 통과했다.
- 실행기는 서명이 확인된 PG17.12 바이너리로 소유 루프백 클러스터를 만들었다. 검증 후 DB 연결·리스너·클러스터를 제거했고 소유 PG 프로세스 0건을 확인했다. 고정 검수 사본도 정리했다.

PG 시험 연결은 로컬 SCRAM이며 HTTP는 메모리 내 `Request/Response`였다. 실제 TLS/HTTPS 전송, Supabase 발급 JWT와 PostgREST의 노출 설정·페이지·오류 응답, 운영에서의 조회 가능 여부는 검증 범위 밖이다. 운영·빌드·배포 변경이나 새 창·에이전트·worktree 생성은 없었다.
