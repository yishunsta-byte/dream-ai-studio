# T252-FIX 공개 승인 공급원 계약

원 설계 `ea1013716420dc55298cbdc6643e900c694742fe`를 보존한다. 독립 검수 `5971ae4`의 여섯 요구에 대해 아래 계약을 후속 구현 기준으로 제안한다. 첫 운영 공개 범위는 권리자가 확인한 완성 이미지 한 건과 메타데이터를 제거한 WebP 사본 한 개다. 합성 목록은 정렬 및 개수 경계를 검증할 만큼 구성한다.

## 1. 익명 이미지 요청

- 정규형은 `/media/public/<slug>/<generation>/cover.webp` 한 가지다. slug는 T249의 소문자 ASCII 규칙과 길이 제한을 따르며 `sign`, `authenticated`, `private`, `signed`를 제외한다. generation은 1 이상 signed BIGINT 범위의 선행 0 없는 ASCII 십진 문자열이다. 문자열로 전달해 JS 숫자 정밀도 손실을 피한다. 경로 전체와 GET·HEAD 메서드를 공유 순수 파서로 판정한다. 쿼리, 퍼센트 인코딩, 중복 구분자, 역슬래시, 점 경로, 대문자 별칭과 후행 슬래시는 허용형에서 제외한다.
- `proxy.ts` 인증 전 분기에서 이 조건에 맞는 GET·HEAD만 조회 핸들러로 통과시킨다. 기존 익명 집합은 그대로 두고 인접 보호 경로는 기존 인증을 유지한다. 정규 경로의 다른 메서드는 405와 `Allow: GET, HEAD`를 반환한다. Auth off에서도 핸들러가 동일 계약을 지키며, 명시적 HEAD와 OPTIONS 거절을 둔다. 프레임워크나 배포 앞단이 원본 요청 경로를 정규화할 수 있으므로 보이는 경로의 검증만으로 충분하다고 판단하지 않는다. 격리 Next와 배포 전 검증 환경에 원본 경로를 보낸다. 별칭이 자동 리다이렉트되거나 보호된 경계를 넘어 승인 파일을 받으면 해당 계층에서 차단하고 재검증한다.
- 핸들러는 경로와 파라미터를 다시 확인한 뒤 정확히 일치하는 활성 세대의 cover 슬롯만 읽는다. 준비·철회·과거 세대 또는 미등록 주소는 404다. DB 조회 실패나 활성 사본의 Storage 장애·부재·무결성 실패는 503이다. HEAD도 GET과 같은 승인 및 파일 검증을 수행하고 본문을 생략한다. Range와 조건부 캐시 갱신은 첫 버전에서 사용하지 않으며 활성 이미지에 대한 Range 헤더는 무시하고 전체 200 계약을 적용한다. 오류와 메서드 거절도 무캐시로 응답한다.

## 2. 이미지 최적화와 캐시

쇼케이스의 대표·카드·목록·상세에서 승인 이미지는 모두 직접 주소를 사용한다. `next/image`를 유지하는 곳은 승인 이미지에 `unoptimized`를 적용한다. 이 변경과 함께 `next.config.ts`의 `images.localPatterns`에 기존 앱이 최적화하는 경로를 조사해 열거한다. `/media/public/` 및 이를 가리키는 rewrite·redirect 별칭을 허용 목록에서 빼고 범용 패턴을 두지 않는다. 최적화 엔드포인트는 proxy matcher에서 제외되므로 직접 최적화 요청, 인코딩 변형, 동일 사이트 절대 URL, 리다이렉트 경유와 기존 예시·작업실 이미지를 HTTP로 확인한다. 철회하기 전부터 최적화 주소에서 승인 이미지가 제공되지 않아야 한다. [Next.js Image 설정](https://nextjs.org/docs/app/api-reference/components/image#localpatterns)

홈 HTML과 RSC는 동적 렌더와 요청별 새 조회를 사용한다. 홈과 이미지 응답의 실제 `Cache-Control`은 `no-store`를 요구한다. CDN 전용 헤더를 설정하는 곳도 `no-store`로 일치시키고, Vercel 앞단 설정 때문에 브라우저 또는 CDN에 공유·stale 캐시가 남는지 검증한다. 홈 진입 링크를 점검해 사전 로드를 끄고, 이전 RSC를 재사용하는 경로는 전체 문서 탐색으로 바꾼다. 새 탐색·새로고침·뒤로 가기 및 새 파일 요청에서 기대 동작을 확인한다. 이미 화면에 그려졌거나 저장된 바이트와 기존에 승인된 진행 중 전송은 철회 시 회수할 수 없다. [Next.js 캐시 가이드](https://nextjs.org/docs/app/guides/caching-without-cache-components) · [Vercel 캐시 헤더 우선순위](https://vercel.com/docs/caching/cache-control-headers#behavior)

## 3. 목록·파일·발행 자격

첫 SQL 초안은 비공개 `dream` 안의 상태 테이블과 두 고정 조회 함수로 범위를 좁힌다. 새 호출 자격은 서로 상속하지 않는다. 함수 전용 소유자는 각각 별도의 NOLOGIN·NOBYPASSRLS 역할이다. 테이블 소유권은 이 역할들에게 주지 않는다. 테이블에는 FORCE RLS를 적용하고, 각 함수 소유자의 SELECT 정책은 활성 행으로 한정한다. 함수에는 고정 `search_path`와 한정된 관계 이름을 쓰며 동적 SQL을 사용하지 않는다. 같은 이관 트랜잭션에서 PUBLIC 실행권을 회수하고 지정 호출 자격에만 부여한다. anon·authenticated·authenticator에는 이 역할이나 함수 권한을 부여하지 않는다. [PostgreSQL 17 함수 실행 권한](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

| 서버 자격 | 허용 연산과 데이터 |
|---|---|
| 목록 전용 | 인자 없는 목록 함수 EXECUTE만 허용한다. 함수 소유자는 활성 조건 열과 slug·활성 세대·승인 ms·명시적 표시 필드·이미지 가로/세로를 읽는다. 호출에는 공개 DTO 구성에 필요한 열만 돌려준다. 저장 키·원본·권리 증빙·담당 UUID는 접근 및 반환 대상에서 제외한다. |
| 파일 조회 전용 | 파라미터로 받은 slug·세대와 고정 cover 슬롯의 단건 조회 함수 EXECUTE만 허용한다. 함수 소유자는 활성 조건과 주소 일치 열·저장 키·MIME·크기·해시만 읽는다. 목록 호출과 기저 테이블 직접 조회 권한을 부여하지 않는다. |
| 발행 서버 | 인증·발행 허용이 확인된 동일 소유자의 기존 검증 트랜잭션에서 원본 ID·리비전·해시를 확인한다. 추가 쓰기 역할은 전용 발행 상태와 요청 원장만 변경할 수 있게 제한한다. 공개 읽기 자격에는 이 역할을 주지 않는다. |

발행·철회 요청은 기존 인증에서 얻은 `verified.userId`가 별도 발행 허용 UUID이면서 원본 소유자와 같은 경우로 제한한다. 서버가 같은 UUID로 소유자 범위 트랜잭션을 열고 같은 출처의 상태 변경 요청, CSRF, 엄격한 입력, 소유 관계·리비전·완료·권리 증빙을 확인한다. 공개 문구와 승인 사본의 해시를 권리 범위에 묶는다. 다른 소유자를 대신하는 발행·철회와 기간 제한 라이선스는 첫 범위에서 제외한다. 권리 만료 시각이 필요한 후보는 받지 않고, 권리 회수 시 담당자가 철회한다.

런타임 파일 읽기에는 기존 `service-role` 키를 사용하지 않는다. 운영 후보는 별도 인증된 다운로드 주체와 비공개 배포 버킷의 작업 종류별 정책이다. 전용 주체의 인증 식별자, 정확한 배포 버킷, 관리된 이미지 키 규칙, 인증된 객체 다운로드 동작에만 SELECT를 허용한다. 관리형 환경의 작업 구분 정책이 실제로 목록·쓰기·삭제·서명 URL 생성과 원본 접근을 거부하는지 별도 검증한다. 해당 정책을 보장할 수 없으면 같은 경계를 제공하는 전용 서비스를 확보할 때까지 운영 연결을 보류한다. 작성·정리 주체는 공개 앱의 다운로드 자격과 분리한다. [Supabase Storage 작업별 정책과 서비스 키](https://supabase.com/docs/guides/storage/security/access-control)

DB가 돌려준 불변 배포 객체 키만 다운로드에 사용한다. 첫 사본 한도는 5 MiB, 가로·세로 각각 최대 4096, 업스트림 전체 5초로 제안한다. 준비 때 실제 WebP 디코딩과 규격을 확인하고 SHA-256·길이를 기록한다. GET·HEAD 모두 이 한도 안에서 사본 전체를 받아 크기·해시·형식을 확인한 후 응답한다. Content-Type은 `image/webp`로 고정하고 `nosniff`를 사용한다. 검증되지 않은 바이트, 저장 주소·서명 URL·자격은 응답에 포함하지 않는다.

## 4. 잠금과 철회

slug마다 계속 남는 상태 행 하나를 잠금 기준으로 삼고, 요청 ID와 결과를 보존하는 작은 발행 요청 원장을 별도로 둔다. 상태 행에는 소유자, 단조 증가 버전/세대, 현재 활성 세대, 준비 중 후보와 정리 상태를 둔다. 최초에는 고유 slug 행을 생성한 뒤 같은 행을 `FOR UPDATE`로 잡는다. 생성 충돌 시 커밋된 행을 다시 읽고 기존 소유 관계를 확인한다. 행을 삭제해 같은 slug의 과거 세대 주소를 다시 쓸 수 있게 하지 않는다.

1. 준비는 잠금 아래 새 세대와 작업 버전을 예약하고 후보를 비활성으로 기록한다. 복제는 트랜잭션 밖에서 수행한다. 예약된 세대와 검증된 내용 해시에서 만든 불변 키에만 생성하며 기존 객체 덮어쓰기를 금지한다.
2. 완료는 같은 잠금에서 현재 버전, 후보 세대, 원본 리비전과 승인된 권리·사본 무결성 증거를 다시 대조한다. 교체 시 이전 세대를 닫고 새 세대를 활성화하는 변경을 같은 커밋에 담는다. 철회는 같은 잠금에서 버전을 올리고 활성 포인터와 준비 후보를 동시에 무효화한다. 준비 중 철회가 먼저 커밋되면 뒤늦은 완료는 충돌로 종료된다. 완료가 먼저면 후속 철회가 그 세대를 닫는다.
3. 원장은 `actor + 요청 ID`에 정규화한 명령 지문과 처리 결과를 저장한다. 지문에는 명령 종류, slug, 예상 버전 및 대상 세대를 포함한다. 같은 ID·같은 지문은 기록 결과를 돌려주며 다른 지문은 충돌로 닫는다. 커밋 응답을 잃으면 같은 ID로 완료 기록을 읽고, 아직 진행 중이면 동일 예약을 확인한다. 재시도가 새 세대를 만들거나 철회된 결과를 다시 활성화하지 않는다. 업로드 응답을 잃으면 기존 예약 키의 실제 무결성 확인 이후에만 재개한다. 철회된 사본은 전송 중이던 복제가 끝날 때 남을 수 있다. 복제 시도 종료가 확정되기 전의 객체 부재를 정리 완료로 기록하지 않는다. 확정 후 폐기된 세대의 키만 처리하고, 활성·준비 참조를 다시 확인해 삭제하며 정리 실패는 재시도한다.

목록과 파일은 요청마다 기본 DB의 새 READ COMMITTED 조회를 사용한다. 철회 커밋 후 시작된 조회는 이전 세대를 돌려주지 않는다. 파일 제거 완료를 기다리지 않고 같은 시점에 새 파일 요청을 404로 닫는다. 승인 전 404 → 활성 200 → 철회 후 404가 같은 URL에서 성립해야 한다. [PostgreSQL 17 READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED)

## 5. 목록의 상태와 정렬

예시 전용 모드는 명시적 설정에서만 선택한다. 운영 모드는 설정·권한·시간 초과·조회 실패·계약 오류를 분류한다. 목록 함수는 승인 시각을 처음부터 정수 epoch ms로 저장한 행을 `approved_ms DESC, slug COLLATE "C" ASC`로 읽는다. UTC 밀리초 문자열로 변환해 T249에 전달하고 미래 판정에는 조회에서 받은 같은 DB 기준 ms를 사용한다. ASCII slug 정렬이 T249와 일치하는지 확인한다. 소수점 이하 밀리초를 추가 정렬 기준으로 사용하지 않는다.

서버 고정 한도는 24건이다. DB는 정렬된 상위 최대 25행을 반환한다. 25번째 행은 추가 승인 작품 존재 확인용이며 그 행까지 동일 계약으로 검증한다. 25행 초과, 중복, 제외, 시각·정렬 불일치와 T249의 예기치 않은 잘림은 공급원 계약 오류다. T249 검사 한도를 25로 맞춘 뒤 의도적으로 상위 24건만 사용한다. 범위 밖 행은 활성화 시 검사하며 홈이 전체를 다시 순회하지 않는다. 24/25번째 승인 ms 동률, 밀리초 미만 차이를 가진 입력의 저장 규칙, ASCII 순서를 구분하는 slug로 경계를 검증한다.

정상 0건만 예시 6개로 연결한다. 정상 승인 목록은 공개 작품만 전달한다. 공급원 불가와 계약 오류에는 로그인 링크와 일시 이용 불가 안내를 렌더한다. 첫 구현의 홈 HTML/RSC는 정상적으로 렌더한 장애 안내도 HTTP 200으로 분명히 계약하고, 정상 빈 목록과 다른 화면 표식을 시험한다. 파일 경로의 장애는 503, 비활성·미등록은 404다. 홈의 성공은 승인 메타데이터 조회에 한정한다. 홈에서는 사본 다운로드를 일괄 확인하지 않는다. 서버 진단은 안전한 분류 코드와 개수만 기록하고 클라이언트에는 공개 DTO 또는 안내만 보낸다.

## 6. 구현 범위와 PG17 선행조건

1. 승인된 PG17 이관 초안 한 파일과 합성 통합 테스트 한 묶음부터 진행한다. 실제 major 17의 소유한 폐기 가능 DB, 새 DB와 기존 합성 스키마, 별도 역할, 두 동시 연결을 준비한다. 제약·역할 간 접근 거부·원본 소유자 일치·잘못된 상태·원장 재시도·양방향 승인/철회 경쟁·지연 복사 완료·롤백을 검증한다. 깨끗한 설치와 기존 상태에서 이관, 실패 후 롤백과 재적용을 구분한다. 이번 설계 작업에서는 합성 PG17 실행 환경을 확인하거나 SQL을 실행하지 않았다.
2. `lib/public-showcase/`에 서버 전용 저장/공급원 모듈, 공유 경로 파서, 제한된 이미지 읽기 어댑터를 두고 공개 미디어 route 핸들러 하나로 연결한다. `proxy.ts`, `next.config.ts`, 쇼케이스 이미지 표현의 변경을 같은 검증 묶음에 둔다. 처음에는 합성 Storage를 주입해 GET·HEAD·OPTIONS, 경로 정규화와 최적화 경유, 권한 실패, 해시/크기/형식 오차, 철회 전후 HTTP와 캐시를 재현한다.
3. `app/(public)/page.tsx`와 T251 공급 분기만 연결하고 T249 변환과 카드 구조를 재사용한다. 운영 장애 분기는 페이지가 맡는다. 합성 Next HTTP에서 빈 목록·승인 1건·마지막 철회·잘못된 행·장애·HTML/RSC·로그인 링크와 비공개 필드 미노출을 확인한다. 발행 검증은 전용 서버 명령 경계로 시작하고 범용 관리 UI는 보류한다.
4. 운영 적용은 관리형 PG17을 지원하는 승인된 이관/카탈로그 검증과 실행 경로, 스키마·역할 프로비저닝, TLS 검증이 된 전용 런타임 풀러, 최소 권한 Storage 정책 및 배포 앞단 캐시 검증을 먼저 충족해야 한다. B8의 17.12는 과거 기록이다. 현 PG18 카탈로그 판별을 완화하거나 관리형 DB에 SQL을 수동 적용하는 방식은 적용 계획에서 제외한다. 실패·롤백 절차와 실제 적용 승인도 별도로 확보한다. 첫 등록에는 동일 소유자 승인 담당자, 원본 ID·리비전·해시와 완료 증거, 공개 및 철회 권리 범위, 슬러그·전체 공개 문구·검증된 WebP 사본을 받는다.

설계 보완만 수행했다. 기존 원보고와 독립 검수는 보존했다. 운영 조회, SQL 실행, 실제 게시와 배포는 이번 작업 범위 밖이다.

Master 전달문 — T252-FIX는 합성 이미지 한 건의 구현 경로에 필요한 여섯 계약을 고정했다. 기존 보고서는 보존했다. 익명 GET/HEAD 및 최적화 차단, 목록·파일별 DB와 제한된 Storage 권한, 소유자 일치, slug 잠금과 철회·재시도, 빈 목록과 장애 및 ms/ASCII 정렬, PG17 시험·이관 선행조건을 명시했다. PG17 실행과 운영 적용은 후속 검증 범위다.
