## 운영 활성화 전 입증

- **실제 Next 호스팅과 프록시.** HTML·RSC 탐색/사전 요청·분석 POST에 단일 보호 전송 경계가 적용되는지 확인한다. 허가 소비 전후와 첫 큐 삽입 전후, 종료 기록 전후에 전송 소유자를 각각 멈춘다. 철회 선행 시 보호 바이트 0건, 시작 선행 시 기존 전송의 완료 또는 큐 정리 확인 이후에만 새 세대 활성, 불명 상태에서 재전송 0건을 확인한다. 호스팅이나 하위 큐의 우회 전송을 차단할 수 없는 경로는 비활성을 유지한다.
- **실제 플랫폼 복원·승격 API.** 두 조정자와 구 실행 경계에서 호출 인계 전후 재개를 시험한다. 응답 유실, 일시적 조회 누락, 중복 방지 보장 기간 경과를 각각 확인한다. 고정 작업 키나 검증 가능한 작업 ID로 기존 결과를 판별하지 못하는 단계의 자동 재개는 닫아 둔다.
- **소유 PG17과 실제 배포 연결.** 예약 및 업무 COMMIT을 각각 지연시켜 별도 연결에 행 없음 또는 예약 상태만 보이게 한다. 두 연결에서 커밋·롤백, 응답 유실, 잠금 기한과 같은 키의 다른 지문을 시험한다. 성공 변경 한 건, 다른 지문 거절, 미확정 중 재실행 0건을 확인한다. 실제 배포에서는 풀러를 통과할 때도 잠금과 재조회가 같은 검증된 백엔드의 트랜잭션인지 입증한다. [격리 시험 계획](T309-REA-AUTHORITY-EVIDENCE-ISSUANCE-DESIGN.md#차후-소유-루프백-pg17-검증) · [플랫폼 확인 범위](T309-REA-AUTHORITY-EVIDENCE-ISSUANCE-DESIGN.md#플랫폼에서-아직-확인하지-못한-조건)

고정 설계의 고유 링크 대상 23/23과 `git diff --check`를 확인했다. 이번 검토는 문서와 소스 읽기로 진행했다. 보호 전송 경계·플랫폼 API·PG17 동시 실행, 운영 변경과 배포는 검토 범위 밖이다.
