## 1. 큰 원칙
1. **화면이 부르는 주소는 그대로 둬요.** 화면은 지금처럼 `/api/...`만 불러요. Supabase로 바뀌는 것은 서버 안쪽이에요.
2. **화면은 Supabase DB를 직접 읽거나 쓰지 않아요.** 예외는 로그인(Auth)과, 4.5MB가 넘는 파일의 직접 올리기(5장)뿐이에요.
3. **비밀키는 서버와 작업 처리기에만** 둬요. 저장소가 공개 상태라 특히 중요해요.
4. 승인 게이트·원본 덮어쓰기 금지·새 버전 저장 같은 규칙은 지금처럼 **서버 서비스에서** 강제해요(PLAN 1.1).

## 2. 환경변수 이름 (값은 Vercel·PC `.env.local`에만)

| 이름 | 쓰는 곳 | 공개 여부 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 화면·서버·처리기 | 공개돼도 됨 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 화면·서버(로그인 세션) | 공개돼도 됨(RLS 전제) |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 일부·작업 처리기만 | **비밀**. `NEXT_PUBLIC_` 금지, 화면 코드에서 import 금지 |
| `DATABASE_URL` | 이전 도구·처리기(직접 Postgres) | **비밀** |
| `DREAM_ALLOWED_EMAILS` | 서버 | 비밀 아님, 저장소에는 안 둠 |
| `DREAM_STORAGE_BUCKET_*` | 서버·처리기 | 비밀 아님 |

- `.env.example`에는 **이름만** 추가해요(값 없음).
- 서비스 키가 화면 묶음에 들어가지 않았는지 빌드 결과물 검사를 `verify-build`에 넣어요.

## 3. 로그인 약속

| 항목 | 약속 |
|---|---|
| 방식 | Supabase Auth, 이메일 매직 링크(또는 GitHub). 비밀번호 저장 화면은 만들지 않음 |
| 사용 대상 | 처음에는 `DREAM_ALLOWED_EMAILS`에 있는 사람만(은영님 혼자 전제). 협업 역할은 P7-3 이후 |
| 세션 | `@supabase/ssr` 쿠키 세션. 서버 컴포넌트·API에서 같은 함수로 사용자 확인 |
| 보호 범위 | 로그인 화면과 정적 파일을 뺀 **모든 화면·모든 `/api`**. Next 16 `proxy.ts`에서 1차로 막고, 각 API에서 한 번 더 확인 |
| 로그인 안 됨 | 화면은 `/login?next=원래주소`로 이동. API는 `401 {error, code:"AUTH_REQUIRED"}` |
| 허용 목록 밖 | `403 {error, code:"AUTH_FORBIDDEN"}`, 화면은 "이 계정은 사용할 수 없어요" |
| 화면 쪽 할 일(Front) | `/login` 화면, 로그인 상태 표시, 로그아웃, 401/403 공통 처리, 세션 만료 시 작성 중 내용 유지 |

## 4. 서버 주소 약속 (지금 19개 그대로)
- 화면에서 부르는 주소·요청 모양·응답 모양은 **바꾸지 않아요**. 백엔드는 안쪽 저장 방식만 바꿔요.
- 오류 응답은 지금처럼 `{ error: "한글 문장", code: "대문자_코드" }`. 새 코드는 `AUTH_REQUIRED`, `AUTH_FORBIDDEN`, `STORAGE_UNAVAILABLE`, `WORKER_OFFLINE`만 추가해요.
- 아이디는 지금처럼 UUID 문자열, 시각은 ISO 8601(UTC) 문자열이에요. Postgres 날짜형을 그대로 내보내지 않아요.
- 크기 숫자(`sizeBytes` 등)는 계속 **숫자**로 내보내요. Postgres `bigint`가 문자열로 오지 않게 서버에서 바꿔요.
- 목록 정렬·개수 제한은 지금 기본값을 따라요.

| 주소 | 바뀌는 점 |
|---|---|
| `GET /api/assets/[id]`, `GET /api/renders/[id]/file`, `GET /api/exports/[id]` | 파일을 직접 보내지 않고 **짧게 유효한 서명 주소로 302 이동**. 화면의 `src`·`href`는 지금 주소 그대로 |
| `POST /api/assets/upload` | 4.5MB 이하는 지금처럼. 큰 파일은 5장의 직접 올리기 |
| `POST /api/backups`, `/api/restore/*` | 로컬 zip 대신 클라우드 백업 방식으로 다시 설계(백엔드 결정 필요). 그동안 화면은 "준비 중" 상태로 막음 |
| `/api/jobs` | `workerOnline`은 처리기의 최근 신호 시각 기준을 유지 |

## 5. 파일 약속

| 항목 | 약속 |
|---|---|
| 버킷 | `assets`(올린 자료), `renders`(만든 영상), `exports`(내보내기 묶음). 모두 **비공개** |
| 경로 | `{owner_id}/{project_id 또는 _library}/{파일 id}.{확장자}`. 원래 파일 이름은 DB에만 저장 |
| 덮어쓰기 | 금지. 같은 경로에 다시 쓰지 않고 새 id로 저장(`upsert:false`) |
| 보기·내려받기 | 서버가 소유자를 확인한 뒤 서명 주소 발급(보기 10분, 내려받기 1시간). 영상은 구간 요청이 되는 Storage 주소라 휴대폰에서 바로 재생 |
| 큰 파일 올리기 | Vercel 함수는 요청 크기가 약 4.5MB로 제한돼요. 그래서 ① 화면이 `POST /api/assets/upload-url`로 올릴 자리를 받고 ② 화면이 Storage에 직접 올리고 ③ `POST /api/assets/upload-complete`로 서버가 파일 형식·크기를 다시 검사한 뒤 등록해요 |
| 검사 | 파일 형식 확인(`file-type`)·크기 제한은 등록 단계에서 서버가 다시 해요. 통과 못 하면 Storage에서 지워요 |

## 6. 작업 처리기 약속
- 처리기는 **이 PC**에서 돌고 Supabase에 `SUPABASE_SERVICE_ROLE_KEY`로 접속해요. Vercel에서는 렌더하지 않아요.
- 작업 가져가기는 Postgres의 `FOR UPDATE SKIP LOCKED`로 하나씩 잠가요. 동시 작업 1개 기준을 유지해요(나중에 pg-boss 검토).
- 처리기는 30초마다 신호 시각을 남겨요. 화면은 `/api/jobs`의 `workerOnline`으로 "PC 처리기가 꺼져 있어요" 안내를 보여요.
- 결과 파일은 `renders` 버킷에 올린 뒤 DB 행을 완료로 바꿔요. 올리기가 실패하면 완료로 표시하지 않아요(실패와 샘플을 완료로 표시 금지).

## 7. DB 약속 (백엔드 담당 범위, 화면이 기대하는 것만)
- 모든 사용자 데이터 표에 `owner_id uuid`를 두고 RLS를 켜요. 서버는 로그인 사용자 기준으로 읽고, 처리기만 서비스 키로 읽어요.
- 고정 마이그레이션 0001~0010은 바꾸지 않아요. Postgres용은 새 폴더의 새 파일로 만들어요.
- 묶음 처리(트랜잭션) 22곳은 같은 묶음 단위를 유지해요. 동기 호출이 비동기로 바뀌는 것만 달라져요.

## 8. 화면(Front) 쪽 할 일 목록
1. `/login` 화면, 로그인 상태·로그아웃(헤더), 401/403 공통 처리
2. 큰 파일 직접 올리기(진행률·취소·실패 안내) — `library-browser`, `audio-editor`
3. "PC 처리기가 꺼져 있어요" 안내(렌더·내보내기 화면, 작업 대기열)
4. 백업·복원 화면의 클라우드 전환 중 "준비 중" 상태
5. 1280·390 화면과 실제 휴대폰 확인
