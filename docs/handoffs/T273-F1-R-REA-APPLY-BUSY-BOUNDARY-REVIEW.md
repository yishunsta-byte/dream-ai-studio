# T273-F1-R REA 적용 잠금 경계 독립 재검수

2026-11-19 KST · Codex(Tester) · 기준 `0c0e5d88ef53118428d5489d4c49a7682aecb750` · 배정 `msg_85b62b6ba4a3`

**통과.** 최상위 쓰기 트랜잭션 시작의 SQLite 잠금 대기 초과가 안전한 재시도 응답으로 구분됐다. 기존 조건부 판정의 잠금 처리 보류를 해제한다. 제품 호출 경로의 응답 처리와 실제 권한 연결은 후속 범위다. [수정 보고](T273-F1-REA-APPLY-BUSY-BOUNDARY.md) · [이전 검수](T273-R-REA-EXPLICIT-PROJECT-APPLY-REVIEW.md)

## 독립 재현

격리 합성 S4 SQLite에 오디오가 하나 있는 v2 타임라인을 저장하고, 별도로 합성한 로컬 컷의 미리보기로 두 연결에 같은 기준의 확인 객체를 생성했다. 재현용 연결의 대기 한도는 40ms로 설정했다. [적용 서비스](../../lib/reference-analysis/project-apply.ts)

| 경계 | 확인 결과 |
| --- | --- |
| 최상위 `BEGIN IMMEDIATE` 잠금 | 첫 연결의 쓰기 잠금이 유지되는 동안 반대 연결에서 정확히 `{ status: "busy", retryable: true }`를 받았다. SQLite 메시지는 없었다. 소유권 조회에 진입하지 않았고 전체 논리 DB 스냅샷도 같았다. |
| 잠금 해제·재전송과 경쟁 | 잠금이나 실패만 해소하면 같은 확인으로 한 번 저장할 수 있었다. 경쟁 확인이 먼저 커밋한 뒤 재시도는 `conflict`였고 추가 리비전이 생기지 않았다. 이전에 성공한 동일 확인의 재전송도 충돌했다. |
| 커밋 경합 | `DELETE` 저널 모드에서 두 번째 연결의 읽기 잠금을 유지했다. 첫 연결은 마지막 `activity_log` 기록에 도달한 후 커밋 중 네이티브 `SQLITE_BUSY`를 그대로 던졌다. 쓰기 연결에는 열린 트랜잭션이 남지 않았고 모든 논리 행이 원래와 같았다. |
| 예상 밖 오류 | 적용 중 `code=SQLITE_BUSY`인 일반 `Error`는 같은 객체로 예외를 전달했다. 별도의 마지막 로그 쓰기 실패 역시 예외를 유지했고 전체 롤백됐다. 기존 포인터 실패·안전 재시도 시험도 통과했다. |

실제 저장은 내용 리비전과 타임라인 이력을 각각 한 단계 진행시켰다. 지정 장면만 이동했고 텍스트·오디오의 절대 시각과 gain을 보존했다. 소유·신선도·대상 범위·비공개 제외의 기존 회귀를 재실행했다. 상위 호출자는 시작 잠금의 `busy` 응답과 본문·커밋 오류를 구분하고, 커밋 오류의 결과가 불명확하면 현재 저장 상태를 재조회해야 한다. [집중 시험](../../tests/reference-analysis/project-apply.test.ts)
