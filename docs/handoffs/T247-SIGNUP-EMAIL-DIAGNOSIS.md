# T247 관리자 가입 확인 메일 미수신 진단

- 담당: Codex(Front)(term_a0a6f98c) · 배정: CX-MASTER-01 `msg_f02a508ad900`
- 상태: **코드 진단·문구 개선 완료 · 운영(Supabase) 확인은 권한 거절로 못 함**
- 대표 메일은 `y***@gmail.com`으로만 적어요(공개 저장소 비밀 검사 때문).

## 1. 왜 운영 확인을 못 했나
- 바로 앞 T246에서 운영 설정값을 읽으려던 동작이 도구 권한 확인에서 **"권한 없는 접근"으로 거절**됐어요.
- Master 재검토(`msg_1f66d00d4b66`) 뒤 Supabase 대시보드 읽기를 따로 1번 시도했어요.
  - 방법: ego에서 운영 프로젝트의 Users 화면을 열고, 대표 메일 행의 상태만 가려서 읽는 스크립트였어요.
  - 결과: 이것도 **Claude Code 자동 승인 검토기가 `[Unauthorized Access]`로 거절**했어요. Supabase 서비스의 401/403이 아니에요.
  - 스크립트가 실행되지 않아서 브라우저를 열지 않았고 요청 ID도 없어요. 시각은 16:3x(KST)예요.
  - 우회하지 않았어요. 같은 정보를 다른 경로로 읽지도 않았어요.
- Auth 로그와 SMTP 설정도 같은 대시보드 접근이라 시도하지 않았어요.
- 실제 메일 재전송 1회도 하지 않았어요.

## 2. 가입 흐름(코드 근거: `app/api/auth/signup/route.ts`, `components/auth/login-form.tsx`)
- 관리자 로그인(`/admin/login`)에는 가입 탭이 없어요. 가입은 일반 `/login`의 회원가입 탭에서만 돼요.
- 서버가 **메일을 보내지 않았는데도 "가입 확인 메일을 보냈어요"를 보이는 경우**가 두 가지 있어요. 둘 다 계정이 있는지 드러내지 않으려고 일부러 그렇게 했어요.
  - **(A) 허용 밖 주소:** 운영 `DREAM_ALLOWED_EMAILS`에 그 주소가 없으면 Supabase를 부르지도 않아요.
  - **(B) 이미 있는 계정:** `user_already_exists`면 성공 문구를 보여요. 또 Supabase는 메일 인증을 켠 상태에서 이미 확인된 계정으로 다시 가입하면 오류 없이 가짜 사용자를 돌려주고 메일은 보내지 않아요.
- 진짜 실패는 성공으로 보이지 않아요.
  - 429 → "잠시 뒤에 다시"
  - 가입 꺼짐 → 403
  - 그 밖 오류 → 502 "가입 메일을 보내지 못했어요"
  - 화면은 모두 "가입하지 못했어요"(빨간 알림)로 보여요.
  - 진짜 실패를 성공으로 보이는 결함은 없어요.
- 다만 위 (A)·(B)에서도 "보냈어요"로 **실발송을 단정**했어요. 그래서 문구를 고쳤어요.
  - 바뀐 문구: "가입 요청을 받았어요. 가입할 수 있는 주소라면 확인 메일이 가요. … 메일이 오지 않으면 이미 가입한 주소일 수 있으니 로그인하거나 비밀번호 찾기를 써 주세요."
  - 바꾼 곳: `app/api/auth/signup/route.ts`의 문구 상수 1줄과 주석
  - 계정 존재를 드러내지 않는 방식은 그대로예요. 세 경우 응답이 같아요.
  - 새 시험 `tests/t247-signup-notice.test.ts` 3건이에요. 실발송 단정이 없는지, 허용 밖·새 계정·이미 있는 계정 응답이 같은지, 429·가입 꺼짐·그 밖 오류가 성공으로 보이지 않는지 확인해요.
  - 관련 4파일 vitest: `4 passed (4)`, `65 passed (65)`
  - tsc: 공유 `.next` 생성 파일 오류 말고는 0건이에요. eslint 0.

## 4. 권하는 조치(사용자 또는 운영 권한이 있는 Master)
1. Supabase 운영 프로젝트 → Authentication → Users에서 대표 메일 계정이 있는지, Confirmed인지만 봐요.
   - **있고 Confirmed면:** 가입이 아니라 `/admin/login`의 "비밀번호 찾기"로 비밀번호를 정하면 돼요. 이게 원래 정한 흐름이에요.
   - **있는데 미확인이면:** Users 화면의 확인 메일 재전송을 1회만 해요. 발송 제한에 걸리면 반복하지 않아요.
   - **없으면:** T246의 운영 허용 목록부터 확인해요.
2. Authentication → Logs에서 가입 시각의 `/signup` 기록과 상태 코드를 보면 원인이 확정돼요.
3. 스팸함을 확인해요.
