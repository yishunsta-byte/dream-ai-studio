## 독립 신뢰 원천과 실제 연결

- **운영 제어 저장소.** 대상 DB·Storage와 별도 자격, 역할, 백업·복구 경계를 가진 서버 전용 저장소에서 `storeId`마다 단일 활성 포인터를 관리한다. 상태·리비전 변경과 최종 응답 판정은 최신성이 보장되는 한 직렬화 지점을 사용한다. 이 저장소 자체가 복구되면 해당 저장소를 닫은 채 독립 감사 기록에서 마지막 전환, 발급까지 갔을 수 있는 세대, 포인터 리비전과 전환 이력의 연속성을 대조한다. 최신성을 입증하기 전에는 활성화하지 않는다. 이전 값은 모두 사용된 것으로 취급하고 검증된 새 세대로 진행한다.
- **채널에 결합한 대상 증명(F309-1).** 외부 증명은 환경·스토어·복원 세대·전환 ID, 플랫폼이 확인한 인스턴스와 복구 사건, TLS 대상, 실제 DB, Auth 발급자와 Storage 프로젝트·버킷·버전 정책, 만료를 묶는다. 새 풀뿐 아니라 **각 실제 PG 연결 생성·재연결과 대여 시** 그 채널의 인스턴스가 증명에 속하는지 확인한다. 같은 주소·인증서·DB 이름·OID·DB 내부 증거를 갖춘 원본과 복원본을 별도 대상으로 구별할 수 있어야 한다. 후보는 입증된 직접 연결이다. 풀러가 백엔드를 바꿀 수 있는 경우 매 트랜잭션에서 실제 백엔드와 증명을 결합하는 방법이 확인된 경우에만 허용한다. 복원·승격 사전 신호를 전환 차단에 사용하거나, 플랫폼이 제공하는 복구 사건과 세션 귀속을 운영 전환 전에 강제 확인한다. 통제할 수 없는 제자리 복원·자동 승격은 비활성으로 유지한다.
- **풀 종료.** 증명 만료·변경·불일치, 대상 확인 실패, 외부 전환 신호가 오면 풀을 즉시 서비스에서 빼고 신규 대여를 막는다. 사용 중인 요청과 트랜잭션을 취소하고 대여 중인 연결도 폐기한다. 중단된 트랜잭션 및 잔여 세션을 대조한 뒤 새 대상·세대에 결합된 풀을 연다. 증명 갱신이 실패하면 이전 증명으로 조회하지 않는다. [T261 TLS·대상 확인](T261-MANAGED-PG17-STAGING-CHECKLIST.md) · [T307 시작 검증](T307-F1-REA-AUTHORITY-LOGIN-PREFLIGHT.md)
- **Auth와 객체 귀속.** 허용된 환경의 Auth 발급자·프로젝트를 서버 자격 및 현재 서버 `getUser`와 대조한다. 검증된 사용자 ID를 해당 발급자와 함께 신뢰된 소유자 매핑에 적용한다. 다른 발급자의 동일 UUID, 이메일 일치, 복원본의 어제 승인만으로 현재 소유권을 얻을 수 없다. Storage는 SQL4 `provider_version`을 지정해 그 버전만 읽거나, 승인된 프로젝트와 비공개 버킷에서 키의 덮어쓰기·재사용 불가와 삭제 시 증거 차단이 강제되는 계약을 채택한다. 현재 SDK는 키로 다운로드하고 바이트·해시를 확인하므로 버전 고정안에는 버전 지정 호출이 필요하다. 목록은 DB 증거를 조회하고, T302는 파일 누락·변조 시 분석을 거절한다. 검증 담당이 증거를 폐기하면 목록에서도 제외한다. [서버 Auth](../../lib/auth/resolve.ts) · [현재 Storage 읽기](../../lib/storage/supabase/reader.ts) · [T302 검증](../../lib/reference-analysis/studio-verified-storage-analysis.ts)
- **공통 조회.** 검증된 대상의 새 소유자 범위 읽기 트랜잭션에서 동일 복원 세대, 자료 증거, SQL4 등록·현재 정책·검증, 현재 권한·용도를 대조한다. 활성 포인터·대상·증명·기한을 확인할 수 없으면 연결 불가다. 정상 대상에서 개별 자료 증거가 누락·만료·불일치하면 목록에서 해당 자료를 제외하고 단건 권한을 반환하지 않는다. 목록 공개 필드는 프로젝트 ID·자료 ID·표시 이름이다. 증거와 경로·해시·세대는 서버 내부에서만 쓴다. [목록 반환](../../lib/reference-analysis/studio-registered-analysis-page.ts)

## HTTP 응답 확정과 철회 순서(F309-2)

1. 앱은 외부 제어 경계에서 `storeId`·복원 세대·전환 리비전·권한 변경 리비전·검증된 사용자·요청 ID·기한에 묶인 준비 허가를 받는다. 현재 Auth와 DB 증거를 재확인해 완성한 응답을 내부 채널로 **전송 경계 하나에 넘긴다.** 이 경계가 브라우저 연결, 일회성 허가 소비, 보호된 첫 바이트와 나머지 스트림, 종료·취소를 소유한다. 앱이 직접 보내는 대체 경로, 공유 캐시, 이전 RSC 사전 요청 재사용을 차단한다. 목록 HTML·RSC 탐색/사전 요청, 분석 POST, 향후 적용 결과 확인이 모두 대상이다. [T301 반환](../../lib/reference-analysis/studio-registered-analysis-page.ts) · [T302 최종 조회](../../lib/reference-analysis/studio-verified-storage-analysis.ts) · [분석 HTTP 응답](../../lib/reference-analysis/studio-analysis-http.ts)
2. **전송 시작의 기준은 전송 경계가 첫 보호 바이트를 외부 전송 큐에 넘기는 시점이다.** 전송 경계의 현재 소유자가 권한 변경 장벽과 직렬화되는 구간 안에서 같은 요청·채널·본문의 허가를 소비하고, 첫 큐 삽입까지 수행한다. 전환·권한 리비전·대상과 요청·Auth·대상 증명·DB 증거의 최단 기한을 대조한다. 큐 삽입을 확정할 수 없는 동안에는 변경 장벽을 통과시키지 않는다. 외부 허가 승인 직후 또는 소비 뒤 첫 큐 삽입 전 정지하면 앱에 전송 권한이 생기지 않는다. 취소·만료가 먼저면 전송 경계가 최초 삽입을 거절한다. 일반 프레임워크 응답 반환이나 큐 삽입 전에 끝나는 검증은 이 경계를 구현하지 못한다.
3. 철회는 같은 장벽에서 시작과 경합한다. Auth·소유자·범위·링크·보관·SQL4 정책·자료 상태 변경은 새 허가·시작을 먼저 닫고 리비전을 전진시킨 뒤 반영한다. 먼저 큐에 들어간 응답은 발급 당시 승인된 전송이다. 철회·만료가 확정되기 전에 나간 바이트나 클라이언트 보관분은 회수할 수 없다. 전송 경계는 아직 넘기지 않은 바이트를 제한된 종료 기한까지 마치거나 연결을 끊고 버린다. 전환에서 이 종료 규칙을 강제하고 종료 상태가 확인된 뒤 새 세대를 연다. 제공자 변경을 우회하는 경로가 확인되거나 시계·대상·상태를 입증할 수 없으면 새 허가를 닫는다.

| 전송 경계가 기록하는 상태 | 시작·정리 및 전환 판정 |
| --- | --- |
| 준비/허가 발급, 첫 바이트 전 | 전송 소유자만 시작을 확정할 수 있다. 전환은 새 시작을 막고 허가를 취소한다. 기한 초과도 소유자가 미전송과 폐기를 확인해야 정리로 세며, 허가 만료나 앱 종료 신호만으로 정리하지 않는다. |
| 시작 확인, 전송 중 | 새 연결이나 앱 재개로 본문을 다시 시작하지 않는다. 기존 전송의 완료 또는 제한 기한 뒤 중단을 기다린다. |
| 정상 종료 또는 취소·중단 확인 | 전송 경계에서 스트림 종료, 추가 쓰기 불가, 미전송 버퍼 제거를 확인한 상태다. 정리에 산입한다. 이미 건넨 바이트의 클라이언트 수신 확인까지 기다리는 의미는 아니다. |
| 첫 큐 삽입·종료 결과 불명, 소유자 장애 | 재생 없이 비활성을 유지한다. 동일 경계의 신뢰 로그에서 결과를 확인하거나 이전 소유자·클라이언트 전송 채널을 차단하고 하위 전송 큐의 추가 방출이 없음을 확인한 뒤 종료로 정리한다. 이전 프록시 또는 앱이 계속 브라우저에 보낼 수 있는 구성은 사용할 수 없다. |

전송 경계는 최초 큐 삽입 전에 요청·채널·전송 소유 번호를 복구 가능한 상태로 기록한다. 중단으로 삽입 결과가 사라지면 미전송으로 추정하지 않는다. 전송 경계가 교대할 때도 구 소유자의 연결·큐 쓰기를 먼저 막고, 이전 채널의 종료를 확인한다. 같은 요청의 본문을 다시 보내는 데 이 기록을 사용하지 않는다.

## 복원·승격·재바인딩 순서

1. **전환 접수.** 승인된 전환 요청 ID·입력 지문·검증 대상·이전 포인터 리비전·백업 복구 지점과 Storage 검증 기준을 외부에 기록한다. CAS에서 한 전환만 접수한다. 새 허가를 닫고 아래의 응답·DB·Storage 정리 기준을 모두 확인한 뒤 대상 작업을 시작한다.
2. **대상 준비.** 격리된 대상에서 승인된 복원·승격·재바인딩을 아래의 단계별 호출 계약으로 수행한다. 플랫폼 완료 결과와 실제 대상 식별, DB 이력·카탈로그, 신뢰 TLS, Auth 매핑과 버킷·객체 신뢰 조건을 새 연결로 대조한다. 스키마 또는 역할 변경은 승인된 별도 마이그레이션에서 처리한다. 이전 활성 세대는 이 단계에 다시 열 수 없다.
3. **새 세대 발급.** 대상이 확인되면 외부 제어 저장소가 새 `restoreGeneration`을 한 번 할당하고 전환 ID·확인 대상과 함께 준비 상태로 고정한다. 대상에 새 세대와 준비 작업 번호를 기록한다. 복원 사본의 자료 증거 및 활성 권한은 새 세대에서 닫힌 상태로 시작하고 아래 기준으로 재구성한다.
4. **자료 검증과 발급.** 실제 새 대상의 등록 객체를 현재 승인된 Storage 검증 경로로 대조한다. 검증 대상 바이트·버전·등록 식별과 SQL4 현재 검증 기록이 모두 확인된 자료에만 새 증거를 만든다. 복원/승격/리바인딩 후 현재 Storage와 이전 검증 기록을 다시 결합할 근거가 없는 자료는 새 검증 기록을 요구한다. 새 검증 경로가 없다면 그 자료를 미승인으로 남긴다. 준비 상태에서는 앱 트래픽을 받지 않는다.
5. **전환 확정.** 격리 확인에서 대상, 제한 역할, A/B, 권한·검증 실패 및 조회 필드를 대조한다. 준비 완료 기록의 전환 ID·지문·대상 증명·새 세대·작업 번호·권한 대조 완료 위치가 현재 외부 전환과 일치해야 한다. 준비 쓰기를 닫고 종료를 확인한 뒤 새 활성 작업 번호를 부여한다. 외부 포인터를 CAS로 활성화하고 새 풀을 연다. 실패 시 닫힌 상태를 유지한다. 이전 환경으로 돌아갈 때도 새 전환과 새 세대를 사용한다.

### 같은 전환의 조정자 교대와 플랫폼 결과 확인(F309-3)

- 전환 단계마다 외부 저장소에 전환 ID, 단계, 환경·대상·입력 지문, 단계 상태와 현재 조정자 작업 번호를 저장한다. 교대는 같은 단계의 기존 상태와 번호를 CAS로 확인하고 작업 번호를 단조 증가시킨다. 이전 번호의 조정자는 재개해도 새 호출 시작, 단계 완료 기록, 후속 단계나 활성 포인터 변경이 거절된다. 번호는 조정자 권한을 구분한다. 아래의 플랫폼 작업 키는 교대해도 그대로다.
- 상태 변경 호출은 공통 실행 경계만 보낼 수 있다. 현재 조정자 번호의 최종 확인과 호출 인계는 교대와 직렬화한다. 복원·승격 등 각 호출 전에 전환 ID·단계에서 정한 **고정 플랫폼 작업 키**와 정확한 대상·인자 지문을 외부 원장에 먼저 기록한다. 이전 조정자는 실행 경계 밖에서 외부 호출 자격을 사용할 수 없다. 인계 기록 후 제공자 전달 여부를 잃었거나 구 실행 경계에 미전송 호출이 남으면 이를 미확정으로 처리한다. 새 조정자는 동일 키나 제공자가 반환한 작업 ID로 진행·완료를 확인한다. 완료는 대상·인자와 실제 결과가 일치할 때만 채택하고, 실행 중이면 기다린다.
- 미실행을 권위 있는 결과로 확인한 경우에만 같은 키로 호출한다. 결과가 유실된 호출은 제공자가 같은 키·인자에 대한 중복 방지를 보장하고 그 보장 기간이 미확정 호출을 모두 덮을 때에만 동일 키 재전송을 허용한다. 일시적으로 조회에 나타나지 않는 작업, 기한이 지난 중복 방지 계약, 완료 여부나 대상이 불명확한 응답은 미확정이다. 새 키 발급과 후속 단계 진행을 막고 전환을 닫아 둔다. 이미 끝난 플랫폼 호출은 새 조정자가 결과를 채택할 수 있어도 다시 실행할 수 없다.

## 백업 이후 권한 재구성(F309-5)

- 백업에 대응하는 검증된 기준 상태와 원천별 이력 위치를 확보한다. Auth 발급자·소유자 매핑 및 자격 상태와 REA 소유자·프로젝트·범위, 링크 용도, 프로젝트·자료 보관/해제에 관한 승인·철회를 대상 DB 밖의 신뢰 이력과 대조한다. 원천별 기준 위치부터 전환 직전의 확정 위치까지 누락 없이 검증한다. 권한 변경 장벽에서 신규 변경을 차단하거나 직렬화해 최종 위치를 고정하고, 활성화 전 그 위치 이후 미처리 변경이 없는지 확인한다. 시간 표지만으로 연속성을 추정하지 않는다.
- 이력이 누락·불일치하는 범위는 비활성이다. 수동 재승인은 새 복원 세대, 현재 검증된 발급자·소유자, 활성 프로젝트·자료·정확한 용도, 최신 권한 리비전에 귀속한다. 권한 재생도 새 세대에서 현재 승인과 철회를 적용하며 백업 속 활성값이나 이전 번호를 그대로 반영하지 않는다. 재생·수동 승인과 철회가 경합하면 먼저 기록된 최신 철회는 이전 위치를 기준으로 한 재생·승인을 거절한다. 이후 새 명시적 승인만 그 철회를 넘어설 수 있다.
- 이전 적용 결과 기록, 미완료 확인 및 백업 이전에 발급된 오래된 Auth 세션은 새 권한 근거가 될 수 없다. 새 세대의 Auth 확인은 현재 발급자에서 다시 검증하며 세션 철회 또는 적절한 재인증 기준을 확인한다. 이전 적용 결과 기록은 T282의 현재 권한 및 세대 일치 검사에서 제외된다. [T280 전이](T280-REA-MANAGED-AUTHORITY-GENERATIONS.md) · [T282](T282-REA-RECEIPT-AUTHORITY-GENERATIONS.md)

## 늦은 쓰기 차단과 현재 SQL4 정책(F309-3·4)

- **DB 저장 경계.** 제한 발급·폐기와 향후 적용 함수는 트랜잭션 안에서 제어 행을 잠근 뒤, 실제 대상·현재 복원 세대·전환 ID·작업 번호·작업 종류·허가 기한을 대조한다. 작업 허가는 검증된 서버 주체에 귀속한다. 요청이 직접 전달한 번호는 승인 근거가 될 수 없다. 잠금은 커밋까지 유지한다. 준비 배치는 승인된 전환과 준비 작업 번호 안에서 증거만 만들 수 있다. 활성 발급·폐기 및 향후 적용은 활성 작업 번호와 현재 상태를 요구한다. 준비 작업은 활성 전환 후에도 재사용할 수 없다. 전환 설치 역할은 같은 행을 배타적으로 잠가 이전 번호와 쓰기를 닫는다. 차단보다 앞서 제어 행을 잠근 트랜잭션이 있다면 먼저 완료 여부를 확인하거나 취소한다. 차단 확정 후에는 이전 세대 커밋이 없어야 한다. 직접 DML 경로와 구 자격을 닫고 세션·풀 종료를 대조한다. 같은 주소로 재연결된 이전 작업도 새 자격과 작업 번호가 없으면 저장에서 거절된다.
- **Storage 변경 경계.** 이전 세대에 발급한 업로드·복사·삭제 권한까지 목록화한다. 제공자에서 자격·서명 권한을 회수하거나 마지막 실제 수락 기한과 처리 중 변경의 종료를 확인한다. 불변성에 의존하는 경우 이전 작업이 새 세대의 객체·버전에 미칠 효과가 플랫폼에서 강제로 차단되어야 한다. 세대가 다른 격리 대상이나 회수 가능한 단기·객체 제한 권한이 후보이며, 이전 프로세스만 종료하는 절차로는 충분하지 않다. 상태를 확인할 수 없는 변경이나 자격이 남으면 전환을 열지 않는다.
- **현재 SQL4 정책.** 운영 조회와 발급은 검증 기록의 `policy_id`, `policy_epoch`, `policy_digest`를 현재 `storage_policies` 행과 정확히 대조한다. 교체 후 새 조회는 이전 정책 증거를 제외한다. 이미 시작한 조회의 최종 전송은 변경 장벽에서 다시 판정한다. 발급·폐기는 제어 행과 정책 공유 잠금부터 시작해 B16의 객체 장벽→검증 작업→자료/현재 상태 순으로 필요한 행을 잠근 뒤 증거 포인터를 잠근다. 여러 객체·작업은 ID 순으로 잠근다. 같은 잠금에서 현재 정책·등록 상태·검증 기록을 다시 비교한다. 파일 확인과 외부 호출은 트랜잭션 밖에서 마친다. 증거 발급 경로는 T281 권한 행을 잠그거나 갱신하지 않는다. 두 계열을 함께 잠그는 향후 쓰기는 제어 행과 T281 소유자→프로젝트→자료, B16 순서를 포함한 공통 순서를 별도 확정하고 경합을 검증한 뒤 제공한다. [SQL4](../../lib/db/postgres/0004_storage_verification.sql) · [B16 잠금 계약](B16-STORAGE-UPLOAD-WORKER-CONTRACT.md) · [T281](../../tests/reference-analysis/managed-authority-generations.sql)
- **운영 역할 준비.** SQL4 고정본은 격리용 제약과 트리거를 제공하며, T307 격리 조회는 현재 정책 테이블까지 대조하지 않는다. 승인된 재검증 진입점과 제한 발급·폐기·전환 함수, 고정 스키마·검색 경로, 필요한 잠금 권한 및 FORCE RLS는 후속 마이그레이션에서 다룬다. 역할 속성과 직접·간접 멤버십, 소유권, 전이 함수의 실제 EXECUTE와 잠금·읽기·쓰기 권한을 시험한다. 발급자는 증거 변경 함수만 사용할 수 있다. [T307 조회](../../lib/reference-analysis/studio-analysis-authority-store.ts) · [T307-F1](T307-F1-REA-AUTHORITY-LOGIN-PREFLIGHT.md)

## 자료 증거와 재실행 규칙

- 자료 증거는 `(storeId, restoreGeneration, ownerId, assetId, objectId, identityDigest, verificationRecordId, storageGeneration)`과 SQL4 정책 식별·epoch·digest, 새 `sourceGeneration`, 요청 ID·지문·시각을 결합한다. 기한은 현재 검증 기록, 전환 증거, 발급 정책 기한의 최솟값을 넘지 않는다. 발급과 폐기 CAS는 실제 대상·세대·작업 번호·현재 SQL4 튜플·예상 포인터 리비전을 대조한다. 자료 포인터는 키마다 지속하고, 폐기하면 리비전을 올려 활성 값을 닫고 폐기 기록을 남긴다. 자료가 없던 상태로 되돌려 리비전을 초기화하지 않는다. 따라서 같은 SQL4 튜플을 읽은 늦은 요청도 과거 리비전으로 폐기를 뒤집을 수 없다. 검증이 사라지거나 폐기된 경우에도 닫는 작업을 수행할 수 있도록 폐기의 CAS는 현재 실패/누락 상태를 명시적으로 관측해 대조한다.
- 변경 객체는 새 등록·검증 및 자체 프로젝트 연결과 승인을 요구한다. 갱신과 만료 후 재활성화에는 새 검증 ID·스토리지 세대와 새 자료 세대를 발급한다. 동일 해시의 재검증도 이 규칙을 따른다. 폐기된 증거를 다시 사용할 수 없다. 폐기에서 복구해야 할 경우 최신 폐기 리비전을 기준으로 새 검증·승인·요청을 시작한다. 현재 T281 권한 조건은 자료 증거 갱신과 별도로 적용된다.
- **DB 요청 원장.** 원장은 `(storeId, restoreGeneration, requestId)`를 하나의 고유 키로 사용한다. 대상·작업 종류·요청 입력의 지문은 확정된 예약 행에 불변으로 저장한다. 같은 ID의 다른 지문은 기존 행과 충돌하며 같은 시도에 새 키를 할당하지 않는다. 예약이 확인된 뒤에만 업무 변경을 시작하고, 발급·폐기 결과와 증거 포인터는 한 트랜잭션에서 확정한다. 이미 확정된 요청의 상태 조회는 읽기 전용이며 포인터·기한·세대를 바꾸지 않는다.
- **진행 중 COMMIT과 재시도.** 별도 읽기에 원장 행이 없거나 예약 상태만 보일 때는 미확정이다. 최초 예약·업무 처리·재실행은 모두 제어 행을 잡은 뒤 같은 요청 키의 트랜잭션 잠금을 획득하고 커밋/롤백까지 유지한다. 잠금 확인과 원장 조회는 같은 실제 연결에서 수행한다. 원래 트랜잭션이 확정적으로 끝났음을 확인하거나, 요청 잠금에서 직렬화한 뒤 `READ COMMITTED`의 새 문장으로 원장을 다시 읽는다. 재실행 판단과 변경은 요청 잠금을 보유한 채 수행한다. 잠금 대기 기한 초과 또는 현재 대상 확인 실패는 미확정 상태를 유지한다. [B16 쓰기 계약](B16-STORAGE-UPLOAD-WORKER-CONTRACT.md) · [T261 미확정 처리 기준](T261-MANAGED-PG17-STAGING-CHECKLIST.md)
- 원장이 확정 성공을 보여 주면 읽기 결과를 반환하고 업무 변경을 생략한다. 예약과 이전 시도의 종료 또는 직렬화가 확인되고 해당 변경이 미적용이며, 같은 요청 지문·현재 대상·세대·유효한 작업 번호·예상 증거 포인터·현재 SQL4 튜플이 모두 맞을 때만 다시 쓴다. 원장 부재가 예약 자체의 미적용으로 확인되면 같은 키·지문 예약부터 재개하며 직접 업무 변경으로 넘어가지 않는다. 외부 원장 및 단계 결과와 다른 부분 상태·관측 불가는 전환을 닫고 조정한다. 플랫폼 호출의 재전송은 앞의 외부 작업 키 계약으로만 결정한다.
- 향후 적용은 DB 쓰기 성공과 적용 결과 기록을 사용자에게 보여 줄 수 있는지를 각각 판정한다. 커밋이 확인돼도 현재 발급자·소유자·권한과 세대·보존 기한 및 최종 응답 허가를 별도로 확인한다. 결과 전달이 거절됐다는 이유로 쓰기를 다시 실행하지 않는다. [T282 적용 결과 기록](T282-REA-RECEIPT-AUTHORITY-GENERATIONS.md)

## 플랫폼에서 아직 확인하지 못한 조건

- 관리형 PG의 제자리 복원·자동 승격을 사전에 차단하거나 관측해 동일 주소의 실제 백엔드 세션에 결합할 수 있는지 확인하지 않았다. 풀러 뒤 실제 세션 귀속, 구 자격 및 진행 중인 쓰기 종료를 증명할 수 있는지도 미확인이다.
- 현재 키 기반 Storage 읽기의 버전 지정 가능 여부, 불변성 강제 범위, 이전 업로드·삭제 권한과 처리 중 요청의 회수·종료를 확인하지 않았다. Auth의 복구 대상·발급자 대조, 외부 변경의 강제 차단·전달 및 독립 권한 이력의 연속성도 미확인이다.
- 실제 Next 호스팅에서 HTML/RSC·POST의 브라우저 전송과 하위 프록시 큐를 하나의 경계가 통제할 수 있는지 미확인이다. 최초 삽입과 종료의 관측, 우회 차단, 장애 시 구 전송 소유자 및 큐 중단을 입증할 때까지 보호 경로를 열지 않는다.
- 플랫폼 복원·승격 API의 고정 키 또는 작업 ID 조회, 중복 방지 범위·보장 기간·조회 최신성은 미확인이다. 결과 유실 시 권위 있게 판별할 수 없는 단계는 자동 재개하지 않는다. 실제 배포 DB에서 동일 요청 잠금과 별도 원장 읽기의 커밋 가시성 및 장애 시 연결 귀속도 검증이 필요하다.
