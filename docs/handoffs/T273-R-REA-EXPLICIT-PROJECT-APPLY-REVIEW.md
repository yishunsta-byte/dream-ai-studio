**조건부 통과.** 기존 장면 순서 적용, 명시적 확인과 신선도, CAS·재전송 방지 및 전체 롤백을 격리 SQLite에서 검증했다. 실제 서버 경로를 연결하기 전에는 쓰기 잠금 대기 초과를 재시도 가능한 응답으로 처리해야 한다. [구현 보고](T273-REA-EXPLICIT-PROJECT-APPLY.md)

## P2 · 동시 쓰기 잠금이 지속되면 `SQLITE_BUSY`가 그대로 호출자에 전달됨

같은 SQLite 파일의 두 연결에서 기준 타임라인과 확인 객체를 각각 준비했다. 첫 연결에서 쓰기 트랜잭션을 열어 둔 채 두 번째 연결에서 적용하면 약 5.4초의 기본 대기 뒤 `SQLITE_BUSY` 예외가 발생했다. 즉시 실패 설정에서도 같은 코드를 재현했다. 논리 DB 스냅샷은 그대로였다. 첫 요청이 정상 커밋된 다음에는 경쟁 객체와 성공 객체의 재전송이 모두 `conflict`로 분리됐다. [REA 오류 처리](../../lib/reference-analysis/project-apply.ts) · [SQLite 연결 설정](../../lib/db/connection.ts)

실제 호출 경계에서 잠금 대기 초과를 타입이 정해진 재시도 가능 상태로 바꾸고, 확정된 리비전 충돌과 구분한다. 응답에 SQLite 원문을 전달하지 않는다. 잠금 이후 재시도에서는 현재 권한·신선도·CAS를 다시 확인한다. 현재 서비스의 원자성은 이 실패에서도 유지됐다.

## 독립 확인

- 합성 S4를 임시 SQLite로 복원하고 마이그레이션했다. 기존 제품 서비스를 통해 실제 합성 WAV가 연결된 v2 타임라인을 저장한 뒤, 별도 합성 MP4에서 생성한 컷 미리보기로 적용을 준비했다. `prepare`와 확인 거부는 DB를 바꾸지 않았다. 동일 위치는 `no_change`, 수정된 리비전·만료는 `stale`, 다른 액터와 변조·다른 서비스의 확인 객체는 거절됐다. 소유자·프로젝트·소스 조회자는 적용 중 동일 연결의 트랜잭션 안에서 실행됐다.
- 사용자가 지정한 두 기존 장면으로 위치를 계산했다. 연결된 소재가 없는 장면, 프로젝트 밖 장면, 미확인 선택과 프레임 단독·이미지 제안을 거절하는 회귀를 확인했다. 적용 성공은 타임라인을 한 리비전 진행시켰고 나머지 클립, 텍스트 및 **실제 오디오 클립의 절대 타이밍·gain**을 보존했다. 기존 타임라인 행은 유지됐으며 후속 검수 단계가 잠겼다. [적용 회귀](../../tests/reference-analysis/project-apply.test.ts) · [기존 타임라인 저장](../../lib/services/timeline.ts)
- 기존 포인터 갱신 실패 시험을 재실행했다. 별도 복사본에서는 포인터·장면 위치·내용 리비전·단계 갱신보다 뒤에 수행되는 `activity_log` 쓰기를 실패시켰다. 실패 후 전체 논리 스냅샷이 동일했고 트리거 제거 뒤 같은 확인으로 한 번만 저장했다. 다른 연결의 오래된 확인과 성공 확인의 재전송은 추가 기록을 만들지 않았다.
- 확인 요약, 저장 응답과 새 타임라인에 참조 파일명·경로·픽셀·원본 PTS·프롬프트·근거 ID·분석 식별자가 없었다. 실행 코드는 서버 모듈이며 제품 라우트·서버 액션·Studio에서 호출되지 않는다. 실제 연결은 확인 의사, 현재 액터·프로젝트·소스·분석의 활성 상태, 시작 점검과 프로세스 간 확인 객체 수명을 담당해야 한다. [적용 서비스](../../lib/reference-analysis/project-apply.ts)
