# T354-R 프로젝트 조회 요청 인증 조립 독립 검수

2026-11-19 KST · Codex(Tester) · 고정 커밋 `344be9c` · Master 배정 `msg_b8ec7a98edbe`

**격리 후보 검수 통과.** 고정 변경 3경로는 요청 인증 조립기, 집중 시험, 인계다. 설치된 `@supabase/ssr` 0.12.7과 `@supabase/auth-js` 2.119.0 및 기존 쿠키 클라이언트를 실행했다. Next 쿠키 저장소와 네트워크 응답은 모의였다.

- 같은 요청에서 SSR SDK가 쿠키의 액세스 토큰만 읽고 `getUser(token)`으로 사용자를 확인했다. 쿠키에 담긴 사용자와 무관하게 SDK가 반환한 사용자와 기존 이메일 허용 정책을 적용했다. 동일 토큰을 후반 Auth와 데이터 요청에도 사용했다. 한 요청의 목록·상세는 인증 결정을 공유했고, 분리된 병렬 A/B 요청은 각자의 쿠키·토큰만 썼다.
- 만료 쿠키 갱신 시 새 토큰만 두 Auth 호출과 조회에 전달됐다. 쓰기 가능한 모의 쿠키 저장소는 갱신값을 받았다. 독립 읽기 전용 쿠키 시험에선 쓰기 시도는 거절됐지만 그 요청에서는 SDK가 갱신 토큰을 사용했고 저장된 쿠키는 그대로였다. 실제 Next 응답에서 쿠키를 지속하거나 proxy가 갱신을 맡는 동작은 별도 연결 검증 범위다.
- 익명·만료·다른 issuer·잘못된 토큰이나 갱신 거부는 401, 이메일 차단은 403, 주체 불일치는 401이었다. Auth 장애·프로젝트 또는 키 설정 불일치에는 고정 503이 반환됐다. 추가 시험에서 두 번째 Auth 응답의 사용자만 바뀌면 데이터 조회 전에 401로 닫혔다. 앱 응답의 `no-store`, 토큰·갱신 자격·공급자 오류 비노출과 제공 시험의 관련 로그를 확인했다.
- 정상 쿠키에서 SDK Auth와 T352 Auth가 각각 GET 한 번씩 발생했다. 갱신 시 SDK 토큰 POST가 추가됐다. T352 Auth와 데이터 조회에서는 `no-store`, 리디렉션 거부와 요청 취소 신호가 적용됐다. 쿠키를 읽는 동안 취소하면 SDK 호출이 없었다. 첫 SDK Auth 호출 진행 중 취소한 독립 시험에서는 그 호출에 신호·캐시·리디렉션 옵션이 전달되지 않았으며 응답을 돌려준 뒤 후속 Auth·데이터 호출 없이 고정 503으로 끝났다. 제품 연결 전 SDK Auth·갱신의 전송 정책과 쿠키 쓰기 주체를 확정해야 한다.

제공 집중 시험 14건을 포함한 관련 회귀는 347건 통과·30건 조건부 건너뜀이었다. 사본의 추가 독립 시험 3건, 소스 타입 검사, 변경 TypeScript ESLint와 diff 공백 검사도 통과했다. 검수 사본을 정리했다.

제품 라우트는 이 조립기를 호출하지 않는다. 실제 Supabase 발급 토큰·Auth·Data API, 실제 Next 쿠키 생명주기, 기존 proxy/렌더 Auth와의 합산 호출 수는 검증 범위 밖이다. 제품 파일·운영·빌드·배포·세션 변경은 없었다.
