# T325-R 관리자·공개 게시 공급원 조립 독립 검수

기준 `80aaa34` · Master 인계 `msg_9c83d1643041` · Codex(Tester)

**판정은 서버 조립 시험 통과.** 관리자 쓰기, 공개 목록, 공개 표지에 대해 신뢰 초기화 함수가 반환한 승인 대상 식별자가 모두 같을 때만 활성 공급원을 반환했다. 관리자 측이 다른 클러스터를 보고하면 공개 리더를 열지 않았다. 목록이나 표지 중 하나라도 다른 DB를 보고하거나 전송 직전 표지 확인이 없으면 관리자 `null`·공개 예시 목록·비활성 표지로 함께 닫혔다. [조립 모듈](../../lib/public-showcase/publication-provider-assembly.ts) · [조립 시험](../../tests/public-showcase/publication-provider-assembly.test.ts)

부분 초기화 실패 시 반환받은 핸들의 종료를 시도했다. 종료 호출을 반복하면 같은 작업을 기다렸고, 한쪽 종료가 실패해도 다른 쪽의 종료를 기다렸다. 종료 오류가 난 경우 그 자원이 닫혔다고 판정할 수는 없다. 초기화 함수가 핸들을 반환하기 전에 실패한 경우 해당 함수가 자기 자원을 정리하는 계약이다.

조립 시험은 합성 트랜잭션과 WebP를 사용했다. 관리자 준비 단계에서 목록과 표지가 숨겨졌고 게시 뒤 같은 세대의 목록과 GET 바이트·빈 HEAD가 일치했다. 철회 뒤 최초 표지 GET/HEAD는 404였으며 재게시로 새 세대가 열린 뒤에도 이전 표지는 404였다. 표지 바이트 읽기 도중 권리가 만료됐을 때 전송 직전 재확인에서 404였고 공개 목록과 GET/HEAD에서도 제외됐다.

별도로 소유 루프백 PG17.12의 T306 고정 SQL 시나리오를 다시 실행했다. 일치하는 시한부·무기한 게시, 정확한 종료 시각, 불일치 롤백과 동일 요청 재시도, 만료 후 목록·표지 차단, 제한 역할과 임시 클러스터 정리를 확인했다. 이 실행은 기존 SQL과 서비스의 일관성을 확인했다. 신규 조립과 실제 DB 자격·TLS·Storage를 연결하는 검증은 후속 범위다. [PG17 시나리오](../../tests/admin/t306-publication-e2e-native.ts)

신규 조립 8/8, 관련 관리자·공개·공용 인증·기존 게이트 19개 파일 541/541, 변경 파일 ESLint와 `git diff --check`가 통과했다. Next 생성물 없는 고정 사본에서 `tsc --noEmit --incremental false`는 통과했다. 공유 작업공간의 동일 명령은 기존 `.next/types/validator.ts`와 `.next/dev/types/validator.ts`에서만 오류 4건을 냈다. 두 파일은 없어진 Studio 경로와 이전 라우트 매개변수 검증을 참조한다. 공유 생성물을 수정하지 않았으며 Tester 빌드를 수행하지 않았다.

제품 관리자 기본 저장소와 공개 홈·표지 기본 연결에 신규 조립 호출이 없음을 고정 소스와 변경분에서 확인했다. 운영 DB·Storage·배포를 변경하지 않았다.
