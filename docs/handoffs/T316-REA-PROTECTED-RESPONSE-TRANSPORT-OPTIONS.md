# T316 보호 분석 응답의 운영 연결 결정안

2026-11-19 KST · Codes(Backend) · 배정 `msg_70fada4431d1`

**권고안.** Next/Vercel 페이지에는 분석 UI와 공용 상태만 렌더하도록 먼저 분리한다. 자료 목록과 분석 결과는 전용 HTTPS 송신 서비스에서만 브라우저에 반환하는 안을 격리 환경의 우선 후보로 검증한다. 그 서비스가 첫 바이트와 종료를 소유하고 이전 송신자를 차단할 수 있다는 근거를 확보할 때까지 실제 자료 연결은 비활성으로 둔다. 전체 Next 호스팅 이동은 이 검증의 선행 조건이 아니다.

## 단계 1 · HTML/RSC에서 자료 제거

1. 클라우드 분석 페이지의 서버 렌더가 자료 목록이나 개인 분석 결과를 읽어 props에 넣지 않도록 분리한다. 초기 HTML·인라인 RSC·별도 Flight/Suspense 조각·라우트 로딩과 메타데이터에는 일반 제목, 로딩·접근 불가 안내, 빈 UI만 둔다. 자료 ID·라벨·선택·결과를 props, URL, 사전 요청, 직렬화된 초기 상태, 공개 정적 산출물에 싣지 않는다.
2. 클라이언트가 활성 화면에서 로그인된 세션으로 목록을 별도 요청하고, 사용자의 선택을 기존 형식의 서버 검증을 거쳐 분석 요청으로 보낸다. UI에는 이미 허용하는 목록 필드와 검증한 분석 DTO만 전달한다. 페이지 이동·로그아웃·계정 교체 또는 복귀 시 진행 중 요청과 보유한 화면 데이터를 정리하고 새 권한으로 조회한다. 라우터 뒤로 가기와 bfcache 복귀에서 이전 결과가 다시 그려지는지 실측한다.
3. 준비 단계의 브라우저 접근 가능 앱 분석 POST는 연결 불가 응답으로 둔다. 보호 기능을 연결할 때 기존 URL, 환경별 도메인·배포 별칭·리다이렉트와 스트림 대체 경로도 점검한다. 도입 후 앱과 생산자는 보호 DTO를 브라우저에 직접 반환할 수 없고, 인증된 내부 채널로만 송신 서비스에 넘긴다. 전송 실패 시 앱 POST나 내부 오리진으로 대체하지 않는다.

## 단계 2 · 전용 송신 계약

- **권한과 키.** 기존 Auth의 검증된 발급자·세션·사용자 매핑을 재사용한다. 보호 서비스가 현재 사용자를 다시 확인한다. 별도 오리진에서는 기존 앱의 호스트 전용 쿠키가 넘어온다는 전제를 두지 않는다. 정확한 오리진으로 승인한 교환을 통해 보호 오리진 전용의 짧은 세션을 만든다. 쿠키 요청은 정확한 Origin, CSRF 및 CORS를 검증한다. DB·Storage 자격은 분석 생산자 서버에, 전송 권한과 송신 자격은 보호 서비스에 분리한다. 교환 증명이나 일회 허가는 URL·공용 로그·HTML/RSC·클라이언트 영구 저장소에 두지 않는다. 서명형을 선택하면 환경별 발급자·audience·키 ID와 허용 기간을 고정하고 키 교체 시 이전 키와 허가의 허용·폐기 상태를 공유한다. 서버 보관형이면 같은 결합 정보를 제어 저장소에서 검증한다. [현재 Auth 경계](../../lib/auth/resolve.ts)
- **공유 상태와 단일 소유자.** 외부 제어 저장소에 현재 대상·복원 세대·권한 리비전·전송 소유 번호를 저장한다. 허가는 검증된 사용자, 요청·연결, 본문 식별, 대상·세대·권한, 가장 이른 기한에 묶는다. 두 인스턴스에 도착해도 현재 송신 소유자 하나만 소비할 수 있다. 준비/시작/정상 종료/폐기 확인/불명을 관측할 수 있게 남긴다. 애플리케이션 락이나 원장만으로 옛 프로세스의 물리 연결을 통제할 수 없다. 교대 시 예전 송신자·연결을 강제로 차단할 수 있는 배치와 시험이 필요하다. [T309 단계별 상태](T309-REA-AUTHORITY-EVIDENCE-ISSUANCE-DESIGN.md)
- **전송·취소·전환.** 최종 TLS 연결 또는 소유가 입증된 모든 후단 큐에서 전송 경계가 허가를 소비하고 최초 보호 바이트 삽입을 철회와 직렬화한다. 신규 시작을 닫은 뒤 보호 바이트가 아직 나가지 않았다면 버퍼를 폐기한다. 이미 시작한 전송은 합의한 종료 기한 안에 완료하거나 끊고, 미전송 큐 제거와 더 이상 쓸 수 없음을 확인한다. 취소·만료, `ReadableStream` 종료, `after()`, 원장 응답 유실은 독립적으로 기록한다. 종료 미확인, 구 송신자 재개 가능, 대상·제어 저장소·키·시계 신뢰 미확인은 전환을 닫아 두는 조건이다. 새 허가·새 세대·구 본문 재전송을 차단하며, 판정 가능해진 뒤 현재 세대에서 새 요청을 받는다.
- **캐시와 종료 증거.** 보호 성공·오류 및 허가 교환에 브라우저/중간 경로의 저장 금지를 적용한다. `Cache-Control: private, no-store`와 실제 CDN별 우선순위를 함께 확인하고 데이터 캐시·라우터 프리페치·서비스 워커 저장·공유 CDN·오류 시 이전 응답 제공을 보호 경로에서 막는다. A/B·로그아웃·뒤로 가기/복귀·리다이렉트와 캐시 헤더/실제 HIT·MISS를 함께 관측한다. 이미 브라우저가 받아 보관하거나 사용자에게 표시된 데이터의 회수는 범위 밖이다. [Vercel 캐시 우선순위](https://vercel.com/docs/caching/cache-control-headers#behavior)

| **1. 기준 재현** | 고정 T313 실행기와 T315-F2 설치기·두 원시 기록을 대조하고, 합성 데이터로 소유 루프백에서 보류·철회·만료·느린 클라이언트·취소를 재현한다. 최초 바이트, 앱 종료, 실제 소켓/큐 종료를 각각 기록한다. 이 단계는 기존 증거 확인이다. |
| **2. 분리 검증** | 별도 합성 앱에서 초기 HTML·인라인 RSC·직접 Flight·기본/전체 프리페치·Suspense·브라우저 탐색/뒤로 가기·캐시·동일 URL 계정 전환을 측정한다. 페이지 경로에서 보호 표식과 허가 소비가 0이고, 승인된 인터랙션에서만 보호 JSON을 받는다. |
| **3. 전송 소유 검증** | 합성 앱/송신 인스턴스를 둘 이상 실행한다. 권한과 키 교체, 다른 오리진·사용자·요청·채널의 허가 재사용, 중복 요청 및 우회 주소를 검증한다. 첫 큐 삽입 전/후 정지, 느린 수신, 취소·만료, 권한 저장소 장애, 송신자 크래시·재개를 양방향 시험한다. 철회가 먼저면 실제 보호 바이트 0이다. 이미 시작한 경우는 종료 또는 폐기 증거와 구 인스턴스의 재전송 불가를 확인한 뒤에만 새 세대가 활성화돼야 한다. |
| **4. 향후 플랫폼 실증** | 별도 승인을 받은 보호 스테이징에서 실제 TLS/프록시 홉·연결 제한·HTTP 버전에 따른 종료를 계층별로 재현한다. 원본 직접 주소와 리다이렉트, 실제 캐시 정책, 구 인스턴스 강제 격리, 독립 권한 저장소의 복구와 키 회전을 증명한다. 지연·메모리·동시 연결과 전환 대기 한도를 측정해 소유권과 비용을 확정한다. |

**판정 요청.** A의 화면 분리를 우선 준비하고 B의 직접 송신 경계를 다음 격리 후보로 채택한다. 별도 오리진 인증이나 하위 큐의 소유·종료 증명이 불가능하면 C의 통제 가능성을 평가한다. 보호 자료의 운영 개통은 호스트에서 같은 계약을 입증하고 Master가 검수한 뒤 결정한다. 이번 작업은 문서·고정 기록·공개 플랫폼 문서 검토에 한정했다.
