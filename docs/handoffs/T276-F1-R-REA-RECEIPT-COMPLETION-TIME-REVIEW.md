# T276-F1-R 영수증 완료 시각 독립 재검수

**통과.** 실행 판정 시각과 영수증 종결 시각이 분리됐다. 쓰기가 지연돼도 영수증 보존 기한을 실행 시작부터 소진하던 문제를 해소했다. 실제 제품 연결과 커밋 직전부터 응답까지의 운영 시계·보존 정책은 후속 범위다. [수정 보고](T276-F1-REA-RECEIPT-COMPLETION-TIME.md) · [이전 검수](T276-R-REA-ATOMIC-APPLY-RECEIPT-REVIEW.md)

## 독립 확인

| 합성 SQLite 사례 | 결과 |
| --- | --- |
| 시작 150ms → 종결 320ms, 보존 기간 150ms | 별도 DB에서 활동 로그 트리거로 지연을 재현했다. 실행 만료가 지난 뒤 종결했으며 적용 성공, `completedAtMs=320`, `retainUntilMs=470`이었다. 각각 새 Node 프로세스의 320ms·469ms 조회에서 원래 영수증이 반환됐고, 470ms는 `unavailable`이었다. 자식 프로세스가 적용하고 응답을 남기지 않는 전용 회귀도 재실행했다. |
| `no_change` 150ms → 160ms | 타임라인 이력이 늘지 않았다. 종결 시각 160ms의 영수증은 다른 프로세스의 309ms 조회에서 반환됐고 310ms에는 만료됐다. 전용 회귀에서 저장 로그 미추가도 확인했다. |
| 종결 시계 또는 보존 계산 오류 | 마지막 활동 로그 기록 뒤 시계를 149ms, NaN, 무한대, 소수, 보존 덧셈 상한 초과 값으로 대체해 모두 `REA_RECEIPT_COMPLETION_TIME_INVALID`를 확인했다. 시계 함수 자체의 예외도 원래 오류로 반환됐다. 매번 확인 소비·타임라인·워크플로·활동 로그와 영수증의 전체 DB 스냅샷이 동일했다. 정상 시계로 같은 확인을 적용할 수 있었다. |
| 영수증 쓰기 실패와 기존 경쟁 | 영수증 종결에 실패를 주입했을 때 전체 롤백을 확인했다. 네이티브 시작 `SQLITE_BUSY`는 무변경·재시도 가능이었다. 별도 프로세스 둘의 같은 ID 적용은 한 번 저장됐고, 다른 확인의 오래된 CAS는 `conflict`였다. 철회·복원 세대에서 이전 확인과 영수증의 거절도 유지됐다. |

`completedAtMs`는 타임라인 쓰기 뒤 영수증 기록 직전의 시각으로 확인했다. 영수증과 타임라인은 같은 트랜잭션으로 커밋된다. [수정 코드](../../lib/reference-analysis/synthetic-apply-store.ts) · [전용 회귀](../../tests/reference-analysis/atomic-apply.test.ts)
