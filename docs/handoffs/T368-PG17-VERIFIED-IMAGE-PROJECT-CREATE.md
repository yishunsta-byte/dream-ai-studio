소유 PG17에서 T367을 통해 실제로 업로드·검증한 PNG 한 건을 사용해 쇼핑숏츠 프로젝트를 생성했다. 앱의 기존 PostgreSQL 생성 서비스와 Storage 검증을 재사용한다. 공용 서비스에는 기본 동작을 따르는 선택형 서버 훅만 추가했다. 새 훅을 사용하면 프로젝트, 기존 순서·상태의 제작 단계 7개, 파일 링크, 감사 기록과 생성 요청 결과가 실제 트랜잭션 한 번으로 확정된다. [직전 업로드 검증](T367-F1-PRIVATE-IMAGE-CLEANUP-RETRY.md) · [전용 서버 조립](../../lib/services/postgres/private-image-project-create.ts)

## 검증

- `node --conditions=react-server --import tsx tests/postgres/t368-run-private-image-project-create.mjs` 통과. 고정 T367 실행기의 소유 PG17 준비와 PNG 업로드를 재사용했다. 기존 Supabase Storage SDK를 사용하는 별도 루프백 HTTP가 T367에 저장된 실제 바이트를 전달했다. 운영 Supabase 접속은 없었다. [격리 시험](../../tests/postgres/t368-private-image-project-create.pg17.mjs)
- 생성 중복 경합을 실제 PostgreSQL 잠금으로 확인했다. 첫 요청에서는 실제 DB COMMIT 뒤 호출자에게 응답 유실을 주입했다. 두 번째와 이후 동일 요청은 기존 ID를 받았고, 프로젝트·7단계·파일 링크·감사 기록과 생성 결과 각각 한 세트만 존재했다. 정책 갱신이 진행 중 생성의 공유 잠금을 기다리는 것도 실제 DB에서 확인했다.
- 공개 버킷, 바이트 변조, 타인 자산, 검증 철회와 정책 갱신을 차단했다. 감사 기록 저장 이후 의도적으로 원장 확정을 실패시켜 전체 롤백을 확인한 뒤 같은 입력으로 성공했다. 설치 충돌과 후보 역할의 직접 원장 접근을 차단했으며, 복귀 뒤에도 기존 쓰기·이력·권한과 생성 기록을 대조했다.
- 기존 B12 PostgreSQL 생성 **20건**, B15 비공개 Storage 결합 생성 **19건**, 관련 Vitest 회귀 **1,171건 통과·300건 조건부 건너뜀**. 변경 파일 ESLint와 기존 `.next` 생성 검증 파일을 제외한 소스 TypeScript 검사 통과. 리스너·소유 PostgreSQL·임시 검증 파일을 정리했다.

검증 범위는 고정 쇼핑숏츠 설정과 PNG 한 건을 사용하는 소유 PG17 후보에 한정한다. 실제 Supabase의 역할·권한·Storage, 제품 POST 연결, 원격 배포는 미검증이다.
