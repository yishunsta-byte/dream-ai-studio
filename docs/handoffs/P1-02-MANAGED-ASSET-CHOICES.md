# P1-02 프로젝트 생성용 검증 자료 목록

기준은 `e91a89c1cc5c17747353681c5b0a95ba6c43393a`다. 이 후보는 쇼핑숏츠 생성 폼이 기존 검증 자료를 선택하는 관리형 읽기 API를 제공한다.

| 항목 | 계약 |
| --- | --- |
| 요청 | `GET /api/projects/asset-choices`, 후속 페이지는 `?cursor=<nextCursor>` |
| 성공 | `200 { assets: [{ id, title, kind }], nextCursor? }`. ID와 커서는 UUIDv7이다. 종류는 `image` 또는 `video`다. 최신 UUIDv7 순서로 최대 100개씩 반환한다. 더 읽을 데이터가 있을 때만 `nextCursor`가 온다. 조회 결과 0건은 `200 { assets: [] }`다. |
| 오류 | 401 로그인 필요, 403 허용 계정 아님, 400 잘못되거나 중복된 커서, 503 관리형 연결 또는 열 권한 미구성·실패. 응답은 캐시하지 않는다. |
| 범위 | 서버가 검증한 Auth UUID와 같은 소유자만 읽는다. 생성 POST와 같은 영수증 상태·세대·정책·유효기간 및 파일 메타데이터 기준을 사용한다. 응답에서 반환하는 자료 열은 ID·제목·종류다. |

목록 조회는 읽기 전용이다. 화면에 자료가 표시된 뒤 만료되거나 보관될 수 있으므로, 생성 POST에서 기존처럼 유효성을 다시 검사하고 필요한 행의 잠금을 잡는다. 503과 200 빈 배열을 화면에서 별도 상태로 표시한다.

고정 `0001_install.sql`은 유지했다. 새 `lib/db/postgres/managed-project-core/0002_asset_choices.sql`은 기존 프로젝트 참조와 자료 테이블의 강제 RLS를 검사하고, 전용 역할에 `dream.assets.title` 읽기 권한만 더한다. 운영에서 적용할 때는 앞선 P1-02 설치와 같은 Postgres 설치 소유자 세션에 `dream.project_core.install_ref`를 설정해야 한다. 새 SQL의 LF SHA-256은 `5b96880eb254337bb7a095b8269a1cea2d9dfae366c1eb778e2276277d87546c`다.

## 자체 검수

- 실제 Next 운영 빌드, 합성 HTTPS Auth, 격리 PostgreSQL 17.12 TLS 1.3에서 확인했다. 미구성 및 새 권한이 없을 때 503, 401·403, 잘못된 커서 400, 정상 빈 목록, 소유 자료 102개의 페이지 100·2와 중복 0을 검증했다.
- 이미지·영상, 다른 소유 자료, 만료·보관 자료를 대조했다. 목록 조회 중 프로젝트·요청 기록의 변화 없이, 조회 직후 보관된 자료의 생성 요청은 400이고 유효 영상은 실제 프로젝트에 연결됐다. 브라우저 역할에는 내부 권한이 0이었다.
- 기존 공통 프로젝트 생성·브리프·동시 요청·재시도·롤백 HTTP 회귀, 집중 52개, 변경 파일 린트와 운영 빌드 추적을 통과했다. T198은 103개 통과, 고정 기준과 동일한 Style DNA 관련 19개 실패다.
- Front, 실제 운영 DB, Vercel은 이번 후보에 포함되지 않는다. 환경이 준비될 때까지 Front는 목록 503 상태에서 생성 제출을 막는다.

재현은 `next build --webpack` 후 로컬 PG17 바이너리 디렉터리를 `P102_PG_BIN`에 지정하고 `node tests/postgres/managed-project-core.pg17.mjs --http --asset-choices`를 실행한다.
