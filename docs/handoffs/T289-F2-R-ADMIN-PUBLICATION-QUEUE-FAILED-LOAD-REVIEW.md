## 추가 재현

**F289-F2-A · 목록에서 항목이 빠지면 진행 중 쓰기의 조회 잠금이 풀립니다.** v0 게시 준비 전송을 보류한 뒤 같은 공급자에서 `initial`만 빈 목록으로 바꿨습니다. 준비 응답을 풀기 전에 상단 새로고침이 활성화됐고, 버튼을 눌러 조회가 한 번 실제 호출됐습니다. 쓰기가 여전히 진행 중이라 게이트가 그 목록을 버리고 “이번 목록은 반영하지 않았어요”를 띄웠습니다. [`rowsAfterList`](../../components/admin/publication-queue.tsx#L72)가 새 목록의 항목만 보존하고, [`anyBusy`](../../components/admin/publication-queue.tsx#L111)는 그 줄 상태에서 잠금을 계산합니다. 같은 공급자에서 진행 중인 쓰기의 잠금이 항목의 표시 여부와 무관하게 응답까지 유지되도록 확인이 필요합니다.

**F289-F2-B · 늦은 미확정 응답이 최신 행에 이전 버전 재시도를 되살립니다.** 커밋 전 실패할 v0 게시 준비를 보류하고, 같은 공급자의 `initial`만 v5로 바꿨습니다. 실패 응답을 풀자 v5 화면에 “같은 게시 준비 요청 다시 시도”가 나타났습니다. 이 버튼은 기존 UUID와 `expectedVersion=0`을 그대로 전송했습니다. 이 시험에서 메모리 공급자는 v0을 v1로 처리했고, v5 화면은 버전 차이로 결과 불일치 안내를 표시했습니다. 이는 실제 서버가 v5에서 v0을 수락했다는 검증이 아닙니다. [`send`의 실패 처리](../../components/admin/publication-queue.tsx#L151)는 최신 행의 존재와 버전을 확인하지 않고 재시도를 기록합니다. 이미 받은 권위 있는 목록이 다른 버전이거나 항목이 빠졌다면, 늦은 실패가 이전 요청 버튼을 다시 만들지 않는지 확인이 필요합니다.

**기존 동작 관찰.** 첫 재시도 응답을 보류해도 같은 줄의 재시도 버튼이 활성 상태였습니다. 두 번째 클릭은 같은 UUID와 본문을 다시 전송했고, 메모리 원장은 v2 한 번만 반영했습니다. 버튼의 `disabled={loading}` 조건은 `42a1969`의 부모에도 있었습니다. 위 두 경계의 회귀 판정과 별도로 기록합니다. [재시도 버튼](../../components/admin/publication-queue.tsx#L209)
