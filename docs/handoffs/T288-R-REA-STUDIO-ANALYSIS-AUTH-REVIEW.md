# T288-R 작업실 분석 전용 Supabase 인증 전송 독립 검수

**판정 — 격리 인증 전송 범위 통과.** 설치된 실제 SDK와 독립 루프백 서버에서 사용자 조회와 세션 갱신의 취소·기한, 네트워크 종료, 요청별 쿠키 격리를 확인했습니다. 서버에 이미 반영된 토큰 회전과 상위 오류 메시지의 SDK 로그는 제품 연결 전에 검증할 조건입니다. [Backend 인계](T288-REA-STUDIO-ANALYSIS-AUTH.md)

| 검수 | 실제 루프백 결과 |
| --- | --- |
| 설치 SDK와 정상 세션 | `@supabase/ssr` 0.12.7, `supabase-js`·`auth-js` 2.119.0을 확인했습니다. 만료 쿠키에서 `POST /auth/v1/token?grant_type=refresh_token` 한 번 후 새 액세스 토큰으로 `GET /auth/v1/user`가 실행됐습니다. 같은 요청의 두 번째 검증은 그 새 토큰을 사용했습니다. 쿠키 및 갱신 응답의 사용자와 GET의 사용자를 다르게 제공하자 GET이 반환한 계정이 채택됐습니다. |
| 요청별 격리·쿠키 | 별도 B 요청은 저장한 B 토큰으로 B만 조회했고, 쿠키 없는 요청은 `AUTH_REQUIRED`였습니다. 생성 후 입력 쿠키를 바꿔도 생성 시점의 사본을 사용했습니다. 루프백이 `Set-Cookie`를 보내도 외부 쿠키 배열은 유지됐고 결과는 검증 사용자 ID와 이메일 또는 제한된 인증 오류뿐이었습니다. |
| 기한·취소·소켓 | 사용자 GET과 갱신 POST 각각에서 헤더 전/본문 일부 이후를 지연시키고 기한·호출자 취소를 적용한 **8개 조합**을 독립 실행했습니다. 모두 `AUTH_UNAVAILABLE`이었고 서버에서 해당 TCP 소켓이 응답 완료 전에 닫혔습니다. 같은 리졸버의 동시 호출 및 종료 뒤 호출은 거절됐고, 늦은 성공을 보내도 추가 전송이나 쿠키 게시가 관측되지 않았습니다. 갱신 성공 뒤 사용자 GET 취소도 집중 회귀에서 통과했습니다. |
| 전송 오류 및 재시도 | 갱신 503, 307, 256KiB 초과, 잘못된 UTF-8 및 소켓 종료 각각에서 해당 갱신 요청 한 번으로 끝났습니다. 리디렉션 대상 요청이나 후속 사용자 조회가 없었습니다. |

## 제품 연결 선행조건

별도 합성 서버는 갱신 POST 접수 직후 구 토큰을 회전 처리하고 응답을 보류했습니다. 클라이언트 취소 후에도 모델의 회전은 유지됐고, 구 쿠키를 받은 새 요청은 갱신이 거절됐습니다. 실제 Supabase의 재사용 유예, 동시 요청 정책, 공용 인증의 쿠키 게시 책임은 이 모델의 검증 범위 밖입니다. 제품 경로에서는 분석의 갱신과 공용 세션 갱신이 동시에 일어날 때의 회수·재시도 정책을 결정해야 합니다.

갱신 400 응답에 `refresh_token_already_used`와 합성 진단 문자열을 넣자 외부 DTO는 `AUTH_REQUIRED`로 제한됐지만 SDK의 서버 콘솔에는 합성 문자열이 기록됐습니다. 운영 연결 전 상위 오류 본문의 로그 허용 범위를 정하고 민감한 메시지가 게시되지 않게 검증해야 합니다. 이 관측에는 합성 응답만 사용했습니다. [응답 전달 경계](../../lib/reference-analysis/studio-analysis-auth.ts#L84)

집중 **10/10**, 네이티브 REA·비공개 reader·타임라인·오디오·API 인증 **22개 파일 410/410** 통과. `t182-auth.test.ts`를 포함한 확장 회귀는 **23개 파일 451/451** 통과. 범위 TypeScript, ESLint `--max-warnings 0`, REA `git diff --check`도 통과했습니다. 운영 Auth·제품 경로를 실행하지 않았고 합성 서버를 닫았습니다.

**Master 전달문** — T288-R 격리 전송 통과. 실제 SDK의 GET/refresh와 8개 지연·중단 조합의 TCP 종료, 세션 격리 및 미게시, 오류 재전송 차단, 410/410 회귀를 확인했습니다. 원격 토큰 회전·공용 쿠키 책임 및 상위 갱신 오류의 SDK 로그를 제품 연결 전 분리 검증해야 합니다.
