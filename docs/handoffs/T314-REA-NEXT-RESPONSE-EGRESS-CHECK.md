# T314 Next.js 분석 응답 전송 경계 로컬 검증

- 담당: Codex(Front) · 배정 Master `msg_0fe985a1c8cf` · 기준 T313-R 통과 `131fde6`
- 대상: `131fde6` 고정 소스 격리 사본 → `npm run build` → `next start`(production, 127.0.0.1:43314)
  - Next.js 16.4.6, Node v26.13.0
  - `proxy.ts`는 그대로 거쳤어요(로그인 설정 없음 = auth off). `.env.local`은 없었어요.
- 바꾼 파일: 이 보고서 하나. 제품 파일·운영 자원·배포·공유 `.next`는 쓰거나 바꾸지 않았어요. 브라우저가 필요 없어 ego는 쓰지 않았어요.

## 시험 장치 (격리 사본 전용, 커밋 안 함)

| 사본 파일 | 역할 |
|---|---|
| `lib/t314/gate.ts` | 합성 허가(발급·소비·철회·만료·대기 해제)와 서버 쪽 사건 기록. 상태는 `globalThis`에 둬요. |
| `app/api/t314-control/route.ts` | 루프백 조작 창구(발급·철회·만료·해제·상태). |
| `app/api/t314/[kind]/route.ts` | 합성 보호 응답 3종: HTML(`text/html`), RSC 유사(`text/x-component`), POST JSON. `ReadableStream`(`highWaterMark: 0`)의 **첫 `pull`에서 허가를 다시 확인하고 소비**해요. 이후 `pull`마다 철회 여부를 확인하고, 철회되면 `controller.error`. 함께 기록: `request.signal` abort, stream `cancel`, `after()`. |
| `app/t314/page/page.tsx` | 실제 App Router 페이지(Suspense 없음). 렌더 중 허가 확인·소비, 거절이면 `notFound()`. |
| `app/t314/suspense/page.tsx` | 셸을 먼저 보내고, 보호 영역은 Suspense 안에서 허가 확인. |

클라이언트는 별도 Node 프로세스예요. `node:http`로 실제 TCP 소켓을 열어 상태·헤더 도착·첫 바이트·받은 바이트·종료 형태를 기록했어요. 같은 측정을 두 번 돌렸고, 결과 형태는 같았어요(바이트 수는 실행마다 조금 달라요).

## 결과

### ① 정상 전송과 같은 허가 재사용 (세 유형)

- 200, 정확한 Content-Type, `private, no-store`, 합성 본문 일치예요.
- 같은 허가를 다시 쓰면 409, 본문 0바이트예요.
- 허가 소비는 유형마다 1회예요.
- 서버 기록 순서: `handler:return → stream:firstPull → consumed → enqueue → close → after:run`

### ② Response를 돌려주기 전(핸들러 대기 중) 철회·만료 (세 유형 × 2)

- 대기 중에는 클라이언트에 헤더가 **도착하지 않았어요**.
- 결과는 철회 403, 만료 410이에요. 본문 0바이트, 정상 종료, 허가 소비 0이에요.
- **보장 가능:** 앱이 Response를 돌려주기 전에 판정하면 상태 코드까지 정확히 제어돼요.

### ③ Response를 돌려준 뒤, 첫 바이트 전 철회 (첫 `pull` 대기 중, 세 유형)

- `Response`를 반환한 뒤에도, 첫 본문 조각이 나오기 전에는 **상태줄·헤더가 소켓에 나가지 않았어요**. 대기 300ms 동안 클라이언트 상태는 없음이에요.
- 철회 뒤 첫 `pull`이 `controller.error`를 내면, 클라이언트는 **헤더도 본문도 없이 `ECONNRESET`**으로 끝나요. 본문 0바이트, 허가 소비 0이에요.
- 서버 기록: `stream:stop:revoked → request:abort → after:run`
- **보장 가능:** 첫 보호 바이트 0. **보장 불가:** 클라이언트가 받는 것은 403/410이 아니라 연결 끊김이에요. 이유를 응답으로 전달할 수 없어요.

### ④ 전송 중 철회 — 느린 수신(클라이언트가 첫 64KB 뒤 읽기 멈춤), 64KB × 400 조각

| 유형 | 철회 시점 서버 enqueue | 철회 시점 클라이언트 수신 | **철회 뒤에 도착한 바이트** | 끝 |
|---|---|---|---|---|
| HTML | 655,360 / 720,896 | 65,529 | 589,831 / 655,367 | aborted |
| POST | 655,360 / 655,360 | 65,529 | 589,831 / 589,831 | aborted |

(두 실행 값을 `/`로 나눠 적었어요.)

- 응답 스트림이 멈춘 뒤에도 **약 0.6MB가 Node·소켓 버퍼에 남아**, 철회 뒤 클라이언트가 읽기를 재개하자 그대로 도착했어요.
- 앱의 다음 `pull` 확인은 버퍼가 빈 뒤에야 돌아요. 철회를 확인한 것은 철회 약 0.3초 뒤였어요.
- **보장 가능:** 철회를 확인한 뒤에는 새로 enqueue하는 바이트가 0이에요. **보장 불가:** 이미 enqueue된 바이트(이 로컬에서 약 0.6MB)는 회수할 수 없어요.

### ⑤ 클라이언트 취소 (첫 데이터 뒤 소켓 파괴, RSC·POST)

- 서버에서 `request:abort`, `after:run`, `stream:cancel`이 같은 ms에 관측됐어요(파괴 직후).
- 그 뒤 추가 enqueue는 0이에요(enqueue 총량 그대로).
- **보장 가능:** 취소를 앱이 관측해요(`request.signal`, stream `cancel`).

### ⑥ 종료 관측 — `after()`·스트림 close ≠ 클라이언트 수신 완료

- 본문 512KB(64KB × 8)에서 클라이언트가 첫 64KB 뒤 멈췄어요.
- 그런데 서버의 **`stream:close`와 `after:run`이 3~10ms 안에 모두 일어났어요**. 클라이언트는 그때 65,529바이트만 받은 상태였어요.
- 이어서 철회해도, 클라이언트가 재개하자 나머지 458,759바이트가 도착했고 **정상 종료(end)**됐어요.
- 본문이 버퍼보다 크면(64KB × 64 = 4MB) `close`와 `after`는 클라이언트가 다 읽을 때까지 미뤄졌어요. 즉 이 신호들은 "버퍼에 다 넣음"이지 "도착함"이 아니에요.
- **보장 불가:** route handler 안에서는 실제 전달 완료를 증명할 신호가 없어요. 세대 전환을 `after()`나 stream close에 묶으면, 아직 전송 중인 바이트를 남긴 채 다음 세대가 열릴 수 있어요.

### ⑦ 실제 페이지 렌더 경로 (App Router, Suspense 없음)

- **렌더 중 대기:** 헤더·바이트 0이었어요(대기 500ms). 철회하면 404 `not-found`(약 6KB 공용 안내)이고 보호 문구 0이에요.
- **정상 HTML:** 200, 보호 문구 있음, 허가 1회 소비. 재사용하면 404예요.
- **RSC 요청**(`RSC: 1`):
  - `_rsc` 없이 보내면 307로 `?…&_rsc`에 보내요. 따라가면 200 `text/x-component`, 보호 문구 있음, 허가 소비예요.
  - 페이지와 같은 렌더 경로라 같은 확인을 거쳐요.
- **프리페치**(`RSC: 1` + `Next-Router-Prefetch: 1`, 해시 리다이렉트 따라감):
  - 200이지만 라우트 트리 정보만 있어요.
  - 페이지 렌더가 없어서 **허가 미소비, 보호 문구 0**이에요(dynamic 페이지 기본 프리페치).
  - `prefetch={true}` 전체 프리페치는 측정하지 않았어요.
- **렌더 확인 뒤 철회**(본문 3MB, 느린 수신): 철회 시점 수신 65,016바이트였는데, 이후 **6,006,726바이트 전부 도착**했고 보호 본문도 완전했어요. 페이지 경로에는 렌더 뒤·전송 전에 끼어들 지점이 없어요.

### ⑧ Suspense 스트리밍 페이지

- 보호 영역 대기 중에 이미 **200과 공개 셸(6,760바이트)이 전송**됐어요.
- 철회하면 보호 문구 0, 대신 `withheld`가 스트리밍되고 상태는 200 그대로예요.
- **보장 가능:** 보호 조각 0. **보장 불가:** 상태 코드(이미 200), 셸 노출.

## 정리: 보장 가능한 부분과 별도 검증이 필요한 부분

**Next route handler 안에서 보장 가능 (이 로컬 production에서 실측):**
1. Response 반환 전 판정 → 정확한 403/410/409, 본문 0, 헤더 0.
2. 첫 `pull` 재확인 → 첫 보호 바이트 0, 허가 미소비. 단 클라이언트에는 연결 끊김으로 보여요.
3. 철회를 확인한 뒤에는 새 enqueue가 0.
4. 클라이언트 취소 관측(`request.signal`, stream `cancel`).
5. dynamic 페이지 기본 프리페치는 렌더·허가 소비를 하지 않아요.

**앱만으로 보장할 수 없는 부분 → 별도 프록시/호스트 검증 필요:**
1. **이미 enqueue한 바이트의 회수:** 로컬 Node/소켓만으로 약 0.6MB예요. 호스트 프록시·CDN 버퍼가 더해지면 늘어나요. 보호 전송은 "첫 바이트 전 판정"까지만 보장된다고 봐야 해요.
2. **전달 완료 증명:** `after()`·stream close는 버퍼 투입 완료일 뿐이에요. 세대 전환(T313 "실제 소켓 종료 확인 뒤 다음 세대")을 Next 안에서 그대로 구현할 수 없어요.
   - T313 실행기는 Node `res`·소켓을 직접 소유했어요. Next route handler는 그것을 노출하지 않아요.
   - 대안은 두 가지예요. 전송 경계를 Next 앞의 별도 프록시나 커스텀 Node 서버로 두거나, 호스트가 응답 종료·연결 종료를 기록하는지 확인해요.
3. **철회 사유 전달:** 첫 바이트 전 철회(③)는 상태 코드 대신 연결 끊김이에요. 클라이언트 재시도 정책에서 구분할 방법이 필요해요.
4. **페이지·RSC 렌더 경로:** 렌더 뒤 전송 전에 끼어들 수 없어요(⑦ 3MB 전부 도착). Suspense는 200·셸을 먼저 보내요(⑧). 보호 분석 결과는 route handler(①~③ 방식)로 주고, 페이지 HTML/RSC에는 넣지 않는 것이 안전해요.
5. **호스트 정책:** 실제 호스트(Vercel 등)가 본문을 사전 버퍼링하거나 응답을 모아 보내는지, 헤더 확정 시점(③의 "첫 바이트 전 헤더 없음"이 유지되는지), 클라이언트 취소가 함수까지 오는지. 로컬과 다를 수 있어요(T303 항목 1·2와 같은 계열).
6. **전체 프리페치(`prefetch={true}`), 클라이언트 라우터 캐시, 브라우저 bfcache:** 이번에는 HTTP 수준만 측정했어요.

## 제약

- 단일 Node 프로세스, 루프백, 합성 허가·본문이에요. 운영 DB·Supabase·외부 플랫폼은 쓰지 않았어요.
- 버퍼 크기(약 0.6MB)는 이 PC의 루프백·Node 기본값 기준이에요.
- 서버 사건 시각은 서버 시계, 클라이언트 시각은 클라이언트 시계예요. 서로 다른 프로세스라 두 시계를 직접 비교하지 않았어요. 순서 판단은 "클라이언트가 멈춘 동안 서버 상태를 읽은 결과"로 했어요.
