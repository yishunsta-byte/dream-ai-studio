## 첫 구현과 합성 수용 기준

1. **PG17 저장 계약부터 구현한다.** 소유한 폐기 가능 PG17에서 승인 상태·원장·역할을 검증한다. §3의 함수 소유자 권한 모델은 실제 SQL에서 고정 `search_path`와 한정 관계명을 사용하는 `SECURITY DEFINER`로 명시한다. 호출자에겐 호출에 필요한 스키마 접근과 조회 함수 실행만 주고, 함수 소유자의 실제 RLS 및 열 제한, 반대 함수 호출·기저 조회·쓰기 거부를 확인한다. [PostgreSQL 17 함수 권한](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)
2. **같은 원장 ID의 재시도와 양방향 경쟁을 시험한다.** 명령 지문은 같은 주소와 버전에서도 승인된 문구·사본 해시·권리 범위가 달라지면 충돌해야 한다. 두 연결에서 준비 중 철회 뒤 완료 거부, 먼저 완료된 대상에 대한 철회 성공, 커밋 응답 유실 후 중복 세대 방지를 확인한다. 복제 결과가 불확실하면 정리를 보류하고 사본이 뒤늦게 나타나도 공개 상태가 살아나지 않는지 확인한다.
3. **합성 WebP 사본 한 건을 연결한다.** 동일 소유자 발행 명령, 승인 문구와 SHA-256을 묶은 5 MiB 이하·최대 4096×4096의 단일 cover, 합성 Storage를 사용한다. 실제 Next에 전용 익명 GET·HEAD, 무결성 검사와 최적화 제한을 함께 붙인다. 같은 URL에서 승인 전 404 → 활성 200 → 철회 후 404, 405와 503, 최적화 경유 차단 및 기존 보호 경로를 확인한다. 원본 경로 검증은 자동 리다이렉트와 클라이언트 URL 정규화 때문에 별칭 검사 결과가 가려지지 않게 실행한다. [Next.js proxy 정규화](https://nextjs.org/docs/app/api-reference/file-conventions/proxy#advanced-proxy-flags)
4. **홈을 연결한다.** 합성 활성 작품, 정상 빈 목록, 계약 오류와 조회 장애를 실제 HTML/RSC에서 검증한다. 별도 다건 합성 목록으로 24·25번째 동률, 밀리초 변환, ASCII slug 정렬을 검사한다. 승인 메타데이터 조회와 사본 검증은 설계에 정의된 각 요청에서 처리한다.

운영 연결 전에는 배포 환경의 경로·브라우저/CDN 캐시, 승인된 PG17 이관 경로, 전용 런타임 TLS 및 Storage 정책을 검증한다. 특히 운영 다운로드 주체로 실제 다운로드가 되고 목록·서명 URL 생성·수정·삭제·원본 접근은 거부되는지 증거가 필요하다. 영상·음악·Range와 범용 발행 UI는 첫 합성 범위 밖이다. [Supabase Storage 접근 제어](https://supabase.com/docs/guides/storage/security/access-control)
