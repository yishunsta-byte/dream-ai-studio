## 1. F043-1 빈 기록 표는 정확한 정의만 받아요

`lib/db/migrate.ts`
- 빈 기록 표가 "새 DB"로 인정되는 조건을 좁혔어요. 아래를 **모두** 만족할 때만이에요.
  - 저장된 정의 SQL이 이 파일이 만드는 문장과 글자 그대로 같음(`CREATE TABLE __schema_migrations (…) STRICT`). 기록 표를 만드는 코드도 같은 상수를 써요.
  - `table_xinfo`가 정확히 4칸이고 이름·형식·NOT NULL·기본값 없음·기본키·숨은 칸 없음까지 같음.
  - `table_list`로 STRICT이고 WITHOUT ROWID가 아님.
- 그 밖은 모두 unrecorded예요. DEFAULT, CHECK, 숨은 생성 칸, 형식 다름, STRICT 없음, WITHOUT ROWID, 띄어쓰기만 다른 정의까지 포함해요. SQL을 실행하기 전에 거부하고, 지금 DB 이관과 직접 migrate가 같은 판정을 써요.

## 2. F043-2 시작 점검과 거부되는 명령은 DB를 바꾸지 않아요

| 파일 | 내용 |
|---|---|
| `lib/db/connection.ts` | `openDatabase(파일, 옵션, {wal})` 세 번째 인자를 더했어요. 기본값은 지금과 같아요(WAL 전환). `wal:false`면 쓰기용으로 열어도 저널 모드를 바꾸지 않아요. 기존 호출은 모두 기본값이라 동작이 같아요. |
| `lib/db/server.ts` | `checkDatabase`는 **읽기 전용**으로 열어요. `withDatabase`(API에서 씀)는 `wal:false`로 열어 검증이 통과한 뒤에만 WAL로 바꿔요. 그래서 모르는 DB에 API가 닿아도 바뀌지 않아요. |
| `lib/db/migrate-command.ts` | 기존 DB는 먼저 읽기 전용 연결로 출처와 기록을 봐요. ① 기록 없음·기록 불일치 → 쓰기용으로 열지 않고 거부 ② 이미 최신 → 읽기 전용으로 검증만 하고 끝(쓰기용으로 안 엶) ③ 새 DB·허용된 올리기 → 그때만 `wal:false`로 쓰기용으로 열어요. 그러면 바꾸기 전 사본보다 먼저 파일이 바뀌는 일이 없어요. 쓰는 연결에서 출처와 기록을 다시 확인하고(잠금 안에서 한 번 더), 사이에 바뀌면 거부해요. 시험용 `afterProbe` 지점을 두었어요. |
| `scripts/db.ts` | seed도 검증이 통과한 뒤에만 WAL로 바꿔요. |

남은 영향: 읽기 전용 연결이 WAL 모드 DB를 열면 SQLite가 빈 `-wal`·`-shm` 곁 파일을 만들 수 있어요. DB 파일 바이트는 바뀌지 않아요. DELETE 모드 DB는 곁 파일이 생기지 않아요(시험으로 확인).

## 3. F043-3 사본은 열어서 확인될 때만 "남겨 두었어요"라고 해요

`lib/db/migration-record.ts` `keptSnapshot(root, record)` (인자가 경로 대신 기록 전체로 바뀌었어요)
- 기존 확인(링크 아닌 폴더, 이름 모양, 실제 경로)에 더해 아래를 확인해요.
  - 머리글이 롤백 모드(18·19번 바이트가 1)이고, `-wal`·`-shm`·`-journal` 곁 파일이 없음. 그래서 읽어도 곁 파일이 생기지 않아요.
  - 기록에 사본 지문이 있으면 지금 파일의 sha256이 같음.
  - 읽기 전용으로 열어 `integrity_check`가 ok.
  - 사본의 기록 표 행(적용 시각 포함)과 모든 객체 정의 지문이 기록 속 DB 상태와 같음.
- 기록에 `snapshotSha256`(선택 칸)을 더했어요. CLI가 사본을 만든 직후 계산해요. T-042 때 쓴 옛 기록에는 이 칸이 없어서, 지문 없이 위 나머지 검사만으로 판단해요. 기록 형식은 엄격한 모양을 그대로 써요.
- 사본 파일은 읽기만 해요.
