# T321 보호 분석 응답의 운영 보장과 스테이징 계획

2026-11-19 KST · Codes(Backend) · 배정 `msg_27c9074b2570` · 고정 기준 T316 `fced9f9`, T320 `e16d213` 및 T320-R

**결정안.** Vercel의 자료 없는 분석 셸과 별도 TLS 송신 서비스의 구성을 채택하고, 독립 원장과 실제 송신 경계를 격리 스테이징에서 검증한다. DB 커밋과 물리 전송 사이에 걸친 요청은 송신 가능성이 있는 미확정 요청으로 관리한다. 이전 송신 경로의 종료 또는 격리를 입증하기 전에는 권한 철회와 세대 전환을 완료로 응답하지 않는다. 이 계약을 적용할 수 없는 환경에서는 실제 자료 연결을 비활성으로 둔다. ## 확인한 근거와 남은 간격

T320-R은 두 소유 루프백 TLS 송신자와 PG17.12에서 허가 단일 소비, 최종 확인 전에 확정된 권한 변경·재시작과 DB 중지의 보호 본문 0바이트, 종료 보고 누락 시 새 세대 보류를 재현했다. 고정 구현의 순서는 `before_write` 결과 수신 → `res.write()` → `first_report`다. 최종 판정 뒤 첫 쓰기 전 정지하거나 첫 쓰기 뒤 보고가 유실되는 구간은 다음 검증 대상이다. [T320 고정 구현](../../tests/reference-analysis/t320-https-durable-egress.pg17.mjs#L226) · [T320 결과와 한계](T320-REA-HTTPS-DURABLE-EGRESS-INTEGRATION.md)

T317은 기존 화면의 분석 자료 분리를 확인했다. T315 느린 수신에서는 앱의 종료 신호 뒤에도 클라이언트에 추가 바이트가 관측됐다. Node의 `finish`는 운영체제에 응답을 넘긴 시점에 관한 신호다. 하위 큐 폐기와 실제 전송 종료에는 계층별 증거가 필요하다. [T317 인계](T317-REA-CLOUD-ANALYSIS-PROTECTED-SHELL.md) · [T315 재현 기록](T315-REA-NEXT-RESPONSE-REPRODUCTION.md) · [Node HTTP ServerResponse](https://nodejs.org/api/http.html#class-httpserverresponse)

## 구현 경계와 완료 기준

1. **첫 전송 의도를 먼저 내구 저장한다.** 실제 대상·복원 세대·권한 리비전·송신자 부팅 ID/소유 번호·사용자·요청/채널·본문 식별·최단 기한을 일회 허가에 결합한다. 외부 차단이 없고 현재 권한과 일치할 때만 원장이 허가 소비와 전송 의도를 한 트랜잭션에서 기록한다. 의도 확정이 불확실하면 출력하지 않고 권위 있는 새 연결에서 상태를 대조한다. 동일 요청은 앞선 결과 확인에만 사용하며 이전 본문이나 송신 권한을 재생하지 않는다.
2. **최종 TLS 연결을 소유한 송신자만 출력한다.** 생산자는 준비한 본문을 인증된 내부 채널로 넘긴다. 송신자가 현재 소유 번호와 기한을 확인하고 자신의 실행 구간에서 최초 보호 바이트 삽입을 한 번 시도한다. 보호 헤더가 있으면 같은 경계에서 제어한다. DB 판정과 소켓 쓰기는 별도 사건이다. 삽입을 확인하기 전에 송신자가 멈추거나 보고가 유실되면 그 요청이 이미 썼을 가능성을 원장에 남긴다.
3. **철회의 접수와 효력 확정을 구분한다.** 같은 원장의 제어 순서에서 철회 요청을 내구 저장하고 해당 범위의 새 허가와 새 전송 의도를 닫는다. 첫 시험은 스토어 단위로 차단한다. 이전에 시작 의도를 얻은 요청은 취소·미송신 폐기, 이미 시작한 스트림의 종료, 또는 구 송신자 강제 격리 중 하나로 정리한다. 이 정리가 입증되면 차단을 유지한 채 실제 권한 변경을 적용·대조하고 철회 완료를 커밋한다. **철회 완료 뒤에는 이전 허가로 새 보호 바이트를 송신 큐에 넣을 수 없어야 한다.** 보류 중인 요청에는 대기 상태를 반환한다. 완료 전에 이미 경계 밖으로 넘긴 바이트의 수신과 회수는 별도로 다룬다.
4. **같은 장벽으로 세대 전환을 닫는다.** 구 요청의 종료 증거를 모으는 동안 새 시작·재시도·활성화를 막는다. 구 송신자와 큐의 종료 또는 격리가 확인돼야 새 소유 번호와 세대를 연다. 구 제어·전송 권한은 다시 발급하지 않는다. 원장 또는 제어기 복구 시 내구 상태 및 종료 보고부터 대조한다.

| 원장 상태 | 대기·실패 판정 |
| --- | --- |
| 준비, 전송 의도 없음 | 미사용 허가를 취소한다. 모든 송신 경로가 내구 전송 의도를 요구하는지 시험한다. |
| 의도 확정, 첫 삽입 결과 없음 | 송신 가능성이 있는 미확정 요청으로 분류한다. 미송신 폐기, 종료, 또는 구 송신자와 관련 큐의 격리 증거가 필요하다. 기한 만료, 앱 종료, 빈 조회로 종결하지 않는다. |
| 최초 삽입 관측 | 제한된 기한에 정상 종료 또는 강제 취소한다. 미전송 큐 폐기 및 추가 쓰기 불가를 확인한다. |
| 종료·폐기·격리 입증 | 구 소유 번호와 해당 채널에 귀속된 증거를 정리에 포함한다. 늦거나 충돌하는 보고를 근거로 구 허가를 되살리지 않는다. |
| 원장·대상·시계·종료 증거 확인 불가 | 새 허가·최초 송신·활성화를 차단한다. 기존 채널은 종료 한도와 추가 쓰기 차단을 적용한다. 상태를 확인할 때까지 전환 미완료다. |

철회 접수 후 완료까지 대기할 수 있다는 제품 계약은 Master 판정 대상이다. 권한·Auth·정책 쓰기는 먼저 전송 장벽을 닫는 경로로 묶는다. 외부 공급자의 변경이 장벽을 우회할 수 있거나 공급자 철회가 먼저 확정된 직후의 0바이트를 별도로 요구하면, 공급자 확정과 송신을 묶는 증거가 확보될 때까지 해당 구성은 비활성이다.

## 다중 호스트의 종료 증거

- 초기 송신은 직접 TLS·HTTP/1.1·응답 뒤 닫히는 연결과 크기를 제한한 JSON으로 좁힌다. 브라우저부터 최종 TLS 소유자까지 실제 홉을 대조한다. 보호 경로에 Vercel rewrite, 관측 불가능한 CDN/L7 프록시, 캐시 또는 재시도가 필요하면 그 홉의 종료 및 큐 폐기까지 입증해야 한다.
- 실제 송신 경계에서 요청 ID와 호스트 부팅 ID·소유 번호·연결 식별을 귀속한다. 최초 삽입, 누적 인계 바이트, 송신 버퍼·소켓 종료, 각 하위 큐의 비움·폐기와 오류를 기록한다. 로그에는 본문과 자격을 남기지 않는다. 독립 클라이언트의 수신량을 대조하되 클라이언트 최종 수신 ACK를 운영 완료 조건으로 삼지 않는다. 소켓 또는 앱의 `finish` 신호 하나로 하위 프록시 큐를 폐기 처리하지 않는다.
- 독립 감독자는 구 프로세스의 새 연결과 이미 열린 채널을 모두 차단할 수 있어야 한다. 시작 ID와 소켓, 실제 네트워크 경로 차단 및 하위 큐 종료를 같은 대상으로 확인한다. 연결된 송신자가 제어기와 분할돼도 새 세대를 열지 않는다. 네트워크 정책이 기존 연결을 끊지 못하거나 하위 큐 상태를 관측할 수 없으면 그 호스트의 전환은 미확인으로 유지한다. DNS·인증서 교체나 애플리케이션 락 만료만으로 종료를 확인하지 않는다.

## 격리 구성과 승인 사항

| 필요한 최소 자원 | 범위와 권한 |
| --- | --- |
| 서로 다른 송신 호스트 2개와 전용 시험 TLS 오리진 | 한 활성 후보와 한 교대 후보에서 합성 인증서를 쓴다. 시험 운영 역할에 리스너·방화벽·기존 연결 차단 및 프로세스/네트워크 관측 권한을 한정한다. 실제 TLS 종료점, 허용 포트, 구 연결과 큐를 닫는 방법을 확정한다. |
| 송신 호스트와 분리된 영속 원장 1개 | 독립 시험 DB와 별도 저장소를 사용한다. 전송 함수, 제어/전환, 종료 증거 기록, 읽기 감사와 이관 역할을 분리한다. 시험 송신자에 DDL, Auth 관리자 또는 운영 자격을 주지 않는다. 최초 스테이징은 자동 복제·승격 없이 시작한다. |
| 독립 시험 클라이언트 및 합성 생산자·감독 도구 | 시험 장비에서 분리된 프로세스·자격으로 구성한다. 클라이언트는 실제 바이트와 우회 경로를 확인한다. 감독 경로는 구 송신자 자체의 종료 메시지에 의존하지 않는다. 시험 종료 시 임시 로그의 보존·삭제와 키/자격 회수를 기록한다. |
| 기존 Vercel·Supabase와의 분리 | 첫 측정은 운영 Vercel·Supabase DB/Auth/Storage를 사용하지 않는다. 앱 호환 검증을 배정한 뒤 별도 보호 Preview/오리진과 승인된 합성 Auth·DB·버킷을 식별하고 프로젝트 ref, 인증 발급자, 실제 TLS·DSN·비밀 범위를 대조한다. 운영 트래픽과 운영 환경 변수를 끌어오지 않는다. [T261 스테이징 점검](T261-MANAGED-PG17-STAGING-CHECKLIST.md) |

**비용 산정 가정.** 송신 2개와 독립 DB 1개를 각각 최대 8시간, 총 24 인스턴스·시간 이내로 산정한다. 독립 시험 장비가 새로 필요하면 최대 8시간을 추가한다. 요청 2,000건과 본문 상한 64KiB를 가정하면 보호 본문 약 125MiB이며, 헤더·TLS·재연결 계측 여유를 포함한 전송 계획치는 250MiB다. 실제 견적은 승인 대상 리전의 단가·최소 청구 시간과 스토리지/백업·공용 IP·망·TLS/도메인·로그 비용을 더해 산정한다. 요금제·기존 자원 재사용·할인은 미정이며 측정값이나 공급자 청구액을 제시하지 않았다.

| --- | --- | --- |
| **1. 전송 의도와 철회 완료 장벽** | 별도 시험 모듈에 준비·의도·최초 전송 보고·종결과 철회 접수/완료를 구현한다. 최종 DB 확인 뒤와 최초 큐 삽입 직전, 삽입 직후 보고 전을 각각 멈추고 규칙을 경합시킨다. COMMIT 응답 유실도 주입한다. | 차단 뒤 신규 의도 0건. 철회 완료 뒤 기존 허가의 새 보호 바이트 0. 미확정 의도에서 철회 완료·새 활성화 0건. 동일 요청의 송신은 최대 1회이며 기존 본문 재송신 0건. |

| **4. 개통 판정** | Backend가 순서·종료·실제 수신·비용 근거를 반환하고 Tester가 독립 검수한다. Master가 철회 대기 허용 시간, 운영 역할, 예산, 중단·회수 기준을 판정한다. | 실제 호스트와 큐의 보장이 확인된 다음 별도 개통 승인. 기능·권한·운영 변경은 이 검토에서 수행하지 않는다. |

이번 작업은 고정 결과·소스·공개 문서 검토에 한정했다. 기존 시험 재실행과 실제 호스트·권한·운영·비용·배포 변경은 없었다.

**Master 전달문** · T321에서 마지막 DB 판정과 첫 쓰기의 간격을 내구 전송 의도와 철회 완료 장벽으로 관리하는 안을 정리했다. 두 호스트의 종료 증거, 운영 환경과 분리한 스테이징 및 비용 가정, 개통 전 새 구현과 합격 기준에 대한 판정을 요청한다.
