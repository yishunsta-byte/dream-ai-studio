## 실행과 결과

PowerShell에서 아래 명령을 실행했고 종료 코드 0을 확인했다.

```powershell
$env:T371_VERIFY_HTTP='1'
node --conditions=react-server --import tsx tests/postgres/t368-run-private-image-project-create.mjs
```

- Next.js 업로드 경로에서 인증 누락(401), 요청 키 누락(400), 1 MiB 초과(413)를 확인했다. 세 요청 모두 업로드 예약을 남기지 않았다.
- 저장 응답 유실 및 임시 파일 삭제 실패 후 같은 요청을 재시도해 원래 자산 ID를 받았다. 임시 파일이 제거됐고 대기 중인 정리 작업은 0건이었다.
- 같은 소유자가 같은 키로 내용을 바꾸면 409를 받았다. 서로 다른 소유자가 같은 키로 같은 PNG를 올리면 각각 별도의 자산 ID를 받았다.
- 업로드로 발급받은 ID로 프로젝트를 저장했다. PostgreSQL에서 프로젝트 1개, 단계 7개, 자산 연결을 확인했고 같은 요청의 재시도는 기존 프로젝트를 반환했다. 권한 철회, 요청 충돌, 트랜잭션 롤백 및 기존 SQLite 저장 경로 검사도 통과했다.

로컬 Next.js와 PostgreSQL 17에서 실행했고 인증과 Storage에는 테스트용 서비스를 사용했다. 실제 Supabase 연결, 브라우저의 파일 선택부터 저장까지의 흐름, 운영 배포는 별도 검증이 필요하다.

## 권리 메모 후속 검수

2026-11-19에 위 명령을 다시 실행해 종료 코드 0을 확인했다. 작업 사본의 업로드 경로, 예약·등록 코드와 권리 메모 HTTP 시험 파일은 Backend 커밋 `f40984d`와 일치했다.

- 최종 파일 쓰기의 응답 유실과 임시 파일 삭제 실패를 차례로 일으킨 뒤 다시 제출했다. 앞뒤 공백이 있는 동일 메모도 기존 자산 ID를 반환했고, PostgreSQL에는 최초 한국어 메모가 남았다.
- 같은 요청 키로 메모를 변경하거나 비우면 각각 HTTP 409였다. 다른 소유자가 같은 키로 제출한 빈 메모는 별도 자산에 NULL로 저장됐다.
- ASCII 501자와 널 문자 입력은 예약 생성 전 HTTP 400이었다. 업로드한 자산으로 프로젝트를 저장하는 후속 검사도 통과했다.

## 파일명 후속 검수

Backend 변경 `d1bde10`과 동일한 업로드 처리기와 시험으로 위 명령을 실행해 종료 코드 0을 확인했다. 로컬 파일 경로를 포함한 이름으로 재시도하면 원래 자산 ID가 반환됐고 PostgreSQL 제목에는 `product.png`만 남았다. 같은 요청 번호로 `renamed.png`를 보내면 409, 새 번호로 ASCII 256자 이름을 보내면 400이었다. 저장 경로에는 제목이 들어가지 않았다. 같은 실행에서 프로젝트 저장과 임시 PG17 클러스터 정리도 통과했다.
