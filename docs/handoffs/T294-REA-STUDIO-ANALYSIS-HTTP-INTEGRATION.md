# T294 작업실 분석 화면과 서버의 격리 HTTP 통합

2026-11-19 KST · Codex(design) · 기준 `64bbf02` · 배정 `msg_ea99cb69c360`

기존 T291 컴포넌트와 T292 공급자를 같은 루프백 출처에서 제공하고, 브라우저의 실제 `fetch`를 T287 등록 자료 서버와 T284 분석 계약에 연결했습니다. 서버는 합성 등록 정보로 PNG의 크기와 SHA-256을 검증하고 읽기용 사본을 만들어 네이티브 분석을 실행했습니다. 저장소 확인 및 별도 원본 수신도 각각 루프백 HTTP를 사용했습니다. HTML, 브라우저 번들, 분석 요청은 모두 시험에서만 제공됩니다.

## 자체 검증

| 검증 | 관측 |
| --- | --- |
| 정상 분석과 권한 경계 | HTTP 요청 본문에는 `projectId`와 `assetId`만 있었습니다. 소유자가 다른 합성 계정과 미인증 모드는 저장소 호출 없이 실패했습니다. 추가 경로가 포함된 요청은 인증 조회 전에 `invalid_selection`을 반환했습니다. 정상 분석의 공개 결과에는 원본 경로·객체 키·해시·계정 및 자료 ID·저장소 자격 증명이 없었습니다. |
| 화면 동작 | 390px 헤드리스 Chromium에서 등록 PNG 선택, 분석, 관찰 근거와 초안 표시, 문구 편집과 복사를 확인했습니다. 화면의 초안은 해당 HTTP 응답의 값과 일치했고, 격리 클립보드에는 편집한 문자열만 전달됐습니다. 복사 검증은 시험용 클립보드를 사용했습니다. |
| 취소·클라이언트 기한 | 사본 작성 직후 재인증을 대기시켜 임시 PNG가 존재하는 상태를 확인했습니다. 사용자 취소와 클라이언트 기한 초과 모두 실제 연결을 끊고, 서버는 해당 신호를 받아 `cancelled`로 종료하며 사본을 지웠습니다. 브라우저에서는 각각 취소 완료 미확인과 시간 초과를 표시했습니다. 같은 자료를 다시 선택할 필요 없이 분석을 재실행했습니다. |
| 서버 기한·실행 슬롯 | 최대 동시 실행 1인 상태에서 첫 분석이 대기 중이면 다른 HTTP 요청은 저장소 조회 없이 `source_unavailable`을 받았습니다. 첫 분석이 정리된 뒤 같은 자료가 정상 분석됐습니다. 별도 시험에서 HTTP 연결을 유지한 채 서버 기한이 먼저 만료되면 사본 정리 후 유효한 T284 `timed_out` 응답을 받았습니다. 늦게 풀린 합성 재인증은 기존 요청을 재개하지 않았습니다. |

집중 시험 5/5, 헤드리스 브라우저와 네이티브 분석을 포함한 전체 21개 파일 242/242, 변경 범위 TypeScript 및 ESLint 경고 0을 확인했습니다. `DREAM_REA_HTTP_BROWSER`에 이미 설치된 헤드리스 Chromium 실행 파일의 절대 경로를 주고 `DREAM_REA_NATIVE_TEST=1`을 설정한 뒤 `node node_modules/vitest/vitest.mjs run tests/reference-analysis`로 재현할 수 있습니다. 브라우저 경로가 없으면 해당 화면 시험만 건너뜁니다.

## 제품 HTTP 연결에 넘길 계약

1. 인증된 작업실에서 현재 계정이 분석할 수 있는 등록 자료 목록을 얻고, 클라이언트의 안정된 공급자 인스턴스에 제품 URI와 상대 기한을 주입합니다. 제품 URI는 후속 통합에서 결정합니다. 연결 전 화면의 미연결 상태를 사용합니다.
2. 제품 핸들러는 JSON에서 정확히 두 ID만 받습니다. 세션, 권한, 파일 식별자, 크기와 해시 등은 서버가 등록 정보로 확인합니다. 실제 세션·권한 검증과 관리형 저장소 연결이 입증된 서버 어댑터가 선행돼야 합니다. 이번에 사용한 `createIsolatedStudioAnalysis`는 합성 연결 전용입니다.
3. 요청의 중단 신호를 서버 분석과 저장소 수신까지 전달합니다. 루프백 Node 어댑터는 요청 중단과 응답 완료 전 연결 종료를 분석 신호로 연결했습니다. 서버 타이머는 연결이 남아 있어도 작동해야 합니다. 핸들러에서 응답을 닫는 것과 분석·사본·슬롯 정리가 끝나는 것은 별도의 사건이므로 실제 호스트에서 취소 신호 전파와 정리를 다시 확인해야 합니다.
4. 현재 공급자는 HTTP 성공 응답만 T284 버전 1 DTO로 읽습니다. `ready`와 클라이언트가 구분해야 하는 `unavailable` 사유는 분석 결과로 반환하며, 시험 핸들러는 이 결과에 HTTP 200과 `Cache-Control: no-store`를 사용했습니다. HTTP 비성공은 공급자에서 일반 실패가 됩니다. 사용자 취소로 응답 연결이 닫힌 경우 클라이언트는 서버의 취소 완료를 확인할 수 없습니다. 운영 상태 코드 정책은 이 화면 계약에 맞춰 결정해야 합니다.

제품 페이지, 공용 인증, 실제 Supabase, 운영 배포는 이번 작업 범위 밖입니다.

**Master 전달문** — 격리 루프백에서 T291·T292·T284/T287을 실제 HTTP로 연결했습니다. 자료 선택부터 결과 편집·복사, 취소 및 기한 만료 뒤 임시 사본 삭제와 슬롯 반환, 동일 자료 재시도까지 검증했습니다. 집중 5/5, 네이티브·헤드리스 포함 242/242입니다. 제품 연결 전 실제 세션·권한과 호스트 연결 종료 전파 검증이 필요합니다.
